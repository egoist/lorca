# Workflow feedback

`crates/cli/src/feedback/` records explicit user outcomes and observed routine failures and stages evidence-backed revisions. A bot's assigned Runner owns the records and applies accepted text. The AppKit and native Go/MyGo desktop apps read and decide through their local CLI; a paired Device's CLI seals the same `feedback.*` request to the assigned Runner and receives a sealed response. Feedback examples, proposals, revision journals and settings live in `feedback/<account hash>/<bot hash>.enc`, a private XChaCha20-Poly1305 file under the account DEK with `workflow_feedback` as associated data. These records reach another Device on request, through ciphertext. A damaged store returns an error and is never replaced with an empty store.

## Outcomes and sources

`feedback.record { bot_id, feedback }` takes `kind`, `origin`, `note`, optional `before`, `after`, `target`, `event_id`, and `excluded`. Kinds are `accepted`, `rejected`, `edited`, `routine_failure`, `explicit`, and `ignored_alert`. An origin has `chat_id`, `message_id` and optional canonical `routine_id`, `review_id` and `task_id`. The Runner validates that the bot belongs to the chat, the originating message is locally available, and a named routine belongs to the bot. Every record carries `lorca://chat/<chat id>/message/<message id>`; the app opens the originating work from this reference. Stable event ids deduplicate replayed outcomes.

The recorder keeps a bounded excerpt of that message and the user's supplied explanation. An edit includes the original and corrected draft. Explicit feedback requires the user's words. Credentials are scrubbed before persistence, including credential fields inside JSON review payloads. Reading a message, leaving a permission question unanswered, and cancelling a turn produce no user preference. An explicitly recorded ignored alert remains a neutral observation and cannot support a proposal. Routine errors are mechanical outcomes, not opinions about what the user wants.

A completed routine job records an observed failure against its run marker (`routine-run-<job id>`), keyed by the job id. A failed check is recorded even when the subsequent model turn succeeds. Stop does not become a failure opinion. The [review queue](review-queue.md)'s decisions are feedback too: when `review_queue::serve` approves, rejects or edits an item on the Runner, `feedback::review_decided` records each `approved`, `rejected` and `edited` history entry once, keyed by `review:<item>:<entry>`, with the item's chat, message, routine, task and review ids, and the payload before and after an edit (a rejection's reason is its note). Created, cancelled, invalidated, executed and interrupted entries record nothing. The feedback module owns no action-execution queue or task registry.

A bot keeps its newest 300 notes, and a pending proposal keeps the examples it cites; decided proposals beyond the newest 100 go first. Deleting the bot deletes its feedback file. Recording, deciding, rolling back, excluding and changing review settings emit `feedback.changed { bot_id, pending_count }` locally, so an open app reads the list again.

## Proposals and revisions

`workflow_feedback` is a coordinator tool with `list` and `propose`. It reads included feedback and stages a specific change; the user's `feedback.accept`, `feedback.reject` and `feedback.rollback` APIs decide revisions. The tool has no apply, review-settings or exclusion-removal action.

`feedback.propose { bot_id, proposal }` takes an existing `target`, complete `after` content, 1–20 evidence feedback ids and an `explanation`. Each evidence record must be included, actionable and linked to available originating work. The Runner reads the current target and keeps its content and hash, the proposed content, evidence and origin refs, rationale, a line diff and `diff_hash`. An unchanged proposal is refused. Repeated identical proposals reuse the same record, including a rejected proposal, so periodic reviews do not repeat that suggestion.

Targets are text, and a proposal's `after` is the complete revised text:

- `routine_prompt { id }`: the task of an existing routine of this bot.
- `playbook { scope: { kind, id }, id }`: the instructions of a saved [skill](playbooks.md) in this bot's scope, or a group project it belongs to. Its name, description and resources stay as the user saved them. Accepting is a guarded `playbooks::save` with the revision and hash the proposal read, and `workflow_feedback` provenance naming the cited messages in a chat of the skill's scope; it is refused when the skill changed since. Drafts are not targets.

A target and its proposed text fit within 24,000 bytes and contain no detected credentials, and a proposal takes no budget, permission, schedule, enablement or connector field.

An acceptance carries the exact displayed `diff_hash`. The Runner serializes feedback decisions, verifies included evidence and the current target hash/revision, persists an `applying` revision first, then writes the guarded target and records the outcome. Replayed acceptance creates no second version. After a process interruption, reading the queue reconciles an unfinished journal against the actual target: applied, not applied, or conflicting. Versions retain before/after content, time, actor Device id and the proposal id.

Routine prompt revisions preserve `feedback_authorization_prompt`, the original authorized task, in the encrypted roster. Auto-review uses that task when judging effectful actions. A feedback revision changes the workflow's wording without granting its new instructions additional action authority. The loop also refuses routine creation, resume, execution and edits, and `edit_bot` and `create_bot`, during a feedback-revised unattended run; listing and pausing routines remain available, and the bot stages a proposal or asks the user in chat for control changes. A task the user edits (`routines.update`, or the bot's `routines` tool at the user's request) is the user's own, and clears the baseline; so does a rollback back to it. A roster from another Device that omits the baseline keeps this Runner's only while the task is still the revised one. Skill and playbook notes likewise provide workflow instructions to the bot; permission rules and integration configuration retain their own review boundaries.

`feedback.rollback { bot_id, id, expected_hash }` restores a revision's previous content only when the current target still equals that revision's accepted content. Later edits refuse the rollback. The app shows its rollback diff first. Rollback appends another numbered revision; it preserves the routine's original action authority and its schedule, paused state and checks.

## Optional review and exclusions

`feedback.settings` reads settings or explicitly sets `review_every_secs` to a day through thirty days, or `null` for off. Review is off initially. The routine scheduler checks due feedback reviews beside its half-minute tick. It starts no model call without new included actionable feedback, and one review per bot runs at a time. `feedback.review` starts a review now.

The coordinator asks the small model of the bot's provider through `models.ask`, with no tools, at most twenty examples and six bounded current targets (the evidence's, the bot's routines, then its skills), at most 4,096 output tokens and a sixty-second deadline. It runs as a `feedback_review` Job under `budgets::for_job`, so the bot's DM [limits](budgets.md) cap it as they cap a turn, and limits that stop it refuse the review; resuming such a stop starts nothing, and the next review runs when asked or at its interval. The model treats examples as untrusted data, cites supplied feedback ids and returns at most two proposals, or an empty list when no concrete improvement is useful. The Runner revalidates evidence and target versions before staging each proposal. A failed attempt counts towards the review interval rather than retrying every tick. Reviewed evidence ids prevent repeated empty reviews. An empty review posts no chat message, notification or feedback event. New proposals emit `feedback.changed { bot_id, pending_count }` locally so an open app updates its review state.

`feedback.exclude` excludes a chat, an individual feedback id, or a workflow target. Exclusion removes stored notes, excerpts and edit text from matching feedback, erases dependent pending proposal content and invalidates those proposals. Future feedback from an excluded chat or target stores only its neutral source metadata. Excluded examples and targets never enter coordinator input. Exclusion or a review-setting change cancels an active review before any returned proposal is saved. Accepted version history retains the content needed for explicit rollback, and is never input to periodic inference. The coordinator tool cannot lift an exclusion.

## In the apps

`feedback.list { bot_id }` answers what the apps show, bounded well under the app socket's message size: the newest 30 included notes (`feedback`, each with its kind, origin, a short note and example, and target) plus every note a pending proposal cites, `feedback_count`, the pending `proposals` with their diffs, the newest 20 applied `revisions` with the change each made (`diff`), `can_rollback` and the target's `current_hash`, `settings.review_every_secs`, and the routines and saved skills a note can name (`targets`).

Give Feedback… on a bot's message opens a short form: Looks good, Not what I wanted, I corrected it (with the user's version of the message), or A note for next time; a note; and the routine or skill it applies to. The DM inspector shows a Feedback section once the bot has any: a row for each suggested change, which opens its explanation, the change as removed and added lines, and the notes it is based on, with Accept as the default button and Reject beside Cancel; and All feedback, which opens the list of suggestions, how often to look for changes (when asked, daily, weekly), the applied changes, and the notes. An applied change opens the same way with Undo Change while the routine or skill still reads as the change left it. A note opens its message in the chat; its menu excludes it, or everything from its chat. Look Now runs `feedback.review` and says when there is nothing to change. The macOS app (`Sheets/FeedbackViewController.swift`, `Model/Feedback.swift`) and the Windows and Linux app (`sheet_feedback.go`, `model/feedback.go`) show the same sheets and words, and the phone the same screens in Details; each reports a refused decision in the app's words, such as a routine that changed after the suggestion.
