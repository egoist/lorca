# Workflow feedback

`crates/cli/src/feedback/` records explicit user outcomes and observed routine failures and stages evidence-backed revisions. A bot's assigned Runner owns the records and applies accepted text. The AppKit and native Go/MyGo desktop apps read and decide through their local CLI; a paired Device's CLI seals the same `feedback.*` request to the assigned Runner and receives a sealed response. Feedback examples, proposals, revision journals and settings live in `feedback/<account hash>/<bot hash>.enc`, a private XChaCha20-Poly1305 file under the account DEK with `workflow_feedback` as associated data. These records reach another Device on request, through ciphertext. A damaged store returns an error and is never replaced with an empty store.

## Outcomes and sources

`feedback.record { bot_id, feedback }` takes `kind`, `origin`, `note`, optional `before`, `after`, `target`, `event_id`, and `excluded`. Kinds are `accepted`, `rejected`, `edited`, `routine_failure`, `explicit`, and `ignored_alert`. An origin has `chat_id`, `message_id` and optional canonical `routine_id`, `review_id` and `task_id`. The Runner validates that the bot belongs to the chat, the originating message is locally available, and a named routine belongs to the bot. Every record carries `lorca://chat/<chat id>/message/<message id>`; the app opens the originating work from this reference. Stable event ids deduplicate replayed outcomes.

The recorder keeps a bounded excerpt of that message and the user's supplied explanation. An edit includes the original and corrected draft. Explicit feedback requires the user's words. Credentials are scrubbed before persistence, including credential fields inside JSON review payloads. Reading a message, leaving a permission question unanswered, and cancelling a turn produce no user preference. An explicitly recorded ignored alert remains a neutral observation and cannot support a proposal. Routine errors are mechanical outcomes, not opinions about what the user wants.

A completed routine job records an observed failure against its run marker, keyed by the job id. A failed check is recorded even when the subsequent model turn succeeds. Stop does not become a failure opinion. `feedback::record_review_change` accepts the review queue's existing item and a history event, retains its review/task/source refs, and records only explicit user `approved`, `rejected` and `edited` events. The review queue can also forward these events through `feedback.record`; its stable history id is the idempotency key. The feedback module owns no action-execution queue or task registry.

## Proposals and revisions

`workflow_feedback` is a coordinator tool with `list` and `propose`. It reads included feedback and stages a specific change; the user's `feedback.accept`, `feedback.reject` and `feedback.rollback` APIs decide revisions. The tool has no apply, review-settings or exclusion-removal action.

`feedback.propose { bot_id, proposal }` takes an existing `target`, complete `after` content, 1–20 evidence feedback ids and an `explanation`. Each evidence record must be included, actionable and linked to available originating work. The Runner reads the current target and keeps its content and hash, the proposed content, evidence and origin refs, rationale, a line diff and `diff_hash`. An unchanged proposal is refused. Repeated identical proposals reuse the same record, including a rejected proposal, so periodic reviews do not repeat that suggestion.

Targets are:

- `routine_prompt { id }`: only the prompt of an existing routine of this bot.
- `plugin_skill { plugin_id, name }`: only a skill named by an installed plugin's manifest. The adapter resolves its note under that plugin's skills folder. An accepted note applies to the bots on that Runner; marketplace refreshes and reinstalls preserve locally revised notes.
- `playbook { scope: { kind, id }, id }`: the canonical playbook API's current content, hash and revision. A bot scope is this bot; a project scope is an existing group containing it. The adapter calls `playbooks.get` and guarded `playbooks.save` and supplies `workflow_feedback` provenance with source chat/message ids. It returns an explicit adapter error when that API is unavailable.

A text target accepts a string; it accepts no budget, permission, schedule, enablement or connector fields. A target and proposed text fit within 24,000 bytes and contain no detected credentials. Playbook content follows its canonical content schema and guarded save, rather than creating another skill record.

An acceptance carries the exact displayed `diff_hash`. The Runner serializes feedback decisions, verifies included evidence and the current target hash/revision, persists an `applying` revision first, then writes the guarded target and records the outcome. Replayed acceptance creates no second version. After a process interruption, reading the queue reconciles an unfinished journal against the actual target: applied, not applied, or conflicting. Versions retain before/after content, time, actor Device id and the proposal id.

Routine prompt revisions preserve `feedback_authorization_prompt`, the original authorized task, in the encrypted roster. Auto-review uses that task when judging effectful actions. A feedback revision changes the workflow's wording without granting its new instructions additional action authority. The loop also refuses routine creation, resume, execution and edits, permission changes and budget-setting tools during a feedback-revised unattended run; listing and pausing routines remain available, and the bot stages a proposal or asks the user in chat for control changes. Roster merges preserve this Runner's authorization baseline when an incoming build omits it. Skill and playbook notes likewise provide workflow instructions to the bot; permission rules and integration configuration retain their own review boundaries.

`feedback.rollback { bot_id, id, expected_hash }` restores a revision's previous content only when the current target still equals that revision's accepted content. Later edits refuse the rollback. The app shows its rollback diff first. Rollback appends another numbered revision; it preserves the routine's original action authority and its schedule, paused state and checks.

## Optional review and exclusions

`feedback.settings` reads settings or explicitly sets `review_every_secs` to a day through thirty days, or `null` for off. Review is off initially. The routine scheduler checks due feedback reviews beside its half-minute tick. It starts no model call without new included actionable feedback, and one review per bot runs at a time. `feedback.review` starts a review now.

The coordinator asks the small model of the bot's provider through `models.ask`, with no tools, at most twenty examples and six bounded current targets, at most 4,096 output tokens and a sixty-second deadline. The model treats examples as untrusted data, cites supplied feedback ids and returns at most two proposals, or an empty list when no concrete improvement is useful. The Runner revalidates evidence and target versions before staging each proposal. Calls count in the bot's DM spending. A failed attempt counts towards the review interval rather than retrying every tick. Reviewed evidence ids prevent repeated empty reviews. An empty review posts no chat message, notification or feedback event. New proposals emit `feedback.changed { bot_id, pending_count }` locally so an open app updates its review state.

`feedback.exclude` excludes a chat, an individual feedback id, or a workflow target. Exclusion removes stored notes, excerpts and edit text from matching feedback, erases dependent pending proposal content and invalidates those proposals. Future feedback from an excluded chat or target stores only its neutral source metadata. Excluded examples and targets never enter coordinator input. Exclusion or a review-setting change cancels an active review before any returned proposal is saved. Accepted version history retains the content needed for explicit rollback, and is never input to periodic inference. The coordinator tool cannot lift an exclusion.

Both desktop apps' DM inspectors open Workflow feedback. Its sheet shows pending explanations, originating-work buttons and exact diffs, Accept revision and Reject, source examples with Exclude, revision history with rollback previews, and Off/Daily/Weekly review controls. Record workflow feedback… on a message records acceptance, rejection, an edited draft, explicit feedback, or a neutral ignored alert, with an optional target and an exclusion checkbox. All controls use `feedback.*` on the local CLI.


The native Windows/Linux implementation keeps typed CLI projections and request adapters in `desktop/model/feedback.go`, with capture/review state and views in `desktop/sheet_feedback.go`. The message menu opens the capture form, whose kind, target, explanation, corrected draft and sensitive-material switch keep persistent values under stable keys. Saving freezes fields and serializes the exact draft before background work; an unchanged retry retains its event id, and an edited retry receives a new one. The review sheet renders evidence, source refs, diffs, guarded decisions and reversal previews, with chat/item/workflow exclusions and explicit Off/Daily/Weekly settings. A same-count `feedback.changed` event advances its view version so an open sheet refreshes without polling; empty reviews add no notification or chat reply. Ordered main-thread replies update state, and callbacks discard results after the sheet closes. Source buttons load older pages and reveal the originating message inside Lorca, reporting missing/offline sources without opening external links. The CLI retains ownership of feedback storage, proposals, revisions, authority, budgets and periodic execution.
