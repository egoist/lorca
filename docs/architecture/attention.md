# Coordinator attention

`crates/cli/src/attention.rs` maintains the account's consolidated attention view. An attention item describes a pending review, blocker, commitment, or important change, with its next action and source chat. `task_id` is the canonical `task-<UUID>` of a task; `review_id` and `message_id` link supporting records. Attention records describe what needs attention; resolving one changes the view and leaves the source task and review lifecycle with their owners.

## Coordinators and reports

Any bot can coordinate. The user's encrypted preferences bind a chat to a bot and optionally choose a default coordinator. A chat uses its binding, then a group's owner, then the default coordinator, then its own bot. A report may name the bot owning the work explicitly. A specialist answering another bot defaults its reports to that requesting bot. Chef is an ordinary bot with the same tool as every teammate.

The `attention` bot tool offers `list`, `report`, `resolve`, and `brief`. A report contains a stable topic `key`, `category` (`review`, `blocker`, `commitment`, `change`), `title`, `summary`, `next_action`, a `source { chat_id, task_id?, message_id?, review_id? }`, and optional `coordinator_bot_id`, `urgent`, and `quiet`. It validates the source chat, bot, and canonical task id shape. Ordinary specialist reports enter the owning coordinator's DM as a quiet handoff marker and admit an `attention_report` Job on that bot's Runner. Hops retain the eight-hop limit. The report asks that bot to inspect active attention and maintain its brief. An urgent report also creates a directly alerting source-chat message. `quiet` saves the observation without waking the coordinator or posting an alert. Applying a synced record starts no job and sends no push.

The shared Rust hooks are `attention::report(app: &Arc<App>, report: Report, actor: Option<&str>, hops: u32) -> Result<Item, String>` and `attention::resolve(app: &App, id: &str, actor: Option<&str>, expected: Option<&Revision>) -> Result<Item, String>`. The actor is the reporting bot, or `None` for the user. `attention::item_id(source, key)` computes the stable projection id so an adapter needs no separate id mapping. The module stores source references and observations and executes no source work.

## Deduplication and resolution

The underlying item's id is a hash of its task id and topic key, or its source chat id and topic key when it has no task. Two bots reporting the same task/topic share one item, while each reporter retains its own observation. The projection unions their source links and reporter ids and uses the latest observation's words. Identical retries from one bot make no write; another reporter with the same words adds its source without waking the coordinator again.

Each record carries a Lamport revision `{ counter, device_id }`. A write advances past all revisions the Device has seen; the Device id orders concurrent writes deterministically. An incoming older revision cannot replace the same reporter's newer record. The coordinator or user resolves an item with a durable resolution record; an optional `expected_revision` refuses a stale UI action. Resolved keys are terminal: late offline reports do not restore them, even with a higher counter. New work uses a new topic key. The active projection omits resolved items and items whose source chats or coordinator have been deleted. `attention.list { include_resolved: true }` includes resolutions for inspection.

## One brief and notification preferences

A coordinator publishes `attention.brief` with `decisions`, `changes`, `next_action`, and `item_ids` linking its active attention items. It contains one to twenty decision/change entries. Empty checks publish no brief. Each coordinator has one current brief in the view, and identical publication is a no-op. The brief also appears as one text message in that bot's DM, linked from the view. The tool permits a bot to publish its own brief and resolve the items it coordinates.

The account preferences independently enable `summaries` and `urgent_direct`, both on by default. Bot tools cannot change these user preferences. Structured text messages carry `notification: summary | urgent | quiet`; phone pushes and the Mac's notification path both honor that tag and the synced preferences. A turn that uses structured reporting marks its other completed text as quiet, so a specialist's closing message or a coordinator's explanation does not repeat the alert. Structured messages alert on arrival, and the generic turn-finished path skips them. Delivery retains the existing three-second read grace, watched-chat suppression, pending-message checks, and encrypted phone envelope. The policy is checked again after notification permission, push authentication, and before a retry.

## Storage and APIs

SQLite's `attention(id, ciphertext)` table keeps observations, resolutions, briefs, and preferences encrypted with the account DEK. A local record and its encrypted outbox write commit in one transaction. Each record travels as an account-encrypted `attention` blob with a hashed latest-only slot and no chat group. Source ids, words, bot ids, and preferences stay inside ciphertext. Devices take attention blobs in live pulls and during their first sync before chat paging. A Device upgrading from a build that skipped this kind replays the attention slots once when its new local table is empty, even when its saved relay sequence is already ahead. Devices retain them across restarts, and upload them again with history after relay recovery. Forgetting the account clears the table. Relay protocol 3 accepts this blob kind.

The local API exposes `attention.list`, `attention.report`, `attention.resolve { id, expected_revision? }`, `attention.brief`, and `attention.preferences { summaries?, urgent_direct?, default_coordinator_bot_id?, coordinators? }`. `coordinators` is a map of existing chat ids to bot ids. Bootstrap includes `attention { items, briefs, preferences }`; `attention.changed` replaces that projection. The macOS AppKit sheet opens from the tray toolbar button, View menu, or ⇧⌘A. It shows the current briefs, every active category, the next action, source-chat buttons with task/review references, Mark resolved, and the alert/default-coordinator controls. The phone's chat list opens the same account view in an Attention sheet; its scroll view uses automatic native content insets to keep the notification controls below the navigation bar. The Windows/Linux Go/MyGo app reads the same snapshot and `attention.changed` projection through `desktop/model/attention.go`. Its native sheet (`desktop/sheet_attention.go`) opens from the tray toolbar button, View menu, command palette, or Ctrl+Shift+A. It shows briefs, each category and next action, source-chat links and Mark resolved; switches and the coordinator menu keep persistent state with stable keys. Resolve sends the inspected uint64 revision; preference writes preserve per-chat bindings. Async CLI replies return through the ordered main-thread queue, and a stale refresh cannot replace a newer event/account. Structured message tags distinguish summary/urgent/quiet notifications with the same read grace and preference checks. Every app renders the local CLI/core projection and keeps no second account store.
