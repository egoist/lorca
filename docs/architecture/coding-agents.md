# Coding agents

A bot hands a coding job to Claude Code or Codex on its Runner and supervises it: the agent works on its own in a git worktree, the bot reads its transcript, sends it follow-ups and stops it, and hears when it is done, stalls, or exits, with the outputs Lorca published from its work. `crates/cli/src/coding/` holds it: `tool.rs` the bot's tool and the review of a start, `mod.rs` the agents on the Runner and their cards, `claude.rs` and `codex.rs` the agents Lorca runs itself, `hosts.rs` those it runs in a terminal host, and `workspace.rs`, `proof.rs`, `screen.rs`, and `lines.rs` the folder, the outputs, a pane's questions, and the transcript. Every agent is driven through one interface (`driver::Driver`): a message, an answer to its pane, its screen, its pane brought forward, and Stop; its supervisor (`supervise`) turns what it reports into the card, the transcript, and the bot's turns.

## Starting one

`coding_agent { action: "start", prompt, agent?, folder?, worktree?, proof?, secrets? }` starts one and answers at once with its id (`agent-3f9a2c1d`), which the bot keeps across turns. `agent` is `claude` or `codex`; without it the Runner's Claude Code, else its Codex, found on the login shell's `PATH` as a terminal would find it. Neither installed is an error that says to install one.

`folder` is where the job is: absolute, `~/…`, or relative to the bot's working directory, which it defaults to. In a git repository the agent never works in the checkout itself but in a worktree of its own under Lorca's folder, `worktrees/<repository>-<hash>/<name>`, on a branch of that name made from the repository's current commit: a new one named after the prompt's first words, or the one `worktree` names, which a later start in the same repository works in again. A folder that is not a repository is worked in as it is. Each has `.lorca-proof/` for the proof, with a `.gitignore` of `*` so git never sees it. The agent gets the bot's prompt, then where it works, that its proof goes in that folder (test output as `.txt` or `.log`, screenshots as `.png`, named `before-…` and `after-…` for a change), what proof the bot expects (`proof`), and to give a pull request's link in its last message.

The start needs the bot's Access to Shell commands ([Bot permissions](bot-permissions.md)), and passes [Auto-review](tools.md) as a command does, on the card of the call (below): the review reads what starts, where, and the prompt, and proposes a rule for Always allow. A routine's or an event's turn, which nobody watches, is refused when the review asks. An agent an event started, a channel's message among them, keeps the owner's task for that event (`Record.event`, without the event's text), and the review weighs its every later action against that task, as it does the turn's own: what someone outside wrote never authorizes it.

`secrets` names the bot's own saved command secrets ([Secret requests](secrets.md)) the job needs, such as `NPM_TOKEN` to publish a package; any other name fails the start, saying to ask for it with `request_secret`. The agent has each as `$NAME` in its environment, looked up again whenever its process starts, and its brief says to use them only with the service each is for. The start's review is told which it holds, and so is the review of every command it runs, none of which takes the fast paths below. An agent given secrets runs as Lorca's own process, never in a Herdr or Luvus pane, whose command line and screen would show them. Saved values never reach an agent otherwise: a value in the prompt or a follow-up goes as its placeholder, which is not filled.

## Where it runs

Where Herdr runs on the Runner (its socket answers `ping`, at `~/.config/herdr/herdr.sock` or `HERDR_SOCKET_PATH`), the agent runs in a pane of a Herdr workspace of its own, made without taking the focus; else where Luvus runs (`luvus ping`), in a Luvus workspace for its folder, opened with the user's own workspace brought back to front. The user can watch it there and type into it. Without either, Lorca runs it itself:

- **Claude Code**: `claude -p` with stream-json in and out (`--input-format stream-json --output-format stream-json --verbose --replay-user-messages`), the protocol of its Agent SDK, with `--permission-mode acceptEdits` and `--permission-prompt-tool stdio`, so edits in its folder run and anything else that would ask comes to Lorca. Its initialize request registers a `PreToolUse` hook for Bash, so every command comes to Lorca, whatever the user's own Claude Code settings allow. A message is a user message; Claude Code says when it takes one up (`--replay-user-messages`), which tells a pause between messages from being done.
- **Codex**: `codex app-server`, the JSON-RPC its own apps speak, over stdio: a thread in the folder (`thread/start`, `approvalPolicy: on-request`, `sandbox: workspace-write`) and a turn per message. Its commands run in Codex's sandbox, which keeps writes to the folder and the network off; what needs more, such as a push or writing a worktree's shared git metadata, asks (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`), and Lorca answers.

Either runs as a process group of its own (a job object on Windows) with the login shell's environment, less the markers a Claude Code session leaves for its children, plus the secrets it was given. Codex passes them to the commands it runs.

In a pane, the host starts the agent with its own command line (`agent.start`, `luvus agent start`): Claude Code with `--settings` adding a `PreToolUse` hook that runs `lorca coding hook <id>` for each Bash command, and Codex with `--ask-for-approval on-request --sandbox workspace-write` and its update check off. The first prompt goes in once the host reports the agent ready and its screen shows no menu, typed rather than pasted, on one line, since Claude Code holds back from acting on a message that is nothing but pasted text; Luvus sends it with Return. The host's events (`pane.agent_status_changed` on Herdr's socket, `luvus events`) say when it works, asks (`blocked`), and is done (`idle`, `done`), and its pane closing ends it; the agent itself is looked for every five seconds, so one that exited in its pane ends too. While it works its pane is read every three seconds, for its card and the transcript. Keys go to the pane one at a time, as an arrow's escape sequence sent with Return reads as Esc.

## What it may do

Every command an agent runs passes the bot's Access as it stands, then Auto-review as the bot's own commands do (`approve`): a command the parser proves only reads, or one that stays in Lorca's own folders (its worktree is in one), runs at once, unless the agent holds secrets; the review model judges anything else, a push or a deploy, against the request behind the turn that started the agent. Files it changes outside its folder, and its other tools that would ask (a web fetch, an MCP tool), go to the review too. What the review allows runs; what it asks about goes on the agent's card as a question, `command`, with why and the rule Always allow adds, answered from any Device with `chats.permission`, as a command's card is. It waits ten minutes, and a message from the user in the chat dismisses it. An agent told no hears why and goes on without it. Claude Code in a pane reaches the same review through its hook: `lorca coding hook` reads the hook's input and asks the `lorca serve` that started the agent (`coding.review { agent_id, command }`, over the local websocket only), which answers once the review or the user has decided; a serve that does not answer lets nothing run.

A pane asks on its screen: a host reports it `blocked`, or its screen ends on a menu while the host reports it idle (Codex's notices, a first question). Lorca reads the question once the screen holds still (`screen::read`): its lines, and the menu's choices with the one the cursor is on. A menu whose first plain "Yes", "Allow", or "Trust" choice lets the agent go ahead once goes to Auto-review, which may answer it; a choice that also stops it asking again ("Yes, and don't ask again", "Always allow") is never one Lorca picks. Allowed, Lorca presses the arrow keys to that choice and Return; an answer that does not take goes to the user. Anything else goes on the card, `choices` or `text`, and only the user's answer (`coding.answer { choice | text }`) is pressed or typed into the pane. The user can answer in the pane itself, and the question leaves the card.

## Following it

What an agent says, runs, shows, and asks, and what it is sent, has the Runner's saved secrets replaced by their placeholders before it reaches its transcript, its log, its card, the review, or the bot (`without_secrets`), as a tool's result does: an agent may print a value its environment or a file holds.

The transcript of an agent Lorca runs is text, the way Claude Code's own screen words it: `> ` and what it was sent, what it said, each tool it used (`● Bash(git status --short)`, `● Edit(src/login.rs)`, paths from its folder), and the first lines of what came back (`  ⎿ …`). The last 5,000 lines stay in memory and every line in `agents/<id>.log` (0600). An agent in a pane has its pane for a transcript.

- `read { id, lines? }` answers what is new since the bot last read, up to its last 200 lines, or its last `lines`, and how it stands.
- `send { id, message, interrupt? }` gives it a follow-up: Claude Code takes it up at its next step or after its turn; Codex's running turn takes it (`turn/steer`), or it starts the next turn; a pane gets it typed, and the agent queues it. `interrupt` stops what it does first (Claude Code's `interrupt` request, `turn/interrupt`, Esc in a pane). An agent Lorca ran whose process is gone, because it was done and idle for an hour or Lorca restarted, starts again on its session (`--resume`, `thread/resume`).
- `stop { id }` ends it; `list` answers the bot's agents in the chat.

An agent is `starting`, `working`, or `idle` (done with what it was asked, waiting for a follow-up), and `asking` while a question waits; once it ended `exited`, `failed`, or `stopped`. One working with nothing new for ten minutes is `stalled`; a spinner's timer ticking is not news.

## When it is done

When an agent goes idle after working, Lorca publishes what changed in its work as [outputs](outputs.md) of the bot's (`proof::publish`): its diff against the commit it started from (commits, edits not committed yet, and new files, up to 2 MiB) as `<branch>.diff`, a saved secret in it as its placeholder, a new version whenever it changed; the pull request or merge request its transcript names, once, as a link; and each file new or changed in `.lorca-proof/`, a screenshot as `before_screenshot` or `after_screenshot` evidence and anything else as a test result or a verification, every one `unverified`, since it is the agent's claim. A text file that holds a saved secret goes out as a copy with its placeholder, and another file that holds one not at all. Then the bot gets a turn of its own, an `agent` job, once no turn runs in the chat, unless a turn read the agent meanwhile: it opens with what the agent said and each output's name, message, output id, and version, which the bot cites as [task evidence](tasks.md). A stalled agent and one that exited by itself wake the bot the same way, with its last lines.

While an agent works, its run time counts toward the limits of the turn that gave it the work, the start or a follow-up ([Budgets](budgets.md)): the turn's scopes hold a run (`BudgetContext::hold`) until the agent is idle, and a time limit reached stops it.

## Stop, quitting, and restarts

Stop in the chat stops every coding agent there, as it does the bot's commands, here or on the Runner when the bot's turn is cancelled there ([Stop](stopping.md)). A start under way when the turn is stopped finishes in a task of its own (`start_unless_stopped`) and stops its agent as soon as it runs, so Stop never leaves one running unfollowed. The card's Stop (`coding.stop`) reaches it from any Device. Deleting the chat or the bot stops and forgets its agents.

`agents/agents.json` (0600) keeps every agent's record: its chat, bot, card, kind, host and pane, session, folder, branch, state, and what it published. Quitting stops the agents Lorca runs, whose cards read "Stopped when Lorca quit" unless they were done, and leaves those in a pane running there. On the next start their handles still work: a done one starts again on a follow-up, and one in a pane that is still there is followed again. An ended agent is forgotten a month later. An update of the CLI waits while an agent Lorca runs is at work.

## The card

The `coding_agent` row that started an agent carries its card from the start, `Body::Tool.agent`: `{ id, kind, host?, task, folder, branch?, state, stalled, question?: { kind: start | command | choices | text, text, command?, choices, reason?, rule? }, output?, outcome?, pull_request?, device?, started_at? }`, with `checking` while Auto-review judges the start. `output` is its last 20 lines; a pane's leave out the agent's input box and the status lines under it (`screen::body`). The card keeps its first place in the relay's log however often it changes, a question on it counts as unread and pushes as a command's does ([Notifications](notifications.md)), and it stays after the agent ended. `coding.transcript` (its last 2,000 lines, or its pane), `coding.stop`, and `coding.answer` go to the bot's Runner from any Device as sealed requests; `coding.show` brings its pane forward on the Runner and is the Runner's own.

Every app shows the card in the chat: the agent's name, with Stop at the end of the line while it runs; what it was asked; how it stands in a word (Starting, Working, Quiet, Done, Ended, Failed, Stopped) with its branch and, in a pane, its host; and while it works its last lines in a code block that scrolls. Before it starts the title is the bot's ("Developer wants to start Claude Code on Workbench") with Allow once, Always allow, and Deny; for a command, "Claude Code wants to run a command" with the command in a code block that opens it whole; for a pane's question, "Claude Code asks" with the question's lines and its choices (a pop-up and Answer on the Mac and on Windows and Linux, a button each on the phone) or Answer for text. A click on what it works on opens its transcript, which follows it every two seconds on the Runner and five elsewhere, and on the Runner offers to show its pane there. The macOS app's are `Chat/AgentCellView.swift` and `Sheets/AgentTranscriptViewController.swift`, the Windows and Linux app's `desktop/agents.go`, and the phone's `AgentRow` in `src/ui/transcript.tsx` and `app/agent/[id].tsx`, which answers text in the answer sheet a command's question uses.
