# Coding agents

A bot hands a coding job to a coding agent on its Runner (Claude Code, Codex, OpenCode, pi, or Vercel's fx), after Grok Bot's coding agents: the bot passes on the user's request under a title, the agent decides how to do the job in the folder it is given, pushes it, opens a pull request, and reports to the user, who reviews the work; the bot then relays that report and does not check it. In the chat the agent is a peer the bot messages: "Messaged ⬢ Title" where the bot wrote it, "You messaged ⬢ Title" where the user wrote it on its page, "Message from ⬢ Title" where it answered. Its transcript reads the way Cursor shows an agent's run. `crates/cli/src/coding/` holds it: `tool.rs` the bot's tool, `mod.rs` the agents on the Runner, their rows and messages, and their review, `settings.rs` which agent a start takes, `workspace.rs` the folder and what changed there, `transcript.rs` the steps, and one driver per protocol: `claude.rs`, `codex.rs`, `acp.rs` (OpenCode and fx), and `pi.rs`. Every agent is driven through one interface (`driver::Driver`: a message, and Stop), and reports the same events: its session, steps of its transcript, working, done, what it asks to do, and that it ended.

## Starting one

`coding_agent { action: "start", title, prompt, agent?, folder?, secrets? }` starts one and answers at once with its id (`agent-3f9a2c1d`), which the bot keeps across turns. The tool tells the bot to say it started the agent and end its turn rather than wait. `title` is a few words that name the job wherever the agent shows ("Docs: use mygo.json in the launcher examples"); `prompt` is the user's request in their words, with only facts the bot knows and the agent cannot find: where the repository is, and what the user already said about the job earlier in the chat. The tool and the system prompt tell the bot to add nothing of its own: no plan, checklist, acceptance criteria, guess at the fix, scope, way to build or check it, commands to run, or branch or worktree. The agent decides all of that.

Which agent: each Runner keeps the five in its user's order of preference, each on or off, in `coding-agents.json` in its data directory (0600; `CodingAgents`, every agent on in Lorca's order until the user changes it). A start without `agent` takes the first one on that is installed on the Runner, found on the login shell's `PATH` as a terminal would find it; one that names an agent the user turned off there, or one not installed, fails and says so. `coding.agents { runner_id }` answers that Runner's agents in order, on or off, installed or not, with what `--version` says, and `coding.agents.set { runner_id, agents: [{ kind, enabled }] }` keeps a new order and answers the same; both go to the Runner sealed when it is another Device, so the phone sets them too. The apps show them in Settings → Coding Agents, a pane for the Runner picked at its top on a computer and a screen under each Runner on the phone, with a switch per agent, and the order changes by dragging a row.

`folder` is where the job is: absolute, `~/…`, or relative to the bot's working directory, which it defaults to. The agent starts in it as it is, after Grok Bot, whose coding agent is a Cursor agent that decides on its own branch: Lorca makes no worktree or branch, and neither does the bot; the agent decides where and how to work, a branch or a worktree of its own included, as it would started in a terminal there. In a git repository Lorca notes the branch checked out and the commit it starts from (`workspace::prepare`), for what its work changed. The agent gets the bot's prompt, then Lorca's brief (`tool::brief`): where the job is; that how to do it, where, on which branch, and how to check it are its to decide; that the user reviews the work and nobody checks it before; to push its work and open a pull request when done, unless the request says otherwise; and to end with its report to the user: what it did, each command it ran to check it with what it printed, and the pull request's link, or why there is none. Auto-review hears the same about push and pull request with each command the agent runs.

The start needs the bot's Access to Shell commands ([Bot permissions](bot-permissions.md)). It asks nobody: what the agent then does is reviewed step by step (below). An agent an event started, a channel's message among them, keeps the owner's task for that event (`Record.event`, without the event's text), and the review weighs its every action against that task, as it does the turn's own: what someone outside wrote never authorizes it.

`secrets` names the bot's own saved command secrets ([Secret requests](secrets.md)) the job needs, such as `NPM_TOKEN` to publish a package; any other name fails the start, saying to ask for it with `request_secret`. The agent has each as `$NAME` in its environment, looked up again whenever its process starts, and its brief says to use them only with the service each is for. The review of every command it runs is told which it holds, and none takes the fast paths below. Saved values never reach an agent otherwise: a value in the prompt or a later message goes as its placeholder, which is not filled.

## How each agent runs

Each runs as a process group of its own (a job object on Windows) with the login shell's environment, less the markers a Claude Code session leaves for its children, plus the secrets it was given, and is spoken to over its stdin and stdout. Stopping it kills the group and, on macOS and Linux, every process that descends from it as `ps` lists them, since Claude Code runs each command in a group of its own; the steps it had under way end as failed:

- **Claude Code**: `claude -p` with stream-json in and out (`--input-format stream-json --output-format stream-json --verbose --replay-user-messages`), the protocol of its Agent SDK, with `--permission-mode acceptEdits` and `--permission-prompt-tool stdio`, so edits in its folder run and anything else that would ask comes to Lorca. Its initialize request registers a `PreToolUse` hook for Bash, so every command comes to Lorca, whatever the user's own Claude Code settings allow. A message is a user message, followed by an `interrupt` request with `send_now` and the message's uuid (when its `system/init` lists `interrupt_send_now_v1`), so the turn under way makes way for it at once: Claude Code moves the command it waits on to the background, or ends it, and takes the message up. Claude Code says when it takes one up (`--replay-user-messages`), which tells a pause between messages from being done. A turn it starts by itself, as when a background command it started ends, takes up no message: its first assistant message after it was done has it working again, so that turn's last message is a report too. `TodoWrite` is its plan.
- **Codex**: `codex app-server`, the JSON-RPC its own apps speak: a thread in the folder (`thread/start`, `approvalPolicy: on-request`, `sandbox: workspace-write`) and a turn per message. Its commands run in Codex's sandbox, which keeps writes to the folder and the network off; what needs more, such as a push, asks (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`), and Lorca answers. `turn/plan/updated` is its plan.
- **OpenCode**: `opencode acp`, the Agent Client Protocol: `initialize` without file or terminal methods, so it works with its own tools, then a session in the folder (`session/new`) and a `session/prompt` per message, which answers once the turn is over. Its permissions come from `OPENCODE_CONFIG_CONTENT` (commands, fetches, and anything outside its folder ask; edits in it do not), and what asks arrives as `session/request_permission`, which Lorca answers allow once or reject. ACP has no steering: a message sent while it works cancels the turn under way (`session/cancel`), and the message starts the next.
- **fx**: `fx acp`, the same Agent Client Protocol as OpenCode, with `FX_PERMISSION_MODE=ask`: fx's own default, `auto`, has its reviewer decide and asks nobody, while `ask` sends every command and change to Lorca as `session/request_permission`. fx reports a command's exit code in its own `command_result` field, and its text as a cut-off record of where the output went, which the transcript leaves out.
- **pi**: `pi --mode rpc`, its JSONL protocol: a `prompt` per message, or `steer` while it works, which it takes up before its next model call. pi holds a steer until the tool under way is done, so while one runs a message stops the run first (`abort`) and then goes as a `prompt`. pi asks nobody before a tool runs, so Lorca writes an extension of its own (`agents/lorca-review.ts`) and loads it with `-e`: its `tool_call` handler sends each call that does more than read (`read`, `grep`, `find`, and `ls` run at once) to Lorca as an extension dialog (`extension_ui_request`), and blocks the call with Lorca's reason when Lorca says no. Another extension's dialog is cancelled, since nobody is at pi's screen.

## What it may do

Every command an agent runs passes the bot's Access as it stands, then Auto-review as the bot's own commands do (`approve`): a command the parser proves only reads, one that stays in Lorca's own folders, or one that only makes, copies, and moves files in the folder it works in, runs at once, unless the agent holds secrets; the review model judges anything else, a push or a deploy, against the request behind the turn that started the agent, with the git state of what a command would discard. Files it changes outside its folder, and its other tools that would ask (a web fetch, an MCP tool), go to the review too. What the review allows runs. What it holds goes back to the agent as a denial that says why (`review::agent_note`): it goes on another way, or stops and names what it needed. What the review asks goes up as a permission card at the end of the chat, where the user reads however far up the agent's row is (`ask_in_chat`): the bot's shell card for the Runner (`plugin_id: computer`), with the command, the reason, which opens with the agent and its title ("Claude Code, the coding agent on “Login”, asks to run this."), and the rule Always allow adds, answered from any Device with `chats.permission`. The row reads `asking` meanwhile. It waits ten minutes. The bot's turn does not wait on it, so the user's messages to the bot leave it up (`mcp::ask_aside`); stopping the agent dismisses it. An agent a routine's run or an event started has nobody to answer (`Record.unattended`): what the review would ask goes back to it at once as a denial that says why, and it goes on without it or names it in its report, for the user to decide. An agent told no hears why and goes on without it.

## Its transcript

What an agent says, runs, shows, and asks, and what it is sent, has the Runner's saved secrets replaced by their placeholders before it reaches its transcript, its file, its row, its message in the chat, the review, or the bot (`without_secrets`), as a tool's result does: an agent may print a value its environment or a file holds.

Each driver turns what its agent reports into steps (`transcript::Item`): `prompt` (what it was sent), `status` (Lorca's own line: "Working in ~/dev/shop on main", "Interrupted"), `thought` (with how long it thought when the agent says), `text` (what it said), `tool` (`{ kind: read | search | edit | execute | fetch | other, title, path?, added?, removed?, status: running | done | failed | denied, output? }`, its output's first twelve lines), `plan` (entries pending, in progress, or completed), and `error`. A step has an id, and a later step with the same id is that step changed: a command running, then done with its output. Every step is appended to `agents/<id>.jsonl` (0600), and the last 4,000 are in memory; a restart folds the file back.

The bot's other actions are for when the user asks about the agent or tells it something; the tool tells the bot not to check on it or review its work on its own, the turn that relays its report included.

- `read { id, lines? }` answers what changed since the bot last read, as Claude Code's screen words it (`> ` and what it was sent, what it said, `● Bash(git status --short)` and the start of what came back), up to its last 200 lines, or its last `lines`, and how it stands.
- `send { id, message, interrupt? }` passes it what the user says, in their words, down the path the user's own messages from its page take ([The user writes to it](#the-user-writes-to-it)): each takes it up at its next step, ending or moving aside a command it waits on: Claude Code's running turn makes way for it (`send_now`); Codex's running turn takes it (`turn/steer`); pi takes it before its next model call (`steer`), or stops a running tool first (`abort`); OpenCode and fx cancel the turn under way (`session/cancel`) and start the next with it. `interrupt` stops what it does first (Claude Code's `interrupt` request, `turn/interrupt`, `session/cancel`, pi's `abort`). An agent whose process is gone, because it was done and idle for an hour, was stopped or failed, or Lorca restarted, starts again on its session (`--resume`, `thread/resume`, `session/load`, pi's `--session` with its session file). One still starting takes no message, nor one that ended before it had a session; `send` says so.
- `stop { id }` ends it; `list` answers the bot's agents in the chat, with their titles, how they stand, and their pull requests and those pull requests' states, and `list { scope: "account", query? }` every agent on the account ([Coding agent roster](agent-roster.md)). Only an agent's own bot reads, messages, or stops it, from its chat.

An agent is `starting`, `working`, `asking` while a question waits, or `idle` (done with what it was asked; a later message resumes it); once it ended `failed` or `stopped`.

## The user writes to it

The agent's page has a composer that writes to the agent itself, after Cursor's: `coding.send { chat_id, message_id, text }`, served on the Runner (sealed to it from any other Device), runs the bot's own `send` (`coding::send`, `Sender::User`), without `interrupt`, so the agent takes the message up when it would take the bot's: at its next step, whatever it is running. Stop then a message is how the user cuts in: a stopped agent with a session starts again on it. A message waits in the agent's queue (`Agent.queued`) from when it is sent until the agent reports it as a `prompt` step, which then carries `from: "user"` (the bot's carry none), and the queue empties when the agent stops or its process ends. `coding.send` waits up to 12 seconds for the message to reach the agent, within a sealed request's 20; an agent that takes longer to start again goes on, and its row says how. A refusal ("Claude Code is still starting.", "… ended before its session began", "… is no longer installed on this Runner.") is the answer, and nothing reaches the chat.

What the user wrote goes in the chat as their message to the agent: `Body::AgentMessage` with `Author::You`, which the apps show as "You messaged ⬢ Title · its first line" and which counts as nothing unread, pushes nothing, and starts no turn. The bot reads it in its history as "[The user wrote to Claude Code (agent-…), your coding agent on “Title”, directly; it has the message]: …", and the tool tells it not to pass that on again; its `read` marks such a prompt `> (from the user)`. Auto-review reads it as the user's words, `User, to the Claude Code on “Title”: …`, so what the agent then does is weighed against it as against the user's messages to the bot, and every command still passes the bot's Access and Auto-review and asks on a card as before. The message changes nothing else: what the agent said last stays unheard until a turn reads it, so one that failed and that the user started again from its page still wakes its bot, which hears it has been started since; its next report wakes the bot to relay it as any does; the agent's run time counts toward the turn that last gave it work; and an agent a routine or an event started is no longer `unattended`, since the user is at its page to answer what it asks.

## When it is done

When an agent goes idle after working, Lorca counts what its work changed against the commit it started from (`workspace::changes`: commits, edits not committed yet, and new files, as files and lines added and removed), notes the branch checked out now, which may be one the agent made, and the last pull request or merge request its transcript names. How that pull request stands follows GitHub's (`pull.rs`): every five minutes the Runner reads `gh pr view <link> --json state,isDraft` with the login shell's environment for each pull request an agent still listed names, until it is merged or closed, and keeps `open`, `draft`, `merged`, or `closed` as the agent's `pull_state`. A link elsewhere than GitHub, or a Runner without `gh` signed in, leaves it unread. A new pull request the agent names starts unread again. Then what it said, its last message, goes in the chat as a message from it (`Body::AgentMessage { agent_id, agent_kind, title, text }`, at most 4,000 characters), which the apps show as "Message from ⬢ Title". It is the agent's report to the user, who reviews the work from it and its pull request: it counts as unread, a Runner pushes it to the phones as a reply ("Title: …"), and the Windows and Linux app posts it as a reply when it arrives ([Notifications](notifications.md)). Then the bot gets a turn of its own to relay it: an `agent` job whose trigger is that message, queued behind any turn running in the chat, including the one that started the agent. `Record.unheard` holds the message until a turn reads it, the `agent` turn or `coding_agent read`; nothing else clears it, so a `send` or `stop` meanwhile leaves the wake in place. The bot reads the message in its history as "[Claude Code (agent-…), your coding agent on “Title”, says]: …", and the turn opens with its pull request and tells the bot to pass the report on to the user: the agent's conclusion, its pull request's link, and the evidence it brought back, the commands it ran and what they printed, saying where the report leaves something out without filling it in (`coding::wake_cue`). That turn only relays: it tells the bot to use no tools, and not to open the agent's code, diff, or transcript, run a build or a test, judge the work against the request, or send the agent anything. The user reviews the work and decides what comes next; what they then say about it, the bot passes on to the agent in their words.

An agent whose process ends on its own while it works is `failed`, and so is one whose turn ends in an error with nothing else to take up (`driver::Event::Failed`: Claude Code's `result` with `is_error`, a Codex turn `failed`, an ACP prompt answered with an error, pi giving up after its retries), as a signed-out agent's first turn does within milliseconds; Lorca stops that one's process, and a later message resumes its session. Its message (`failed`) says why. It wakes the bot the same way, and the turn reads which kind of message woke it from that message's `failed`. That turn opens with why it ended and its last lines, and tells the bot to tell the user, and, when it ended for a passing reason such as a lost connection, that it may start it again on its session with a message asking it to go on, adding nothing of its own; an agent the bot started again before that turn ran is named as running again, and the bot is told not to start it again. The failed message itself does not count as unread; the bot's reply does.

While an agent works, its run time counts toward the limits of the turn that gave it the work, the start or a later message ([Budgets](budgets.md)): the turn's scopes hold a run (`BudgetContext::hold`) until the agent is idle, and a time limit reached stops it.

## Stop, quitting, and restarts

Stop in the chat stops every coding agent there, as it does the bot's commands, here or on the Runner when the bot's turn is cancelled there ([Stop](stopping.md)). A start under way when the turn is stopped finishes in a task of its own (`start_unless_stopped`) and stops its agent as soon as it runs, so Stop never leaves one running unfollowed. `coding.stop` reaches it from any Device. Deleting the chat or the bot stops and forgets its agents.

`agents/agents.json` (0600) keeps every agent's record: its chat, bot, row, kind, title, session, folder, branch and base commit, state, changes, pull request and its state, and the message from it the bot has yet to hear. Quitting stops every agent, and the row of one at work reads "Stopped when Lorca quit"; one that was done waits, and a later message resumes its session. An ended agent is forgotten a month later. An update of the CLI waits while an agent is at work.

## In the apps

The `coding_agent` row that started an agent carries it from the start, `Body::Tool.agent`: `{ id, kind, title, task, folder, branch?, state, outcome?, pull_request?, pull_state?, changes?: { files, added, removed }, device?, started_at?, updated_at? }`. A row that sent one a message carries `target_agent_id`. Both keep what the bot wrote the agent as their `detail`. The row keeps its first place in the relay's log however often it changes; the agent's question is its own card, which counts as unread and pushes as any permission card does ([Notifications](notifications.md)).

Every app draws the rows as centered markers with the agent's logo in place of a bot's avatar, "Messaged ⬢ Title · the first line", and the agent's message as "Message from ⬢ Title · its first line". A click on any of them opens the agent's page: its transcript as Cursor draws a run (the prompt in a card, "Thought for 3s", what it said, reads and searches folded into "Explored 16 files 5 searches", "Ran …", "Edited … +12 −3", its plan as a checklist), how it stands, its branch, its pull request, Stop while it runs, and its composer ([The user writes to it](#the-user-writes-to-it)). Each message's card names who wrote it: You, in the accent's tint, or the bot; one the agent has yet to take up reads Queued at the end. The composer reads "Message Claude Code", says under it when the agent takes the message ("Claude Code takes it up at its next step.", "Sending starts Claude Code again on its session."), is off while the agent starts or once it can take none, and keeps the text with why when a message does not go. It follows the agent with `coding.transcript { chat_id, message_id }` (its last 400 steps, the row's agent, `queued`, and `open`, whether a message can reach it), every two seconds on the Runner and five elsewhere, sealed to the Runner from any other Device. The chat's details list the agents under Coding, open ones first, then the latest, leaving out any that ended or sat idle for three days, and agents on the same pull request as one row, the first of them: Working, Needs attention, Ready for review (done with a pull request), Draft, Merged or Closed (its pull request's `pull_state`, which wins over idle, stopped, and failed), Finished, Run failed, or Stopped, with the pull request's number or the branch. The Windows and Linux app also lists every agent on the account, from `coding.list`, in a Coding agents flyout in the main window's header, whose button shows while one is live (open, and when done, changed in the last three days) and carries as its badge how many are at work now, starting, working, or asking, with no badge when none is; a row opens the agent's page. The Windows and Linux app's are `desktop/agents.go`, `desktop/codingagents.go`, and its Settings → Coding Agents pane; the phone's are in `src/ui/transcript.tsx`, `src/ui/AgentScreen.tsx` (opened as `app/agent/[id].tsx`, its composer the chat's `Composer` without the `+` disc), and its Coding Agents settings screen.
