# Coding agents

A bot hands a coding job to a coding agent on its Runner (Claude Code, Codex, OpenCode, pi, or Vercel's fx) and supervises it, after Grok Bot's coding agents: the bot gives the job a title and a brief, the agent works on its own in the folder it is given, and the bot hears from it when it is done. In the chat the agent is a peer the bot messages: "Messaged ⬢ Title" where the bot wrote it, "Message from ⬢ Title" where it answered. Its transcript reads the way Cursor shows an agent's run. `crates/cli/src/coding/` holds it: `tool.rs` the bot's tool, `mod.rs` the agents on the Runner, their rows and messages, and their review, `settings.rs` which agent a start takes, `workspace.rs` the folder and what changed there, `transcript.rs` the steps, and one driver per protocol: `claude.rs`, `codex.rs`, `acp.rs` (OpenCode and fx), and `pi.rs`. Every agent is driven through one interface (`driver::Driver`: a message, and Stop), and reports the same events: its session, steps of its transcript, working, done, what it asks to do, and that it ended.

## Starting one

`coding_agent { action: "start", title, prompt, agent?, folder?, secrets? }` starts one and answers at once with its id (`agent-3f9a2c1d`), which the bot keeps across turns. The tool tells the bot to say it started the agent and end its turn rather than wait. `title` is a few words that name the job wherever the agent shows ("Docs: use mygo.json in the launcher examples"); `prompt` is the user's request in their words, with what only the bot can tell the agent (the folder, what it found, how to check the work, and whether a pull request was asked for), which the tool tells it not to replace with a plan or checklist of its own: the agent decides how to do the job, and the bot leaves the job to it while it has one.

Which agent: each Runner keeps the five in its user's order of preference, each on or off, in `coding-agents.json` in its data directory (0600; `CodingAgents`, every agent on in Lorca's order until the user changes it). A start without `agent` takes the first one on that is installed on the Runner, found on the login shell's `PATH` as a terminal would find it; one that names an agent the user turned off there, or one not installed, fails and says so. `coding.agents { runner_id }` answers that Runner's agents in order, on or off, installed or not, with what `--version` says, and `coding.agents.set { runner_id, agents: [{ kind, enabled }] }` keeps a new order and answers the same; both go to the Runner sealed when it is another Device, so the phone sets them too. The apps show them in Settings → Coding Agents, a pane for the Runner picked at its top on a computer and a screen under each Runner on the phone, with a switch per agent, and the order changes by dragging a row.

`folder` is where the job is: absolute, `~/…`, or relative to the bot's working directory, which it defaults to. The agent works in it as it is, after Grok Bot, whose coding agent is a Cursor agent that decides on its own branch: Lorca makes no worktree or branch, and the agent decides how to work, a branch or a worktree of its own included, as it would started in a terminal there; the bot says so in the prompt when the user asked for one. In a git repository Lorca notes the branch checked out and the commit it starts from (`workspace::prepare`), for what its work changed. The agent gets the bot's prompt, then where it works, to end with a short summary of what it did and how it checked it, and to give a pull request's link if it opens one.

The start needs the bot's Access to Shell commands ([Bot permissions](bot-permissions.md)). It asks nobody: what the agent then does is reviewed step by step (below). An agent an event started, a channel's message among them, keeps the owner's task for that event (`Record.event`, without the event's text), and the review weighs its every action against that task, as it does the turn's own: what someone outside wrote never authorizes it.

`secrets` names the bot's own saved command secrets ([Secret requests](secrets.md)) the job needs, such as `NPM_TOKEN` to publish a package; any other name fails the start, saying to ask for it with `request_secret`. The agent has each as `$NAME` in its environment, looked up again whenever its process starts, and its brief says to use them only with the service each is for. The review of every command it runs is told which it holds, and none takes the fast paths below. Saved values never reach an agent otherwise: a value in the prompt or a follow-up goes as its placeholder, which is not filled.

## How each agent runs

Each runs as a process group of its own (a job object on Windows) with the login shell's environment, less the markers a Claude Code session leaves for its children, plus the secrets it was given, and is spoken to over its stdin and stdout:

- **Claude Code**: `claude -p` with stream-json in and out (`--input-format stream-json --output-format stream-json --verbose --replay-user-messages`), the protocol of its Agent SDK, with `--permission-mode acceptEdits` and `--permission-prompt-tool stdio`, so edits in its folder run and anything else that would ask comes to Lorca. Its initialize request registers a `PreToolUse` hook for Bash, so every command comes to Lorca, whatever the user's own Claude Code settings allow. A message is a user message; Claude Code says when it takes one up (`--replay-user-messages`), which tells a pause between messages from being done. `TodoWrite` is its plan.
- **Codex**: `codex app-server`, the JSON-RPC its own apps speak: a thread in the folder (`thread/start`, `approvalPolicy: on-request`, `sandbox: workspace-write`) and a turn per message. Its commands run in Codex's sandbox, which keeps writes to the folder and the network off; what needs more, such as a push, asks (`item/commandExecution/requestApproval`, `item/fileChange/requestApproval`), and Lorca answers. `turn/plan/updated` is its plan.
- **OpenCode**: `opencode acp`, the Agent Client Protocol: `initialize` without file or terminal methods, so it works with its own tools, then a session in the folder (`session/new`) and a `session/prompt` per message, which answers once the turn is over. Its permissions come from `OPENCODE_CONFIG_CONTENT` (commands, fetches, and anything outside its folder ask; edits in it do not), and what asks arrives as `session/request_permission`, which Lorca answers allow once or reject. ACP has no steering: a message sent while it works waits for the turn to end.
- **fx**: `fx acp`, the same Agent Client Protocol as OpenCode, with `FX_PERMISSION_MODE=ask`: fx's own default, `auto`, has its reviewer decide and asks nobody, while `ask` sends every command and change to Lorca as `session/request_permission`. fx reports a command's exit code in its own `command_result` field, and its text as a cut-off record of where the output went, which the transcript leaves out.
- **pi**: `pi --mode rpc`, its JSONL protocol: a `prompt` per message, or `steer` while it works, which it takes up before its next model call. pi asks nobody before a tool runs, so Lorca writes an extension of its own (`agents/lorca-review.ts`) and loads it with `-e`: its `tool_call` handler sends each call that does more than read (`read`, `grep`, `find`, and `ls` run at once) to Lorca as an extension dialog (`extension_ui_request`), and blocks the call with Lorca's reason when Lorca says no. Another extension's dialog is cancelled, since nobody is at pi's screen.

## What it may do

Every command an agent runs passes the bot's Access as it stands, then Auto-review as the bot's own commands do (`approve`): a command the parser proves only reads, one that stays in Lorca's own folders, or one that only makes, copies, and moves files in the folder it works in, runs at once, unless the agent holds secrets; the review model judges anything else, a push or a deploy, against the request behind the turn that started the agent, with the git state of what a command would discard. Files it changes outside its folder, and its other tools that would ask (a web fetch, an MCP tool), go to the review too. What the review allows runs. What it holds goes back to the agent as a denial that says why (`review::agent_note`): it goes on another way, or stops and names what it needed. What the review asks goes up as a permission card at the end of the chat, where the user reads however far up the agent's row is (`ask_in_chat`): the bot's shell card for the Runner (`plugin_id: computer`), with the command, the reason, which opens with the agent and its title ("Claude Code, the coding agent on “Login”, asks to run this."), and the rule Always allow adds, answered from any Device with `chats.permission`. The row reads `asking` meanwhile. It waits ten minutes. The bot's turn does not wait on it, so the user's messages to the bot leave it up (`mcp::ask_aside`); stopping the agent dismisses it. An agent a routine's run or an event started has nobody to answer (`Record.unattended`): what the review would ask goes back to it at once as a denial that says why, and it goes on without it or names it in its last message. An agent told no hears why and goes on without it.

## Its transcript

What an agent says, runs, shows, and asks, and what it is sent, has the Runner's saved secrets replaced by their placeholders before it reaches its transcript, its file, its row, its message in the chat, the review, or the bot (`without_secrets`), as a tool's result does: an agent may print a value its environment or a file holds.

Each driver turns what its agent reports into steps (`transcript::Item`): `prompt` (what it was sent), `status` (Lorca's own line: "Working in ~/dev/shop on main", "Interrupted"), `thought` (with how long it thought when the agent says), `text` (what it said), `tool` (`{ kind: read | search | edit | execute | fetch | other, title, path?, added?, removed?, status: running | done | failed | denied, output? }`, its output's first twelve lines), `plan` (entries pending, in progress, or completed), and `error`. A step has an id, and a later step with the same id is that step changed: a command running, then done with its output. Every step is appended to `agents/<id>.jsonl` (0600), and the last 4,000 are in memory; a restart folds the file back.

- `read { id, lines? }` answers what changed since the bot last read, as Claude Code's screen words it (`> ` and what it was sent, what it said, `● Bash(git status --short)` and the start of what came back), up to its last 200 lines, or its last `lines`, and how it stands.
- `send { id, message, interrupt? }` gives it a follow-up: Claude Code takes it up at its next step or after its turn; Codex's running turn takes it (`turn/steer`); pi takes it before its next model call (`steer`); OpenCode and fx after their turn. `interrupt` stops what it does first (Claude Code's `interrupt` request, `turn/interrupt`, `session/cancel`, pi's `abort`). An agent whose process is gone, because it was done and idle for an hour or Lorca restarted, starts again on its session (`--resume`, `thread/resume`, `session/load`, pi's `--session` with its session file).
- `stop { id }` ends it; `list` answers the bot's agents in the chat, with their titles, how they stand, and their pull requests.

An agent is `starting`, `working`, `asking` while a question waits, or `idle` (done with what it was asked, waiting for a follow-up); once it ended `failed` or `stopped`.

## When it is done

When an agent goes idle after working, Lorca counts what its work changed against the commit it started from (`workspace::changes`: commits, edits not committed yet, and new files, as files and lines added and removed), notes the branch checked out now, which may be one the agent made, and the last pull request or merge request its transcript names. Then what it said, its last message, goes in the chat as a message from it (`Body::AgentMessage { agent_id, agent_kind, title, text }`, at most 4,000 characters), which the apps show as "Message from ⬢ Title", and its bot gets a turn of its own, an `agent` job whose trigger is that message, once no turn runs in the chat, unless a turn read the agent meanwhile (`Record.unheard`). The bot reads the message in its history as "[Claude Code (agent-…), your coding agent on “Title”, says]: …", and the turn opens with where the agent works, what it changed, its pull request, and to check its work, then send a follow-up or tell the user how it went. An agent whose process ends on its own while it works is `failed`, and its message (`failed`) says why, with the same wake-up.

While an agent works, its run time counts toward the limits of the turn that gave it the work, the start or a follow-up ([Budgets](budgets.md)): the turn's scopes hold a run (`BudgetContext::hold`) until the agent is idle, and a time limit reached stops it.

## Stop, quitting, and restarts

Stop in the chat stops every coding agent there, as it does the bot's commands, here or on the Runner when the bot's turn is cancelled there ([Stop](stopping.md)). A start under way when the turn is stopped finishes in a task of its own (`start_unless_stopped`) and stops its agent as soon as it runs, so Stop never leaves one running unfollowed. `coding.stop` reaches it from any Device. Deleting the chat or the bot stops and forgets its agents.

`agents/agents.json` (0600) keeps every agent's record: its chat, bot, row, kind, title, session, folder, branch and base commit, state, changes, pull request, and the message the bot has yet to hear. Quitting stops every agent, and the row of one at work reads "Stopped when Lorca quit"; one that was done waits, and a follow-up resumes its session. An ended agent is forgotten a month later. An update of the CLI waits while an agent is at work.

## In the apps

The `coding_agent` row that started an agent carries it from the start, `Body::Tool.agent`: `{ id, kind, title, task, folder, branch?, state, outcome?, pull_request?, changes?: { files, added, removed }, device?, started_at?, updated_at? }`. A row that sent one a message carries `target_agent_id`. Both keep what the bot wrote the agent as their `detail`. The row keeps its first place in the relay's log however often it changes; the agent's question is its own card, which counts as unread and pushes as any permission card does ([Notifications](notifications.md)).

Every app draws the rows as centered markers with the agent's logo in place of a bot's avatar, "Messaged ⬢ Title · the first line", and the agent's message as "Message from ⬢ Title · its first line". A click on any of them opens the agent's page: its transcript as Cursor draws a run (the prompt in a card, "Thought for 3s", what it said, reads and searches folded into "Explored 16 files 5 searches", "Ran …", "Edited … +12 −3", its plan as a checklist), how it stands, its branch, its pull request, and Stop while it runs. The page is view-only: follow-ups go through the bot. It follows the agent with `coding.transcript { chat_id, message_id }` (its last 400 steps and the row's agent), every two seconds on the Runner and five elsewhere, sealed to the Runner from any other Device. The chat's details list the agents under Coding, open ones first, then the latest, leaving out any that ended or sat idle for three days: Working, Needs attention, Ready for review (done with a pull request), Finished, Run failed, or Stopped, with the pull request's number or the branch. The Windows and Linux app's are `desktop/agents.go` and its Settings → Coding Agents pane; the phone's are in `src/ui/transcript.tsx`, `app/agent/[id].tsx`, and its Coding Agents settings screen.
