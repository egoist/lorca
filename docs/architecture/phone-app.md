# Phone app

`mobile/` is an Expo app (React Native, expo-router, TypeScript) for iOS and Android. A phone is a Device and never a Runner, and it links the same Device core the CLI is built from rather than porting it: `crates/mobile` (`lorca-mobile`) wraps the `lorca` library, built without the `runner` and `server` features, in a UniFFI object with three calls, and `mobile/modules/lorca-core` is the Expo native module around it.

- **The core** (`crates/mobile/src/lib.rs`): `Core.start(home, name, os, osVersion, model, listener)` loads the App from the app's own folder, sets the host facts (a phone cannot probe them), and starts the relay sync loop on an embedded tokio runtime; `request(method, params)` is one call of the JSON API in `crates/cli/src/api.rs`, blocking on the module's background queue, answering `{ result }` or `{ error: { message } }`; `wake()` asks the relay again now (the app calls it on foreground, since the sync socket may have died while iOS suspended the app). Every event on the App's bus reaches the listener as the `{ event, data }` frame the websocket carries.
- **The native module** (`mobile/modules/lorca-core`, picked up by Expo autolinking): a Swift `Module` and a Kotlin one, each about forty lines, forwarding `start`, `request`, and `wake` and turning the listener's frames into a `sendEvent`. `bun run core` (`build.ts`) builds the Rust for `aarch64-apple-ios` and the simulator into an xcframework with the UniFFI Swift beside it, and for `arm64-v8a` and `x86_64` with `cargo ndk` into `jniLibs` with the Kotlin (over JNA). The built pieces are gitignored; a Rust change needs `bun run core` and a native rebuild, a JS change is a Metro reload.
- **The JS side** (`mobile/src/core`): `engine.ts` starts the core, mirrors its events into the zustand store (`store.ts`, the way the macOS app's AppStore mirrors the CLI: `snapshot`, `roster.changed`, `message.*`, `job.*`, `chat.usage`, `relay.status`, `identity.changed`; events that arrive while a `bootstrap` snapshot is on its way wait and apply after it, as in the macOS app, so a snapshot built before the relay connected cannot undo that `relay.status`), and offers the screens the same verbs the macOS app has, each one request (`chats.send`, `bots.create`, `bots.update`, `pair.accept`, `providers.connect_*`, `providers.list_models`, `providers.api_key`, `providers.disconnect`, `device.rename`, `device.unpair`, `device.update`, `identity.forget`, `sync.wake`, …). `prefs.ts` keeps the one thing that is the phone's own, the dictation language. Nothing about the account is stored outside the core's folder.
- **Pairing**: the phone scans the QR code the desktop app shows, pastes a string from the app or `lorca pair` on another computer, or opens it as a `lorca://pair?…` link; `pair.accept` does the handshake in the core and the first `bootstrap` snapshot fills the store.
- **Relay status**: the chat list's title slot (`src/ui/ChatsScreen.tsx`) stays empty while the relay connects, and speaks once that has taken a second, or four after the app comes to the foreground, when the socket the suspension killed is replaced: "Connecting…" with a spinner, or, once a try has failed (`relayError`), "Can’t connect" or, for an unknown machine, "Pair this phone again" beside a warning glyph. A tap on those opens an alert with the error (`src/ui/relay.ts`) and Try Now (a wake) or Unpair This Phone. "Update Lorca to sync" takes the slot over all of them. Settings › Account › Relay shows the error in place of "Connecting…".
- **Attachments**: the composer's `+` offers the photo library, the camera, and the file picker; a picked file's path goes with `chats.send`, and the core copies, encrypts, and uploads it as a `file` blob ahead of the message. A bubble that shows an attachment this phone does not have asks `files.path`, which fetches the blob and answers with the file; a fetch that failed says Couldn't download · Retry and is asked again only on a tap (`fileErrors` in the store). Images render as thumbnails sized from the width and height in the message (full screen on tap); other files as a name-and-size card, which opens the file: Quick Look on iOS (`previewFile` in the native module, a `QLPreviewController` over the app), the share sheet on Android (`expo-sharing`). Both take the file under its own name, the private named copy `files.path { named: true }` keeps.
- **Skills** (`app/chat-info/skill/[id].tsx`, `save-skill/[id].tsx`, `src/ui/skills.ts`): Details lists the bot's or the group's skills and opens each in its own screen; Add Skill writes one or saves one from the chat's messages, drafted on the bot's Runner. See [Playbooks](playbooks.md#app-and-api).
- **Project** (`app/chat-info/project/[id].tsx`, `src/ui/project.ts`): as in the desktop apps, a group's Details has a Project section right after its name and description, with the group's [project context](project-context.md#the-apps) (`useProject`, from `projects.get`, which Details asks for when it opens and again on `projects.changed`): a row per entry with its kind and its link's host, or who suggested it, an orange mark for two versions or a link that could not be opened, five rows before Show More, and Add to Project, a menu of the kinds, Link, and File (picked with the document picker and sent to `projects.asset`). A row slides in the entry's screen: Title, the text, and the Link with Check Now and when it was last checked in the footer, or the file, which opens in Quick Look; who saved it in a footer; Add, Save, Accept, or Keep This Version in the toolbar; Remove at the bottom; and the desktop apps' alert when another Device saved first.
- **Outputs** (`src/ui/outputs.tsx`, `app/chat-info/output/[id].tsx`, `app/chat-info/outputs/[id].tsx`): as in the desktop apps, a chat's Details has an Outputs section after its name and description, hidden while there is none: the three latest outputs (`useOutputs`, from the loaded messages and `outputs.list`, which Details asks for when it opens) with their check's Passed, Failed in red, or Not verified, and View All for the rest. A row slides in the output's screen inside the same sheet: a preview (the image, the first 256 KB of a text file, or the file's name and size; a tap opens it in Quick Look on iOS), who published it and when, the check, the versions as a list to pick from, and Open (Quick Look, or the link in the in-app browser) and Share… (the share sheet, where the phone saves a copy), or Try Again when the file could not be fetched. See [Outputs and evidence](outputs.md).
- **Tasks** (`app/chat-info/durable-task/[id].tsx`, `src/ui/durableTasks.tsx`; not the Running tasks of `app/tasks`, which are a chat's commands): Details has a Tasks section after the name and description, with the chat's [durable tasks](tasks.md#in-the-apps) from the snapshot and `tasks.changed` (`useDurableTasks`), what waits on the user first, five rows before Show More, and New Task. A row slides in the task's screen: its state, reason, result and evidence (an output opens on that version's screen), the step the state allows as a row in the tint color, the goal, owner, next step, and Done when as a form Save writes back, what it waits for, its links, and Cancel Task. The core sends each write to the task's authority Runner.
- **Limits** (`app/chat-info/limits.tsx`, `src/ui/limits.ts`): Details' Runs with ends with a Limits row ([Budgets](budgets.md#in-the-apps)): the DM's limits, or Limit reached in orange when its newest turn stopped. A task's screen and a routine's screen have the same row; a routine that stopped leads its row and its screen with Limit reached and drops Run Now. A routine's screen and its row in Details are in [Routines](routines.md#the-apps). The row slides in the Limits screen: a stopped card with Resume, the five limits as fields (empty for none, dollars and minutes), and what the work used, with the limit it reached in orange. Save in the toolbar sets the limits; Resume saves them, then goes on, asking first when it would grant the limits again in full. `budgets` comes from the snapshot and `budgets.changed`.
- **Review** (`app/chat-info/review/[id].tsx`, `src/ui/reviews.ts`, `src/core/reviewEdit.ts`): as in the desktop apps, Details has a Waiting for review section after the name and description while the chat's bots have something open ([Review queue](review-queue.md#in-the-apps)); a row pushes the review screen. Its header reads like the permission card ("Chef wants to run a command on Workbench", the rationale under it), then one field holds the command, the call's arguments, or the draft, the details follow, and Reject sits apart at the bottom. Approve is the toolbar's Done-style button; an edit goes up first as the next version. A call's arguments come from the core as its JSON text and go back the same way (`exactJson.ts`, `requestText` in the native module's JS), since `JSON.parse` would round an id past 2^53.
- **Templates** (`src/core/templates.ts`, `src/ui/TemplateShareScreen.tsx`, `app/template.tsx`): Details' Share as Template, Settings › Shared Links, and New Bot from Template, which `lorca://t/…` links open; see [Bot templates](templates.md#in-the-apps).
- **Secrets**: [the card and a Runner's list](secrets.md#in-the-apps).
- **Feedback** (`app/chat-info/feedback/[id].tsx`, `feedback-item.tsx`, `give-feedback/[id].tsx`, `src/core/feedback.ts`): a DM's Details has a Feedback section after Routines with the bot's suggested changes, All Feedback, and Give Feedback, which picks one of its replies, since a long press selects text ([Workflow feedback](feedback.md#in-the-apps)).
- **Workflows** (`app/workflows/`): New Workflow in the chat list's New menu lists the marketplace's [workflows](workflows.md#the-apps); a workflow's screen sets it up on a Runner, runs its sample, and offers its schedule.
- **Access** (`src/core/access.ts`, `src/ui/AccessScreen.tsx`, `app/chat-info/access/[id].tsx`, `access-plugin.tsx`): a DM's Details has an Access row after Description, and a "needs more access" card's Edit Access… opens the same screen; see [Bot permissions](bot-permissions.md#requests-to-the-user).
- **Named accounts** (`src/ui/AccountScreen.tsx`, `app/chat-info/account/[id].tsx`, `app/settings/account/[id].tsx`): a plugin's rows in Details and in a Device's Plugins name each [named account](integrations.md) (Gmail · Work) with its state in a word or two (`src/ui/plugins.ts`) and no description; a tap slides in the account's screen, the desktop apps' Account card: its Name, which `plugins.rename` keeps when editing ends, and its sign-in row (Signed in, Not signed in, Needs more access, Needs setup, Can’t connect with the server's reason in the footer), with Sign in or Sign in again and Sign out. Sign in sends `plugins.connect` to the Runner, and the page opens in the in-app browser as a card's does; the Runner keeps the tokens. Adding an account and its setup are left to a computer. Browser's row slides in the bot's [browser profiles](browser-sessions.md#in-the-apps) (`src/ui/BrowserScreen.tsx`, `app/chat-info/browser/[id].tsx`). Any other plugin's row slides in the same screen with its state. Every plugin's screen ends with its [call limit](budgets.md#shared-connector-admission): Calls and At once as menus of the usual values (60 a minute, 4 at once), the Runner's own value shown when it is another, which `connector_limits.set` saves at once.
- **Dictation**: the primary disc is Dictate while the field is empty (a small microphone sits inside the field once there is text). While recording, the field shows Grok Bot's pill: a stop square, the elapsed time, and bars that follow the microphone, with Send still beside it. The words land in the field after whatever was typed when the user taps the square, or go out at once when the user taps Send. The recognizer (`expo-speech-recognition`) listens in the first of the phone's preferred languages it supports (`src/ui/dictation.ts`; a Chinese speaker on an English-region phone gets zh-CN), or the language chosen in Settings or by a long press on the microphone.
- **Notifications** (`src/core/push.ts`, `expo-notifications`): after pairing, and on every launch and foreground, the app asks for permission once, reads the native device token, and registers it with the relay through the core (`push.register { platform, token, environment }`). The Swift module writes the core's push key into the build's keychain group (`group.app.lorca` or `group.app.lorca.dev`) at start and on `identity.changed` (removed when the phone holds no account); the notification service extension is its own target, generated at prebuild by `@bacons/apple-targets` from `targets/notify`. A tap opens the chat, a reply in the chat on screen makes no banner, and opening a chat dismisses its notifications.
- **Releases and updates**: iOS builds go to TestFlight, which updates them; Android builds are APKs in this repo's GitHub releases tagged `mobile-vX.Y.Z`, made by `scripts/release-ios.ts` and `scripts/release-android.ts` here or in `.github/workflows/release-mobile.yml` ([docs/releasing-mobile.md](../releasing-mobile.md)). The version is `version` in `app.config.ts`, and Android's versionCode is made from it (1.2.3 is 1002003); its iOS Info.plist answers export compliance (`ITSAppUsesNonExemptEncryption` false: standard algorithms, no App Store distribution in France). The Android release build updates itself (`src/core/updates.ts`): once a day, at launch or back in the foreground, it reads the `mobile-v` tags through the GitHub API, since the repo's latest release is the CLI's, takes the newest published release newer than itself, and offers it in an alert with the release's notes (Install Update, Remind Me Later, Skip This Version); Settings › Updates checks at once or installs what a check found, shows the download's progress, and holds the switch for the daily check, with the choices in `prefs.ts`. `Updater.kt` in the native module downloads the APK, checks it against the size and SHA-256 GitHub lists for the asset and that it is this app and newer, and commits it to a `PackageInstaller` session, which installs only an APK signed with the installed app's key and then stops the app. It asks for no confirmation from Android 12 (`UPDATE_PACKAGES_WITHOUT_USER_ACTION`) once the user has let Lorca install apps; otherwise the installer's confirmation shows, from the foreground. Lorca Dev never updates.
- **Turns**: sending is `chats.send`; the core admits a `turn` Job on the bot's Runner or a group room, exactly as any Runner's CLI does. When a direct turn already owns the chat, the Runner promotes the new user message as steering after the current model step and its tools settle, and a question the turn waits on is dismissed rather than waited for; the admitted Job then exits when it reaches the lock because that message was already handled. In a group, the current member settles and the newly admitted room takes over. The `job.started` / `job.finished` events drive the "is working" row and "Chef stopped without replying"; `job.thinking`, `job.retry`, and the running tool rows fill in what the bot is doing, which the core reads in the Runner's `machine` blob and the chat log. The row shows every turn in flight, whichever Device started it, and is back when the app is closed and opened again (see Working state in [the macOS app](macos-app.md)). The phone has no hard Stop control.

While something waits on the user, the chat list has an Attention button beside Settings (a tray on iOS, Material's inbox on Android). It opens `app/attention.tsx`, a form sheet after the Mac's popover: each coordinator's latest brief (the bot, when, and Decision, Changed, and Next lines), then a grouped list of items, urgent first, each with its category's symbol, the title, the next action, and "Review · Launch copy". A tap opens the item's chat; a long press offers its other source chats and Mark as Resolved. The header's ⋯ menu holds the Briefs and Urgent Items notification switches and the coordinator (Automatic, or one bot); with nothing left the sheet says so. Bootstrap and `attention.changed` supply the list from the core (see [Coordinator attention](attention.md)).

The UI is native: a native stack with large titles, search, and toolbar items; a composer after Grok Bot's phone app, a liquid-glass `+` button and glass pill (`expo-glass-effect`, a filled pill where glass is unavailable) floating over the transcript with the Dictate or Send disc inside the pill's right edge, riding the keyboard as a `KeyboardStickyView` while the transcript's `KeyboardChatScrollView` lifts the last messages with the keys by growing its bottom inset, so the list is never resized; form sheets on iOS and full-screen Material modal screens on Android for chat info, new bot, new group, and settings; a Device's screen under Settings (`app/settings/device/[id].tsx`), where a Runner whose CLI updates itself has a Lorca CLI row with its version and where its update stands ([Updates and the service](runtime.md#updates-and-the-service)), the row itself offering Update while a newer release is out and the Runner is online; provider credential screens under Settings, with API-key fields and an in-app browser for subscription OAuth, the same browser that opens a computer's plugin sign-in from its card, and custom providers after the built-in ones: Add Custom Provider is a native menu of the same presets as the desktop apps (one the account has is checked and opens it) and Other Server…, opening a form (`app/settings/custom-provider.tsx`: name, API menu, base URL with the URL the CLI will call and, for a server on localhost, a note to name it as the Runners reach it, key, a Models row, and a Default Model menu) whose Models row slides in a picker (`app/settings/custom-models.tsx`) of the server's listed models with a native search bar that offers Add "…" for an id it does not list; the two share their rows through `src/ui/modelDraft.ts`; Link previews and context menus on iOS chat rows, with swipe actions on an iPhone row as in Messages (Pin and Delete to the left, Mark as Read to the right while it has unread messages; one row open at a time, closed when the list scrolls), and Material long-press menus on Android; SF Symbols on iOS and Material Symbols on Android; UIKit semantic colors and Material 3 dynamic colors, the palette built once per appearance (`src/ui/theme.ts`) and Android's Material palette for `@expo/ui` views given once at the root; message text follows the Dynamic Type size on iOS (Android sizes it in sp); haptics by what happened (`src/ui/haptics.ts`): UIKit's feedback generators on iOS, the system haptic constants on Android, which follow its touch-feedback setting. Android presses ripple rather than highlight (`src/ui/Pressable.tsx`), alerts are Material 3 dialogs from Compose rather than AppCompat's (`src/ui/alert.tsx`, `Alert.alert`'s arguments; UIKit's alert on iOS), and the app theme is Material 3 with dynamic colors (`plugins/with-material-theme.js`), which Android's own text handles and overscroll take. Forms (`src/ui/forms.tsx`) follow each platform's lists: iOS's uppercase section titles, disclosure chevrons, trailing checkmarks, and UIKit switches; on Android, subheaders in the primary color, no chevrons, a radio button (or a checkbox where several can be picked) before a choice, Material 3's Compose switch with the whole row toggling it, and a dropdown arrow on a value menu. A photo opens full screen and zooms by pinch or double tap: in a zooming UIScrollView on iOS, by gestures on the UI thread on Android. Android toolbar actions and popup menus are Jetpack Compose views from `@expo/ui`: the chat list has Settings on the leading side and the New menu on the trailing side, with no title, and its search field in the capsule at the foot of the list, while the composer's attachment sources open in a Material bottom sheet. Conversation headers overlay the transcript on both platforms; UIKit supplies its navigation material, while Android lays a nearly opaque veil in the surface color (the wallpaper's tint included) through the status bar and controls and fades it into the transcript, leaving scrolled messages faintly visible like Gemini; its controls are a Material top bar's: Back, the members and title at the start, Running tasks, and ⋮. The transcript follows the macOS app: bubbles with the bot's name above and its avatar beside the bubble's bottom edge in a group, neither in a DM; "Today 4:13 AM" separators after fifteen minutes; the "is working" row ("Working…" in a DM, "Chef is working…" in a group, or what the one working bot is doing, in the Mac's words and by its rules, such as "Thinking…" or "Running command: Install dependencies…" (`workingActivity` in `src/ui/format.ts`), its words shimmering inside `ShimmerView`, a native container in `lorca-core` that masks its children with the Mac's sweeping gradient) and the breathing green dot on avatars; "Message from ◉ X" and "Messaged ◉ X" markers; tool calls never shown, except a `bash` call's command card while the command needs the user, after the Mac's (`showsCard` in `src/core/model.ts`): the command's first line in a code block that opens the whole command in a sheet on tap (`app/command/[id].tsx`: a form sheet on iOS, a Material full-screen dialog on Android, Copy in its bar); while Auto-review asks, its question with the answers; once the bot handed the running command over, Stop on the title's line and its last lines in a code block that scrolls past six lines, fading at an edge with more past it (Android's `fadingEdgeLength`, a gradient in the block's color on iOS); at a question, Answer, which opens `@expo/ui`'s bottom sheet sized to its content (SwiftUI's on iOS, Material's on Android; `src/ui/AnswerSheet.tsx`) holding only a field, with the command's question as its placeholder, that takes the text as typed, without capitalization or correction, and hides it unless the question is a yes or no, and Send; the sheet closes when the command ends; Running tasks (see [Terminal sessions](terminal-sessions.md)) as a terminal button beside the chat's ⋯ (a native bar button on iOS, the Android header's own button), which opens them as rows in a sheet with its own stack (`app/tasks/`), each sliding in its command's details: the bot and how the command stands, Run in Background while the bot's call waits on it, Stop Command, the whole command, and its last lines; sidebar-style previews and stamps, and in the chat list, while a chat has a turn in flight, three dots lighting up in turn and "Working…" in place of its preview.

A window at least 700 pt wide (a tablet, or a tablet window with room to spare) shows two panes (`app/(main)/_layout.tsx`, `src/ui/layout.tsx`): the chat list as a sidebar (320 pt, 375 pt from 1100 pt) and the open chat beside it; a narrower one stacks the chat over the list. The route group `(main)` holds the list and the chat in a stack of their own inside the root stack, so sheets and the pairing screen cover both panes. The sidebar (`src/ui/Sidebar.tsx`) is the same `ChatsScreen` in a native stack of its own, one screen deep, in an independent navigation tree, so it keeps the native bar and toolbar buttons; the pane's stack starts at an empty "Select a chat" screen, a chat picked in the sidebar replaces the one open, its row stays lit, and the chat's bar has no back button. Sidebar rows open their menu on a long press on both platforms, with no Link preview. On iOS the sidebar sits in a `CompactWidthView` (`modules/lorca-core`), a container that overrides the horizontal size class to compact as a split view's sidebar column does. On both platforms the sidebar's search field is a capsule at the foot of the list (`src/ui/SidebarSearch.tsx`; glass on iOS, filled on Android), level with the composer and riding the keyboard: UIKit moves a search bar into the bottom toolbar only on an iPhone, and on Android the search action is an item of the activity's one action bar, which react-native-screens hands to whichever stack updated its header last, so a sidebar's item would vanish once the pane opens a chat. The transcript sits in a `SoftScrollEdgeView`, which gives its scroll view the soft top edge a phone has where an iPad would rule a line under the bar. Bubbles and Markdown measure against the pane's width (`usePaneWidth`) and stop growing at 620 pt.
