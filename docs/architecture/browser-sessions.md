# Browser sessions

A bot's browser profiles: each keeps its own sign-ins on the bot's Runner, opens in a window there, lets the user take the browser from the bot and hand it back, and records a workflow the user does once so the bot can repeat it. `crates/cli/src/browser.rs` answers the `browser.*` methods and forwards them to the bot's Runner; `browser/runner.rs` keeps the records, the open browsers, and their input gates, `browser/recording.rs` and `browser/recorder.js` record, `browser/steps.rs` is the steps a skill keeps, and `browser/replay.rs` runs them.

## Profiles

A profile (`Session` in the code) has a stable `browser-<uuid>` id, `bot_id`, `runner_id`, a `name`, `state` (`stopped`, `bot`, `taking_over`, `human`), `selected`, `revision`, `created_at`, and `recording` while the user records in it. It belongs to one bot on the Runner it was made on. Every method and every Browser call checks the bot's current assignment, so a bot moved to another Runner starts over with that Runner's profiles.

The Runner keeps the records in `browser/sessions.enc`, encrypted with the account DEK (`browser-sessions` as associated data), written to a private file and renamed into place. Each profile's Chromium folder is `browser/profiles/<id>` (0700): its cookies, storage, and history stay there between opens, on that Runner only, as the plugins' secrets do. A restart leaves every profile closed and opens no window. Deleting a profile closes its browser and removes its folder; forgetting the identity removes `browser/`.

A bot's first profile is its `selected` one, and opening another selects that. The bot's Browser calls go to its selected profile while that is open with the bot in control (`bot`). With none open they go to the plugin's shared headless browser, as for a bot without profiles, so Browser works on a Runner without a screen.

Profiles keep sites' sign-ins apart; the browser and the bot's tools still run as the Runner's user. A dedicated Runner, or a Runner inside an OS isolation boundary, is the stronger separation, through the bot's assignment.

## Opening

The curated Browser plugin (`playwright`) supplies the server. Opening a profile starts a headed Playwright MCP process of its own (stdio, `--user-data-dir browser/profiles/<id>`, `--output-dir browser/output/<id>`, PNG image answers), then brings its current tab forward; opening an open profile only brings it forward. A Browser plugin whose arguments or environment set their own profile, config, CDP endpoint, extension, or port can't open profiles, and those `PLAYWRIGHT_MCP_*` variables are taken out of the login shell's environment for these processes. Chrome is the default browser; the Runner's `PLAYWRIGHT_MCP_EXECUTABLE_PATH` picks another Chromium.

The apps' Open Browser gives the user control (`human`). The bot opens one with `browser_session { action: "open" }`, which passes [Auto-review](tools.md) as a plugin action does (refused in a routine nobody watches) and gives the bot control (`bot`). Profiles are part of the Browser plugin for a bot's [Access](bot-permissions.md): a bot whose Access leaves Browser out has no `browser_session`, and every call of it checks the grant first (`permissions::check_plugin`, any grant to the plugin, whichever of its tools the grant lists). Closing (`browser.stop`) revokes the bot's input at once and cancels an open still starting; with no call in flight it closes Chromium first so it writes out its cookies, then ends the process. Removing the Browser plugin closes every profile's browser.

## Taking over

Every Browser call in a profile holds that profile's input gate until its server answers. Take Over marks the profile `taking_over` at once, so new calls wait, and `human` once the call in flight has answered; on the Runner the window comes forward. Waiting calls keep their turn and codemode state, and the chat's Stop ends them. `browser_session` waits during a takeover too, and the bot can't open a profile over the user. The bot's other tools run as usual.

Return to Bot sends the revision the app last saw: a profile that changed since (another Device took it over again, or closed it) is not handed back. It wakes the waiting calls, which find the same page, tabs, and sign-ins.

A call the chat's Stop ends keeps the gate until its server answers, up to ten seconds, and is not called off: rmcp forgets a request it cancels while the server goes on with it. A call that answers in none of that time, or runs out of time, closes its browser, which ends any input it had left.

## Recording a workflow

Record starts a recording in a profile with the user in control: on the Runner it opens the browser for the user, or takes it from the bot as Take Over does; from another Device it records only a browser already open on the Runner's screen (`state` not `stopped`), since the user does the task in that window, and otherwise answers to record it on the Runner. `browser.record` puts the recorder (`recorder.js`) in the profile's Playwright MCP process through the server's run-code tool (`browser_run_code_unsafe`, or `browser_run_code` in older releases), with a binding of a random name. It keeps its state on the browser context, so later documents and tabs record too, and it hears only the user's own input (trusted events): clicks, what was typed into a field once the field is left or Enter is pressed, choices in a menu, checkboxes, a file picked after a click that asked for one (the file's name only), Enter and Escape, and a page the user went to themselves, such as from the address bar; a page a step led to within four seconds belongs to that step. A password field, a field whose autocomplete names a password, a one-time code, or a card, and a field labelled as a secret, token, PIN, or code, is never read: its step says `secret: true`. A value the user typed that is one of the Runner's saved [secrets](secrets.md) is kept only as its `{{secret:NAME}}`; a page title or a locator that shows it has it replaced or is left out, and the steps on that page keep no screenshot while it can show the value. Each element becomes Playwright locators, the ones that find exactly one element first: test id, role and name, label, placeholder, id or name, text, and only for an element with none of those, where it sits on the page. Each step's screenshot is a JPEG of the page once the step settled (1.2 s, or the next step), with password and secret fields masked; a recording keeps at most 100 steps.

`browser.stop_recording { chat_id, text }` stops it and checks what came back: each step must be one a steps file takes, typed text that matches an account credential is kept as a secret, and a screenshot is read only from the recorder's own folder. The recording (`Recording`: steps, where each happened and the page it settled on, screenshots) is kept on the Runner in `browser/recordings/<profile>--rec-<uuid>.enc`, encrypted with the account DEK (`browser-recording`); a profile keeps its newest 20, and deleting the profile deletes them. Then the user's message, the app's `text` in the user's language, goes to the chat with `recording { id, bot_id, profile, steps }` and addresses the bot (`runtime::send_recording`), and the bot's turn starts as for any message; a recording of nothing sends nothing and answers `message_id: null`. The user keeps the browser. Closing the browser drops a recording in progress, and Return to Bot is refused until the recording stops.

On its Runner the bot reads that message with the recording (`recording_content`): the steps as `browser-steps.json` takes them, where each happened and the page it settled on, marked as data from websites, how to make a skill of it, and the screenshots (at most 12) while the message is the user's latest and the model takes images. The bot drafts the skill with `propose_playbook` (kind `recording`, citing that message), asks about what the recording doesn't show, and offers a routine; the draft is used only once the user saves it (see [Playbooks](playbooks.md#workflow-capture-and-standing-instructions)).

## Running recorded steps

A skill keeps its steps in `scripts/browser-steps.json`: `{ profile, inputs?, steps }`, where `inputs` names each `{{name}}` the steps use with what it is, and a step is `goto { url }`, `click`, `fill { value | secret }`, `select { values }`, `check`, `uncheck`, `upload { files }` (each with 1–8 `targets`), or `press { key }`, with an optional `element` and `note` in words, `expect { url?, title?, text? }`, and `timeout` (1–60 s, else 15). A `fill` value, and nothing else, may type one of the bot's saved secrets as `{{secret:NAME}}`; the credential scrubbing every skill passes through keeps such a name. Saving or drafting a skill checks the file as a run reads it.

`browser_session { action: "run", skill, inputs }` repeats a saved skill's steps (a draft never runs) in the bot's profile the file names, opening it for the bot first. It passes [Auto-review](tools.md) as one action whose arguments list the steps in words, and like opening a window it is refused in a routine when Auto-review would ask, since nobody is there to answer. Each step holds the profile's input gate, so a takeover waits for the step and the run waits for the browser to come back. A step calls the Browser server's own tools on the first of its targets the page has, trying the next when one matches nothing, more than one element, or an element that can't take the action, and looking again until its time is up; then its `expect` must hold: the current tab's address or title contains the text, or the text is on the page. A step that types a password the recording didn't keep does not run; the profile keeps the sign-in. A step that types `{{secret:NAME}}` needs that Browser secret saved for the bot before the run starts, and the run fills it in right before the call, only while the current tab is on the secret's site, as the bot's own Browser calls do (`secrets::fill_call`); what the browser answers, and the run's notice, show the placeholder. A step the page no longer matches stops the run: a screenshot of the page goes to the chat as the bot's output, a notice says which step and why, and the result ends the turn (`terminate`) rather than letting the bot try another way. A routine runs a recorded skill the same way, its task naming the skill. The chat's [Stop](stopping.md) ends a run at once: no further step starts, and the step in flight keeps the gate until its call answers, up to ten seconds, and otherwise closes the browser, as a stopped Browser call does.

## Signing in with a saved secret

A bot that needs a password for a site asks for it on a card ([Secret requests](secrets.md)) and types it as `{{secret:NAME}}` with `browser_type` or `browser_fill_form`. The Runner fills it in right before the call reaches the browser, and only while the current tab is on the secret's site, over https; the page's echo comes back with the placeholder.

## Screenshots

A screenshot of a profile, the bot's `browser_take_screenshot` while its profile is open or Take Screenshot in the apps, is published as the bot's [output](outputs.md) in the chat through `outputs::publish`: one series per profile and chat, `Browser · <name>.png`, each screenshot its next version, with `after_screenshot` evidence that is `unverified` ("What the Work browser showed."). The PNG is queued as an encrypted `file` blob before the encrypted chat message, as any output's file is, and paired Devices open it from the transcript or the chat's outputs. Publishing the browser's own capture file needs no file Access. A screenshot shows the page; it says nothing on its own about whether a task worked.

## Methods and Devices

`browser.sessions { bot_id }` answers `{ sessions }`. `browser.create { bot_id, name }` answers `{ session }`; `browser.open`, `browser.takeover`, `browser.resume { revision }`, `browser.stop`, and `browser.record` take `bot_id` and `session_id` and answer `{ session }`; `browser.delete` answers `{}`; `browser.screenshot { chat_id }` answers `{ message_id }`, for a chat the bot is in, and `browser.stop_recording { chat_id, text }` answers `{ session, message_id }`. The bot's Runner answers them all. Another Device sends them as sealed `request`s and waits up to 150 seconds, the time a browser takes to start or a call in flight to answer; a timeout leaves the outcome unknown, and the apps ask again.

| | On the bot's Runner | On another Device |
| --- | --- | --- |
| List, add, delete | yes | yes, through the relay |
| Open Browser | a window on this screen | no: it opens only on the Runner |
| Take Over, Return to Bot, Close | yes | yes; the user signs in at the Runner |
| Record | yes, opening the browser when it is closed | only a browser open on the Runner's screen, where the user does the task |
| Stop Recording | yes | yes |
| Take Screenshot | yes | yes, what the Runner's browser shows |
| Watching or typing from afar | no | no |

None of these change the bot's Runner. Control of other applications on the Runner is not part of it.

## In the apps

The Browser plugin's sheet, opened from a bot's inspector, has a Profiles section for that bot (`Sheets/BrowserProfiles.swift` on the Mac, `desktop/browser_profiles.go` on Windows and Linux). A row per profile shows its name and how it stands: Closed, Open, Taking over…, You have control in orange, while the bot waits on the user, or Recording in red; its tooltip says what that means for the bot, or for a recording what to do, and an action in flight reads Opening…, Starting…, Stopping…, Closing…. The section's + names a new profile in an alert. A click or a right-click on a row opens its menu: Open Browser on the Runner, elsewhere a disabled "Open on <Runner>"; Take Over or Return to Bot; Record, which a closed profile's menu elsewhere offers as a disabled "Record on <Runner>", and while it records Stop Recording in their place, which sends the recording to the chat the inspector shows and closes the sheet over it, or says that nothing was recorded; Take Screenshot, into that chat; Close Browser, also while an open or a takeover waits; and Delete…, which asks first. A failure is an alert with the Runner's words. With no profile yet, a note says what one is for. While the sheet is up it asks the Runner again every two seconds, five through the relay, and an answer begun before an action never covers the action's own. Opened from Settings, the sheet is the Runner's and has no Profiles section.

On the phone, which is never a Runner, Browser's row in a bot's Details slides in a Browser screen (`mobile/src/ui/BrowserScreen.tsx`) with the same rows and words, Add Profile as the section's last row (an alert that asks for the name), and the menu on a tap: SwiftUI's on iOS, labelled for VoiceOver with the row's words and state, Material's dropdown on Android, with Delete… in a group of its own. Its first item is the disabled "Open on <Runner>": opening a window and signing in happen at the Runner. Record and Stop Recording follow the Mac's rule for another Device: Record is there while the browser is open on the Runner's screen, a disabled "Record on <Runner>" while it is closed, and Stop Recording goes back to the chat, where the bot answers. The screen asks the Runner again every five seconds while it is up.
