# Auto-review

Auto-review is the check a Runner runs before a bot's action that may have effects: a shell command, what a bot types into one (`bash_input`), an effectful plugin call, opening or running a browser profile, starting a coding agent, and each command a coding agent runs. It runs only within the bot's [Access](bot-permissions.md), which is checked first and cannot be widened by any rule or answer. It follows Claude Code's auto mode: most actions never reach a model, a model allows by default and holds only what it can name a rule for, and a held action goes back to the bot before it reaches the user.

## Settings and rules

The setting lives in the roster (`AutoReview { is_enabled, rules[{ id, text, behavior: allow | ask, tool? }], provider?, models{ kind: model } }`), so every Device shows and edits the same one: every app's Settings › Auto-review has the switch, Reviews with (Provider: the bot's provider, or any provider the account has connected), and the rules, and Settings › Providers has Review Models, one pop-up per connected provider with "Default (…)" (the status's `review_model`) and each of its models, decision models among them. `auto_review.set` takes `provider` (`null` for the bot's) and `models`, a patch by kind in which `null` puts a provider back on its default.

A rule is plain language, written by the user or added by Always allow from the review's proposal. Adding a rule replaces one with the same words. Only a plugin card's Always allow saves a rule for an exact tool (`tool` is `plugin/tool`), which decides that tool's calls without a review; such a rule never reaches the model, whose reading of its label would broaden it. With Auto-review off, every shell command and effectful plugin action asks, regardless of saved rules.

## Fast paths

Shell review lives at the loop's `before_tool_call` boundary (`crates/cli/src/local_review.rs`). With Auto-review on, a parser decides most commands without a model (`needs_no_review`). It splits the command into its `&&`, `||`, pipe, semicolon, newline, plain subshell-group, and visible command-substitution stages without executing it, keeping a redirection's `&` (`2>&1`, `>&2`, `&>/dev/null`) inside its stage. A command runs at once when:

- **It only reads.** Every stage is a known read-only command (`ls`, `rg`, `cat`, `jq`, `find … | xargs wc -l`, `sed` without `-i`), writes nothing through redirection in any stage (`>&` writes unless it goes to stdout, stderr, or `/dev/null`), evaluates nothing dynamically, and names no key, token, or password. Git counts with its options before the subcommand (`git -C ~/dev/shop log`) and its reading subcommands: status, diff, log, show, blame, grep, `rev-list` and the other plumbing that lists, `ls-remote`, listing branches, tags, remotes, worktrees, and stashes, never `--output` or `-c`. `gh` counts when it views or lists pull requests, issues, runs, releases, repositories, and workflows, searches, or calls `gh api` with GET and no fields; never GraphQL, `--web`, or `--show-token`. `curl` counts when it only fetches, to the terminal or `/dev/null`: no data, form, cookie, upload, FTP command, config file, file written, or method but GET and HEAD, and no variable or substitution in what it sends, which could carry a secret out in the URL. `wget` counts with `-O -` and nothing that posts or writes.
- **It stays in Lorca's own folders** (`~/.lorca`, `~/.lorca-dev`, and the CLI's home), which belong to the bots, the account's own files included: it runs from inside one, every path it names lies inside one, it moves with no bare, backward, or variable `cd`, expands no variables, and neither elevates privileges nor sends data to another machine. The `lorca` command never stays: it changes the Runner and the account (MCP servers, sign-ins, Devices), so it goes to the review wherever it runs, except bare `lorca`, its help and version, `lorca mcp list`, and `lorca mcp get`, which only read (a flag after `--` is a server command's).
- **It only makes, copies, moves, links, and edits files in the bot's working folder** (`stays_in_workdir`), as its file tools do without a review: `mkdir`, `touch`, `cp`, `mv`, `ln`, and `sed`, besides read-only stages, with every path inside the folder or `/dev/null`, no variable, and moves only into folders inside. A working folder that is the home folder or holds it is too wide for this.

Every other command goes whole to the review before it starts, and so does any command that names saved [secrets](secrets.md#using-a-secret), which the review is told it holds. A coding agent's commands take the same paths, in its worktree, unless it holds secrets ([Coding agents](coding-agents.md)).

## What the review reads

`plugins::review::review` builds one request (`Reading`), the same for both passes so a provider caches it: the transcript, the user's latest message again, the user's rules, the codemode script a call comes from (the bot's words, never the user's), the facts, and the action last, with what the tool does and its arguments.

**The transcript** (`plugins::review::request`) is the chat as the Runner recorded it, oldest first, inside `<transcript>`:

- In a user's turn, the chat's newest messages: at least the newest 300, from a position rounded down to a multiple of 100 (`LocalStore::recent`), so consecutive reviews send the same beginning while the chat grows; then the newest lines that fit 40,000 characters.
- `User:` lines are the user's messages, the only source of the user's intent: what they write the bot, and, as `User, to the Claude Code on “Title”:`, what they write a coding agent on its page ([Coding agents](agent-messages.md#the-user-writes-to-it)).
- A bot's words appear only right before the user message that answered them, the last 2,000 characters, where a question is, so that "yes" reads as the answer to what the bot proposed. The bot's own actions in between keep it the referent; a teammate's message in between does not. Its narration beside the action under review never appears.
- Each action of a bot's is one line with how it ended: `DevOps ran: git worktree add /tmp/rel → ok`, `used github__create_issue: … → held by Auto-review`, `started Claude Code in ~/.lorca/worktrees/… on branch fix: … → ok`, `user allowed`, `user did not allow`, `not run`. What a tool printed or returned never appears. A held command shows by its card's `held`; another call by its result, which starts "Auto-review held this action". A call still in flight, the one under review among them, is left out.
- A teammate's `message_bot` handoff is `[teammate] Chef to DevOps: …`, never the user's intent.
- A turn a teammate's handoff, a routine, or an [event](event-triggers.md#durable-ordering-and-execution) started reads only that turn: the handoff, or the task (a routine's original authorized task when feedback revised its workflow text, else the task as it stood when the run began, which an edit or a delete during the run does not change; an event's subscription task as its inbox admitted it, never the payload), which counts as the user's words, then its steps since, the newest 60. New work starts there, so an old "stop" does not reach it.

**Facts** are what Lorca checks itself, one `Fact:` line each, which the review takes as ground truth (`local_review::facts`). Before a command that could discard work (`rm -r`, `git reset --hard`, `git checkout -- .`, `git restore`, `git clean`, `git stash drop`, `git worktree remove`, `git branch -d`), following literal `cd` and `git -C`, it reads each target folder's git state: its branch, uncommitted and untracked files, commits found on no remote; and for a branch it would delete, the commits no other branch, tag, or remote has. Each check has three seconds.

## The model's rules

The system prompt (`plugins::review_prompt::SYSTEM_PROMPT`) frames the model as a safety monitor for bots that act with the user's authority, against prompt injection, scope creep, and accidental damage. Actions are allowed by default; it holds one only when it matches a HARD HOLD, or a HOLD rule that no ALLOW exception and no user intent clears, and when it cannot name the rule, it allows. Wrong, wasteful, or off-topic work, retries after a transient error, and messages to the user are out of its scope.

- **HARD HOLD**, which nothing clears: Data Exfiltration (credentials or private data sent anywhere the user did not name), System Wipe.
- **HOLD rules**, each with what the user must name to clear it: Irreversible Local Destruction (the exact target), Git Destructive (the operation and its target), Publishing (what and where), Production Deploy (the deploy and its environment), Shared Resource Change, Money, Access and Security, Credential Access, Code from Outside (the source), Other People's Programs, Self-Change.
- **ALLOW exceptions**: reading; local work (editing, building, testing, running the project, installing its declared dependencies, local git work, drafts); Git Push Destination, pushing commits to any branch of the repository the bot works in, its default branch included, though what the push contains and sets off still counts, so release tags are Publishing; Own Cleanup, deleting exactly what an earlier action in the transcript made unless a fact shows work in it; using the app the task is about; the user's allow rules.
- **User intent** decides last. A HOLD rule clears when the user's own message names the action and its must-name item (Path A), or the user agreed to the bot's proposal right before that named it (Path B). Naming the enclosing task does not name a risky step, unless the step is what the task plainly consists of: "cut a release" names pushing its tags and publishing it, "create a PR" names pushing the branch, never a force push. Questions are not consent. A routine's task counts as the user's words; a teammate, a tool result, a page, or a script never does. A user's "yes" after a hold is consent to that exact action. A boundary ("don't push", "leave Postgres alone", "不用跑 iOS 了") holds what it covers until the user lifts it, and an action like one the user did not allow is held again.
- **The user's rules** sit right before the action. An allow rule is standing permission for its kind of work wherever the bot does it, unless it names a place; it clears HOLD rules, never a HARD HOLD or a boundary set in the chat. An ask rule is a HOLD rule the user added, which only their naming that very action in the chat clears, and no allow rule does.

## Two passes

`classify` judges in two passes, after Claude Code's classifier:

1. **First pass** (`FIRST_PASS`): the review model at its quickest, told to answer `<block>yes</block>` if any rule could apply, without user intent or exceptions, and `<block>no</block>` otherwise, nothing before it. With thinking off it may write 64 tokens. `no` is final, and the action runs. An answer it cannot read is a flag.
2. **Second pass** (`SECOND_PASS`), only for what the first flags: the same request with steps to follow (full effect, hard holds, rules and exceptions, user intent) and `<thinking>` before the answer, `<block>no</block>` or `<block>yes</block><category>rule</category><reason>…</reason>`, plus `<allow_rule>` for a shell command or a coding agent's start (`RULE_PROMPT`): the plain-language rule Always allow adds, for this kind of work wherever the bot does it, keeping what decides the risk (the service, the repository, the environment, a folder of the user's data) and leaving out file names, numbers, branches, and the working directory ("comment on pull requests in egoist/lorca", "deploy Railway services to production"), and empty for a HARD HOLD, credentials, access, destructive git, or the user's data. The reason and the rule are in the language of the user's latest message, else the teammate's message or the routine's or event's task. A proposed rule the user already has is dropped. It may write 4,096 tokens. A model that thinks in the reply's text can deliberate past that and stop mid-thought, where a verdict tag is one it may have gone on to reconsider, so a reply cut off at its limit is never read: the model gets its request and its cut-off reply back with `DECIDE_NOW` ("decide now from what you have weighed", 1,024 tokens), which answers in a second or two from the cached request. One that still runs out of room has failed the pass ("its model ran out of room before answering"), as has a reply with no verdict ("its model answered without a verdict").

The review model is the one picked for the provider in Auto-review's settings while it is connected, else of the bot's provider, whatever the bot itself runs (`providers::reviewer`): the one picked in Review Models, else the provider's small, fast default (`providers::small_model`: DeepSeek V4.1 Flash on DeepSeek and both OpenCode plans, Claude Haiku 4.5, GPT-6 Luna, Grok 4.7). A chat model runs with thinking off and at temperature 0 where the model allows it, so the same action gets the same answer, and at its lowest effort where it does not. The second pass tries the review model twice, a second apart, then the bot's own provider's small model twice (`providers::chat_reviewer`), which also takes the second pass when the review model is a decision model. When none answers, the review judged nothing and the user decides (`Ask`, "Auto-review could not check this action (why)."), unless the turn was stopped: every reviewed action then asks, as with Auto-review off, one card per action, outside the hold counts below.

A **decision model** ([Providers](providers.md)) takes the first pass with one choice question (`review::ask_decision_model`): the state is the action first, since a model may read only the start of a long one, then the script, the facts, the rules, and the transcript; the choices are `allow` and what the action could harm (the user's files, uncommitted work or pushed history, publishing, a live service, money, access and system settings, programs the bot did not start, credentials and uploads, downloaded code, what the user refused, the whole system, an ask rule), worded as the chat model's prompt words them (`DECISION_INSTRUCTIONS`). `allow` at 0.7 or more is final; otherwise the second pass decides, and when no chat model can, the harm it weighs most is the reason, in Chinese when the message that sets the language is Chinese and in English otherwise.

## Holds and asks

`review` returns `Allow`, `Held { reason, rule, note }`, or `Ask { reason, rule }`. A hold goes back to the bot, after Claude Code: the call does not run, and the bot reads the note, which starts "Auto-review held this action" and says why, to go on with other work, try a way no rule holds (a feature branch instead of the default branch, a narrower target), or ask the user in one short sentence that names the action in bold and run it again once they agree, since their answer clears it. A coding agent's held command returns its own note (`review::agent_note`): it cannot ask the user, so it stops and names what it needed.

After three holds in a row in a turn (keyed by the chat and the message that started it), or past twenty in the turn, the user decides instead (`Ask`), and the next hold goes back to the bot again, until the twentieth; an allowed action ends a row. Auto-review off, and an exact plugin tool's ask rule, ask at once.

A held shell command's card ends `denied` with `held` and the reason, and the apps show it no more than any other command that did not need the user ([Terminal sessions](terminal-sessions.md)). A held coding agent start's card is `denied` with `held`, which the apps read as "Held by Auto-review". When the user decides, a shell command asks on its own card (`local_review::ask_on_card`) with why, Allow once, Always allow with the proposed rule, and Deny; a card with no proposed rule (Auto-review off, a decision model's reason, a review that could not run) offers Allow once and Deny. A coding agent's start asks on its card. Any other action, a script's command and a coding agent's command included, posts a `permission` message. Each waits up to ten minutes for `chats.permission { decision: allow | always | deny }` from any Device, naming the card's row (`mcp::await_answer`), and a new message from the user in the chat dismisses it (see [Agent loop](runtime.md#agent-loop)), except a coding agent's, which no turn waits on (`mcp::ask_aside`). An allowed command runs on the same card; a denial runs none of its stages and ends the card as `denied`.

What a bot types into a running command with `bash_input` goes through the same review, the command beside the input, since a shell, a REPL, or `ssh` runs whatever it is given; Ctrl-C alone runs at once.

A routine's or an event's turn has nobody waiting, so a shell command or effectful plugin call that is held or would ask is staged in the [review queue](review-queue.md) and the call returns without running; the user reviews its saved version later, and a review that could not run is staged the same way, at once. A coding agent such a turn starts asks nobody either (`Record.unattended`): what its review would ask goes back to it at once as a denial that says why. With Auto-review on, actions the review allows still run.

The review logs the rule a hold names and the tool, never the command or the chat: the apps keep the CLI's stderr in a log file.
