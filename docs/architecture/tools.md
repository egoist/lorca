# Tools

Team tools (the CLI):

- `tasks { action: list | get | create | update | run, ... }` — [durable tasks](tasks.md): goals, ownership, acceptance criteria, dependencies, next action, blockers, results, and evidence. Mutations require a request id; updates and runs require the current revision. A queued record starts only through run, and completion requires result and evidence.

- `message_bot { bot_id, message, context?, expected_output?, acceptance_criteria?, task_id? }` — a durable delegation to a bot outside the current chat, returning a handoff id, job id and Runner queue state. The caller's chat shows a "Messaged ◉ X" marker: the tool row carries the recipient's id as `target_bot_id`, and the apps take its name and avatar from the roster for the marker and for "Messaging X…" while the call runs. The target's own DM gets a "Message from ◉ X" marker with the contract and a `message` Job (with `from_bot_id`, `hops`, `task_id` and `handoff`) whose envelope goes to the **target bot’s Runner**. The recipient’s result, or why it could not finish, comes back to the caller’s chat as a "Message from ◉ X" marker and starts the caller’s next turn. The tool refuses a member of the same group: they read that chat and take their own turn. See [Handoffs](handoffs.md).
- `handoffs { action: list | get | follow_up | cancel | report, handoff_id?, job_id?, … }` — inspect contracts and attempts after a restart, follow up with the same handoff id, cancel outstanding work, or report a recipient’s outcome with result links and evidence. A recipient report binds to its active delegated turn; completion is its claim, which the requester checks against the acceptance criteria ([reports](handoffs.md#reports-and-continuation)).
- `attention { action: list | report | resolve | brief, … }` — structured source-linked reviews, blockers, commitments and changes; ordinary reports route to the coordinator, urgent items also alert directly, and quiet checks alert nobody. Coordinators keep one brief of decisions and changes and resolve finished attention (see [Coordinator attention](attention.md)).
- `list_teammates` — decrypted local roster with each bot’s id, Runner, online state, and the provider, model, and thinking it runs with. `message_bot` and `edit_bot` name a bot by that id, since two bots can share a name; a user’s `@Name` arrives with the id (see Mentions in [the lead bot](bots.md#the-lead-bot)), the system prompt gives the caller its own id and that of a bot whose message started the turn, and `create_bot` answers with the new bot’s.
- `memory_update { action: append | replace | remove | supersede, text?, old_text? }` — changes the bot’s curated `MEMORY.md` one fact at a time (see [Memory](bots.md#memory)).
- `memory_log { text }` — one line in the bot’s daily log.
- `project_context { action: list | read | refresh | asset | propose, entry_id?, fresh?, kind?, title?, text?, url? }` — the current group's [shared context](project-context.md). Discovery is bounded, complete reads are lazy, a live-source refresh records retrieval or failure, and proposals remain unverified until the user accepts them. The runtime binds the group and checks membership; private memory stays separate.
- `recall { query?, since?, until?, limit? }` — searches the bot’s memory files and every chat it is in, by words and by time (`24h`, `3d`, `today`, `yesterday`, a date).
- `create_bot { name, description, provider?, model?, thinking?, workdir? }` — a new teammate on the caller’s Runner with its own DM; in a group chat it joins that chat. The description says both what it does and how it should work. This is how a lead bot builds its team.
- `edit_bot { bot_id, name?, description?, provider?, model?, thinking?, workdir? }` — changes a teammate’s profile, or the caller’s own. Only the passed fields change; a description is the complete account of the bot’s job and working style, and the new profile applies from that bot’s next turn. Both tools hold `model` and `thinking` to what the apps’ Model and Thinking menus offer: a model of the provider’s, named by its id, its name, or a gateway id without the `vendor/`, in any case, and a level that model takes; `default` is the provider’s default model or the model’s default level. As in the inspector, another provider starts on its default model and thinking unless the call names them, and another model keeps the bot’s level only when it takes it. A model the provider lacks is refused with its models and the providers that have it, and a level the model lacks with its levels. The result says what the bot runs from its next turn (“Claude Opus 5.5 on Anthropic, thinking high”).
- `workflow_feedback { action: list | propose, proposal? }` — included explicit feedback and routine failures, or a concrete workflow revision with evidence and a diff. The user decides it through the app; the tool cannot apply it, change review settings or lift exclusions (see [Workflow feedback](feedback.md)).
- `stage_review { payload, target, rationale, task_id?, guarded_paths? }` — an editable draft or exact proposed shell/plugin call for later version-bound approval on its Runner (see [Review queue](review-queue.md)).
- `routines { action: list | create | edit | pause | resume | run | delete, routine?, name?, schedule?, timezone?, missed_run_policy?, prompt?, check?, enabled? }` — the caller’s own routines and their checks, a check run once as it is saved (see [Routines](routines.md)).
- `channels { action: list | create | edit | allow | pause | resume | delete, channel?, account?, name?, listen?, task?, chats? }` — the caller's own [channels](channels.md): Telegram or Slack accounts on its Runner it listens on, the chats it answers in, what it takes, and its task for each message. A turn nobody started may only list and pause.
- `search_plugins { query? }` / `install_plugin { plugin }` / `connect_plugin { plugin }` — the marketplace, an install on the caller’s Runner that the user allows on a permission card first, and a sign-in card for an installed plugin (see [Plugins](plugins.md#plugins) and [Marketplace](marketplace.md)).
- `codemode { code }` — runs a JavaScript script that calls the installed plugins' tools, the bot's own file and memory tools, and commands (see [Codemode](plugins.md#codemode)).
- `publish_output { name, path? | url?, mime?, task_id?, replaces?, evidence? }` — shares a generated file or an existing HTTPS document reference in the caller's chat. Files use encrypted attachment blobs; every version is a separate message. The tool returns an immutable reference for task evidence and is also available in codemode as `tools.publish_output`. The turn prompt directs bots to publish test results and before/after screenshots for visual work. External creation and uploads use the reviewed service or shell tools. See [Outputs and evidence](outputs.md).
- `coding_agent { action: start | read | send | stop | list, title?, prompt?, agent?, folder?, worktree?, secrets?, id?, message?, interrupt?, lines? }` — Claude Code, Codex, OpenCode, pi, or fx on the bot's Runner (the first the user turned on that is installed there, unless the bot names one), in a git worktree of `folder`, on `prompt`, under a `title` the user sees, with the saved command `secrets` it needs in its environment. It answers at once with an id the bot keeps across turns; the bot reads the agent's transcript, sends it follow-ups (queued, or `interrupt`ing), and stops it, and gets a turn when the agent's message lands in the chat because it is done or ended. Starting one needs Shell commands, and every command it runs passes Access and Auto-review; the chat shows it as "Messaged ⬢ Title" ([Coding agents](coding-agents.md)).
- `request_secret { use: browser | command | plugin, why, site?, plugin?, secrets: [{ name, label }] }` — asks the user for a password, an API key, or a one-time code on a card in the chat and waits for the answer; the value goes sealed to the bot's Runner and the bot uses it by name: `{{secret:NAME}}` in what Browser types on the secret's site, `bash`'s `secrets: ["NAME"]` for a command's environment, or a plugin's setting (see [Secret requests](secrets.md)). Every tool result has the Runner's saved values replaced by their placeholders.
- `browser_session { action: list | create | open | run, session_id?, name?, skill?, inputs? }` — with the Browser plugin on the bot's Runner and in its Access, the bot's browser profiles there: listing them, adding one, opening one in a window, which passes Auto-review, and running a saved skill's recorded steps (`run`), which passes it as one action and stops at a step the page no longer matches, with a screenshot in the chat and the turn ended. While one is open the bot's Browser calls use it, and they wait while the user has taken it over (see [Browser sessions](browser-sessions.md#running-recorded-steps)).

Plugin tools (`<plugin>__<tool>`, such as `github__create_issue`) come from the MCP servers of the plugins installed on the bot's Runner. A bot calls them from codemode scripts; the model never gets them as tools of its own, so the tool list is the same for the whole turn, and from one turn to the next.

Coding tools (`lorca_agent::tools`, ports of pi’s built-ins, same schemas and truncation rules: 2000 lines / 50KB, whichever first):

- `read { path, offset?, limit? }`, `write { path, content }`, `edit { path, edits: [{ oldText, newText }] }`
- `bash { command, description, timeout?, background? }` — `description` says what the command does in a few words, for the status line. It runs `/bin/bash` (else `/bin/sh`), or on Windows Git for Windows' bash, with the login shell's environment (below), and this Runner's own `lorca` first on PATH with `LORCA_HOME` and `LORCA_PORT` pointing it at this Runner (`shell::bot_shell_extras`), so the `lorca` a bot runs, `lorca mcp add` included, is its own Runner's whatever else is installed; `LORCA_SHELL` names another shell. On Windows the tool looks for that bash as it is built, once a turn, so a Git installed while Lorca runs serves the bot's next turn: `%ProgramFiles%\Git`, `%ProgramFiles(x86)%\Git`, `%LOCALAPPDATA%\Programs\Git` (a per-user install), then the Git of each `git.exe` on PATH (`…\Git\cmd\git.exe` → `…\Git\bin\bash.exe`), with the tool walking PATH itself, past the Windows directory and relative entries. It never runs a bare `bash`, which `Command` would find in System32 before PATH: that `bash.exe` is WSL's and runs the command in Linux. When none is found, the call fails with a note to install Git for Windows or set `LORCA_SHELL`. The result is stdout and stderr together, tail-truncated, with the full output in a temp file. Stop kills the process group, or on Windows the job object the shell starts in, which holds every process the command starts, also one whose parent has exited, where `taskkill /T` no longer finds it. The stopped call reads what the command printed on its way out for a second at most, so a process the kill missed that still holds the output does not hold the turn. The command runs in a terminal of its own that can outlive the call, a pseudo console on Windows, and `background` leaves a server, a watcher, or a long build running past it ([Terminal sessions](terminal-sessions.md)). A Windows before 10 1809 has no pseudo console (`tools::terminals`): there the command runs on pipes with stdin closed, and the tool's description tells the model that interactive input is not available
- `bash_input { session_id, text, enter? }` — types into a command `bash` left running, Enter after the text unless `enter` is false (`\u0003` is Ctrl-C; a text that spells one key out as its escape, `\u0003` as six characters or `\u001b[B`, types that key), and waits for what it does next; `bash_output { session_id, wait_seconds? }` — what it printed since the bot last read it, waiting up to five minutes for more. Neither is offered where commands run on pipes
- `grep { pattern, path?, glob?, ignoreCase?, literal?, context?, limit? }`, `find { pattern, path?, limit? }`, `ls { path?, limit? }` — respect `.gitignore` through the `ignore` walker, no `rg`/`fd` needed

Every bot has a working directory on its Runner (`workdir`, default `~/.lorca/workspaces/<bot id>`, so a rename never moves files); relative paths resolve there. The tools run as the Runner's user and retain that user's normal filesystem, process, credential, and network access. The working directory is context, not a security boundary: absolute paths and shell commands can control the rest of the computer.

Commands and stdio plugin servers run with the user's login-shell environment (`lorca_agent::login_shell`), since a CLI the app starts inherits launchd's bare `PATH`. When `lorca serve` starts, it runs the account's shell once as an interactive login shell and reads the variables it exports (`env -0`, written to a private temp file). The account's shell is its passwd entry, ahead of `$SHELL`, which launchd leaves stale after `chsh`. That shell gets a session of its own: under a terminal, an interactive shell in the CLI's session stops as it tries to take the terminal over. Every `bash` command and stdio server starts with those variables: the shell's `PATH` first, then the CLI's own, then the usual install folders (`~/.local/bin`, `~/.bun/bin`, `~/.cargo/bin`, mise shims, Volta, `/opt/homebrew/bin`, `/usr/local/bin`). So `npx`, `uvx`, `bun`, or `cargo` resolve as in the user's terminal, and a fish user's config sets up `PATH` while the command itself runs in bash. Exported keys come along as they would from a terminal, and a command that names one (`echo $OPENAI_API_KEY`) goes to Auto-review. The shell has five seconds, at most three of them interactive before a plain login shell tries; when none answers, commands keep the CLI's own environment. On Windows the CLI keeps the environment it started with, and a bare program name starts the file a terminal would run (`login_shell::find_program`), since `Command` appends only `.exe` and npm installs `npx` as `npx.cmd`: the first `PATH` folder that has the name with a `PATHEXT` extension, tried in `PATHEXT`'s order there, or the name itself when it already ends in one. Only `.com`, `.exe`, `.bat`, and `.cmd` count, the files `Command` can start, so Node's extensionless `npx` shell script and a `.js` or `.ps1` are passed over; relative `PATH` folders are skipped, and a name found in none goes to `Command` as it is. A batch file runs through `cmd.exe` with the standard library's escaping of its arguments (CVE-2024-24576): each arrives as written, `%PATH%` unexpanded and `&` never a second command, and one holding a line break cannot be passed, so the start fails.

On macOS and Linux each `bash` call's command runs in a terminal session of its own, which can outlive the call, take input, and run in the background: [Terminal sessions](terminal-sessions.md) has the terminal, when a call returns, background commands, the command's card, answering and stopping, and Running tasks.

A bot's [Access](bot-permissions.md) is checked before Auto-review and again when a tool starts, nested codemode calls included: Shell commands gates `bash`, `bash_input`, `bash_output`, and `coding_agent` (and every command a coding agent runs), and Files the read and write coding tools. A refused call puts an access request in the chat, and no account rule overrides it.

Every `bash` command, what a bot types into one with `bash_input`, and every effectful plugin call passes [Auto-review](auto-review.md) at the loop's `before_tool_call` boundary (`crates/cli/src/local_review.rs`, `crates/cli/src/plugins/review.rs`): a parser runs read-only commands, commands that stay in Lorca's own folders, and file commands in the bot's working folder at once, and a model judges the rest against the chat that asked for it. A held action goes back to the bot with why; after three holds in a row the user decides on the command's card or a `permission` message.
