# Tools

Team tools (the CLI):

- `message_bot { bot_id, message }` — a message to a bot outside the current chat. The caller's chat shows a "Messaged ◉ X" marker: the tool row carries the recipient's id as `target_bot_id`, and the apps take its name and avatar from the roster for the marker and for "Messaging X…" while the call runs. The target's own DM gets a "Message from ◉ X" marker and a `message` Job (with `from_bot_id` and `hops`) whose envelope goes to the **target bot’s Runner**. The tool refuses a member of the same group: they read that chat and take their own turn.
- `list_teammates` — decrypted local roster with each bot’s id, Runner, and online state. `message_bot` and `edit_bot` name a bot by that id, since two bots can share a name; a user’s `@Name` arrives with the id (see Mentions in [the lead bot](bots.md#the-lead-bot)), the system prompt gives the caller its own id and that of a bot whose message started the turn, and `create_bot` answers with the new bot’s.
- `memory_update { action: append | replace | remove | supersede, text?, old_text? }` — changes the bot’s curated `MEMORY.md` one fact at a time (see [Memory](bots.md#memory)).
- `memory_log { text }` — one line in the bot’s daily log.
- `recall { query?, since?, until?, limit? }` — searches the bot’s memory files and every chat it is in, by words and by time (`24h`, `3d`, `today`, `yesterday`, a date).
- `create_bot { name, description, provider?, workdir? }` — a new teammate on the caller’s Runner with its own DM; in a group chat it joins that chat. The description says both what it does and how it should work. This is how a lead bot builds its team.
- `edit_bot { bot_id, name?, description?, provider?, thinking?, workdir? }` — changes a teammate’s profile, or the caller’s own. Only the passed fields change; a description is the complete account of the bot’s job and working style, and the new profile applies from that bot’s next turn.
- `routines { action: list | create | edit | pause | resume | run | delete, routine?, name?, schedule?, prompt?, check?, enabled? }` — the caller’s own routines and their checks, a check run once as it is saved (see [Routines](bots.md#routines)).
- `search_plugins { query? }` / `install_plugin { plugin }` / `connect_plugin { plugin }` — the marketplace, an install on the caller’s Runner that the user allows on a permission card first, and a sign-in card for an installed plugin (see [Plugins](plugins.md#plugins)).
- `codemode { code }` — runs a JavaScript script that calls the installed plugins' tools and the bot's own file tools (see [Codemode](plugins.md#codemode)).

Plugin tools (`<plugin>__<tool>`, such as `github__create_issue`) come from the MCP servers of the plugins installed on the bot's Runner. A bot calls them from codemode scripts; the model never gets them as tools of its own, so the tool list is the same for the whole turn, and from one turn to the next.

Coding tools (`lorca_agent::tools`, ports of pi’s built-ins, same schemas and truncation rules: 2000 lines / 50KB, whichever first):

- `read { path, offset?, limit? }`, `write { path, content }`, `edit { path, edits: [{ oldText, newText }] }`
- `bash { command, description, timeout? }` — `description` says what the command does in a few words, for the status line. It runs `/bin/bash` (else `/bin/sh`), or on Windows Git for Windows' bash, with the login shell's environment (below); `LORCA_SHELL` names another shell. On Windows the tool looks for that bash as it is built, once a turn, so a Git installed while Lorca runs serves the bot's next turn: `%ProgramFiles%\Git`, `%ProgramFiles(x86)%\Git`, `%LOCALAPPDATA%\Programs\Git` (a per-user install), then the Git of each `git.exe` on PATH (`…\Git\cmd\git.exe` → `…\Git\bin\bash.exe`), with the tool walking PATH itself, past the Windows directory and relative entries. It never runs a bare `bash`, which `Command` would find in System32 before PATH: that `bash.exe` is WSL's and runs the command in Linux. When none is found, the call fails with a note to install Git for Windows or set `LORCA_SHELL`. The result is stdout and stderr together, tail-truncated, with the full output in a temp file; Stop kills the process group (the process tree on Windows). On macOS and Linux the command runs in a terminal of its own that can outlive the call (Terminal sessions, below). On Windows it runs on pipes with stdin closed, and the tool's description tells the model that interactive input is not available there
- `bash_input { session_id, text, enter? }` — types into a command `bash` left running, Enter after the text unless `enter` is false (`\u0003` is Ctrl-C; a text that spells one key out as its escape, `\u0003` as six characters or `\u001b[B`, types that key), and waits for what it does next; `bash_output { session_id, wait_seconds? }` — what it printed since the bot last read it, waiting up to five minutes for more. Neither is offered on Windows
- `grep { pattern, path?, glob?, ignoreCase?, literal?, context?, limit? }`, `find { pattern, path?, limit? }`, `ls { path?, limit? }` — respect `.gitignore` through the `ignore` walker, no `rg`/`fd` needed

Every bot has a working directory on its Runner (`workdir`, default `~/.lorca/workspaces/<bot id>`, so a rename never moves files); relative paths resolve there. The tools run as the Runner's user and retain that user's normal filesystem, process, credential, and network access. The working directory is context, not a security boundary: absolute paths and shell commands can control the rest of the computer.

Commands and stdio plugin servers run with the user's login-shell environment (`lorca_agent::login_shell`), since a CLI the app starts inherits launchd's bare `PATH`. When `lorca serve` starts, it runs the account's shell once as an interactive login shell and reads the variables it exports (`env -0`, written to a private temp file). The account's shell is its passwd entry, ahead of `$SHELL`, which launchd leaves stale after `chsh`. That shell gets a session of its own: under a terminal, an interactive shell in the CLI's session stops as it tries to take the terminal over. Every `bash` command and stdio server starts with those variables: the shell's `PATH` first, then the CLI's own, then the usual install folders (`~/.local/bin`, `~/.bun/bin`, `~/.cargo/bin`, mise shims, Volta, `/opt/homebrew/bin`, `/usr/local/bin`). So `npx`, `uvx`, `bun`, or `cargo` resolve as in the user's terminal, and a fish user's config sets up `PATH` while the command itself runs in bash. Exported keys come along as they would from a terminal, and a command that names one (`echo $OPENAI_API_KEY`) goes to Auto-review. The shell has five seconds, at most three of them interactive before a plain login shell tries; when none answers, commands keep the CLI's own environment. On Windows the CLI keeps the environment it started with, and a bare program name starts the file a terminal would run (`login_shell::find_program`), since `Command` appends only `.exe` and npm installs `npx` as `npx.cmd`: the first `PATH` folder that has the name with a `PATHEXT` extension, tried in `PATHEXT`'s order there, or the name itself when it already ends in one. Only `.com`, `.exe`, `.bat`, and `.cmd` count, the files `Command` can start, so Node's extensionless `npx` shell script and a `.js` or `.ps1` are passed over; relative `PATH` folders are skipped, and a name found in none goes to `Command` as it is. A batch file runs through `cmd.exe` with the standard library's escaping of its arguments (CVE-2024-24576): each arrives as written, `%PATH%` unexpanded and `&` never a second command, and one holding a line break cannot be passed, so the start fails.

**Terminal sessions** (`lorca_agent::tools::bash_session`, kept by `crates/cli/src/shell.rs`). pi's bash runs a command on pipes with nothing on stdin and fails fast, because the person is at the terminal and answers there. A Lorca bot's Runner is often a computer nobody is sitting at, so a command gets a pseudo-terminal of its own: `openpty`, then `setsid` and `TIOCSCTTY` in the child, so `/dev/tty` is that terminal and `sudo`, `ssh`, `gpg`, `getpass`, and `[Y/n]` questions ask there, never on a terminal `lorca serve` was started from. The shell leads its own session and process group, which is what stopping it kills. The terminal is 80×24 with `TERM=xterm-256color` and `PAGER` and `GIT_PAGER` set to `cat`, and echo is off, so what is typed (a `y`, a password) never comes back as output; a program that echoes for itself (readline, curses) still does, and prompts print as usual. The child ignores SIGHUP, so a job the command leaves in the background (`server > log 2>&1 &`) outlives the shell as under `nohup`. A reader drains the terminal into the session's last 200 KB whether or not anyone reads it, so a command never blocks on a full terminal; the raw bytes also go to a temp file once they pass 50 KB, up to 64 MB. What the model reads and what a card stores is text (`tools::sanitize`, after pi's `stripAnsi` and `sanitizeBinaryOutput`): escape sequences go, a carriage return redraws its line, a backspace takes back a character, and other control characters go. The temp file keeps the raw bytes.

A call returns when the command exits, as on pipes, or while it still runs: 2 s after it stops on an open line that reads like a question (`password`, `passphrase`, `[Y/n]`, `(yes/no`, `Enter `, `Press `, `PIN`, `token`, `code`, `OTP`, or a line ending in `?`, `:`, `>`, `)`, `]`, `$`, or `#`), or after 20 s with no output at all (`WAITING_AFTER`), which is also how a command blocked on something outside its terminal, such as a macOS permission dialog, surfaces instead of holding the turn. That result is the output so far, a note on where the command stands, and the session id; `bash_input` and `bash_output` wait the same way, and `timeout` still kills the command when it runs that long. At a question the note quotes it. Silence is not a question: a quiet command may be working, or asking where the terminal never shows it, since a question printed into a pipe or a file (`| tail`, `> log`) stays there, so the note says both. When the command has also put its terminal in raw mode, as a menu or a yes/no choice does (`BashSession::reads_keys`: the master reads the terminal's modes on macOS and Linux, pipe or not), the note says it is probably waiting for a key at a question it printed out of sight, to stop it and run it with its non-interactive options, and how to press Enter and the arrow keys. A question counts until something is typed after it: with echo off, an answered question stays the last line until the command prints again. The session stays on the Runner after the turn ends.

Every `bash` call has one card, the call's own row, from start to finish: `Body::Tool.run { session_id?, command, state, prompt?, output?, outcome?, device?, reason?, rule?, decision? }`. The row goes up with the card as the call starts (`running`), so it takes its place in the chat before anything the call leads to; `shell::Sessions` notes the call (`begin`), and the card follows it: `checking` while Auto-review judges the command, `asking` while it waits for the user's answer (below), then `running` or `waiting` once a session runs it (`insert`, as the command spawns), with its last 20 lines of output: `waiting` only at a question the user can read, whose line has held still for 2 s (`PROMPT_QUIET`) or has been followed by 20 s of silence, and `running` while it prints or is merely quiet, and at the end `exited`, `failed` (a nonzero code), `stopped`, `denied`, `expired`, or `dismissed` (the user wrote in the chat instead of answering), with how it ended, which a later turn reads in the rebuilt call when the call had left the command running. A call that returns (`call_ended`) leaves a running command's card to its session; a call no session ran, because it was not allowed or ran on pipes, ends its card from its result. The call's result and its card go up in one write, under the same lock as the session's own updates, so no Device sees the call returned beside a card from before. The apps show the card only while the command needs the user: while Auto-review asks, and once the bot has handed the running command over (`handed_over`), until it ends. It hands it over when its turn ends with the command still running (`Sessions::hand_over`, from the turn's `finish`), or when it waits on the command (`bash_output` with a wait) while the command sits at a question (`Sessions::bot_waits`), and a card stays handed over. Until then the bot deals with it: a question it answers itself with `bash_input`, or a command it waits out, reads only as the working row's activity, and one that ended leaves the chat, so the transcript does not shift for the commands a turn runs. The card keeps its first place in the relay's log however often it changes (`Slot::first_and_latest`), so it sits in the same place on every Device. The bot reaches only the sessions it started in the chat it runs in; the system prompt tells it that `/dev/tty` is the command's own terminal, to run scaffolders and installers with their non-interactive options since a question printed into a pipe or a file never shows, to answer what it knows with `bash_input`, and to send the user to the command's card for a password, a passphrase, or a one-time code rather than asking for it in a message. A command its call left running that ends by itself (exits, or dies on a signal) wakes its bot: once any turn in the chat is done, and unless that turn read the end itself with `bash_input` or `bash_output`, the Runner starts a `command` job (`shell::wake_job`, `runtime::command_job`), whose turn opens with how the command ended and its last lines (`turns::command_cue`), so the bot hears the result of an answer the user typed and carries on. A Stop, the idle limit, or Lorca quitting wakes nobody.

The user answers from any Device: `bash.stdin { chat_id, message_id, text }` writes the text and a Return to the terminal, on this Runner or sealed to it as a `request`, and nothing keeps it: not the row, the message store, a log, or a push, and with echo off, not the output the bot reads. `bash.stop` ends the command, from its card or from Running tasks.

**Running tasks** are the commands a chat's bots have running in their terminals, handed over or not: rows whose card is `running` or `waiting` with a `session_id`. A Device counts one once it has run there for two seconds (`AppStore.taskDelay` on the Mac, `TASK_DELAY_MS` on the phone), so a quick `ls` never shows; one that was already running when the Device heard of it counts at once. While a chat has any, a terminal button sits in the chat's toolbar and opens them in a list: each command's description, who runs it (in a group), and how long it has run. On the Mac each entry also holds the command's first line in a code block that opens the whole command, its last lines in a block that grows to ten lines and then scrolls, and Stop; on the phone each is a row that slides the command's details in. One that ends while the list is open stays, reading Finished, Failed, or Stopped, until the list closes. So a command the bot is still dealing with, which shows only as the working row's activity, can be read and stopped without stopping the turn: the bot's call returns with the command stopped, and its turn goes on.

Stop in the chat, deleting the chat or its bot, quitting Lorca (SIGTERM, SIGINT, SIGHUP, or the app that started the CLI going away), 30 minutes without output or input (`IDLE_LIMIT`), and a ninth command starting while eight run (`MAX_SESSIONS`; the oldest stops) each kill the session's process group, close its terminal, and say so on its card. A card that a Lorca which quit left open (checking, asking, running, or waiting) reads "Stopped when Lorca quit" once it starts again.

Shell review lives at the loop's `before_tool_call` boundary (`crates/cli/src/local_review.rs`). With Auto-review on, a parser is the fast path: it splits the command into its `&&`, `||`, pipe, semicolon, newline, plain subshell-group, and visible command-substitution stages without executing it, keeping a redirection's `&` (`2>&1`, `>&2`, `&>/dev/null`) inside its stage, and a command whose every stage is a known read-only one (`git status`, `ls`, `rg`, `find … | xargs wc -l`), that writes nothing through redirection in any stage (`>&` writes unless it goes to stdout, stderr, or `/dev/null`), evaluates nothing dynamically, and names no key, token, or password runs at once. So does one that stays in Lorca's own folders (`~/.lorca`, `~/.lorca-dev`, and the CLI's home), which belong to the bots, the account's own files included: it runs from inside one, every path it names lies inside one, it moves with no bare, backward, or variable `cd`, expands no variables, and neither elevates privileges nor sends data to another machine. Every other command goes whole to Auto-review before it starts. The command's card is `checking` while the review runs, which the apps do not show. When the review asks, the card itself asks (`local_review::ask_on_card`): why, Allow once, Always allow, and Deny, and a proposed plain-language allow rule for this kind of work wherever the bot does it, which keeps what decides the risk (the service, the repository, the environment, or a folder of the user's data) and leaves out one-off details such as file names, numbers, branches, and the working directory ("comment on pull requests in egoist/lorca", "deploy Railway services to production"), and which Always allow adds to Auto-review. A card with no proposed rule (Auto-review off, or a review that could not run) offers Allow once and Deny. The answer is `chats.permission` naming the card's row, from any Device, as for a permission card (`mcp::await_answer`); an allowed command runs on the same card, and a denial runs none of the stages and ends the card as `denied`. What a bot types into a running command with `bash_input` goes through the same review, the command beside the input, since a shell, a REPL, or `ssh` runs whatever it is given; Ctrl-C alone runs at once.

**Auto-review** (`crates/cli/src/plugins/review.rs`) is shared by shell and plugin actions. Its setting lives in the roster (`AutoReview { is_enabled, rules[{ id, text, behavior: allow | ask, tool? }] }`), so every Device shows and edits the same one. A rule is plain language, written by the user or added by Always allow from the review's proposal. Only a plugin card's Always allow saves a rule for an exact tool (`tool` is `plugin/tool`), which decides that tool's calls without a review. Everything else goes to a small model on the bot's provider, whatever the bot itself runs (`providers::review_model`: DeepSeek V4.1 Flash on DeepSeek and both OpenCode plans, Claude Haiku 4.5, GPT-6 Luna, Grok 4.7), with thinking off and at temperature 0 where the model allows it, so the same action gets the same answer, and at its lowest effort where it does not. The model reads the chat that asked for the work (`plugins::review::request`): the message that started the turn (the user's, a teammate's `message_bot` handoff, or a routine's marker with the task as it stood when the run began, which an edit or a delete during the run does not change), then each step since, its newest 30 (what the bots said, the commands they ran and the tools they used, and how the user answered a command that asked), with the user's latest message repeated after them. Before a user's message it also reads up to ten lines of the two hours of chat ahead of it, so a short reply ("yes", "create a PR") reads as the answer to what the bot proposed; a handoff or a routine starts new work, and nothing before it is read. The user's rules come next, beside the action, and a plugin call from a codemode script comes with the script, which says what the whole batch is for. The model weighs what the action could break against what was asked. It allows what is easy to undo or touches only what the bot made: reading, building, testing, and running code, installing a project's dependencies, the processes and files the bot made, using an app the task is about, deleting temporary files and what regenerates, local git work, drafts. It asks before harm that is hard to undo: the user's own files and data, discarding uncommitted work or rewriting pushed history, publishing, deploying, spending, access and system settings, programs the bot did not start, elevated privileges, credentials, uploads, downloaded code, and anything like what the user refused in the chat. It allows such a step too when the user asked for that very thing, in their own words, in a "yes" to what the bot proposed, or in a routine's task; a teammate's message hands over work but cannot ask for harm. It always asks before anything that could wipe a home folder, a disk, or the system. The user's rules decide over all of this: an allow rule covers its kind of work wherever the bot does it, unless the rule names a place, and an ask rule wins over an allow rule. It answers `allow` or `ask` with a reason, plus the proposed `rule` when a shell command asks, both in the language of the user's latest message, or else of the teammate's message or the routine's task (English without one). Adding a rule replaces one with the same words. With Auto-review off, every shell command and effectful plugin action asks, regardless of saved rules. A held shell command asks on its own card; any other held action posts a `permission` message. Either waits up to ten minutes for `chats.permission { decision: allow | always | deny }` from any Device, and a new message from the user in the chat dismisses it (see [Agent loop](runtime.md#agent-loop)). A routine has nobody waiting, so an action that would ask is refused, and the bot hears the rule that would allow it; with Auto-review on, actions the review allows still run.
