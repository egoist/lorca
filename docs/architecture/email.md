# Bot email

An account may take one email address on the relay's mail domain, `bots.lorca.app` for Lorca's relay, and every bot on every Runner of the account shares it. There is none until the user asks for one in Settings. Mail comes in through Cloudflare Email Routing and a mail Worker (`mail/`), which seals a copy to each Runner; it goes out through the relay, which sends with Cloudflare Email Sending. `crates/relay/src/mail.rs` keeps the addresses and sends, `crates/cli/src/mail.rs` is a Device's side, and `crates/cli/src/mail/` the Runner's inbox and the bots' tools.

## Addresses

The relay hands out the address (`POST /v1/mail/address` with a machine's bearer, so any paired Device asks): a random name of eight letters and digits that start with a letter (`k7f3m9q2`), or a name the user picks when it is free and allowed. A name is 3 to 32 lowercase letters, digits, dots, and hyphens, starts and ends with a letter or digit, has no `..`, and is not a reserved mailbox (`postmaster`, `abuse`, `admin`, `support`, `noreply`, `lorca`, …). Asking again changes the address and gives the old one up; `DELETE /v1/mail/address` gives it up. A given-up name stays with the account that held it, which alone may take it back, so mail meant for one account never reaches another; deleting an account keeps its names taken.

Each bot writes from `name+<tag>@domain`. The tag is the bot's name in lowercase letters, digits, and hyphens (`+scout`, `+ops-lead`); a bot whose name gives none (`研究员`), or two bots whose names give the same one, use the eight characters of the bot id. Mail to `name+scout@…` goes to Scout; mail with no tag, or a tag that names no bot, goes to the lead bot: the coordinator the user picked for [Attention](attention.md), else the first bot in the roster. A bot sends from its own tagged address, so a reply to it comes back to that bot.

The relay keeps `mail_addresses` (name, identity, whether given up, a suspension), `mail_runners` (the machines that take an identity's mail), and `mail_usage` (messages sent and bounces per identity and day). Every Device asks `GET /v1/mail/address` when its sync socket opens and when the relay sends `{"type":"mail"}` on it, which it does when the address is taken, changed, given up, or suspended. A Runner that sees an address and is not yet listed says it takes the account's mail (`PUT /v1/mail/runner`); unpairing a machine drops it. The relay never learns which bot a message is for.

## Mail in

Email Routing's catch-all on the mail domain sends every message to the mail Worker's `email()` handler. The Worker takes the name from the envelope recipient, drops the `+tag`, and asks the relay where it goes (`GET /v1/mail/route/<name>`, with the bearer it shares with the relay's `--mail-token`). It refuses with a permanent error (`setReject`) mail to a name nobody holds ("No such address"), to a suspended address, mail over 4 MiB less 4 KiB ("Message too large"; an `event` envelope holds 4 MiB of ciphertext), and mail for an account out of storage ("Mailbox full"). When the relay cannot be reached or no Runner takes the account's mail yet, it throws, which Email Routing answers with a temporary failure, so the sender's server tries again. Otherwise it reads the message once and seals, to each listed Runner's box key, `lorca-mail/1`, a JSON line (a delivery id, when it came, the envelope sender and recipient), and the raw message, with libsodium's sealed box over `@noble` (`mail/src/seal.ts`; a test vector in `mail/test/seal-vector.json` is opened by the CLI's tests). Each copy goes to `PUT /v1/mail/deliveries/<id>.<n>`, which stores it as an `event` envelope for that machine alone, under the identity's quota, kept seven days unread like other sealed envelopes ([Event triggers](event-triggers.md#relay-transport)). The Worker keeps nothing.

A Runner opens the envelope in the sync loop before its cursor moves past it, as it does a gateway's event; the first line tells the two apart. Every Runner picks the bot the same way from the roster it shares (the `+tag`, else the lead bot), and only the Runner hosting that bot keeps the message; the others let their copy go. The one that keeps it parses it (`mail-parser`, every charset): the headers, the text (HTML as text), the first `Authentication-Results` (the receiving server's `dkim`, `spf`, and `dmarc` verdicts), a calendar invitation or answer in a line, and the attachments, which it saves under `workspaces/<bot id>/mail/<delivery id>/` in the CLI's folder. It stores the message encrypted with the account key in `lorca.sqlite3` (`mail`, associated data `mail`), before the relay copy goes, so a storage failure reads it again. A message with a Message-ID the bot already has (a sender that retried) is kept once.

A message for a bot that is waiting for mail goes to that wait. Any other waits for the bot's turn: once a bot has messages waiting and none in a turn, its Runner starts a `mail` Job in the bot's DM with up to ten of them. The turn opens with a notice, "Email · from Acme Support" (or "Email · 3 messages"), runs unattended as an [event's turn](event-triggers.md#durable-ordering-and-execution) does, and carries the messages after the transcript as untrusted data that cannot instruct, approve, or grant anything; its task, which Auto-review reads, is fixed: tell the user what the mail is and what they need to do, or answer `PASS`. A week without a message from the user holds the turns, as it holds routines. A Runner that stops during a mail turn marks its messages read rather than run them again: the turn may have answered already. Only the inbox admits a `mail` Job; one arriving as a relay `job` blob is dropped.

## The bots' tools

A bot has two tools while the account has an address and its [Access](bot-permissions.md) gives it Email, a built-in connection `email` that the Access sheet lists with the Runner's plugins (`email` reads, `send_email` writes). The system prompt names the bot's address.

- `email { action: address | list | search | read | wait }` reads the bot's own mail on its Runner: its address, the newest twenty messages received and sent, a search by words, one message by id with its attachments' paths, and a wait for a message from a sender or with words in its subject, up to ten minutes. A wait first takes a matching message that came in the last ten minutes and no turn has read, so a sign-up in a [browser profile](browser-sessions.md) can wait for its verification code or link. What the tool returns says the mail is untrusted.
- `send_email { to, cc?, subject, text, reply_to?, attachments?, invite? }` sends from the bot's tagged address. `reply_to` names a message the bot has: the reply goes to its sender, with `Re:` and the thread's `In-Reply-To` and `References`. `attachments` are files on the Runner (the bot's Files access to read them), 3.5 MB in all. `invite { title, start, end, location?, description? }` adds `invite.ics`, a METHOD:REQUEST invitation in UTC with the recipients as attendees; an answer to one reads as "Calendar reply to …: ann@example.com accepted". The bot proposes times from a connected Calendar ([Integrations](integrations.md)) with its own tools.

A send is checked like a plugin's action: Access first, then a question before the first message to anyone this Runner's bots have not written to or heard from ("First email to ann@example.com"), else [Auto-review](tools.md). The user's Always allow for Email's `send_email` covers new recipients too. A turn nobody watches (a mail turn, a routine, an event) stages the send in the [review queue](review-queue.md) as a call to the `email` connection, which the Runner sends once the user approves it.

## Mail out

The Runner sends `POST /v1/mail/send { tag, from_name, to, cc, subject, text, html?, in_reply_to?, references?, attachments? }` with its bearer. The relay checks that the account holds an address that is not suspended, that the tag is lowercase letters, digits, and hyphens, that there are one to `--mail-max-recipients` (10) recipients, none on the mail domain, headers on one line, and that the account has sends left today: `--mail-daily-sends` (100), `--mail-new-daily-sends` (20) in its first week. Then it calls Email Sending's REST API (`POST /accounts/<id>/email/sending/send`) with `from: { address: "name+tag@domain", name: "<bot>" }` and the threading headers. Email Sending makes the Message-ID, adds SPF and DKIM, and keeps suppression lists. The answer's permanent bounces and suppressed recipients count against the day; `--mail-bounce-limit` (5) of them suspend the address for a week, a suspension that follows the account to a new name. A suspended address bounces mail to it and sends nothing; the apps say Suspended.

Email isn't end-to-end encrypted. A message is readable by the sender's and Cloudflare's mail servers and, while it passes, by the mail Worker as it seals it and by the relay as it sends one. Lorca stores mail only encrypted for the account: sealed to a Runner on the relay, under the account key on the Runner.

## Apps

`mail.get` asks the relay and answers the status; `mail.apply { name? }` takes or changes the address, answering `{ mail }` or `{ problem: taken | reserved | invalid }`; `mail.release` gives it up. The status is `{ available, domain, address: { name, email, state: active | suspended }, lead_bot_id, bots: [{ bot_id, email }] }`; the snapshot carries it as `mail` (`null` until this Device asked the relay), and `mail.changed` sends it again when it changes or the roster does.

The Mac and the Windows and Linux apps list Settings › Email while the relay offers email. Without an address it has an Address row with Get an Address…; with one, the address with Change… and Copy (and those with Give Up Address… in its menu), Status: Suspended in red while it is, Give Up Address…, and a note on which bot gets which mail. Get an Address and Change Address are one sheet: Random name, or Your own name with the domain beside the field, and the problem under it. Give Up asks first. The phone has an Email row in Settings, opening the same screens in its idiom.

## Deploying

The relay offers email with `--mail-domain` and `--mail-token` (`LORCA_RELAY_MAIL_DOMAIN`, `LORCA_RELAY_MAIL_TOKEN`); without them `/v1/mail/*` answers `404` and the apps show nothing. Sending also takes `--email-account-id` and `--email-api-token`, a Cloudflare API token that may send email; without them mail comes in and `send_email` says the relay can't send. `LORCA_RELAY_EMAIL_API_URL` points sending at a test server.

The Worker deploys from `mail/` with `bun run deploy` (`wrangler deploy`): `RELAY_URL` in `wrangler.jsonc`, `MAIL_TOKEN` as a secret (`wrangler secret put MAIL_TOKEN`). The mail domain needs Email Routing with a catch-all rule that sends to the Worker, and Email Sending set up for the same domain. A subdomain keeps bots' mail apart from the reputation of mail from the main domain. `bun test` in `mail/` runs the handler against a stand-in relay, and `crates/relay`'s `mail::end_to_end` test runs a Runner's core against a relay with a stub of Email Sending.
