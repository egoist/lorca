# One-time routines, routines on events, and calendar events

Most [routines](routines.md) repeat on an interval or a cron schedule. Three more kinds place their runs another way: a **one-time routine** runs once at a date and time and is then removed, after Grok Bot's one-time reminders; a routine **on events** runs once for each event a service sends about one subject (a **watch** follows one pull request and ends itself once it merges or closes; a routine with its own **webhook** runs for each request to its URL); and a routine **around calendar events** runs a set time before or after each matching event of a Google Calendar account. The bot sets each up with the `routines` tool, as it does any routine, and every paired Device lists and manages them the same way. `crates/cli/src/routine_triggers.rs` and `routine_events.rs` hold what is particular to them; the scheduler in `crates/cli/src/routines.rs` runs them.

## One-time routines

`schedule: "once 2026-10-12 09:00"` is a date and a 24-hour time on the routine's clock (its `timezone`, as for cron), stored in that canonical form; `2026-10-12T09:00`, `9:00 am`, and `at 9:00` read the same. A time that daylight saving skips runs at the same clock time an hour later, and a repeated one at its earlier instant. Creating one, or giving it a new time, refuses a time that has passed.

The routine is due at that instant until a run at or after it: its Runner took the time (`last_scheduled_at`), or a run started then or later. A run by hand before the time leaves it due at its time. A Runner that was off then runs it when it is back, so a one-time routine refuses `missed_run_policy: skip`, and it has no check. Once its run ends, the Runner deletes the routine and the roster goes up without it; the chat keeps the run's marker and reply, and later turns read the marker as `[Routine · Name ran on its schedule]`. A routine whose time was taken but whose run never ended (the CLI exited) is removed at the Runner's next tick. Resuming a paused one-time routine whose time has passed runs it at once.

## Routines on events

A routine with `receiver` (and `subject`, unless the receiver's events are its own) runs on events: its schedule is `on events`, it has no check, no next run, and no missed runs, and `schedule_text` says what starts it (`Watches acme/project#42`, `When its webhook is called`). The core knows no service. A receiver is named by the relay ([Hosted receivers](receivers.md)): `github` takes a pull request as `owner/repo#42`, and `webhook` takes none. Which receiver and subject fit a request, the bot reads in the service's plugin skill (the GitHub plugin's "Watching pull requests"). Only the bot's Runner sets one up, and the receiver and subject can't change afterwards: the bot deletes the routine and makes another.

The Runner gives the routine an [event subscription](event-triggers.md) of its own (`routine_events::open`): `routine_id` the routine, `event_types` the receiver's name, a filter that `/subject` equals the subject (none without one), `fifo`, and the routine's name and task. The roster keeps `events { receiver, subject, subscription_id, status, source_name, title, url, endpoint, key, last_event { summary, at }, ended_at }`. The Runner then subscribes the subject with the relay's receiver, handing it the subscription's id, generation, and signing secret, and for a webhook the hash of a key it makes (`routine_events::subscribe`). `status` keeps the answer:

- `subscribed`: the receiver seals the subject's events to the Runner; it named its service ("GitHub"), and the subject's title and link, or the webhook's `endpoint`, which the routine keeps with its `key`.
- `needs_setup`: the user does something first, such as installing the GitHub App on the repository or authorizing it. The bot gets the setup link to give the user, the apps show Install App, and the Runner subscribes again every two minutes until it is done, and at once when an app the user comes back to asks (`routines.subscribe`, at most every five seconds): every app does for its routines that wait on setup when it becomes active, likely from finishing it in the browser.
- `gateway`: the relay has no such receiver (a self-hosted relay). The events come through a [gateway the user runs](event-triggers.md#user-controlled-gateway) from the subscription's route, and the bot gets the steps.
- `pending`: the relay was out of reach; the Runner tries again every two minutes.

A receiver that turns the subject down (a pull request that doesn't exist, or is already merged or closed) refuses the routine: the tool says why and deletes it.

**Each event is one run.** An event's payload is `{ subject, kind, summary, title?, url?, ends?, unsubscribed?, data? }`, from the receiver. The inbox deduplicates it by delivery id and admits it as an `event` Job with the routine as its scope ([Durable ordering](event-triggers.md#durable-ordering-and-execution)), so a paused routine, its [limits](budgets.md), and the away rule hold it as they hold a scheduled run, and the run uses the routine's task. Its note opens with the event's own words (`Event on acme/project#42: Changes requested by kim.`) and carries the payload as data from outside, never instructions; the run reads the subject itself through the bot's plugin before it reports. When the run ends, the routine keeps it as its last run and the event's summary and time as `last_event`, and takes the payload's title and an `https://` link. An event with `ends` (a pull request merged or closed) makes its run the routine's last: once it ends the routine is deleted, as a one-time routine is, and a run the user [stops](stopping.md) still ends it. `unsubscribed` (the GitHub App taken off the repository) puts the routine back to subscribing, and so to Install App. Nothing polls: between events a routine on events does nothing.

Run Now runs the task with a note that no event came, so the bot reads the subject itself. Deleting the routine removes its subscription on the Runner and its row on the relay, and a webhook's URL with it; the Runner also sweeps subscriptions whose routine is gone, deleted on another Device. A [webhook's key](receivers.md#routine-webhooks) is regenerated on the Runner (`routines.regenerate_key`, asked through a sealed request from another Device): the relay takes the new hash and the old key stops working.

## Calendar events

A schedule around events is `15m before events`, `at events`, `10m after events`, or `when events end`: so many minutes (at most a day) before an event starts, or after it ends. It needs `calendar`, the Google Calendar account on the bot's Runner (its id or name; the only one when there is one), which the bot's Access must allow, and may take `event_match`, words a matching event has in its title, description, place, or guests (every event without them). It has no check. The roster keeps `{ plugin_id, account, matching?, upcoming, done, synced_at? }`.

The Runner reads the account's calendar every fifteen minutes, sooner after an edit, by `list_events` with `startTime`, `endTime`, `orderBy: "startTime"`, and `fullText` set to the words, through the same check machinery (Access, read-only calls, limits, health, backoff). It looks a day ahead (past the offset), and back a day for runs after events end. It keeps the matching events in `upcoming` (at most fifty): their id, title, start, end, and link, from the calendar and so data. It leaves out all-day events, cancelled ones, ones the user declined, and out-of-office, focus-time, working-location, and birthday entries, and filters by the words itself as well. A read starts no run; when the events it keeps change, the roster goes up so every Device shows the next one.

Each event runs once: when its time comes, the Runner adds its key (`id@start`) to `done` before the run starts, and runs the earliest due event, the next one after it at the next tick. A moved event has a new key, so it runs at its new time. An event due before the routine was set up or resumed is not its to run. Late, because the Runner was off, an event runs anyway with `coalesce`, but not one more than a minute late with `skip`, nor a run due before an event that has already started. The run's note names the event, its time on the routine's clock, its link, and the account, as data from the calendar; the bot reads the event with its Calendar tools when the task needs more. Run Now runs for the next matching event, which keeps its own run. `done` keeps only events still in reach.

## Across Devices

What a calendar read returns has the Runner's saved [secrets](secrets.md#keeping-values-out) replaced by their placeholders before it is kept or reaches a run, as a turn's tool results do. Only the bot's Runner reads the calendar and sets its `upcoming`, `synced_at`, and `done`, and only it writes a routine's `events`: how it listens, the title and link, the webhook's address and key, the latest event, and its end. Setting up a routine on events or around calendar events is refused elsewhere, since the Runner's plugins and subscriptions decide it. When another Device writes the roster from an older copy, the Runner keeps its newer reads and the runs it took (`routine_triggers::keep_reads` and `routine_events::keep_reads`, beside `routines::keep_checks`) and uploads again.

A [bot template](templates.md), a marketplace bot, and a [workflow](workflows.md) carry repeating routines only (`schedule::parse_repeating`): a date, a subject, a webhook, and a calendar belong to one account.

## The apps

The CLI gives `schedule_text` in English (`Once on 2026-10-12 at 9:00 AM`, `Watches acme/project#42`, `When its webhook is called`, `15 minutes before events matching “Customer call”`), which the bot reads, and beside it what the apps word themselves in English and Chinese: `once_at`, `events`, and `calendar { account, matching, minutes, after, next_event }`. Only a one-time routine names its timezone when the computer keeps other hours; events keep their own times.

In every app a routine row's symbol says what places its runs while it is on: an alarm, a pull request, a link for a webhook, a calendar, else a clock. The routine sheet (the phone's Routine screen) adds, under Schedule, the Calendar account of a routine around events, whose Next run names the event (`Today 9:45 AM · Customer call: Acme`, or `None in the next day`), and for a routine on events, in place of Next run and Missed runs:

- the subject: a watch's Pull request with its title, which opens it on GitHub;
- the service: Connected, Connecting…, Your gateway with a note, or Install App… in orange, which opens the setup link (`receivers.setup` with the subject: the install link, or the authorize link where the App is installed already) in the browser. While setup waits, the routine's state reads App not installed (Needs setup for another service), with a note that says what to do;
- Last event: when it came and what it was, or None yet.

A routine with a webhook has a Webhook section: Webhook URL, Webhook key (hidden until a click or tap shows it), and Authorization header (`Bearer <key>`), each with Copy, and Regenerate (Regenerate… beside the key, Regenerate Key… on the phone), which asks first: services that send the old key stop reaching the routine. A one-time routine has no Missed runs row. A calendar that can't be read reads Check failed, with a note that says so.
