# One-time routines, watches, and calendar events

Most [routines](routines.md) repeat on an interval or a cron schedule. Three more kinds place their runs another way: a **one-time routine** runs once at a date and time and is then removed, after Grok Bot's one-time reminders; a **watch** follows one pull request and ends itself once it merges or closes; and a routine **around calendar events** runs a set time before or after each matching event of a Google Calendar account. The bot sets each up with the `routines` tool, as it does any routine, and every paired Device lists and manages them the same way. `crates/cli/src/routine_triggers.rs` holds what is particular to them; the scheduler in `crates/cli/src/routines.rs` runs them.

## One-time routines

`schedule: "once 2026-10-12 09:00"` is a date and a 24-hour time on the routine's clock (its `timezone`, as for cron), stored in that canonical form; `2026-10-12T09:00`, `9:00 am`, and `at 9:00` read the same. A time that daylight saving skips runs at the same clock time an hour later, and a repeated one at its earlier instant. Creating one, or giving it a new time, refuses a time that has passed.

The routine is due at that instant until a run at or after it: its Runner took the time (`last_scheduled_at`), or a run started then or later. A run by hand before the time leaves it due at its time. A Runner that was off then runs it when it is back, so a one-time routine refuses `missed_run_policy: skip`, and it has no check. Once its run ends, the Runner deletes the routine and the roster goes up without it; the chat keeps the run's marker and reply, and later turns read the marker as `[Routine · Name ran on its schedule]`. A routine whose time was taken but whose run never ended (the CLI exited) is removed at the Runner's next tick. Resuming a paused one-time routine whose time has passed runs it at once.

## Watches

A routine with `pull_request` (`owner/repo#42`, `owner/repo/pull/42`, or the pull request's GitHub link) watches it through GitHub on the bot's Runner. The bot gives a repeating schedule, `every 10m` when it gives none, and no check: the watch is the routine's check. The Runner picks the plugin when the watch is set up: GitHub from the marketplace, else any installed plugin that offers `pull_request_read` or `get_pull_request`, and the bot's [Access](bot-permissions.md) must allow it. The roster keeps `{ repo, number, plugin_id, seen?, ended_at? }`.

At each due time the Runner reads the pull request as a check reads (`routines::run_check`): the bot's Access, only calls that read, the routine's [limits](budgets.md), and its health, backoff, and pause after failed sign-ins all apply. It calls `pull_request_read` with `method: "get"`, or `get_pull_request`, and reads GitHub MCP's trimmed pull request or the REST one: state, merged, draft, head commit, commit and comment counts, title, and `updated_at`. The first read only records what it saw. A later read that finds a change starts a run whose note says what changed (new commits, comments, review comments, ready for review or back to draft, a new title, merged, closed, reopened, or other activity such as a review or a label), marked as data from GitHub and never instructions; the run reads the pull request itself before it reports. A read that finds nothing new runs no turn. A read that fails to connect or sign in counts in health as a check's does; any other failure starts the run with the error, so the bot can fix or delete the watch.

A read that finds the pull request merged or closed sets `ended_at`, and its run is the watch's last: once that run ends the routine is deleted, and a restart in between removes it ten minutes later. A watch the bot sets up on a pull request that is already closed is deleted at once, and the tool says so. Run Now reads first and runs whatever it found. A last run the user [stops](stopping.md) still ends the watch.

## Calendar events

A schedule around events is `15m before events`, `at events`, `10m after events`, or `when events end`: so many minutes (at most a day) before an event starts, or after it ends. It needs `calendar`, the Google Calendar account on the bot's Runner (its id or name; the only one when there is one), which the bot's Access must allow, and may take `event_match`, words a matching event has in its title, description, place, or guests (every event without them). It has no check. The roster keeps `{ plugin_id, account, matching?, upcoming, done, synced_at? }`.

The Runner reads the account's calendar every fifteen minutes, sooner after an edit, by `list_events` with `startTime`, `endTime`, `orderBy: "startTime"`, and `fullText` set to the words, through the same check machinery (Access, read-only calls, limits, health, backoff). It looks a day ahead (past the offset), and back a day for runs after events end. It keeps the matching events in `upcoming` (at most fifty): their id, title, start, end, and link, from the calendar and so data. It leaves out all-day events, cancelled ones, ones the user declined, and out-of-office, focus-time, working-location, and birthday entries, and filters by the words itself as well. A read starts no run; when the events it keeps change, the roster goes up so every Device shows the next one.

Each event runs once: when its time comes, the Runner adds its key (`id@start`) to `done` before the run starts, and runs the earliest due event, the next one after it at the next tick. A moved event has a new key, so it runs at its new time. An event due before the routine was set up or resumed is not its to run. Late, because the Runner was off, an event runs anyway with `coalesce`, but not one more than a minute late with `skip`, nor a run due before an event that has already started. The run's note names the event, its time on the routine's clock, its link, and the account, as data from the calendar; the bot reads the event with its Calendar tools when the task needs more. Run Now runs for the next matching event, which keeps its own run. `done` keeps only events still in reach.

## Across Devices

What a read returns has the Runner's saved [secrets](secrets.md#keeping-values-out) replaced by their placeholders before it is kept or reaches a run, as a turn's tool results do. Only the bot's Runner reads GitHub or the calendar and sets a watch's `seen` and `ended_at` or a calendar's `upcoming`, `synced_at`, and `done`. Setting up a watch or a routine around events is refused elsewhere, since the Runner's plugins decide it. When another Device writes the roster from an older copy, the Runner keeps its newer reads and the runs it took (`routine_triggers::keep_reads`, beside `routines::keep_checks`) and uploads again.

A [bot template](templates.md), a marketplace bot, and a [workflow](workflows.md) carry repeating routines only (`schedule::parse_repeating`): a date, a pull request, and a calendar belong to one account.

## The apps

The CLI gives `schedule_text` in English (`Once on 2026-10-12 at 9:00 AM`, `Watches acme/project#42`, `15 minutes before events matching “Customer call”`), which the bot reads, and beside it what the apps word themselves in English and Chinese: `once_at`, `pull_request { repo, number, title, url }`, and `calendar { account, matching, minutes, after, next_event }`. Only a one-time routine names its timezone when the computer keeps other hours; a watch counts time and events keep their own.

In every app a routine row's symbol says what places its runs while it is on: an alarm, a pull request, a calendar, else a clock. The routine sheet (the phone's Routine screen) adds, under Schedule, a watch's Pull request with its title, which opens it on GitHub, and the Calendar account of a routine around events, whose Next run names the event (`Today 9:45 AM · Customer call: Acme`, or `None in the next day`). A watch shows Next check and Last check as a check does. A one-time routine has no Missed runs row. A watch or calendar that can't be read reads Check failed, with a note that says which.
