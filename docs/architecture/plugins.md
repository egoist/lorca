# Codemode and Plugins

## Codemode

A bot uses plugins by writing a script, after pi's codemode: `codemode { code }` runs JavaScript whose calls reach the plugins' tools, and only what the script outputs or returns reaches the model. A script pages through an API, runs calls in parallel, filters what came back, and hands the bot the lines that matter, so the results it read never fill the bot's context, never become chat rows, and never sync.

- **The sandbox** (`lorca_agent::codemode`): each script runs in a fresh QuickJS VM (`rquickjs`) on a thread of its own, with a 256 MiB heap, no timers, network, file system, or modules, and one way out: the bridge that carries its calls and output. Stop ends it wherever it stands, and so does its deadline: 30 minutes, 10 in a routine, questions to the user included. The code is an async function body and may start with `// @options: {"max_output_tokens": …, "timeout_ms": …}`; the output has a 10,000-token budget, keeping its start and end, with the whole text in a temp file the result names. The host bounds what a script sends it: past 16 MB of output or 1,000 calls it has not awaited the script stops, an image (ten at most) is made one a model takes as the script ends, converted, turned upright, or scaled down, with a note, a call whose arguments cannot be read rejects without running, and `store()` writes over their limits fail the script.
- **What a script calls** (`plugins::mcp::PluginCatalog`): `tools.<plugin>__<tool>(args)` for every tool of the plugins installed on the Runner, the bot's own `read`, `write`, `edit`, `grep`, `find`, `ls`, `memory_update`, `memory_log`, and `recall` with their arguments (`turns::SCRIPTABLE_TOOLS`), and `bash`. A script's `bash` takes the bot's arguments but is its own (`shell::script_bash`), pi's: on pipes with nothing on stdin, one command at a time, a call as long as its command, no terminal session and no card. It resolves to `{ output, truncated, full_output_path?, exit_code, wall_time_seconds }`, the output whole up to 1 MB (its start and end past that), also when the command exits nonzero; a timeout, Stop, or signal rejects. Auto-review judges each command with the script, and one it holds asks in a `permission` message. The tools that hand work to teammates, change bots or routines, install or sign in to plugins, or reach a command left running stay calls of their own. A plugin tool resolves to its whole MCP `CallToolResult` (`content`, `structuredContent`, `isError`), uncut; the other tools to their text. A plugin whose server offers resources (as `catalog.json` remembers) has three more tools, named as Codex's and pi's (`ToolKind`): `list_mcp_resources` and `list_mcp_resource_templates`, a page at a time (`cursor`, `nextCursor`), with MCP Apps' `ui://` interfaces, icons, and `_meta` left out, and `read_mcp_resource { uri }`, whose text comes as text, images a model takes as images, and other binary contents saved to a private file in the temp folder that the result names. They only read, so they never ask. At most eight calls run at once, and one that may ask the user runs alone. `searchTools(query)` ranks the plugins' tools, `describeTool(name)` gives one's declaration, and `describeNamespace(id)` gives a plugin's name and what it does, its servers' instructions whole, and every tool it has, connecting a plugin with no saved tool list first. A call to a name no tool has rejects with the closest names (`tools.github_create_issue` suggests `tools.github__create_issue`), or every name when there are few, as in pi. `store(key, value)` and `load(key)` keep JSON values for later scripts in the chat, in the Runner's database per chat and bot (`codemode_store`), never synced. `models.ask(prompt, { system?, maxTokens? })` asks the small model of the bot's provider, the one Auto-review uses unless the user picked another (`scripts::ModelsAsk`), to rate, sort, or summarize items one at a time without reading them itself: four answer at once and 200 per turn, and each call's tokens and cost count in the chat's spending and toward the turn's [limits](budgets.md), not its context size.
- **The listing**: the tool's description, rendered once per turn, declares what scripts can call as TypeScript: the shared MCP result types and how to read them, `models.ask`, the bot's own tools by name with what `bash` resolves to and how a script's `bash` differs (`turns::SCRIPT_GUIDANCE`), and each plugin's section (its name, description, what it still needs, and the first 1 KB of its servers' instructions, pointing at `describeNamespace()` for the rest) with its tools' declarations, built from their JSON Schemas, within about 3,000 tokens, each plugin getting a tool in before any gets all of its tools. A plugin with no saved tool list is named, and `describeNamespace()`, `searchTools()`, or a call by name connects it.
- **Every call goes through the loop**: argument checks, then the turn's `before_tool_call`, where a plugin tool that is not read-only (Plugins, below) or a command ([Tools](tools.md)) goes to Auto-review with the script beside it. A call that is refused, left unanswered, or dismissed by a new message ends the script: calls still waiting never start or ask, and the result says which ran. A question a script or turn stopped waiting on reads as dismissed, never as the user's no. The script's row carries its calls in its details, and while it runs its `description` names the plugin of its latest plugin call, so the working row reads "Using GitHub…"; the finished row reads "Used GitHub". While its latest command came after its latest plugin call, `script_command` carries that command's `description` beside it (from the call's record, `NestedCall::description`), and the working row reads "Running command: Run the tests…", as it does for the bot's own command; an app that does not know the field reads the plugin.

## Plugins

User-authored skills are [Playbooks](playbooks.md): explicit bot or project procedures with reviewed authoring, revisions, and portable export. Their catalog accompanies plugin skill metadata at turn time; full content loads through `read_playbook` when needed.

A plugin is an MCP server (or several) a bot can use, after Grok Bot's marketplace: GitHub, Jira, Notion, Stripe, Zapier, a headless browser, and the other services the [marketplace](marketplace.md) lists. A plugin is described by a manifest (`crates/cli/src/plugins/mod.rs`): `id`, `name`, `description`, `icon`, `author`, `category`, and `featured` for the marketplace, `servers` (`stdio` with `command`, `args`, `env`, and `cwd`, or `http` with `url`, `headers`, and `auth`: `oauth`, `optional` when it signs in only once the server answers with a 401, with a preregistered client's `client_name`, `callback_port` or `callback_url`, and `auth_server_metadata_url` as [MCP servers](mcp-servers.md#values-and-sign-in) tells, or `bearer`; either with a `timeout` for its calls), `variables` (setup fields, `secret` ones never read back, which a bot can also ask the user for on a card: [Secret requests](secrets.md)), `skills` (notes written to the plugin's folder that the prompt points the bot at), and `tools` hints (`readonly` and `draft` patterns, `hide`, pi's ordered `exposure`, `ToolHints::hides`, and `messages`, the tools that write to people, which wait in a chat as [drafts](drafts.md)). `${VAR}` in args, env, and headers is filled from the variables, and `${VAR:-default}` takes the default for an empty or unset one; a header or an environment variable that names a variable with no value and no default is left out, so an optional key left unset is never sent as its placeholder (Context7 refuses every call made with one). The servers the user adds themselves are plugins too, read from the Runner's `mcp.json` ([MCP servers](mcp-servers.md)). A stdio server starts in its `cwd`, else its plugin's folder, with the login shell's environment (see [Tools](tools.md)), so a `command` such as `npx` or `uvx` resolves from the user's `PATH`, on Windows through `PATHEXT` as a terminal finds it (`npx` is npm's `npx.cmd`); the manifest's `env` goes on top. A server that cannot start says so with the file it found: `Cannot start npx (C:\Program Files\nodejs\npx.cmd): batch file arguments are invalid`.

**Installed per Runner, with access selected per bot.** The Runner holds the install under `~/.lorca/plugins/` (`installed.json`, the plain variables; `secrets.json`, mode 0600, the secret variables and OAuth tokens; a folder per plugin with its skills) and advertises each plugin's id, name, and state (`ready`, `needs_setup`, `needs_auth`, `insufficient_access`, `connecting`, `error`) in its `machine` blob, so every Device lists what each Runner has without a secret leaving it. Each bot's [Access](bot-permissions.md) says which of them it may use, how far (read, draft, write), and which of their tools; a bot's turn leaves out the plugins it may not use. A bot with no policy may use them all. Installing, removing, setting variables, signing in, and reading a plugin's detail run on the Runner: locally when the app's CLI is that Runner, else as a `request` sealed to it (`plugins.install`, `plugins.rename`, `plugins.uninstall`, `plugins.variables`, `plugins.connect`, `plugins.sign_out`, `plugins.detail`), so a phone installs a plugin on another computer and hands it a key through ciphertext.

A manifest with `named_accounts` installs separate instances with stable ids, `service_id`, and `account_name`; each instance has its own tokens, codemode namespace, and Auto-review rules. Slack and the three Google services use native PKCE endpoints, with the same encrypted paired-Device sign-in requests. Their configuration, account selection, and recovery are in [Integrations and named accounts](integrations.md).

An installed marketplace plugin follows the [marketplace's index](marketplace.md#the-index) in use, keeping its variables, secrets, and sign-ins; the index, the bot templates, and the marketplace sheet are in [Marketplace](marketplace.md).

**At turn time** (`crates/cli/src/plugins/mcp.rs`, `rmcp`), the system prompt carries a bounded catalog of installed plugin ids, names, states, and skill locations, and the turn's codemode listing declares their tools (Codemode, above). A plugin's tools come from `catalog.json` in its folder, every tool its servers offered when they last connected, the ones it hides left out as they are listed, so listing them starts no server and reads the same from turn to turn. A server writes it each time it connects, and a plugin that becomes ready (an install, a setup, a sign-in) connects once in the background to write it. A script's call connects its server on first use; the Runner keeps connected servers in a pool (stdio children, or streamable HTTP with the plugin's headers, a pasted token, or the saved OAuth tokens), so later calls reuse them. A server has two minutes to start and answer the handshake, and a connection that began before the plugin's settings changed (an install, a setup, a sign-in, a removal) is dropped rather than kept or saved. A remote server's handshake that fails on the network, or with 408, 429, or a 5xx other than 501, is tried again after a quarter of a second and then a second (`serve_retrying`), as pi does; a tool call never is, since the server may have done it. Servers connect side by side, one connection at a time per server, and one whose process ended or whose transport closed leaves the pool, so the next call starts it again. A stdio server runs in a process group of its own (a job object on Windows), so stopping it stops what it started too, `npx`'s node or `uvx`'s python; its stderr is read for as long as it runs, into the log, and when it fails the handshake its last lines (stack frames left out) are the error, as in pi. A call has its server's `timeout`, ten minutes unless it says (`ServerSpec::call_timeout`), counted again from each progress notification, and one that runs out or is stopped is called off at the server (`notifications/cancelled`). A server that says its tools changed (`tools/list_changed`) is listed again, into the pooled connection and `catalog.json`. A tool list ends at a page with no cursor, an empty one, or one the server gave before, 100 pages at most (`all_tools`), where `rmcp`'s own reader would ask for the same page forever. A result's text, images, embedded text, and resource links reach errors and hooks, an image made one a model takes (`lorca_agent::images::prepare`, off the async threads: converted, turned upright, or scaled down to fit 2000×2000, with a note), since a refused one fails every later turn; an image nothing reads, audio, and other binary data are named, never carried as base64. Browser-flow OAuth tokens are refreshed by the transport and written back as soon as the handshake rotates them. Optional token fields a server sent empty or null, as `"scope": ""`, are dropped before tokens are saved or restored (`tidy_tokens`), so a refresh never asks for an empty scope. A device-flow token is a plain bearer; the Runner refreshes and saves its rotating pair itself, and drops the pooled connection before that bearer expires so the next use reconnects with a fresh one.

The CLI checks the bot's Access for the plugin, the tool, and what it does before Auto-review and again right before the MCP request, a codemode child call or a routine check's included. Cached tool annotations do not authorize a capability. A tool the server marks read-only (`readOnlyHint`) or the manifest lists as such runs at once within an allowed read grant. A manifest's `tools.draft` declaration requires a draft grant and still crosses Auto-review; other effectful tools require write. The mark counts only as the live server gives it, never as `catalog.json` holds it, since a bot can write that file: the review connects the server, through the pool, to read it and the tool's description. Any other tool goes through the same Auto-review boundary as local actions: the loop's `before_tool_call` (`mcp::review_call`), before the MCP call, with the script it comes from beside the call, marked as the bot's own words. When it asks, the card reads "Chef wants to use GitHub · create_issue · repo: …"; Always allow saves the exact `plugin/tool`. For an unattended routine, a held effectful call stages its exact arguments and original server/tool in the persistent [review queue](review-queue.md), then returns without executing or waiting. A refusal ends the script (Codemode, above). Server instructions appear in the plugin's section of the listing and do not replace the server’s own tool description at the permission-review boundary.

**Sign-in** for a remote server is the MCP authorization flow, held by the Runner through `rmcp`: discovery from the server's challenge, dynamic client registration as a native app, PKCE, and a loopback redirect on a free port, whose code the Runner swaps for the tokens with its PKCE verifier. The browser opens on the Device where the user asked (`plugins::sign_in`): the Runner's own, or any other Device's, which listens on its own loopback and sends the redirect with its request (`redirect_uri`). The Runner registers that redirect and answers with the page and the sign-in's id; the Device opens the page (a computer's browser, or a phone's in-app browser through the `plugin.auth` event) and sends the Runner where the browser landed (`plugins.sign_in.finish`), sealed like every request, or that the page closed first (`plugins.sign_in.cancel`), after which the card asks again. So a phone signs a computer's plugin in with nobody at the computer. It starts from a card in the chat, as in Grok Bot: after an install that needs a sign-in, or when the bot calls `connect_plugin`, the bot posts a `permission` message with `tool` `connect` ("Chef needs a sign-in to GitHub · Sign in to GitHub on Workbench · Sign in · Not now"); Sign in answers it with `chats.permission { decision: allow }`, and the card then reads "Finish signing in in the browser on Pocket" (the Device where the page opened), "Signed in", or "Sign-in failed: …" (`decision` `allowed`, `connected`, `failed`). Once the plugin is signed in, by any card, its sheet, or a pasted token, every card of the Runner's bots that asks for it reads Signed in, and Sign in on a card that waited through it reads Signed in without starting another. A chat holds one waiting sign-in card per plugin and Runner: asked again before the user writes, as when the bot calls `connect_plugin` after an install already put the card up, the Runner answers with that card; asked after, it puts up a new one and the old one reads Dismissed. The inspector's plugin sheet offers the same sign-in, and once signed in, Sign Out, which forgets the server's tokens and a waiting device code on the Runner (`plugins::sign_out`, the sealed `plugins.sign_out`); nothing is revoked at the server, which honors a token until it expires. A signed-in server that refuses a call for want of access (`insufficient_scope`) leaves the plugin reading insufficient access, and the next sign-in asks for the scope it named too (`needs_more_access`). Discovery is seeded from the server's own 401 challenge, since GitHub keeps its resource metadata under the server's path. Saved tokens, and the challenge of a server that signs in only when asked, carry the origin of the server they came from (`Store::sign_in_secret`) and count only while the server is there, so tokens never go to another host and a server moved to one starts out signed out; one saved before they carried it counts anywhere. A manifest can name a `token_variable` so a pasted token stands in for the sign-in, and `client_id_variable` / `client_secret_variable` (or fixed `client_id` / `client_secret`) for a server that registers no clients on the fly; the card says what to fill in when nothing is set. With a `client_id` and a `device_authorization_endpoint` plus `token_endpoint`, the sign-in is the device flow (RFC 8628) instead: the Runner asks for a code, the card shows it with the link ("Copy code and open github.com" on the Mac, the same on the phone), and the Runner polls until the code is entered. While the code waits, the plugin reads "Enter the code at github.com" and `plugins.detail` carries the code and link on the server's `auth` (`code`, `link`), never the machine blob, so the plugin sheet, where a sign-in starts with no card, shows the same code and button on any Device. Nothing opens on the Runner's screen, so the card works from any Device, and no client secret ships. GitHub's entry uses the device flow with Lorca's own OAuth app. GitHub may issue an eight-hour access token and a rotating refresh token; Lorca refreshes it directly at GitHub's token endpoint, persists the new pair before connecting, and uses the access token as the MCP bearer. A saved browser-flow sign-in whose server metadata cannot be found again also falls back to a bearer. `LORCA_OAUTH_NO_BROWSER=1` fetches the authorize page instead of opening a browser, for tests against a fake server.

**The bot** can search the [marketplace](marketplace.md) (`search_plugins`) and, when the user agrees on a permission card with `tool` `install`, install a plugin on its own Runner (`install_plugin`), as Grok Bot's InstallPlugin does after a question. It is told in the result what setup the user still owes (a sign-in, a variable).

**The apps.** The marketplace sheet is in [Marketplace](marketplace.md#in-the-apps). A plugin shows its real mark on a white tile, in light and dark mode alike (`Design/PluginLogo.swift`: mostly Simple Icons' CC0 paths in the brand's color, Playwright's logo for Browser, and the brand's own mark for the rest), in the marketplace, the inspector, and Settings; a plugin without one shows the SF Symbol its manifest names. A DM inspector's Plugins section has a row per plugin the bot's Runner has, ending in a green check when it is ready and an orange exclamation mark when it needs something; the mark's tooltip, or a click on it, says what the Runner reports (the same row lists plugins in Settings and the marketplace). A plugin's sheet shows its state, the sign-in per OAuth server, the variables (secret fields write only), the Always allowed rules for its tools with Reset, its skills, and Remove; Browser's, opened from a bot's inspector, also lists the bot's [browser profiles](browser-sessions.md#in-the-apps). Settings → Plugins lists what the picked Runner has installed, and the servers of its `mcp.json` in a section of their own ([MCP servers](mcp-servers.md#in-the-apps)). Settings → Auto-review has the switch ("Lorca checks each action before it runs and asks you first when needed") and a card per rule: its text, with its behavior, Edit, and Delete in a footer beneath it. The section's plus button and each rule's Edit button open sheets; the text of a rule for an exact plugin tool is read-only there, while its Allow automatically or Ask first behavior can change. The transcript shows the permission card: the question ("Chef wants to use GitHub"), the call, Auto-review's reason, Allow once, Always allow, and Deny, and under them the rule Always allow adds ("Always allow adds the rule “…”."); an install offers Allow and Deny. A shell command asks on its own command card instead (see [Terminal sessions](terminal-sessions.md)), and what a bot types into a running command asks on a permission card with the command in a code block (its first two lines; a click opens the whole command in a sheet with Copy), Allow once, and Deny. Answered, the card is the answer and the call, and an Always allow says which rule it added. The row's height and the card's layout come from one measurement (`PermissionCellView.Layout`). A shell card's `command` is the whole command (its first 8,000 characters), which `Message::for_app` takes from the reviewed arguments the apps otherwise never get. The phone shows the same card, with Sign in's page in its in-app browser; an answer that cannot reach the Runner (asleep or offline) puts the card back and says why in an alert. It shows the Runner's plugins in chat details, and Auto-review in its settings.

MCP tool and resource calls share the Runner's [call limits](budgets.md#shared-connector-admission) across bots: a rate and a number at once per installed account and per service, waits that observe cancellation, and the service's retry guidance holding later calls, never replaying a failed one. The plugin sheet's Call limit row opens them.
