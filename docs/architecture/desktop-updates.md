# Desktop app updates

How the [Windows and Linux app](desktop-app.md) updates itself, and how another Device starts that update.

## The updater

The updater lives in `updater.go`. MyGo's updater plugin stands where Sparkle does on the Mac. It checks once a day in the background, and a window of its own shows a new version's release notes with Install Update, Remind Me Later, and Skip This Version, the download's progress, and the offer to relaunch. It installs releases signed with the update key, as a delta from the running version when the release has one, and keeps the user's choices in `updater.json` in the app's data directory. **Check for Updates…** opens that window, and General has the version, the last check, and switches for automatic checks and automatic installs, which follow the plugin's changes (`updater.OnChange` redraws the windows). The window speaks the language picked in Settings, else the system's; a new pick reaches it at the next launch, as the Mac's reaches Sparkle. Its releases are this repo's, tagged `desktop-vX.Y.Z` (`updates` in `mygo.config.ts`, with the public key). The repo's latest release stays the CLI's, so release builds find the newest `desktop-v` release through the GitHub API (MyGo's `tagPrefix`), and read its update manifests. `bun run release-desktop` uploads to a draft of the version through `go tool mygo build -upload`, here or in the Release desktop workflow (`.github/workflows/release-desktop.yml`), which a `desktop-vX.Y.Z` tag or a run by hand starts: it drafts the release with the changelog's section and builds Windows x64, Linux x64, and Linux arm64 side by side on Ubuntu and macOS arm64 on a Mac runner, which signs it with the Developer ID and notarizes its disk image, and publishing the draft, without making it the latest release, releases the update. The app has its own version, `version` in `desktop/mygo.config.ts`, apart from the Mac app's, and its own release notes, the version's section of `desktop/CHANGELOG.md`: [docs/releasing-desktop.md](../releasing-desktop.md). A build that cannot write where it is installed, `mygo dev`'s or the Debian package's in `/opt`, leaves the menu item and the General rows out.

## Updates from another Device

Any paired Device can update the desktop app on a Runner, as it can a [self-updating CLI](runtime.md#updates-and-the-service). The app, when it can update itself, tells the CLI it runs how its updates stand each time the CLI answers (`remoteUpdates` in `updater.go`): `app.update_status { version, auto, latest?, state?, error? }` on the local websocket. `auto` is automatic checks and automatic installs both on; `latest` comes from the app's own look at its signed feed (`mygo.Updater.Check`) when the CLI answers and the last look is a day old, and daily after. The CLI keeps what the app said for as long as that connection stays open (`crates/cli/src/app_update.rs`) and puts it in its `machine` blob as the Device's `app`, so every Device sees the app's version beside the CLI's. A connection that closes takes it away: an app that quit offers nothing.

The Devices pane of the desktop app and the phone's Device screen show a **Lorca app** row from `app`, in the CLI row's words, with Update while a newer version waits and the Runner is online. Update on another Runner is `device.update_app { id }`, sealed to that Runner as `app.update.install` ([Requests between Devices](requests.md)); its CLI hands the request to the app as the `app.update.install` event and answers at once. This computer's own row opens the update window instead. The app checks its feed again, installs the newer version it offers as Install Update does (`state` `installing`), then (`restarting`) asks its CLI `app.relaunch_when_idle`, which answers once no turn of that Runner's own is in flight and no command a bot left running is open, and what it queued for the relay has gone up, as the CLI waits before it restarts into a release of its own (`update::until_idle`; a day later it stops those commands instead). The app then relaunches (`mygo.App.Relaunch`): quitting stops its CLI, and the new version starts the CLI it carries. A request names no version and no download: the app installs only what its own feed offers, signed with the update key. A request while a background check runs follows the check; one while an install is under way changes nothing. A CLI that restarts while the app waits drops the wait, and the app asks the next one when it answers.
