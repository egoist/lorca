# Bots, Routines, and Memory

## The lead bot

A new identity starts with one bot, **Chef**, a chief of staff on the first Runner: an ordinary bot whose description has it plan the work, delegate each task to the right teammate with `message_bot`, propose a new one for `create_bot` when none fits, and do hands-on work when necessary. Nothing about it is privileged; rename or delete it like any bot.

A chat has a `kind`. A DM is one bot and never gains or loses members; there is one DM per bot. A group holds one to six bots, can add or remove them after creation, and has an `owner_bot_id` (the bot holding the work; defaults to the first member, `chats.set_owner` changes it).

Deleting a bot removes its DM and routines and removes it from every group. A group with other bots keeps its transcript and moves ownership when needed; a group whose last bot was deleted is removed. The macOS sidebar treats Delete on a DM as this bot deletion and says so in its confirmation sheet. Deleting a group removes only that chat.

Who answers, after Grok Bot's rooms:

- **DM:** its bot, always. An `@Name` is a reference the bot acts on: it calls `message_bot`, which delivers the message into that bot's own DM with the user, where that bot answers (and can message back).
- **Mentions:** picking a bot from the composer's `@` menu records its id, and `chats.send` carries the picks as `mentions`. The CLI keeps the picks whose `@Name` is still in the text, adds any other `@Name` that only one bot answers to, and stores the ids on the message (`Body::Text.mentions`). A bot reads the first `@Name` of each as `@Name (id bot-1a2b3c4d)`, so a name two bots share still says which one the user meant.
- **Attachments:** a user message can carry files. Their bytes travel as `file` blobs; before a turn the Runner fetches any it lacks (`files::prefetch`), copies each into the bot's workspace at `attachments/<attachment id>/<name>` (a stable path, so every turn names the same file), and the transcript's user message gets a line per file naming that path, plus the pixels as an image content part for an image up to 5 MB, so a vision-capable model sees it and any model can open it with its tools.
- **Group:** a room exchange (`run_room`). The Device that received the user's message offers every member a turn, one at a time, in chat order with the members the message mentions first. A member's turn is a `room_turn` Job with the whole transcript plus an ephemeral cue (round number, how many messages are new to it); the member replies to the group or answers `PASS`, which never becomes a bubble. A round with at least one reply is followed by another, offered only to members that have heard something new; the exchange ends after a silent round or after the fourth round, which is marked winding down so members add only what is essential. A new user message waits for the current member's turn, including its command, to settle; the old room then yields and a replacement room starts with the new mentions first. **Stop** cancels immediately. A member on another Runner gets its job through the relay and reports back with a `job_result` blob (`sent`, `pass`, `error`) sealed to the requesting Device; the room waits up to five minutes for it and skips an offline Runner.
- **Bot to bot:** `message_bot` from any chat to a bot outside it; the message lands in the target's DM. Each hop carries `hops`; after eight bot-to-bot hops without a user message the tool refuses, so two bots cannot loop. Members of one group talk to each other in the group.

## Routines

A routine is a task a bot runs on a schedule in its direct chat with the user, after Grok Bot's routines: a morning brief, an hourly check, a weekly report. The bot owns its routines: the user asks for one in chat and the bot sets it up with the `routines` tool (a name, a schedule, the prompt, written as an instruction to itself, and a check when the routine watches for something), and edits, pauses, resumes, runs, or deletes it the same way. The system prompt of every turn explains routines and lists the bot's own with each one's next run, or that it checks first.

The roster also carries Auto-review (see [Plugins](plugins.md#plugins)). Routines live in the roster (`Routine { id, bot_id, name, prompt, schedule, is_enabled, enabled_at, last_run_at?, last_outcome?, paused_reason?, check?, created_at }`), so every paired Device lists them and can pause, resume, run, or delete one (`routines.create` / `routines.update` / `routines.delete` / `routines.run`, and `routines.describe` to read a schedule back). The bot's Runner runs them (`crates/cli/src/routines.rs`): every half minute it starts the routines of its bots whose next run is due, or their checks, and starts none while a run or check of the routine is going on.

A schedule (`crates/cli/src/schedule.rs`) is `every 30m`, `every 2h`, `every 1d`, or five cron fields read in the Runner's local time (`0 9 * * 1-5`), never more often than every five minutes. An interval counts from the last run, or from when the routine was created or resumed; a cron fires at the next matching minute after that. The CLI says a schedule in words on the wire (`schedule_text`: "Weekdays at 9:00 AM", "Every 2 hours", "On the 1st of every month at 8:30 AM", else "Cron 5 4 * * 1-3") and gives `next_run_at` and `is_running` beside every routine.

A run is a `routine` Job in the bot's DM. It opens with a "Routine · Name" marker (a system notice carrying the routine id), then the turn runs with the routine's prompt as the task and a system prompt that says nobody is typing: the bot does the work, replies with what the user should know, or answers `PASS`, which leaves only the marker. Later turns rebuild the marker as `[Routine "Name" ran on its schedule. Task: …]`, so the bot can talk about a run afterwards; the daily log names the routine as the turn's source. `job.started` / `job.finished` carry `routine_id`, so the apps show the routine as running and the bot at work. A run's outcome (`sent`, `pass`, `error`) is kept on the routine. Run Now from a Device that is not the Runner seals the job to the Runner like any turn.

**Checks.** A routine that watches for something (an inbox, a repository, a feed, a page) carries a `check`: JavaScript the Runner runs at each due time before the bot does, without a model, so an interval with nothing new runs no turn; only the small-model calls a check makes with `models.ask()` cost anything, in the chat's spending. The bot writes it with the `routines` tool (`check`, at most 8,000 characters; `""` on edit removes it). It runs as a codemode script (see [Codemode](plugins.md#codemode)) in a sandbox of its own (`routines::run_check`, five minutes at most) whose calls only read: the bot's `read`, `grep`, `find`, and `ls`, and the plugin tools whose manifest lists them as read-only or whose server marks them `readOnlyHint`, the same test Auto-review applies. `CheckRunner` refuses any other call, which ends the check. `store()` and `load()` reach the values the bot's scripts keep in its DM, so a check keeps what it has seen and returns only what is new, and `models.ask()` can screen items on the small model. What the check returns starts the run: a `routine` Job whose `check` carries it as text (at most 4,000 characters), which the turn reads after the transcript, marked as data from its tools and not instructions; Auto-review reads the routine's task, never what the check found. A check that returns nothing, `null`, `false`, or an empty string, list, or object ends there, with no marker, no turn, and no roster write. The Runner keeps the time each check ran in memory (`routines::Checks`), the schedule counts from it, and the local app hears the routines again (`roster.changed`, sent and not uploaded) so it shows the next check. A check that fails starts the run with its error, so the bot does the task without it and fixes or removes the check. Saving a check runs it once, in the turn that saved it, and hands the bot the result, so a broken check shows at once and its first run records what is already there. Run Now runs the check first, then the turn whatever it found. One check of a routine runs at a time: a check on save or Run Now waits for one already running (`routines::check_now`). A due check that finds something while a run started by hand waits for it still starts its own run, after that one, since the waiting run's check no longer sees what the first one stored as seen. The roster carries `check` so every Device shows it, and only the Runner writes it: a roster from a build without the field keeps the Runner's check (`routines::keep_checks`) and goes up again with it. Other Devices never hear of the checks that found nothing, so they show a past-due routine with a check as due at its next schedule time.

When the user has not written in any chat for seven days, due routines are paused instead of run (`paused_reason: away`) with a notice in the bot's DM, as Grok Bot does, so nothing keeps spending on results nobody reads; the switch turns them back on.

The macOS app's DM inspector has a Routines section: a row per routine (clock, pause, or running icon; the schedule in words and the next run, or the next check; a switch that pauses or resumes) that opens a sheet with the state, schedule, next run or check and last run, the prompt, the check in a monospaced block when there is one, and Run Now, Pause/Resume, Edit in Chat (which puts `Edit my routine "Name": ` in the composer), and Delete. With none, the section says routines are set up by asking the bot. The Windows and Linux app's sheet is the same. The phone's chat details show the same list with a switch; a tap offers Run Now and Delete.

## Memory

Every bot keeps its own long-term memory on its Runner, in Grok Bot's shape of a curated profile over append-only logs, as plain markdown under `~/.lorca/workspaces/<bot id>/` (keyed by id, so a rename or a changed working directory never moves it; `crates/cli/src/memory.rs`):

- `MEMORY.md` is the curated memory. Its first 200 lines or 24 KB, whichever cuts first, open in every turn's system prompt; past that nothing loads, and the prompt tells the bot how much is cut off and asks it to consolidate. The bot writes it only through `memory_update`, one dated entry per call (`- 2026-09-17 · from your chat with the user · the user prefers short replies`), never a whole-file write, so two of its turns cannot clobber each other: `append` adds a fact (an exact duplicate is refused), `replace` rewrites one unique passage, `supersede` strikes the old entry through with a date and adds the new fact so the file shows what changed, `remove` deletes a passage.
- `memory/<topic>.md` files hold longer notes the bot reads with `read` when it needs them; the prompt lists their names.
- `memory/log/YYYY-MM-DD.md` is the bot's diary: what happened, not what is true. The Runner appends one line per finished turn (`- 09:05 · in group "Standup" · said "Sent the three flagged invoices…" · used bash, edit`), and the bot adds events with `memory_log`. Logs are never loaded into a prompt; `recall` finds them.

Every write is atomic and goes through a credential scrubber first (API keys, AWS and GitHub tokens, bearer tokens, JWTs, private key blocks, `password: …` values become `«redacted N chars»`), since memory is bot-authored as often as person-authored.

Two things keep a bot's chats from being islands, after OpenMausBot. Every turn carries a **recent-work brief**, a bracketed note after the transcript: the newest thing the bot said in each of its *other* chats over the last two days, at most ten lines and about 350 tokens, newest first (`- today 09:05 · group "Standup" · you said: "…"`), so a bot in a group knows what it did in its DM an hour ago without the transcript. It stays out of the system prompt, which it would change each time the bot speaks elsewhere, costing the chat its prompt cache. And `recall` searches the memory files and every chat the bot is in by words and by time, naming the chat and the speaker of each hit.

Before a compaction summarizes part of a chat, a silent **memory flush** turn runs over the messages about to be cut, with a prompt to save what is durable and not yet in memory, and only `memory_update` and `memory_log` run; nothing it says reaches the chat, a failure or a two-minute timeout is logged and the compaction goes ahead (`LORCA_MEMORY_FLUSH=0` turns it off). A compaction of a turn's own context (before the turn, or between its model calls) asks the flush as that turn's next request: the turn's system prompt, tools, and every message, then the prompt naming the message the kept part starts with, so the provider's prompt cache serves the context, and the hooks refuse every tool but the two. Any other compaction asks it as a request of its own, with only those two tools, over the newest of the history one request may carry. This is what keeps a fact from being lost because it was only ever said in conversation.

The macOS app's DM inspector shows the bot's memory (`bots.memory`): the index against its load budget, an editor (`bots.memory.write`, refused with the bot's current text when the file changed under the editor, then Reload or Overwrite), and a Show button for the folder. For a bot on another Runner the CLI asks that Runner through the relay (a `request` / `response` pair, see [Protocols](protocols.md)), so the same rows read and edit it; only the folder cannot be opened, and an offline Runner shows as such with a Retry. The phone shows no memory yet.
