# Terminal sessions

`lorca_agent::tools::bash_session` runs each `bash` call's command in a terminal of its own on macOS and Linux, and `crates/cli/src/shell.rs` keeps the sessions on the Runner: which chat and bot each belongs to, the card that shows it, and what ends it. The tools that start and read them are in [Tools](tools.md), and so is Auto-review of a command and of what is typed into one.

## The terminal

pi's bash runs a command on pipes with nothing on stdin and fails fast, because the person is at the terminal and answers there. A Lorca bot's Runner is often a computer nobody is sitting at, so a command gets a pseudo-terminal of its own: `openpty`, then `setsid` and `TIOCSCTTY` in the child, so `/dev/tty` is that terminal and `sudo`, `ssh`, `gpg`, `getpass`, and `[Y/n]` questions ask there, never on a terminal `lorca serve` was started from. The shell leads its own session and process group, which is what stopping it kills. The terminal is 80×24 with `TERM=xterm-256color` and `PAGER` and `GIT_PAGER` set to `cat`, and echo is off, so what is typed (a `y`, a password) never comes back as output; a program that echoes for itself (readline, curses) still does, and prompts print as usual. The child ignores SIGHUP, so a job the command leaves behind with `&` (`server > log 2>&1 &`) outlives the shell as under `nohup`, though no session follows it from then on: a bot starts what should keep running with `background` instead (below). A reader drains the terminal into the session's last 200 KB whether or not anyone reads it, so a command never blocks on a full terminal; the raw bytes also go to a temp file once they pass 50 KB, up to 64 MB. What the model reads and what a card stores is text (`tools::sanitize`, after pi's `stripAnsi` and `sanitizeBinaryOutput`): escape sequences go, a carriage return redraws its line, a backspace takes back a character, and other control characters go. The temp file keeps the raw bytes.

## A call that returns while its command runs

A call returns when the command exits, as on pipes, or while it still runs: 2 s after it stops on an open line that reads like a question (`password`, `passphrase`, `[Y/n]`, `(yes/no`, `Enter `, `Press `, `PIN`, `token`, `code`, `OTP`, or a line ending in `?`, `:`, `>`, `)`, `]`, `$`, or `#`), or after 20 s with no output at all (`WAITING_AFTER`), which is also how a command blocked on something outside its terminal, such as a macOS permission dialog, surfaces instead of holding the turn. That result is the output so far, a note on where the command stands, and the session id; `bash_input` and `bash_output` wait the same way, and `timeout` still kills the command when it runs that long. At a question the note quotes it. Silence is not a question: a quiet command may be working, or asking where the terminal never shows it, since a question printed into a pipe or a file (`| tail`, `> log`) stays there, so the note says both. When the command has also put its terminal in raw mode, as a menu or a yes/no choice does (`BashSession::reads_keys`: the master reads the terminal's modes on macOS and Linux, pipe or not), the note says it is probably waiting for a key at a question it printed out of sight, to stop it and run it with its non-interactive options, and how to press Enter and the arrow keys. A question counts until something is typed after it: with echo off, an answered question stays the last line until the command prints again. The session stays on the Runner after the turn ends.

## Background commands

`bash { …, background: true }` is for what is meant to keep running: a dev server, a watcher, a long build. The command gets the same review, card, and session as any other, and its call waits at most 2 s (`BACKGROUND_SETTLE`), so a command that fails at once (a port in use, a typo) or asks at once still reads as usual, and one that prints where it listens says so. Past that, the call returns with the output so far, the session id, and a note that the command runs in the background, to read with `bash_output` and stop with `bash_input` `\u0003`; the session is marked `background` (`BashSession::background`), and the note says the same at every later read, whether the command is quiet or has put its terminal in raw mode for keys of its own, as a dev server's shortcuts do. Only `bash` on a terminal takes the parameter, so it is offered on macOS and Linux. The system prompt tells the bot to start such commands this way, never with `&` or `nohup`.

The user can send a command there too, while the bot's call still waits on it: Run in Background (below) asks `bash.background { chat_id, message_id }`, on this Runner or sealed to it as a `request`, as `bash.stop` is. `BashSession::send_to_background` marks the session, and the call waiting on it returns at once (`Stop::Backgrounded`) with the output so far and a note that the user sent the command to the background and the bot should go on with its work; the card's `background` says so on every Device. From then on the command is a background command like any other. A command that already ended answers that it has. Send now under a message the bot's turn holds does the same for every command running in the chat before it interrupts the turn's step (see [Agent loop](runtime.md#agent-loop)); a call cancelled at that moment still reads as sent to the background, and its command runs on.

The Runner treats one differently from a command its call happened to leave running:

- **Stop leaves it running.** Stop in the chat (`shell::Sessions::stop_chat`, from `runtime::cancel_chat` and a cancelled turn) ends every other command there; a background one ends from its card, from Running tasks, or by the bot. A cancelled `bash_input` or `bash_output` call on it leaves it running too, while the `bash` call that starts one takes it down when cancelled within those 2 s.
- **Its card stays out of the chat** unless it asks. At the end of a turn, `hand_over` hands over a background command (any bot's in the chat) only while it sits at a question; one that comes to a question later is handed over once no turn runs in the chat (`Sessions::hand_over_asking`, which finds the chat lock free, and looks again every 5 s while a turn holds it), since a turn may still answer it. Otherwise it shows in Running tasks.
- **The idle limit spares it** unless it sits at a question: a server with no traffic prints nothing for hours.
- **The count limit stops it last:** when a ninth command starts, the oldest command that is not in the background stops, and a background one only when every other running command is one; the command starting never stops itself.

It wakes its bot when it ends by itself, as below, so a bot hears that its server crashed or its build finished.

## The command's card

Every `bash` call has one card, the call's own row, from start to finish: `Body::Tool.run { session_id?, command, state, prompt?, output?, outcome?, device?, reason?, rule?, decision? }`. The row goes up with the card as the call starts (`running`), so it takes its place in the chat before anything the call leads to; `shell::Sessions` notes the call (`begin`), and the card follows it: `checking` while Auto-review judges the command, `asking` while it waits for the user's answer (below), then `running` or `waiting` once a session runs it (`insert`, as the command spawns), with its last 20 lines of output: `waiting` only at a question the user can read, whose line has held still for 2 s (`PROMPT_QUIET`) or has been followed by 20 s of silence, and `running` while it prints or is merely quiet, and at the end `exited`, `failed` (a nonzero code), `stopped`, `denied`, `expired`, or `dismissed` (the user wrote in the chat instead of answering), with how it ended, which a later turn reads in the rebuilt call when the call had left the command running. A call that returns (`call_ended`) leaves a running command's card to its session; a call no session ran, because it was not allowed or ran on pipes, ends its card from its result. The call's result and its card go up in one write, under the same lock as the session's own updates, so no Device sees the call returned beside a card from before. The apps show the card only while the command needs the user: while Auto-review asks, and once the bot has handed the running command over (`handed_over`), until it ends. It hands it over when its turn ends with the command still running (`Sessions::hand_over`, from the turn's `finish`), or when it waits on the command (`bash_output` with a wait) while the command sits at a question (`Sessions::bot_waits`), and a card stays handed over. Until then the bot deals with it: a question it answers itself with `bash_input`, or a command it waits out, reads only as the working row's activity, and one that ended leaves the chat, so the transcript does not shift for the commands a turn runs. The card keeps its first place in the relay's log however often it changes (`Slot::first_and_latest`), so it sits in the same place on every Device. The bot reaches only the sessions it started in the chat it runs in; the system prompt tells it that `/dev/tty` is the command's own terminal, to run scaffolders and installers with their non-interactive options since a question printed into a pipe or a file never shows, to answer what it knows with `bash_input`, and to send the user to the command's card for a password, a passphrase, or a one-time code rather than asking for it in a message. A command its call left running that ends by itself (exits, or dies on a signal) wakes its bot: once any turn in the chat is done, and unless that turn read the end itself with `bash_input` or `bash_output`, the Runner starts a `command` job (`shell::wake_job`, `runtime::command_job`), whose turn opens with how the command ended and its last lines (`turns::command_cue`), so the bot hears the result of an answer the user typed and carries on. A Stop, the idle limit, or Lorca quitting wakes nobody.

## Answering and stopping

The user answers from any Device: `bash.stdin { chat_id, message_id, text }` writes the text and a Return to the terminal, on this Runner or sealed to it as a `request`, and nothing keeps it: not the row, the message store, a log, or a push, and with echo off, not the output the bot reads. `bash.stop` ends the command, from its card or from Running tasks.

Stop in the chat (except for a background command), deleting the chat or its bot, quitting Lorca (SIGTERM, SIGINT, SIGHUP, or the app that started the CLI going away), 30 minutes without output or input (`IDLE_LIMIT`; a background command only at a question), and a ninth command starting while eight run (`MAX_SESSIONS`; the oldest stops, a background one last) each kill the session's process group, close its terminal, and say so on its card. A card that a Lorca which quit left open (checking, asking, running, or waiting) reads "Stopped when Lorca quit" once it starts again.

## Running tasks

Running tasks are the commands a chat's bots have running in their terminals, handed over or not: rows whose card is `running` or `waiting` with a `session_id`. A Device counts one once it has run there for two seconds (`AppStore.taskDelay` on the Mac, `TASK_DELAY_MS` on the phone), so a quick `ls` never shows; one that was already running when the Device heard of it counts at once. While a chat has any, a terminal button sits in the chat's toolbar and opens them in a list: each command's description, who runs it (in a group), and how long it has run. On the Mac and on Windows and Linux each entry also holds the command's first line in a code block that opens the whole command, its last lines in a block that grows to ten lines and then scrolls, and Stop; on the phone each is a row that slides the command's details in, with Stop Command. One that ends while the list is open stays, reading Finished, Failed, or Stopped, until the list closes. So a command the bot is still dealing with, which shows only as the working row's activity, can be read and stopped without stopping the turn: the bot's call returns with the command stopped, and its turn goes on.

While the bot's call still waits on a command (the row's `is_running`) and the command is not in the background, Run in Background sits before Stop (`runsInForeground` in each app), and on the phone above Stop Command; it sends the command there (above), and the bot's turn goes on with the command running. The Mac's Chat menu has Run Command in Background (⌃B, also in the command palette) for every such command in the chat; it is disabled otherwise, so ⌃B stays the composer's. The Windows and Linux app has the same menu item and palette entry without a shortcut, since Ctrl+B toggles the sidebar there.
