# Protocols

## App ↔ CLI (local WS)

[Durable tasks](tasks.md) add `tasks.list`, `tasks.get`, `tasks.create`, `tasks.update`, and `tasks.run`. Bootstrap carries `tasks`, and `tasks.changed { task }` carries each persisted change. Mutations carry `request_id`; edits and runs also require `expected_revision`. A stale revision is an error. Remote task writes route to the task's fixed authority Runner through sealed `tasks.*` requests; `tasks.validate_run` and `tasks.finish_run` validate and settle the assigned Runner's run.

JSON on `ws://127.0.0.1:4862/ws`. Requests are `{ id, method, params }` and get `{ id, result }` or `{ id, error: { message } }`; events are `{ event, data }`.

Only local programs get in (`ws.rs`). A browser lets any page open a websocket to 127.0.0.1 and leaves the check to the server, so every route answers `403` to a request that carries an `Origin`, which a page's always does and the clients below never send, or whose `Host` is not `127.0.0.1:<port>` or `localhost:<port>`, as a DNS-rebound page's is not. The upgrade also takes `Authorization: Bearer <token>`, compared in constant time, or answers `401`. The token is `serve-token` in the CLI's data directory: `lorca serve` makes it once it holds the port and keeps it for later starts. Every client reads it there on each connection, so a CLI it starts and one it finds running (`lorca service`, another app) both take it: the macOS app (`CLIClient`) and the Windows and Linux app (`client.go`) from `LORCA_HOME` or the build's default folder, the one they start the CLI with, and `lorca`'s commands that go through a running serve (`serve_call`) from their own, saying so when the serve on the port keeps another folder. `/` answers `lorca`, for a check that the port answers, and nothing else.

CLI → App: `attention.changed` (the decrypted attention list), `budgets.changed` (every Runner's limits, what its work used, and what stopped), `reviews.changed` (an item of the encrypted local review projection and the change: [Review queue](review-queue.md)), `snapshot` (what `roster.changed` carries, with each chat's newest messages, the relay's state, the turns in flight, and `budgets`), `roster.changed` (devices, with `unknown: true` on a machine that never sent its `machine` blob, bots, chats, routines, `providers`, the account's credentials as statuses: `kind`, `is_connected`, a masked `detail`, `base_url?`, and for a custom provider, listed after the built-in ones in the order they were added, its `name`, `api`, and `models` (`id`, `name?`, `context_window?`, `max_output?`, `images?`, and the thinking `levels` it takes, which the pickers offer for it as they do the catalog's), and `models`, the model catalog's `provider`, `id`, `name`, thinking `levels`, and `decides` (a decision model) for every model in its order, which the pickers offer and a newer catalog replaces), `message.added` / `message.updated` / `message.removed`, `chat.removed`, `job.started` / `job.finished` (with `routine_id` for a routine's run) / `job.retry` / `job.thinking`, `chat.usage`, `relay.status`, `provider.auth` (the OAuth URL a phone opens in its in-app browser), `plugin.auth` / `plugin.auth.done` (a plugin's sign-in page for a phone's in-app browser, and that it can close), `pair.completed`, `identity.changed`.

Routines take an IANA `timezone` and a `missed_run_policy` (`coalesce` or `skip`) on `routines.create` and `routines.update`, and `routines.describe { schedule, timezone?, missed_run_policy? }` checks both. A routine on the wire carries its `health` and a derived `state` ([Routines](routines.md)). `device.service_status { id? }` answers `{ installed, running }` for this CLI's service, or another Runner's through the sealed `service.status` request.

`handoffs.list/get/follow_up/cancel/report` inspect and manage durable delegated work through the same local API. Their request and report shapes, source-chat destination and per-attempt job comparison are described in [Handoffs](handoffs.md#inspection-follow-up-and-recovery).

The app may choose ids (`bots.create.id`, `chats.create.id`, `chats.send.message_id`) so its optimistic rows match the CLI’s events.

The snapshot and `roster.changed` list the user's skills without their bodies (`playbooks`); `playbooks.get` / `playbooks.save` / `playbooks.remove` / `playbooks.draft` / `playbooks.export` read and change one. Edits and removal carry the displayed revision and content hash; a draft carries the picked source-message ids and is saved inactive. The [Playbooks API](playbooks.md#app-and-api) defines the content and results. Each skill syncs as an account-encrypted `playbook` blob in a latest-only slot of its own, grouped under its group chat or its bot's DM; the roster carries none. A phone's `playbooks.draft` is a sealed request to the bot's Runner.

[Workflow feedback](feedback.md) adds `feedback.list` / `feedback.record` / `feedback.propose` / `feedback.accept` / `feedback.reject` / `feedback.rollback` / `feedback.settings` / `feedback.exclude` / `feedback.review`, each answered by the bot's Runner, and `feedback.changed { bot_id, pending_count }` when a bot's feedback changes there; the app then reads the list again.

`outputs.publish { chat_id, bot_id, name, path? | url?, mime?, task_id?, replaces?, evidence? }` publishes on the producing Runner and returns `{ message, task_evidence }`. `outputs.list { chat_id, task_id? }` returns `{ outputs: [Message] }`, every version this Device has synced. Each output is a text/attachment message with additive `output` provenance, version and evidence metadata, delivered through the existing snapshots, message events and encrypted chat blobs. File bytes use the account-encrypted `file` transport. `files.path { attachment, named?: true }` fetches a file on any paired Device; `named` preserves its filename and extension for native handlers. See [Outputs and evidence](outputs.md) for fields, references and version rules.

What the apps get of a chat is a view of the message rows in `lorca.sqlite3` (`LocalStore::page`, then `Message::for_app`). A snapshot queries each chat's newest 60 messages and sets `has_more` when older rows remain; `chats.messages { chat_id, before?, limit? }` queries the page before a message id, oldest first, with `has_more`. The macOS transcript asks for it as it scrolls within reach of the first row and holds what is on screen in place; the phone asks from FlashList's `onStartReached`. Both keep pages they loaded when a later snapshot arrives. A `tool` message reaches the apps, in snapshots, pages, and `message.*` events, with its name, summary, running state, the first 400 characters of its detail, and a command's `terminal`, and without its arguments and result: the apps show none of that, and a file read or a command's output runs to hundreds of kilobytes. Permission cards likewise omit their reviewed argument payload. A Runner's database keeps the complete rows for later model context and permission handling. The no-Runner mobile core persists only `Message::for_app()` for these rows, so a phone never stores the full arguments or tool result it cannot use.

## CLI ↔ relay

Shared project context uses `projects.get` / `projects.save` / `projects.refresh` / `projects.asset` / `projects.asset_path` on the local API and `projects.changed` events. [Shared project context](project-context.md#local-api) defines their fields. The Mac and the Windows and Linux app call them for a group's Project section. Independent encrypted `project_context` blobs carry `{ chat_id, entry }`, one immutable revision per slot, grouped by the existing chat id. First sync pulls these revisions before transcript pages, so discovery includes briefs older than the initial message page.

Protocol **3** accepts the opaque `task`, `handoff`, `review`, `attention`, `project_context`, `playbook`, and `event` blob kinds alongside the existing kinds. Task records use account-DEK encryption and independent latest-only slots, outside roster snapshots and chat groups. Task sync and first sync include that kind; replicas advance by revision. `event` joins the sealed-to-machine kinds and their consume/retention lifecycle. The subject modules own the meanings and authority of the other encrypted kinds.

- Every request, the sync socket's upgrade included, carries `Lorca-Protocol: <n>`, the relay protocol the build speaks (`relay::PROTOCOL` in the CLI; the relay's own is in `/v1/health`), and a `User-Agent` of `lorca/<version> (<os>)`. The relay's client is its own `reqwest` client, so neither reaches a provider. The number goes up when Devices come to rely on something new from the relay or the relay stops serving something old; 1 is group paging and `DELETE /v1/identity`, 2 is `POST /v1/machines`, which a Device without the identity key pairs with. A relay started with `--min-protocol` answers a lower number (none is 0) with `426` on every `/v1` route but the healthcheck. The CLI then sets `relay_update_required` (in `hello`, the snapshot, and `relay.status`), waits fifteen minutes between tries instead of backing off from two seconds, and clears it when a session connects or the relay URL changes. The macOS app says so once per launch in a sheet with Check for Updates, and its Device pane reads "update Lorca to sync"; the phone shows "Update Lorca to sync" in the chat list's title slot and in Settings.
- Machine bearer for blobs, the sync socket, the machine list, and a paired machine attesting another; identity signature for registering the identity and for the machines an identity device attests.
- PUT/GET non-file blobs as base64url ciphertext in JSON, and PUT/GET files as binary ciphertext. `roster` is a whole-roster snapshot of bots, chats, and routines (latest wins); `chat` is one upsert or removal of a message; `machine` is a Device’s metadata, the turns in flight on it, and its [limits](budgets.md#storage-protocol-and-resuming) and what its work used; `credentials` is the account's provider credentials; `review` is one Runner-owned durable review record; `key` is the DEK sealed to the content key.
- Handoffs: `kind=handoff` encrypted with the account DEK, with independent request, Runner-report and requester-cancellation slots per attempt. Each update includes the request, so results can merge before the request’s own blob. `Job.handoff` binds a turn to the contract or to the requesting bot’s result continuation ([Handoffs](handoffs.md)).
- Jobs: `kind=job` with `recipient_machine_pubkey`, sealed to that machine’s box key, deleted by the Runner after the turn.
- Events: `kind=event` with `recipient_machine_pubkey` and no slot or group, a gateway's signed envelope sealed to the Runner's box key. The Runner stores it in its encrypted inbox before its sync cursor moves past it, then deletes the blob ([Event triggers](event-triggers.md#relay-transport)).
- Questions: `kind=request` sealed to one Runner (`crates/cli/src/requests.rs`: `{ id, verb, requested_by, body }`), answered with a `kind=response` sealed to the Device that asked (`{ request_id, body, error? }`); each side deletes the blob it consumed, and the asker gives up after 20 s, or 75 s for the start of a plugin sign-in, whose discovery and registration the Runner cuts off at 45 s, or 150 s for `mcp.reconnect`, which answers once a server has connected or failed. The `feedback.*` verbs read, record, review and decide workflow revisions on the assigned Runner through the same sealed request/response path. The other verbs are `memory.read` and `memory.write`, so a bot's memory can be shown and edited from a Device that is not its Runner; `budgets.*` and `connector_limits.*`, so a bot's limits and call limits are set from any Device; `plugins.install` / `plugins.rename` / `plugins.uninstall` / `plugins.variables` / `plugins.connect` / `plugins.sign_out` / `plugins.detail`, so plugins on a Runner are managed from any Device, and `plugins.sign_in.finish` / `plugins.sign_in.cancel`, with which the Device that asked for a sign-in (its `redirect_uri` on `plugins.connect` or `permission.answer`) hands back where its browser landed (see Sign-in in [Codemode and Plugins](plugins.md#plugins)); the `mcp.*` methods but `mcp.parse`, so a Runner's own MCP servers are managed from any Device; `permissions.catalog`, so a bot's Access sheet lists its Runner's plugins and their tools; `permission.answer`, so a permission card is answered from any Device; `bash.stdin`, `bash.stop`, and `bash.background`, so a command a bot runs is answered, stopped, or sent to the background from any Device; `chats.send_now`, so a message the bot's turn holds is read at once from any Device; the `events.*` methods but `events.forward`, so a Runner's event subscriptions are managed from any Device; `service.status`, so the Devices pane shows whether `lorca service` runs on a Runner; and `update.install` and `update.auto`, so a self-updating Runner's CLI installs its latest release, or turns its automatic updates on or off, from any Device. A request is refused up front when the Runner is unknown or offline.
- Slots: a `review` (hashed `review/<id>` slot), `roster`, `chat`, `machine`, or `credentials` blob goes up with a `slot` (`Slot` in `app.rs`, `ChatBlob::slot`), and the relay deletes the blobs of that slot it supersedes, so the log holds a message once and not once per streamed chunk. A message's versions and its removal share the slot named by the message id. An upsert sets `keep_first`, which spares the slot's oldest blob: its seq holds the message's place in the log, so a Device that replays from the start gets the transcript in order, first the early version and later the final one. A tool row is the exception: its running version goes up without arguments or results, for the status line on other Devices, and the finished row supersedes it outright, so the relay keeps one version of each call, at the finished row's place. A row that shows a terminal keeps its first place as a message does, since the transcript shows it. A removal supersedes every version. The SQLite outbox does the same before upload: a queued version updates its row without moving its queue position. `App::upsert_message` holds one lock from the SQLite write that gives a message its `position` to the enqueue, so the sending Device's transcript order is the log's order.
- Groups: a `chat` blob and a message's `file` blob go up with `group`, the chat's id (`ChatBlob::group`). Deleting a chat queues its id in `State::group_deletes`, drops what the outbox still held for it, and the sync cycle calls `DELETE /v1/groups/{group}` until it lands: the relay deletes the group's rows and the attachments' objects in one transaction, gives the bytes back to the quota, and remembers the group in `deleted_groups`, so a blob that names it later (a Runner finishing a turn in a chat another Device deleted) gets `409` and the outbox drops it. The other Devices learn of the deletion from the roster. A bot's avatar is a `file` with no group: the Device that replaces or removes it, or deletes its bot, removes its local copy and queues the attachment id in `State::blob_deletes`, and the sync cycle calls `DELETE /v1/blobs/{id}` until it lands, which removes the row and the object.
- `GET /v1/groups/{group}/blobs?before=<place>&limit=` reads a chat backwards a message at a time: `{ slots: [{ place, blobs }], has_more }`, oldest first, where a slot is a message (its first and latest blob, or its removal) or the chat's read mark, and `place` is the slot's lowest seq. A message other than a tool row keeps the place its first version took however late its last one landed, so pages read backwards give the transcript in the log's order. A page is up to 500 slots and 8 MiB, and leaves out the group's `file` blobs. A relay without the route answers `404`, and the Device replays the log.
- `GET /v1/blobs?since=` answers a page of up to 8 MiB of ciphertext (and at least one blob); a Device asks again from the last seq it got. A Device at seq 0 first takes `roster,machine` alone, so chats have their names and bots before their messages land.
- Every Device keeps `last_seq` and its outbox in `lorca.sqlite3`; queued ciphertext is a binary SQLite BLOB. Uploads retry until the relay accepts them. Attachment transfers have a ten-minute request timeout.

```
App_B → CLI_B
CLI_B encrypts user message + job-for-A → relay
CLI_A fetches envelopes for A, decrypts, runs loop, encrypts reply
CLI_B fetches chat blobs, decrypts → App_B
```
