# Protocols

## App ↔ CLI (local WS)

JSON on `ws://127.0.0.1:4862/ws`. Requests are `{ id, method, params }` and get `{ id, result }` or `{ id, error: { message } }`; events are `{ event, data }`.

App → CLI: `hello`, `bootstrap`, `identity.create`, `identity.restore`, `pair.start` / `pair.status` / `pair.cancel` / `pair.accept`, `sync.account` (the account's `providers`, answered once the sync loop has pulled the account this Device holds, its roster, Devices, and credentials, or after 30 s: onboarding asks after a restore or a pair), `config.set`, `bots.create` (`runner_id` may be another Device; it must be a Runner; `template_id` and `greeting` add a marketplace bot) / `bots.update` / `bots.delete`, `chats.create` / `chats.dm` / `chats.send` / `chats.stop` / `chats.delete` / `chats.rename` / `chats.pin` / `chats.add_bot` / `chats.remove_bot` / `chats.mark_read` / `chats.messages` / `chats.search` / `chats.compact`, `routines.create` / `routines.update` / `routines.delete` / `routines.run` / `routines.describe`, `marketplace`, `plugins.install` / `plugins.uninstall` / `plugins.set_variables` / `plugins.connect` / `plugins.detail` (`runner_id` names the Runner) / `plugins.auth.cancel` (a phone's sign-in page closed) / `auto_review.set` / `chats.permission`, `bash.stdin` / `bash.stop` (a command's row, on its Runner from any Device), `bots.memory` / `bots.memory.write` (this Runner's bots), `providers.connect_deepseek` / `providers.connect_anthropic` / `providers.connect_opencode` / `providers.connect_opencode_go` / `providers.connect_chatgpt` / `providers.connect_grok` / `providers.connect_custom` (adds a custom provider, or saves the one `kind` names, and answers its `kind`) / `providers.list_models` (a custom provider's server's chat models, before saving) / `providers.api_key` (one saved key and base URL, for an editor) / `providers.auth.cancel` / `providers.disconnect` (the account's credentials; a custom provider is deleted), `ui.watching` (the chat on screen in the desktop app), `push.register` / `push.unregister` (a phone's device token).

CLI → App: `snapshot` (what `roster.changed` carries, with each chat's newest messages, the relay's state, the turns in flight, and `models`, the model catalog's `provider`, `id`, `name`, and thinking `levels` for every model in its order, which the pickers offer), `roster.changed` (devices, bots, chats, routines, and `providers`, the account's credentials as statuses: `kind`, `is_connected`, a masked `detail`, `base_url?`, and for a custom provider, listed after the built-in ones in the order they were added, its `name`, `api`, and `models` (`id`, `name?`, `context_window?`, `max_output?`, `images?`, and the thinking `levels` it takes, which the pickers offer for it as they do the catalog's)), `message.added` / `message.updated` / `message.removed`, `chat.removed`, `job.started` / `job.finished` (with `routine_id` for a routine's run) / `job.retry` / `job.thinking`, `chat.usage`, `relay.status`, `provider.auth` (the OAuth URL a phone opens in its in-app browser), `plugin.auth` / `plugin.auth.done` (a plugin's sign-in page for a phone's in-app browser, and that it can close), `pair.completed`, `identity.changed`.

The app may choose ids (`bots.create.id`, `chats.create.id`, `chats.send.message_id`) so its optimistic rows match the CLI’s events.

What the apps get of a chat is a view of the message rows in `lorca.sqlite3` (`LocalStore::page`, then `Message::for_app`). A snapshot queries each chat's newest 60 messages and sets `has_more` when older rows remain; `chats.messages { chat_id, before?, limit? }` queries the page before a message id, oldest first, with `has_more`. The macOS transcript asks for it as it scrolls within reach of the first row and holds what is on screen in place; the phone asks from FlashList's `onStartReached`. Both keep pages they loaded when a later snapshot arrives. A `tool` message reaches the apps, in snapshots, pages, and `message.*` events, with its name, summary, running state, the first 400 characters of its detail, and a command's `terminal`, and without its arguments and result: the apps show none of that, and a file read or a command's output runs to hundreds of kilobytes. Permission cards likewise omit their reviewed argument payload. A Runner's database keeps the complete rows for later model context and permission handling. The no-Runner mobile core persists only `Message::for_app()` for these rows, so a phone never stores the full arguments or tool result it cannot use.

## CLI ↔ relay

- Every request, the sync socket's upgrade included, carries `Lorca-Protocol: <n>`, the relay protocol the build speaks (`relay::PROTOCOL` in the CLI; the relay's own is in `/v1/health`), and a `User-Agent` of `lorca/<version> (<os>)`. The relay's client is its own `reqwest` client, so neither reaches a provider. The number goes up when Devices come to rely on something new from the relay or the relay stops serving something old; 1 is group paging and `DELETE /v1/identity`. A relay started with `--min-protocol` answers a lower number (none is 0) with `426` on every `/v1` route but the healthcheck. The CLI then sets `relay_update_required` (in `hello`, the snapshot, and `relay.status`), waits fifteen minutes between tries instead of backing off from two seconds, and clears it when a session connects or the relay URL changes. The macOS app says so once per launch in a sheet with Check for Updates, and its Device pane reads "update Lorca to sync"; the phone shows "Update Lorca to sync" in the chat list's title slot and in Settings.
- Machine bearer for blobs, the sync socket, and the machine list; identity signature for registering and attesting machines.
- PUT/GET non-file blobs as base64url ciphertext in JSON, and PUT/GET files as binary ciphertext. `roster` is a whole-roster snapshot of bots, chats, and routines (latest wins); `chat` is one upsert or removal of a message; `machine` is a Device’s metadata and the turns in flight on it; `credentials` is the account's provider credentials; `key` is the DEK sealed to the content key.
- Jobs: `kind=job` with `recipient_machine_pubkey`, sealed to that machine’s box key, deleted by the Runner after the turn.
- Questions: `kind=request` sealed to one Runner (`crates/cli/src/requests.rs`: `{ id, verb, requested_by, body }`), answered with a `kind=response` sealed to the Device that asked (`{ request_id, body, error? }`); each side deletes the blob it consumed, and the asker gives up after 20 s, or 75 s for the start of a plugin sign-in, whose discovery and registration the Runner cuts off at 45 s. The verbs are `memory.read` and `memory.write`, so a bot's memory can be shown and edited from a Device that is not its Runner; `plugins.install` / `plugins.uninstall` / `plugins.variables` / `plugins.connect` / `plugins.detail`, so plugins on a Runner are managed from any Device, and `plugins.sign_in.finish` / `plugins.sign_in.cancel`, with which the Device that asked for a sign-in (its `redirect_uri` on `plugins.connect` or `permission.answer`) hands back where its browser landed (see Sign-in in [Codemode and Plugins](plugins.md#plugins)); `permission.answer`, so a permission card is answered from any Device; and `bash.stdin` and `bash.stop`, so a command a bot left waiting is answered or stopped from any Device. A request is refused up front when the Runner is unknown or offline.
- Slots: a `roster`, `chat`, `machine`, or `credentials` blob goes up with a `slot` (`Slot` in `app.rs`, `ChatBlob::slot`), and the relay deletes the blobs of that slot it supersedes, so the log holds a message once and not once per streamed chunk. A message's versions and its removal share the slot named by the message id. An upsert sets `keep_first`, which spares the slot's oldest blob: its seq holds the message's place in the log, so a Device that replays from the start gets the transcript in order, first the early version and later the final one. A tool row is the exception: its running version goes up without arguments or results, for the status line on other Devices, and the finished row supersedes it outright, so the relay keeps one version of each call, at the finished row's place. A row that shows a terminal keeps its first place as a message does, since the transcript shows it. A removal supersedes every version. The SQLite outbox does the same before upload: a queued version updates its row without moving its queue position. `App::upsert_message` holds one lock from the SQLite write that gives a message its `position` to the enqueue, so the sending Device's transcript order is the log's order.
- Groups: a `chat` blob and a message's `file` blob go up with `group`, the chat's id (`ChatBlob::group`). Deleting a chat queues its id in `State::group_deletes`, drops what the outbox still held for it, and the sync cycle calls `DELETE /v1/groups/{group}` until it lands: the relay deletes the group's rows and the attachments' objects in one transaction, gives the bytes back to the quota, and remembers the group in `deleted_groups`, so a blob that names it later (a Runner finishing a turn in a chat another Device deleted) gets `409` and the outbox drops it. The other Devices learn of the deletion from the roster. A bot's avatar is a `file` with no group: the Device that replaces or removes it, or deletes its bot, removes its local copy and queues the attachment id in `State::blob_deletes`, and the sync cycle calls `DELETE /v1/blobs/{id}` until it lands, which removes the row and the object.
- `GET /v1/groups/{group}/blobs?before=<place>&limit=` reads a chat backwards a message at a time: `{ slots: [{ place, blobs }], has_more }`, oldest first, where a slot is a message (its first and latest blob, or its removal) or the chat's read mark, and `place` is the slot's lowest seq. A message other than a tool row keeps the place its first version took however late its last one landed, so pages read backwards give the transcript in the log's order. A page is up to 500 slots and 8 MiB, and leaves out the group's `file` blobs. A relay without the route answers `404`, and the Device replays the log.
- `GET /v1/blobs?since=` answers a page of up to 8 MiB of ciphertext (and at least one blob); a Device asks again from the last seq it got. A Device at seq 0 first takes `roster,machine` alone, so chats have their names and bots before their messages land.
- Every Device keeps `last_seq` and its outbox in `lorca.sqlite3`; queued ciphertext is a binary SQLite BLOB. Uploads retry until the relay accepts them. Attachment transfers have a ten-minute request timeout.

```
App_B → CLI_B
CLI_B encrypts user message + job-for-A → relay
CLI_A fetches envelopes for A, decrypts, runs loop, encrypts reply
CLI_B fetches chat blobs, decrypts → App_B
```
