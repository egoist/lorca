# Compaction and usage

**Compaction** keeps a long chat inside the window (`lorca_agent::compaction`, pi's prompts and cut rule; `LORCA_COMPACTION=0` turns it off): when the transcript a turn rebuilds is estimated above `window - 16k` tokens, or more than 400 messages of the chat are not covered by a summary yet, or a turn's own context grows past the window between model calls (the loop's `prepare_next_turn` hook), or the provider answers that the prompt is too long, the older part is summarized by the same model into a structured checkpoint (goal, progress, decisions, next steps, files touched), about 20k tokens of recent messages stay as they are, and a `Compaction { bot_id, summary, after_message_id }` on the chat (local, per bot) makes every later turn start from the summary and the messages after that one. The summary covers the whole chat since the last one, in pieces of at most the window less twice the reserve, each piece updating the summary of the ones before, so a backlog of any size compacts. A compaction of the context a turn sends (a transcript over the threshold that the turn rebuilds whole, or a context that grows between the turn's model calls) asks the summary inside the conversation instead (`compaction::compact_in_place`): the request is the turn's next one, with its system prompt, tools, thinking, cache points, and messages, and the checkpoint prompt as one more user message that names the message the kept part starts with. The provider's prompt cache serves everything the turn's last request sent, where a summary of the transcript as text pays for all of it again. It falls back to the summary of the transcript when the window leaves under 4,096 tokens for the reply, or the model answers with a tool call, a reply the limit cut off, an error, or anything but the checkpoint. A backlog past what a turn rebuilds, a prompt the provider called too long, and Compact summarize the transcript. The memory flush runs first, the same way (see [Memory](bots.md#memory)). Automatic compaction is silent, as in Grok Bot; the inspector's Context row shows the result, and its Compact button (`chats.compact`) does it by hand with a notice in the chat, on the bot's Runner: here, or as a `chats.compact` [request](requests.md#verbs) sealed to that Runner from any other Device. The row reads Compacting… until the Runner answers, and the reason when it could not (the Runner is offline, say).

**Usage** is counted where the turns run: each Runner keeps what its turns in a chat used (`Chat::usage`: the last turn's context size, window, and model, and the tokens, cost, and turns so far) and uploads it after every change as a `ChatBlob::Usage { chat_id, runner_id, usage }` in the chat's group, in a latest-only slot per chat and Runner. Every other Device keeps each Runner's latest report (`Chat::runner_usage`), so a bot on another Runner shows its Context row and Compact there too. The apps get one usage per chat (`Chat::shown_usage`, in the snapshot, `roster.changed`, and `chat.usage`): the context of the Runner the chat's bot (a group's owner) runs on, or of the latest report until that Runner has one, and what the turns on every Runner spent. A Device that first syncs gets a report with the chat's newest messages, or after that Runner's next turn when it is older.
