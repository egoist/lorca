# macOS chat

The AppKit chat belongs to the [macOS app](macos-app.md) and reads its state from the local CLI.

## Transcript

Transcript: a view-based `NSTableView` (`Chat/ChatViewController.swift`), which builds cells for the rows on screen and, past a few hundred rows, estimates the heights of the rest until they come into view. `ChatLayout` parses a message's Markdown and measures it once per message version and bubble width, and the cell lays out from the segment heights it measured, so a reload or a resize asks for heights it already has. A bubble stops growing at 580 pt, so resizing a wide window measures nothing; during a live resize only the rows on screen are measured, the rest once it ends. A new message, the working row, and an older page go in as one run of inserted and removed rows (`ChatRow.changedRun`), which leaves the other cells, and a text selection in them, alone. Scrolled back, the first message on screen holds its place through replies, older pages, and width changes. Accessibility clients see the table the same way (`Chat/TranscriptTableView.swift`): one row element per row, whose words ("Chef: …", the message as shown) and frame come from the chat, and whose cell is the real one while the row is on screen and a stand-in with the same words while it is not. So VoiceOver or the Accessibility Inspector reads the whole transcript without the table building a cell. A row keeps its element through replies and older pages, and a row a screen reader moves to scrolls into view between the titlebar and the composer, which near the first message asks for the page before it.

Bot-to-bot messages are centered markers (`HandoffCellView`): "Messaged ◉ Writer" where one was sent, "Message from ◉ Writer" where one came from a bot outside the chat (a [handoff](handoffs.md)'s report too, in a group as well), with a one-line preview without bold or code marks and the whole message in a popover on a click.

## Composer

Composer: the `+` button opens a file panel; files dropped on the composer or pasted (file URLs, or an image with no text beside it, written to a temporary PNG) attach the same way. Chips above the text show a thumbnail or the file's name and size, each with a remove button; a message can be attachments alone. The draft belongs to the chat on screen: opening another chat clears it (its text, files, `@` picks, and the message it replies to), and a visit to Settings keeps it. The app mints the attachment ids and hands the CLI paths (`chats.send { attachments: [{ id, path, name, mime, width, height }] }`), so the bubble it shows at once matches the message the CLI echoes back. In a bubble, images are thumbnails sized from the width and height in the message and files are cards; a click opens Quick Look, with Open and Save As in the context menu. An attachment from another Device is fetched through `files.path`, which pulls the `file` blob from the relay into `~/.lorca/files/` and answers with the path; the bubble reloads when it lands. The Dictate button (`mic.fill`, the primary disc while the field is empty) starts Apple's speech recognizer (`Speech` + `AVAudioEngine`, `Dictation.swift`). While recording, the text gives way to Grok Bot's pill: a stop square, the elapsed time, and bars that follow the input level, with Send still beside it. The transcript accumulates and lands at the caret when the square is clicked; Send commits it and sends in one go; Escape discards it. The recognizer listens in the language of the keyboard input source in use (a Pinyin input method means zh-CN, whatever the system language), else the first of the system's preferred languages it supports (matched on language and region, so "zh-Hans-CN" finds "zh-CN"), or the language chosen in Settings › General or the button's right-click menu (`Preferences.dictationLanguage`). The bundle declares `NSMicrophoneUsageDescription` and `NSSpeechRecognitionUsageDescription`.

## Outputs

What a chat's bots published shows in the inspector's Outputs section (`Inspector/InspectorViewController.swift`), after the group's name and before a DM's profile, and only while the chat has one. `AppStore.outputs(in:)` asks the CLI for `outputs.list` the first time a chat is shown, keeps every version, and follows the message events after that; a new snapshot drops what it kept, and the next look asks again. The section has the three latest outputs, one row per output (`OutputSeries`): its kind's symbol, its name, when it was published and, in a group, by whom, and how its check went (Passed, Not verified, or Failed in red). View all, beside the section's title when there are more, opens every output in a sheet (`OutputsViewController`). A row opens the output's sheet (`Sheets/OutputViewController.swift`): a `QLPreviewView` of the file, or the link's address; the check, with its result, the bot's summary, and the command; and the versions, newest first, each of which the sheet can show. Open, the default button, hands the shown version's file to its app or the link to the browser; Save As… copies the file; Done closes. A row's menu has Open and Save As…, or Open Link and Copy Link.

A file's bytes come from the CLI (`files.path`), fetched from the relay when another Device published it. They are kept under their attachment id with no extension, so Quick Look, Open, and Save As… ask for `named: true`, a private copy under the file's own name (`AppStore.openableURL`). A transcript tile opens its file the same way. A fetch that failed keeps its reason until the user retries, so scrolling does not ask again: the tile says Couldn't download · Retry and retries on a click, and the output's sheet says the file couldn't be downloaded, gives the CLI's reason, and turns Open into Try Again. See [Outputs and evidence](outputs.md).

## Working state

Working state, after Grok Bot: the CLI's `job.started` / `job.finished` events (and `running_turns` in the snapshot) name the chat and bot of every turn in flight on any Device. From them the app shows a breathing green dot on the bot's avatar in the sidebar, an "is working" row after the last message (the bot's avatar beside a shimmering line: "Working…" in a DM and "Chef is working…" in a group, or what the one working bot is doing: "Thinking…" from the Runner's `job.thinking`, sent when the model starts thinking and read until that bot's next message or the end of its turn, else its latest tool as an activity such as "Running command: Install dependencies…" from the call's `description`, kept between calls so it does not flash), the Stop button, and "Chef stopped without replying" when a turn ends with nothing said. A turn reads the same on every Device, whichever one started it. Each Device lists the turns in flight on it (the turns it runs and the group exchanges it holds, each with what it is doing, thinking or a retry, until the bot's next message) in its `machine` blob (`turns`), uploaded again whenever the list changes, and a Runner uploads each call's row as the call starts. Every other Device keeps each Device's latest list (`device_turns` in SQLite) while the relay's last machine list shows that Device online (`turns_online`, kept while this Device's own socket reconnects) and drops it when the relay shows it offline; a Device uploads its list again whenever its socket connects. So a Runner that quits mid-turn never shows that turn again, and one that only lost the relay shows it again when it is back. The CLI merges those lists with its own jobs, including one it sent to a Runner that has not listed it yet, and tells the app what changed (`App::turns_changed`). The Device that asked for a turn keeps the job in SQLite (`sent_jobs`) until its `job_result` arrives or its five-minute wait runs out, so a CLI or phone core that starts again shows its own turn at once (`runtime::resume_sent_jobs`) and the other Devices' turns once the relay says they are online. Stop cancels a turn wherever it runs: the CLI seals `job_cancel` to the Device that lists it. Replies arrive in chunks: the bubble appears with the first completed paragraph (or sentence, after 1.5 s) and grows by paragraphs, the way Grok Bot's server re-sends a message as it grows. Tool calls never appear in the transcript, as in Grok Bot: the CLI keeps them as `tool` messages so a later turn can rebuild its context, and the app renders none of them, leaving the "is working" row (with the running tool's activity) and whatever the bot says before and after its work. The exceptions are a sent `message_bot`, shown as the "Messaged ◉ X" marker, and a `bash` call's command card while the command needs the user (`Chat/CommandCellView.swift`, `ToolInvocation.isShown`; see [Terminal sessions](terminal-sessions.md)): while Auto-review asks, who wants to run it, the command's first line in a code block that opens the whole command in a sheet on click, why, Allow once, Always allow, and Deny, and the rule Always allow adds; once the bot handed the running command over, Stop on its title's line and its last lines in a code block of their own that grows to six lines and then scrolls, the newest line in view and an edge with more lines past it fading out (a gradient mask on the scroll view's layer, since the block's color is see-through); at a question, a field that hides what is typed unless the question is a yes or no, with Send. When the card leaves with the cursor in that field, the composer takes it. A bot asking for a secret has a card of its own (`Chat/SecretCellView.swift`, [Secret requests](secrets.md#in-the-apps)). Running tasks (see [Terminal sessions](terminal-sessions.md)) sit behind a `HoverButton` with the terminal symbol in the toolbar at the content area's trailing edge (`MainWindowController.updateRunningTasks`), whose item carries the toolbar's own badge (`NSItemBadge`, macOS 26 and later) with their number when there are two or more. The item stays in the toolbar while a chat shows and only its button hides, so the toolbar keeps its layout, and the button stays while its transient popover (`Chat/RunningTasksViewController.swift`) is open; clicking a command in it closes the popover and opens the whole command in a sheet. Sidebar rows carry an unread count pill beside the preview (the CLI counts each finished bot reply, failed response, and pending confirmation, from its own turns or the relay, unless the app reports that chat as the one on screen; reading a chat on one Device uploads a `ClearUnread` chat blob that zeroes the count on the others, and so does a message the user sends, on every Device it reaches), a preview without a "You:" prefix (a bot's name only in groups; "Messaged X" and "Message from X: …" for bot-to-bot messages), and a stamp that is the time today, "Yesterday", the weekday within a week, then the date. A transcript inserts "Today 4:13 AM" separators after fifteen minutes of silence; in a group a bot's name sits above the first bubble of a run with its avatar beside that bubble's bottom edge, the run's later bubbles follow 4 pt below in the same column, and a DM shows neither.
