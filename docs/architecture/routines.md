# Routines

A routine is a task a bot runs on a schedule in its direct chat with the user, after Grok Bot's routines: a morning brief, an hourly check, a weekly report. The bot owns its routines: the user asks for one in chat and the bot sets it up with the `routines` tool (a name, a schedule, the prompt, written as an instruction to itself, and a check when the routine watches for something), and edits, pauses, resumes, runs, or deletes it the same way. The system prompt of every turn explains routines and lists the bot's own with each one's next run, or that it checks first.

The roster also carries Auto-review (see [Plugins](plugins.md#plugins)). Routines live in the roster (`Routine { id, bot_id, name, prompt, schedule, timezone, missed_run_policy, last_scheduled_at?, health?, is_enabled, enabled_at, last_run_at?, last_outcome?, paused_reason?, check?, created_at }`), so every paired Device lists them and can pause, resume, run, or delete one (`routines.create` / `routines.update` / `routines.delete` / `routines.run`, and `routines.describe` to read a schedule back). The bot's Runner runs them (`crates/cli/src/routines.rs`): every half minute it starts the routines of its bots whose next run is due, or their checks, and starts none while a run or check of the routine is going on.

A schedule (`crates/cli/src/schedule.rs`) is `every 30m`, `every 2h`, `every 1d`, or five cron fields read in the routine's explicit IANA `timezone` (`0 9 * * 1-5`), never more often than every five minutes. An interval counts elapsed seconds from the latest run, completed check, schedule checkpoint, creation, or resume; a cron fires at the next matching minute in its stored timezone. Creation and records that omit `timezone` use UTC. `chrono-tz` carries the IANA rules on every Device. A nonexistent daylight-saving minute skips that day; a repeated minute fires once at its earlier UTC instant. Travel and a Runner timezone change leave the stored zone in force. The CLI says a schedule in words on the wire (`schedule_text`: "Weekdays at 9:00 AM", "Every 2 hours", "On the 1st of every month at 8:30 AM", else "Cron 5 4 * * 1-3") and gives the same UTC `next_run_at` and absolute `next_run_text` (date, clock, UTC offset, and IANA zone) beside every routine, with `is_running`. `routines.describe { schedule, timezone? }` previews both. The model routines tool and `routines.create` / `routines.update` accept `timezone` and `missed_run_policy`; changing the schedule or zone re-arms it from now.

A run is a `routine` Job in the bot's DM. It opens with a "Routine · Name" marker (a system notice carrying the routine id), then the turn runs with the routine's prompt as the task and a system prompt that says nobody is typing: the bot does the work, replies with what the user should know, or answers `PASS`, which leaves only the marker. Later turns rebuild the marker as `[Routine "Name" ran on its schedule. Task: …]`, so the bot can talk about a run afterwards; the daily log names the routine as the turn's source. `job.started` / `job.finished` carry `routine_id`, so the apps show the routine as running and the bot at work. A run's outcome (`sent`, `pass`, `error`) is kept on the routine. Run Now from a Device that is not the Runner seals the job to the Runner like any turn.

**Checks.** A routine that watches for something (an inbox, a repository, a feed, a page) carries a `check`: JavaScript the Runner runs at each due time before the bot does, without a model, so an interval with nothing new runs no turn; only the small-model calls a check makes with `models.ask()` cost anything, in the chat's spending. The bot writes it with the `routines` tool (`check`, at most 8,000 characters; `""` on edit removes it). It runs as a codemode script (see [Codemode](plugins.md#codemode)) in a sandbox of its own (`routines::run_check`, five minutes at most) whose calls only read: the bot's `read`, `grep`, `find`, and `ls`, and the plugin tools whose manifest lists them as read-only or whose server marks them `readOnlyHint`, the same test Auto-review applies. `CheckRunner` refuses any other call, which ends the check. `store()` and `load()` reach the values the bot's scripts keep in its DM, so a check keeps what it has seen and returns only what is new, and `models.ask()` can screen items on the small model. What the check returns starts the run: a `routine` Job whose `check` carries it as text (at most 4,000 characters), which the turn reads after the transcript, marked as data from its tools and not instructions; Auto-review reads the routine's task, never what the check found. A check that returns nothing, `null`, `false`, or an empty string, list, or object ends there, with no marker and no turn. The Runner persists `health.last_check_at`, `last_success_at`, and `status: quiet`, and uploads the encrypted roster, so every Device shows the same next check and success history. A script error starts the run with its error, so the bot fixes or removes the check; connection, authentication, and read-only refusals update health and recovery without starting a model turn. Saving a check runs it once, in the turn that saved it, and hands the bot the result, so a broken check shows at once and its first run records what is already there. Run Now runs the check first, then the turn whatever it found. One check of a routine runs at a time: a check on save or Run Now waits for one already running (`routines::check_now`). A due check that finds something while a run started by hand waits for it still starts its own run, after that one, since the waiting run's check no longer sees what the first one stored as seen. The roster carries `check` so every Device shows it, and only the Runner writes it: a roster from a build without the field keeps the Runner's check (`routines::keep_checks`) and goes up again with it. The Runner also keeps its newer health and schedule cursor when a stale roster arrives; an explicit resume or schedule/check edit re-arms the routine. Checks in flight use memory locks; their completed timestamps survive restarts.

When the user has not written in any chat for seven days, due routines are paused instead of run (`paused_reason: away`) with a notice in the bot's DM, as Grok Bot does, so nothing keeps spending on results nobody reads; the switch turns them back on.

## AppKit controls

The macOS app's DM inspector has a Routines section: a row per routine (clock, pause, or running icon; the schedule in words and the next run, or the next check; a switch that pauses or resumes) that opens a sheet with the state, schedule, next run or check and last run, the prompt, the check in a monospaced block when there is one, and Run Now, Pause/Resume, Edit in Chat (which puts `Edit my routine "Name": ` in the composer), and Delete. With none, the section says routines are set up by asking the bot. The AppKit sheet also offers Change Timezone and a Missed runs menu (Run once or Skip), shows the assigned Runner and its availability, and lists the last check, last successful check, retry time, and recovery action separately from the last model run. Run Now is unavailable when the Runner is offline or authentication has paused the routine. Details scroll inside a bounded sheet so the run, pause, edit, delete, and Done actions remain visible. The phone's chat details show the same list with a switch; a tap offers Run Now and Delete.

## Windows and Linux controls

The native Go/MyGo app reads the same CLI routine output through `desktop/model`: explicit IANA timezone and policy, absolute zone/offset `next_run_text`, separate check attempt/success timestamps, combined retry time, recovery action, and Runner availability. Its inspector names failed, blocked, and waiting routines; a routine opens a native details sheet with Change Timezone, Run once/Skip, the task/check, and independent health history. Actions and Done stay outside the scrolling details so small windows keep them visible. Run Now is disabled while running, while the assigned Runner is unavailable, or after an authentication pause; Resume follows the existing CLI boundary and re-arms from now.

Timezone editing keeps its draft across rebuilds and saves through `routines.update`; the CLI validates the IANA name. Policy selection uses a keyed native select and its `OnChange` callback. Only timezone/policy fields are sent: the UI never writes health, checkpoints, or Runner ownership. The store applies confirmed replies through its ordered main-thread queue and ignores an older policy reply after a newer edit. A discarded timezone sheet keeps a later reply from reopening it or taking the keyboard.

Devices includes Runner service discovery with the existing install/status commands, safe read-only status, and log. It asks `device.service_status { id }` through the local CLI, which owns the sealed request to a remote Runner. A reply for a Device the user stopped viewing is discarded. The commands run on that owned Runner; the UI installs no service and keeps bot assignments in force. English-key Chinese strings cover these controls and state labels.

## Missed occurrences and recovery

`missed_run_policy` is `coalesce` by default: one current check or model run handles everything missed while the Runner was unavailable. It commits the account-encrypted `last_scheduled_at` checkpoint before admission, including during a relay bulk pull; a rejected SQLite write leaves the occurrence pending and admits no work. It counts the next occurrence from that checkpoint or the completed run/check. `skip` discards an occurrence more than 60 seconds late and advances the checkpoint to now; the next cron occurrence retains the chosen timezone. Neither policy queues historical turns. A restart after admission consumes that occurrence; coalesce does not promise replay of work interrupted by a process exit.

Check health has independent last-attempt and last-success timestamps, a status (`quiet`, `ready`, `failed`, `blocked`), connection and authentication failure counts, `retry_at`, and a safe recovery action. It stores categories and instructions rather than raw external errors or credentials. The Runner stores health and the schedule cursor as XChaCha20-Poly1305 ciphertext in SQLite's `routine_runtime` table, bound to `routine-runtime:<id>` with the account key. Definitions stay in the routines table. Legacy plaintext runtime fields migrate at the next state save. The same health travels inside the encrypted account roster; roster edits on another Device preserve the assigned Runner's newer checkpoint. Deleting a routine deletes its runtime row.

Connection failures back off from five minutes, doubling to a six-hour cap. The next scheduled attempt waits until both its schedule and backoff allow it. Successful checks reset their own failure streak and update success time. Three consecutive authentication failures pause the routine with `paused_reason: authentication` and `state: blocked`: reconnect the account provider in Settings or sign in to the integration on the assigned Runner, then Resume. Resume clears suspension/backoff and re-arms from now. Model-provider failures use an independent `health.model` streak, so a successful quiet check does not erase model authentication failures; model results leave check timestamps alone. Provider request retries finish before this routine-level accounting runs.

The CLI derives `state`, `runner_id`, `runner_available`, `retry_at`, and `recovery_action` for the app. An enabled routine assigned to an offline Runner reads `waiting_for_runner`; no other Runner takes it over. Availability comes from this local Runner or the relay's current Device presence. Offline recovery says to start Lorca or `lorca serve` on the assigned Runner and points to [the CLI service](runtime.md#updates-and-the-service) for an owned computer that stays available.
