# Routines

A routine is a task a bot runs on a schedule in its direct chat with the user, after Grok Bot's routines: a morning brief, an hourly check, a weekly report. The bot owns its routines: the user asks for one in chat and the bot sets it up with the `routines` tool (a name, a schedule, the prompt, written as an instruction to itself, and a check when the routine watches for something), and edits, pauses, resumes, runs, or deletes it the same way. The system prompt of every turn explains routines and lists the bot's own with each one's next run, or that it checks first.

The roster also carries Auto-review (see [Plugins](plugins.md#plugins)). Routines live in the roster (`Routine { id, bot_id, name, prompt, schedule, timezone, missed_run_policy, last_scheduled_at?, health?, is_enabled, enabled_at, last_run_at?, last_outcome?, paused_reason?, check?, pull_request?, calendar?, created_at }`), so every paired Device lists them and can pause, resume, run, or delete one (`routines.create` / `routines.update` / `routines.delete` / `routines.run`, and `routines.describe` to read a schedule back). The bot's Runner runs them (`crates/cli/src/routines.rs`): every half minute it starts the routines of its bots whose next run is due, or their checks, and starts none while a run or check of the routine is going on.

A schedule (`crates/cli/src/schedule.rs`) is `every 30m`, `every 2h`, `every 1d`, or five cron fields (`0 9 * * 1-5`) read in the routine's IANA `timezone`, never more often than every five minutes. A routine can also run once at a date and time, watch one pull request until it merges or closes, or run a set time before or after calendar events; [One-time routines, watches, and calendar events](routine-triggers.md) describes those three. A routine keeps the timezone it was made in: the Runner's (`schedule::local_timezone`, through `iana-time-zone`) unless the bot names another, so travel or a Runner moved to another zone leaves its hours as they were. `chrono-tz` carries the IANA rules, so every Device finds the same next instant: a minute that daylight saving skips does not fire that day, and one it repeats fires once, at its earlier instant. An interval counts elapsed seconds from the latest run, check, due time taken, creation, or resume. The bot's system prompt names the Runner's timezone and lists each routine with its own, and the `routines` tool takes `timezone` and `missed_run_policy`, as `routines.create` / `routines.update` do; `routines.describe { schedule, timezone?, missed_run_policy? }` checks them and gives the next run. A new schedule or timezone counts from now. The CLI says a schedule in words on the wire (`schedule_text`: "Weekdays at 9:00 AM", "Every 2 hours", "On the 1st of every month at 8:30 AM", "Once on 2026-10-12 at 9:00 AM", "Watches acme/project#42", "15 minutes before each event", else "Cron 5 4 * * 1-3") and gives `next_run_at`, `is_running`, and `state` beside every routine. A due time past for more than a minute (an offline Runner, or quiet checks the Runner did not upload) is given as the next one from now.

A run is a `routine` Job in the bot's DM. It opens with a "Routine · Name" marker (a system notice carrying the routine id), then the turn runs with the routine's prompt as the task and a system prompt that says nobody is typing: the bot does the work, replies with what the user should know, or answers `PASS`, which leaves only the marker. Later turns rebuild the marker as `[Routine "Name" ran on its schedule. Task: …]`, so the bot can talk about a run afterwards; the daily log names the routine as the turn's source. `job.started` / `job.finished` carry `routine_id`, so the apps show the routine as running and the bot at work. A run's outcome (`sent`, `pass`, `error`) is kept on the routine. Run Now from a Device that is not the Runner seals the job to the Runner like any turn.

**Checks.** A routine that watches for something (an inbox, a repository, a feed, a page) carries a `check`: JavaScript the Runner runs at each due time before the bot does, without a model, so an interval with nothing new runs no turn; only the small-model calls a check makes with `models.ask()` cost anything, in the chat's spending. The bot writes it with the `routines` tool (`check`, at most 8,000 characters; `""` on edit removes it). It runs as a codemode script (see [Codemode](plugins.md#codemode)) in a sandbox of its own (`routines::run_check`, five minutes at most) whose calls only read: the bot's `read`, `grep`, `find`, and `ls`, and the plugin tools whose manifest lists them as read-only or whose server marks them `readOnlyHint`, the same test Auto-review applies. `CheckRunner` refuses any other call, which ends the check. `store()` and `load()` reach the values the bot's scripts keep in its DM, so a check keeps what it has seen and returns only what is new, and `models.ask()` can screen items on the small model. What the check returns starts the run: a `routine` Job whose `check` carries it as text (at most 4,000 characters), which the turn reads after the transcript, marked as data from its tools and not instructions; Auto-review reads the routine's task, never what the check found. A check that returns nothing, `null`, `false`, or an empty string, list, or object ends there, with no marker and no turn. Each check is recorded in the routine's `health` (below), and the schedule counts from it, across restarts too. A script error starts the run with its error, so the bot fixes or removes the check; a check that can't connect, can't sign in, or calls something that is not read-only starts no turn and only counts in `health`. Saving a check runs it once, in the turn that saved it, and hands the bot the result, so a broken check shows at once and its first run records what is already there. Run Now runs the check first, then the turn whatever it found. One check of a routine runs at a time: a check on save or Run Now waits for one already running (`routines::check_now`). A due check that finds something while a run started by hand waits for it still starts its own run, after that one, since the waiting run's check no longer sees what the first one stored as seen. The roster carries `check` so every Device shows it, and only the Runner writes it: a roster from a build without the field keeps the Runner's check (`routines::keep_checks`) and goes up again with it. The Runner likewise keeps its newer `health` and `last_scheduled_at`, and a pause after failed sign-ins, over a roster another Device wrote from an older copy, unless that Device resumed the routine or changed its schedule, timezone, or check.

A routine has nobody to ask, so it leaves what needs the user for review: a draft or a proposed call through `stage_review`, and any new shell command or effectful plugin call Auto-review holds, staged as a persistent [review item](review-queue.md) while the call returns without running. A notice in the chat says it waits; the user edits and approves it, or rejects it, on any paired Device later. The Runner runs an approved call apart from the routine's turn and writes how it went back to that notice.

When the user has not written in any chat for seven days, due routines are paused instead of run (`paused_reason: away`) with a notice in the bot's DM, as Grok Bot does, so nothing keeps spending on results nobody reads; the switch turns them back on.

## Missed occurrences and recovery

When the Runner takes a due time it saves it as `last_scheduled_at` before any work starts, even during a relay bulk pull; a save that fails admits nothing, and the due time stays pending. So a restart neither runs a due time again nor drops it. `missed_run_policy` says what a Runner that was off at due times does when it is back: `coalesce` (the default) makes one run, or one check, for everything it missed; `skip` takes a due time more than a minute late without running it and waits for the next. Neither queues a run per missed time. A turn cut short by the CLI exiting is not run again.

`health` (`crates/cli/src/routine_health.rs`) is the Runner's record of the checks and runs: `last_check_at` and `last_success_at`, the last check's `status` (`quiet`, `ready`, `failed`, `blocked`), streaks of failures to connect and to sign in, and `retry_at`. It holds kinds of failure, never what a tool said. A check that can't connect waits five minutes before the next try, doubling each time to six hours, and the next due time waits for it too; a check that passes clears its streaks. Three failed sign-ins in a row pause the routine (`paused_reason: authentication`) until the user reconnects the provider or signs in to the plugin, then resumes it, which clears the streaks; a run already sent to the Runner skips with a notice, and Run Now is refused. The runs keep their own streak in `health.model`, counting only failures to reach or sign in to the model provider after its own retries, so a quiet check clears none of it.

Health and the due time are fields of the routine, saved in SQLite with it and carried in the encrypted roster. To keep a quiet routine from uploading the roster on every check, the Runner saves a due time it took, and a check that leaves the routine as it stood (another quiet one), without uploading them; a check that changes how it stands (the first, a failure, a pass after one, a pause) goes up with the roster.

The CLI gives each routine a `state` for the apps: `running`; `blocked`, paused after failed sign-ins or with a check that called something that is not read-only or that the bot's [Access](bot-permissions.md) leaves out; `paused`; `waiting_for_runner` while the bot's Runner is offline, since no other Runner takes it over; `failed` while checks or runs fail to connect or sign in, or the last check failed; else `on`.

A routine can have [limits](budgets.md): its runs and checks count toward them together. Once it reaches one, the scheduler skips it and Run Now is refused until the user resumes it in its Limits sheet, after raising the limit or granting the limits again in full. That stop comes before any health state.

## The apps

The Mac's DM inspector has a Routines section: a row per routine (a clock, or an alarm, pull request, or calendar for the other kinds, a pause, or a running icon; the schedule in words and the next run, or the next check; a switch that pauses or resumes). A routine that needs something leads its line with it, in a word or two (Limit reached, Needs sign-in, Waiting for Runner, Can't connect, Sign-in failed, Check failed), in orange while the user has to act. The row opens a sheet with the state, a note on what happened and how to fix it while something is wrong, the schedule (naming the routine's timezone, as "New York time", when the Mac keeps other hours now or in half a year), the next run or check, Missed runs (Run once or Skip), the last check and, while checks fail, the last successful one, the last run, a Limits row that opens the routine's [Limits sheet](budgets.md#in-the-apps), the prompt, the check in a monospaced block when there is one, and Run Now, Pause/Resume, Edit in Chat (which puts `Edit my routine "Name": ` in the composer), and Delete. Run Now waits for an online Runner, for Resume after failed sign-ins, and for Resume in Limits after a limit. The bot owns the routine's timezone and missed-run policy as it does the rest, so the sheet changes them through Edit in Chat. With no routines, the section says routines are set up by asking the bot.

The Windows and Linux app's inspector rows and sheet are the same; the sheet keeps its actions under the scrolling content, so a short window shows them.

The phone's chat Details list the routines with a switch (`app/chat-info/[id].tsx`, words in `src/ui/routines.ts`); a routine that needs something leads its line with the same words, with an orange mark instead of its clock while the user has to act. A tap slides in the Routine screen (`app/chat-info/routine/[id].tsx`) inside the same sheet: the state with its note, Run Now, Pause or Resume, and Limits; then Schedule: the schedule in words with its timezone as the row's value ("New York time") when the phone keeps other hours, the next run or check, Missed runs, the last check and last run with how each went under it, and the last successful check while checks fail, with what a missed run does as the section's footer; the task, the check, and Delete Routine. The phone has no Edit in Chat: the Task footer says to ask the bot in chat.

Each app's Devices pane (the phone's Device screen in Settings) asks an online Runner whether `lorca service` keeps its CLI running (`device.service_status`, see [Updates and the service](runtime.md#updates-and-the-service)) and shows it as Background service: Running, Installed, not running, or Not installed. While it is not installed, a line under the card (the phone's Machine section) says to run `lorca service install` in Terminal on that computer to keep its bots running while Lorca is closed; the routine sheet of a Runner that is offline says the same.
