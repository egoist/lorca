# CLI (runtime)

`crates/cli`, binary `lorca`. Local websocket for the app. Files live under the private data directory: `~/.lorca/` by default and for Lorca, `~/.lorca-dev/` when launched by Lorca Dev, or the explicit `LORCA_HOME`. It contains `identity.json` (master secret, identity devices only), `machine.json` (machine secret, identity and content public keys, account DEK, `name`, `os`), `credentials.json` (the account’s providers, as last merged), `settings.json` (relay URL), `mcp.json` (the user's own MCP servers, [MCP servers](mcp-servers.md)), `catalog.json` (the last model catalog fetched from lorca.app, its ETag, and when it was checked; see [Providers](providers.md)), `marketplace.json` (the same for the marketplace index; see [Marketplace](marketplace.md#the-index)), `update.json` (the CLI's own updates: [Updates and the service](#updates-and-the-service)), `plugins/` ([Plugins](plugins.md#plugins)), `lorca.sqlite3` (WAL-mode plaintext local state), and `files/<attachment id>` (attachment bytes, sent from here or fetched from the relay). SQLite holds devices, bots, chat metadata, routines, Auto-review, usage, compactions, sync bookkeeping, messages, the durable relay outbox, the jobs this Device sent to other Runners and still waits on, and the turns the other Devices list. The JSON and database files are mode 0600 and the directory is mode 0700; SQLite may create `-wal` and `-shm` companions inside that directory while it is open.

Commands:

- `lorca serve` — the app connects here; `lorca` alone lists the commands and starts nothing, so a bot's `lorca` never starts a second service
- `lorca identity new` / `identity restore <phrase>` / `identity show`
- `lorca pair` — show a pairing string and wait; `lorca pair <string>` joins
- `lorca provider set <kind> [api-key] [--base-url <url>]` — connect DeepSeek, Anthropic, OpenCode Zen (`opencode`), or OpenCode Go (`opencode-go`) with an API key, or open the browser sign-in for `chatgpt` and `grok`. The key is checked against the API first and read from stdin when omitted. `provider add <name> <base-url> [--api chat-completions|responses|messages|system-one|decisions] [--model <id>]… [--api-key-stdin]` adds a custom provider, its server checked first; `provider remove <kind>` (a custom provider's kind deletes it) / `provider list`. A running `lorca serve` carries out the change over the local websocket; with none, the command changes `credentials.json` itself and runs one sync pass
- `lorca mcp list` / `get` / `add` / `add-json` / `remove` / `enable` / `disable` / `sign-in` / `sign-out` / `hide` / `show` / `reload` / `import` — the servers in `mcp.json`, through a running `lorca serve` or in that process ([MCP servers](mcp-servers.md#managing-it))
- `lorca marketplace reload` — check lorca.app for a newer marketplace index now, through a running `lorca serve` or, with none, into `marketplace.json` for the next start
- `lorca models reload` — check lorca.app for a newer model catalog now, through a running `lorca serve` or, with none, into `catalog.json` for the next start
- `lorca chats list` / `chats set-owner <group> <bot>` — the chats with each group's owner, and a new owner for a group, the group named by its title or id and the bot by its name or id (`App::find_group`, `App::find_member`). A running `lorca serve` carries out the change over the local websocket; with none, the command changes the database itself and runs one sync pass
- `lorca update` — install the latest release now, through a running `lorca serve`, which restarts into it once no bot is at work, or with none over this binary; `--check` says whether one is out, `--auto on|off` turns automatic updates on or off. A CLI an app carries says the app updates it
- `lorca service install` / `uninstall` / `status` — keep `lorca serve` running from login on ([Updates and the service](#updates-and-the-service))
- `lorca status` / `doctor` (which also says whether `mcp.json` reads)

Bind: `127.0.0.1:4862` (`--port`, `LORCA_PORT`). Relay: `LORCA_RELAY_URL`. If the port is busy the CLI fails loudly.

Outgoing requests (providers and their sign-ins, the relay, MCP servers over HTTP) use the proxy in `HTTPS_PROXY`, `HTTP_PROXY`, or `ALL_PROXY`, less the hosts in `NO_PROXY`, else the system's: the HTTP and HTTPS proxies in macOS's network settings, or Windows' Internet Options with their bypass list (reqwest's `system-proxy`). So the CLI reaches a provider the way the browser does behind a proxy app set as the system proxy, and a ChatGPT sign-in whose browser half went through the proxy swaps its code through it too; OpenAI refuses the swap from a country it does not serve. Neither a PAC file nor macOS's bypass list is read, so on a Mac with a system proxy a model or MCP server on the computer itself is reached through the proxy as well.

Over HTTPS, those requests, lorca.app's, and the relay's sync socket check certificates with one rustls config per process, from `crates/tls` (`lorca-tls`). On macOS and Windows the system decides, through rustls-platform-verifier: the Keychain or the Windows certificate store, as in the browser, so a root an administrator installed for a TLS-inspecting proxy such as Zscaler is trusted. `SSL_CERT_FILE` there names a PEM file of more roots to trust beside the system's; a file that does not read is logged and skipped. On Linux the CLI trusts the system's CA store, or what `SSL_CERT_FILE` and `SSL_CERT_DIR` name in its place (rustls-native-certs), together with the Mozilla roots it carries (webpki-roots), so a container without a CA store still connects. The phone core trusts the carried roots alone. `reqwest::Client::new()` would trust only reqwest's bundled roots, so Device code builds its clients with `lorca_tls::client()` or `client_builder()` (HTTP/1.1); the MCP client, on reqwest 0.13, takes `client_config` and offers h2. A provider check or turn whose request fails reads `lorca_tls::describe`: reqwest's words, then the last cause in the chain, so a certificate the system does not trust says `invalid peer certificate` where a refused connection says so.

## Installing the CLI

A computer without the app installs `lorca` with `curl -fsSL https://lorca.app/install-cli.sh | sh` (macOS, Linux) or `irm https://lorca.app/install-cli.ps1 | iex` (Windows). The script downloads the computer's build from the latest GitHub release of this repo, tagged `cli-vX.Y.Z` (`LORCA_VERSION` names another release): `lorca-cli-macos-aarch64`, `lorca-cli-linux-aarch64`, `lorca-cli-linux-x86_64`, or `lorca-cli-windows-x86_64`, the arm64 Mac build in a shell under Rosetta; an Intel Mac and Windows on Arm have none. It checks the archive against the `.sha256` beside it and renames `lorca` into `~/.local/bin` (`LORCA_INSTALL_DIR`), so a running `lorca serve` keeps its own file, then puts that folder on PATH: a line in the profile of the user's shell, or the user `Path` in the registry on Windows (`LORCA_NO_MODIFY_PATH=1` skips it). The Linux builds are static musl binaries; the Windows build is `x86_64-pc-windows-gnu` against the Universal CRT, and there the `bash` tool runs Git for Windows' bash: a bot's commands fail until Git for Windows is installed or `LORCA_SHELL` names a bash ([Tools](tools.md)). `.github/workflows/release-cli.yml`, run by hand or by a `cli-v*` tag, names the release after the `lorca` crate's version, builds with cargo on macOS and cargo-zigbuild on Linux, writes `lorca-cli.json` and signs it, installs the builds with both scripts on Linux, macOS, and Windows runners and reads the manifest back with `lorca update --check`, and drafts the release, or updates the draft an earlier run left; a published release is left alone, and publishing the draft makes it the one the scripts install: [docs/releasing-cli.md](../releasing-cli.md).

## Updates and the service

Only the builds `release-cli.yml` makes replace themselves (`update::SELF_UPDATING`, from `LORCA_SELF_UPDATE` at build time); an app updates the CLI it carries with itself, through Sparkle or MyGo's updater, and a dev build or `cargo build` never updates. Each `cli-v` release carries `lorca-cli.json` (`kind` `lorca-cli`, `version`, and each build's archive with its SHA-256 and size) and `lorca-cli.json.sig`, an Ed25519 signature of that file by a key in `update::KEYS`. `lorca serve` reads both from the repo's latest release (`LORCA_DOWNLOAD_URL` stands for the releases page, as it does for the install scripts) one to ten minutes after it starts and then daily, at once when the relay answers `426`, and when a Device asks. With automatic updates on, the default (`auto_update` in `settings.json`), a newer release goes in: the archive has to match the signed manifest, the binary in it has to start and say the manifest's version, and a rename puts it in place of the running binary, the old one kept beside it (`.lorca-previous`, or `lorca-<version>.old.exe` on Windows). The CLI restarts into it once no turn of its own is in flight and no command a bot left running is open (a command still open a day later is stopped, as quitting stops it), after what it queued for the relay has gone up or ten seconds have passed. On macOS and Linux it `exec`s the new binary with its own arguments, keeping its pid; on Windows it exits with 75 to the `lorca service` supervisor, and without one it waits for a restart by hand. A job that lands during the restart stays on the relay for the new process. `update.json` holds the last check, the restart under way, and a release that went back: a new release that starts three times without reaching the relay or staying up a minute puts the old binary back, restarts into it, and is passed over by automatic updates.

Every Device's `machine` blob carries the `version` it runs and, for a self-updating CLI, `update`: `auto`, a newer `latest` the last check found, `state` (`installing`, `restarting` while it waits for its bots, `installed` when only a restart by hand is left), and the last `error`. The apps' Device panes show it and offer Update. `device.update` and `device.auto_update` act on this CLI or, by `id`, on another Runner through the `update.install` and `update.auto` requests ([Protocols](protocols.md)). A request names no release and no download: a Runner installs only what its own signed manifest offers.

`lorca service install` keeps `lorca serve` running from login on and whenever it stops: a launchd agent, `app.lorca.serve`, on macOS (its log `~/Library/Logs/Lorca/serve.log`); a systemd user unit, `lorca.service`, on Linux, with lingering so it runs without a login (its log in the journal); and on Windows a Run-key entry that starts `lorca service run` at sign-in, a supervisor that starts `lorca serve` again whenever it exits (its log `serve.log` in Lorca's folder). The service starts `lorca serve` with `LORCA_SERVICE=1` and the installing command's folder, port, and `LORCA_RELAY_URL`, and its log starts over past 20 MiB. Install refuses while another `lorca serve` answers on the port, as the app's does on a Mac with Lorca, and on Linux without a systemd user session (a container, WSL without systemd) it says to start `lorca serve` from the system's own init.

## Agent loop

`crates/agent` (`lorca-agent`) is a port of pi-agent-core: `run_agent_loop` / `run_agent_loop_continue`, the same event sequence (`agent_start`, `turn_start`, `message_start/update/end`, `tool_execution_start/update/end`, `turn_end`, `agent_end`), steering and follow-up queues, `before_tool_call` / `after_tool_call` / `should_stop_after_turn` hooks, sequential or parallel tool execution, and `terminate` hints from tools, plus pi's harness behaviors: a model catalog with rates and windows, thinking levels, cost on every message, compaction, and turn-level retry. Tool arguments are salvaged from cut-off JSON, coerced and checked against the tool's schema before a call runs (a failure is an error result the model reads), and never run from a message the token limit cut off; a `prepare_next_turn` hook can swap the context or provider between turns. A tool can declare an `output_schema` and return `structured` output beside its text, and return an error result (`is_error`) when a failure has output to go with it. A tool that calls other tools while it runs (`Tool::execute_with`) gets the loop's `ToolRunner`, which puts each call through the same argument shim, schema check, `before_tool_call`, and `after_tool_call` as the model's own, with the calling call as the hooks' `parent`. Every adapter puts the transcript through the same transform first (another model's thinking as text, failed turns left out, a result for every call, images downgraded for a text-only model) and retries a request that fails before it streams. A `Provider` turns a request into a stream of assistant events and never fails: errors become an assistant message with `stop_reason` `error` or `aborted`. The crate also ships `agent::harness::AgentHarness`, a general agent over the loop for hosts other than Lorca (model switching through a provider factory, skills and prompt templates, queues, hooks, events, an example chat), with persistence left to the host; the Lorca CLI uses the loop directly. `docs/agent/` is the crate's own documentation.

```
on decrypted Job:
  build context from the chat (this bot's turns are assistant, other bots' text is user "[Name]: …",
                               this bot's tool rows become tool_call + tool_result pairs)
    + this turn's notes, which later turns leave out: the recent-work brief, the group's turn cue or
      a finished command's, "Continue." after the bot's own reply, a template bot's setup
    cache points: the rebuilt transcript's end, and where the last turn's ended
  run_agent_loop_continue(context, provider = the account's creds, tools, sink)
    events → job.started / job.finished / job.retry / job.thinking (chat, bot) → local app WS, which shows the bot at work
           → the turn and what it is doing (thinking, a retry) → this Runner's `machine` blob, which every
             other Device's CLI turns into the same events
           → each finished turn's usage → chat.usage (context size, cost so far)
           → a reply grows in chunks, not tokens: the text so far is re-sent at paragraph ends,
             or at a sentence end after 1.5 s of silence, never mid-word; the end sends it complete
           → every chunk and every completed message is encrypted with the account DEK → relay,
             so a paired phone watches the reply grow the way the local app does
    tool calls execute: each call's row goes up as the app sees it when the call starts, for the
                        status line on other Devices, and whole when it ends
  a pending confirmation or a turn ending with a reply or failure → an encrypted phone push (see Notifications)
```

Turns in one chat run one at a time on a Runner. A direct turn registers an `AgentMessageQueue` from `crates/agent` while it owns the chat lock. A new user message goes into that queue, and the agent loop drains it at its next safe boundary: the current provider step and any tool calls finish, then the message is added before the next provider call. Until then the message is `queued`: the Runner marks it before it pushes it and clears it when the turn reads it (the promotion), when a turn starts on it as its trigger, or on Stop, so every Device shows it waiting with Send now under it. `chats.send_now { chat_id, message_id }`, here or sealed to the bot's Runner as a `request`, has the turn read it at once (`turns::send_now`): every command running in the chat goes to the background and runs on (`Sessions::background_chat`, so a call waiting on one returns), then the turn's `StepInterrupt` cancels the step, so a reply in progress stops where it got to (its words stay a bubble) and other tools are cancelled, and the loop reads its queue. On a Windows before 10 1809, where a command runs on pipes and no session keeps it, the cancelled step stops the command. Send now is for direct chats. A question never holds a message back: the user's message dismisses whatever the chat's turn is asking them (a command's card or a permission card; `mcp::dismiss_questions`), the action does not run, and the call returns telling the bot the user wrote instead of answering, with a hint that ends the run unless the message is there to read next. A question that would go up while the queue holds a message is dismissed without asking. In a group, where a member's turn has no queue, the dismissed call ends the member's turn, and the room the message admitted answers it. Every message still admits a Job, so delivery survives Device races; the active turn marks messages it actually promotes, and those Jobs exit when they later reach the chat lock. In a group, a newer room waits while the current member settles, then takes the lock before another member starts. `chats.stop` is separate: it cancels active and waiting jobs immediately and sends a sealed `job_cancel` to another Runner.

## Notifications

Replies, failed responses, and pending confirmations reach the user wherever they are not looking.

- **Phones** (`crates/cli/src/push.rs`): when a turn ends with a reply or a failed response, or a question appears (a pending permission card, or a command's card that asks), the Runner seals a notice `{ title: the bot's name, subtitle: the group's title, body: the first 280 characters, chat_id }` and posts it to the relay's `/v1/push`. A post the relay does not take (no answer, `429`, or a `5xx`) goes again 2 s later and then after twice the last wait, until a minute has passed, so a turn that ends while the relay restarts still alerts; a `401` (a relay that restarted with a new `--secret`) signs in again before the next try, and any other `4xx` is final. The envelope is `nonce(12) || ciphertext` of ChaCha20-Poly1305 under the push key with `push` as associated data: the IETF cipher, so iOS opens it with CryptoKit alone. Apple, Google, and the relay see "New reply" and ciphertext. On an iPhone the notification service extension (`mobile/targets/notify`) reads the push key from the app group's keychain, opens `c`, and sets the title, subtitle, body, thread, and `chat_id` before the alert shows; on Android `PushService` in the native module opens it through the core (`push_open(home, c)`, which needs only `machine.json`) and posts the notification. A push that cannot be opened shows the fixed words. Android's FCM tokens come from the Firebase project `lorca-a03db` (`mobile/google-services.json` through `android.googleServicesFile`, one client for `app.lorca` and one for `app.lorca.dev`), and the relay's `--fcm-service-account` is a key of the same project.
- **The macOS app** (`Notifier.swift`) posts a system notification itself from the CLI's events: a new question (a pending permission card, or a command's card that asks) alerts while the turn waits for an answer; on `job.finished` it takes the bot's last completed or failed response in that turn, for a turn on this Runner or another. A failure shows the error text, including when the bot sent partial output first. Confirmation alerts say what action needs approval; repeated card updates do not repeat the alert, and resolving or removing a card clears its Mac notification. A click brings the app forward on the chat; opening a chat clears what was posted for it. The Dock badge (`AppDelegate.swift`) shows the sum of the chats' unread message counts and clears when that total is zero or the Device has no identity.
- **Read on another Device**: the Runner waits three seconds before asking for a phone push, and the macOS app waits the same interval before posting its notification. Replies, failed responses, and questions (pending permission cards, command cards that ask) each count as unread when they arrive. Both notification paths check the chat's current unread count after the wait; an encrypted `ClearUnread` from a paired Device cancels the alert. A confirmation is checked again for a pending decision, so answering, denying, or expiring it during the wait cancels its alert. They check again after push authentication and before each retry of a push, or after notification permission, and drop a pending alert if its account or chat is gone. This is a grace period for sync: a read mark that arrives after delivery cannot prevent the alert that already showed.
- **Watching**: neither fires for a reply, failure, or confirmation the user watches arrive. The macOS app tells its CLI which chat is on screen while it is frontmost (`ui.watching { chat_id | null }`, cleared when the app disconnects); the Runner skips the push for that chat and the app skips its own notification. The phone app shows no banner for the chat it has open while it is in front. On iOS the notification handler declines it. On Android, where `PushService` posts the notification itself, the JS side hands the native module the chat on screen (`setOpenChat`) and the module follows the activity's resume and pause itself, so a push that lands as the user leaves is not lost behind a busy JS thread; while the app is in front `PushService` posts nothing for that chat, and what it posted for the chat comes down when the chat comes on screen.
- **Phone reads**: the focused chat route sets `openChatId`, and the engine follows the app's foreground state. While both are active, unread counts arriving in roster events or snapshots trigger `chats.mark_read`; returning to the app reads the visible chat too. An inactive or backgrounded phone leaves new replies unread, even while the chat remains mounted. A read mark acknowledges replies already received, so an open chat on a disconnected phone does not suppress later replies.
