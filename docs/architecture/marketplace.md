# Marketplace

The marketplace (`crates/cli/src/marketplace.rs`), after Grok Bot's, offers plugins and bots: a JSON index of plugin manifests (`plugins`, the [plugins](plugins.md#plugins) a Runner installs) and bot templates (`bots`). An entry with `featured` is listed under Featured Plugins or Featured Bots, in index order, and `category` names its section, one of Grok Bot's filter categories (`credentials`, `productivity`, `communication`, `design`, `code`, `data`, `sales`, `finance`, `research`, `support`). Each remote plugin in the index is the service's own server, and it needs no account, signs in through dynamic client registration with the Runner's loopback redirect (GitHub's device flow aside), or takes a personal API key the user copies from the service (Zhihu, Metaso). Slack, Gmail, Google Calendar, and Google Drive are the exception: they take the OAuth client of an app the user registered, in their setup, and declare `named_accounts`; their setup, service eligibility, and account instances are in [Integrations and named accounts](integrations.md). `marketplace { query? }` answers with the plugins, each with the Runners that have it, and the bots, each routine with its schedule in words (`schedule_text`); a query keeps the entries that have every word.

## The index

The index is `crates/cli/marketplace/index.json`: a `version`, the UTC time it was `updated`, and the `plugins` and `bots` in order. Every build carries it, and the site serves it, minified, at `https://lorca.app/marketplace/v1.json` ([Website](website.md)), so a plugin or bot added to it reaches every Device without a release: edit the file, merge, and deploy the site. A change must move `updated` later (`bun run check:catalog`, and the Catalog workflow on a pull request).

**Updating the index**: the index in use is the one with the latest `updated` of the bundled one, the one cached in `marketplace.json` in Lorca's folder, and the served one, and a later one replaces it whole, so an index can also drop or reorder entries. `lorca serve` checks the server when it starts; after that every app's `bootstrap` checks, as does each use of the index (the marketplace, an install from it, a bot added from a template, and a bot's `search_plugins` and `install_plugin`), and `marketplace.reload` (`lorca marketplace reload`) checks even within the hour. Any other check within the hour of the last one is skipped, and nothing checks on a timer. A check sends the cached ETag as `If-None-Match`, so an unchanged index costs a 304, and gives up after five seconds; a failure keeps the index in use. A bot's search or install that finds nothing checks first, at most every five minutes, since the plugin may have been published after the last check. `LORCA_MARKETPLACE_URL` points the checks elsewhere (a mirror, or `bun run web`'s `/marketplace/v1.json`), and `LORCA_MARKETPLACE_FETCH=0` turns them off; only `lorca serve` and `lorca marketplace reload` turn checking on, so tests never reach lorca.app. The request and its ETag are the model catalog's (`crates/cli/src/served.rs`, [Providers](providers.md)).

Installed marketplace plugins follow the index in use: when `lorca serve` starts and whenever a later index arrives, the Runner replaces the manifest it installed with the index's when that changed, matching named instances by `service_id` and retaining each instance id and account name, keeping variables, secrets, and sign-ins, so a new sign-in method or server reaches existing installs without a reinstall. A plugin the index no longer lists, and one installed from its own manifest (`plugins.install { runner_id, manifest }`), are left as they are.

**Reading an index**: an index written for a newer Lorca never breaks an older one. Fields a build does not know are ignored. An entry it cannot read (a server type it does not know, an id that is not lowercase letters, digits, and dashes, a routine whose schedule it cannot parse) or whose id came earlier in the list is left out. An index is refused whole when its `version` is not 1, its `updated` is not `YYYY-MM-DDTHH:MM:SSZ`, or it lists no plugin the build reads. A change older builds cannot read is served as `v2.json` beside v1. The index is not signed, and it names what installed plugins run: their commands, servers, headers, and read-only tools, so what lorca.app serves over HTTPS changes them on every Runner.

## Bots from the marketplace

A bot template is a bot's starting point: `id`, `name`, `summary` (its line in the marketplace), `description` (the new bot's description, so its instructions), `symbol_name` and `accent`, `category`, `featured`, `author`, `plugins` (the marketplace plugins it works with), `routines` (`name`, `schedule`, `prompt`), and `memory` (facts it starts with). `bots.create { template_id, greeting }` makes a bot from one, as Grok Bot's template import does: the template's profile, its routines added paused, and the app's `greeting` ("Hi Researcher, introduce yourself.", in the user's language) as the user's first message in its DM. The turn that answers carries the setup (`Job.setup`: a `TemplateSetup` of the plugins, the routines' names, and the facts), and the Runner puts a cue after the greeting (`turns::setup_cue`): save the facts with `memory_update`, ask once whether to turn the routines on and resume them only on a yes, call `install_plugin` for each plugin the Runner lacks (the user allows or denies each on its card), and greet the user. The cue exists only in that turn's context; the chat keeps the greeting and the reply.

## In the apps

Any bot is also shared as a [template](templates.md), by a link or a file, that makes a bot on another Runner or account; those are separate from this index.

The macOS marketplace (`macos/Sources/Lorca/Marketplace/`) is a sheet, as Grok Bot's is an overlay, of up to 800 by 700: the marketplace icon at the foot of the chats' sidebar opens it, as do File › Marketplace… (⌘⇧M, so the command palette has it too), Add from Plugins… in a DM inspector's Plugins section (on that bot's Runner), and the same row in Settings › Plugins (on the picked Device). Its top bar has Back, the Runner that plugins install on and bots are added to (a pop-up when there are two or more), and Close, which Escape presses from any page. The home page has the title with "N installed" (the Runner's plugins, on a page of their own), the search over plugins and bots, and then Featured Plugins, Featured Bots, and a section per category (its plugins, then its bots, leading with what the featured sections do not show and keeping half the rows for bots when it has both), each a two-column grid of up to four rows with View all (a featured section's lists every plugin or every bot, the featured ones first); a query puts the results in their place, and a category's View all or the results offer All, Plugins, and Bots when both kinds are there. A plugin's row offers Add, then shows Added, Connect, or Set Up (the last two open the plugin's own sheet), or its state in a word or two, with what it said in full as the tooltip; its page has the description, its state on the Runner with Manage…, its servers, skills, and setup variables, and its developer, category, and website. A service with named accounts adds one at a time: Add, and the page's Add Account… once it has one, ask for the account's name in an alert (a blank name is the next free Account N) and open the new account's sheet. Its row reads Added once one account is ready; its page lists Accounts on the Runner, each with its state in a word or two (Connected, Needs a sign-in, Needs more access, Needs setup, Can’t connect), and a click on an account opens its sheet. A bot's row and page offer Add; its page shows Instructions, Memories, Routines, and Plugins beside a list of the four, as Grok Bot's does, and adding the bot closes the sheet on its chat. The plugins' marks, rows, and sheets elsewhere in the apps are in [Codemode and Plugins](plugins.md#plugins).
