# macOS app

SPM `Lorca.app`, AppKit.

The app starts the bundled `lorca` (Contents/Resources/bin/lorca; `LORCA_CLI` overrides, PATH is the fallback) as `lorca serve --port <port>`, logs it under `~/Library/Logs/Lorca/` or `~/Library/Logs/Lorca Dev/`, and restarts it if it exits. Lorca uses port `4862`; Lorca Dev uses `4863`. If something already listens on that build's port, that instance is used.

Which window a launch opens depends on the identity, which only the CLI knows, so the app keeps a hint: `Preferences.hadIdentity`, whether the CLI's last answer had one. With it, the main window opens during AppKit launch with a loading indicator and the saved inspector visibility. Without it (a fresh install, or a Mac whose identity went away) no window opens until the snapshot picks onboarding or the main window, so onboarding never replaces a main window that just appeared; a startup failure or the 2.5-second deadline opens the main window on the offline recovery controls. The main window's inspector keeps its width while the snapshot loads; the chat and inspector views are built when their data arrives, and automatic layout changes apply without a collapse animation. A dedicated serial queue probes localhost, locates and spawns the CLI, and reads its readiness pipe while AppKit builds the window on the main thread. Only lifecycle notifications and the ready callback return to the main thread; stopping the launcher fences queued starts and terminates its child. It launches its child with `--ready-stdout`; after loading local state and binding its server, the CLI flushes `{"event":"ready","port":<port>}` to stdout. The app reads this startup pipe and opens its websocket on that signal. CLI logs go to stderr, and the app saves both streams in its log. An existing CLI is used once the localhost probe succeeds. A dropped connection backs off from 400 ms and asks the launcher to prepare the endpoint again; a child restart connects on its new readiness signal.

The first request is `bootstrap`, which carries identity, chat metadata, and messages together. The app buffers incoming events until the snapshot arrives, applies the snapshot and buffered changes with view notifications held back, then publishes one complete state with the connection marked ready. The sidebar creates its scroll view and outline when rows first arrive, with their previews and activity order, and restores the selection after creating the rows. Settings navigation, the Device picker, and offline/empty-state views are created on first use. The window configures its saved frame and toolbar before attaching the split view, sized to that frame, since a window takes the size of its content view controller; it uses deferred creation and is ordered front once with opening animations disabled. Notifications and the updater start after this initial presentation (or after startup fails). A startup failure or 2.5 seconds without a snapshot replaces the loading indicator with the offline recovery controls. `LORCA_TRACE_STARTUP=1` writes launch milestones and elapsed times to `startup.log` in the app's log directory. CLI milestones are recorded on the launcher queue and window milestones on the main thread. `bun run test:mac-startup` checks that the launcher progresses with the main thread blocked, handles fragmented readiness and early exit, and cancels queued starts without leaving a child running.

First run: the CLI's `bootstrap` snapshot has `has_identity: false`, and the app shows onboarding: create (the CLI returns the phrase), restore (phrase → relay), or pair (paste the string from a computer that already has the identity). After create, the user names the first bot (the CLI's default Chef, edited through `bots.update`), then connects an API-key or subscription provider for the account (skippable; Skip for Now during a browser sign-in cancels it through `providers.auth.cancel`). In Chinese, onboarding offers **幕僚长** and a Chinese description for the default profile; Continue saves those values through `bots.update`. Restore and pair wait a moment for the first sync and show the provider step only when the account has none connected. Onboarding is the app's window until it finishes: closing it leaves the app running, the Dock icon brings it back (`applicationShouldHandleReopen`), a notification click brings it forward, and the menu commands that open the main window (New Bot, New Group Chat, Marketplace, Pair a Device, Find, Command Palette) are disabled. Settings › Advanced › Show Onboarding Again, like Debug › Show Onboarding, hides the main window and opens onboarding. Over an identity nothing there can run (create, restore, and pair refuse), so closing it is Cancel: the main window comes back as it was, on the same pane with its history, and a notification click does the same before opening its chat.

Settings is a mode of the main window. The foot of the sidebar has two icons and a button: the gear opens General (as ⌘, does), this Mac's icon, red while the CLI is not answering and orange while the CLI cannot connect to the relay (its tooltip says why), opens the Devices pane on this Mac, and at the other end the marketplace icon (`circle.grid.2x2`) opens the marketplace. The sidebar gives way to the settings sidebar: a search field where the chats' one is, the panes, and Back (a chevron and the word; Escape does the same) in the footer, where the chats' sidebar has the two icons (General, Providers, Auto-review, Plugins, Bots, Devices, Advanced). Plugins, Bots, and Devices each show one Device, picked from a pop-up in the window's toolbar: a standard toolbar item at the content area's trailing edge, in the toolbar while Settings is up. On macOS 26 the item's view is a plain container holding the pop-up on a glass capsule of its own (`NSGlassEffectView`), and the other panes hide that capsule: a toolbar item entering, leaving, or hiding makes the toolbar lay its glass out again, which blinks the back and forward buttons, and a hidden pop-up in a standard item leaves its platter behind. It lists the paired Devices with Pair a Device at its foot (`MainWindowController.updateToolbar`). The titlebar's Create button and the inspector toggle belong to the chats and leave while Settings is up. It starts on this Mac, and the pick holds across the three panes: the root keeps it in `settingsDeviceID` and hands it to the `DevicePaneViewController`s (`Settings/DeviceSettingsViewControllers.swift`). Providers has the account's credentials, with Connect and Disconnect for each; Bots lists the bots assigned to the Device, each opening its chat; Plugins has what the Runner installed and the marketplace; Devices has the machine key, role, last seen, relay (with why the last try to connect failed, while it is not connected), and Unpair. A Device that is not a Runner shows a note in Plugins and Bots. A query (⌘F focuses the field) narrows the list to the panes and settings that match, each setting under its pane (a Device pane's bots and plugins are those of the picked Device); picking a setting opens the pane, scrolls to its row, and flashes it. The index is `SettingsEntry` (`Settings/SettingsSearch.swift`): a title, keywords, and the row label the panes take their labels from, so the results and the pages share one spelling. Both sidebars use a standard `NSSearchField`, which brings AppKit's capsule and focus ring. From macOS 26 a sidebar's list fills the pane and scrolls under everything in it, as System Settings' does: the bars (the chats' search field and footer, Settings' search field and Back footer) are `NSSplitViewItemAccessoryViewController`s the root sets on the sidebar's split view item for whichever sidebar shows, so AppKit insets the list by them through the safe area and softens the rows passing behind them and the titlebar. On macOS 14 and 15 the bars and the list are stacked inside the pane (`SidebarChrome.floats`). The selection says which sidebar shows (`Selection` is `chat` or `settings(pane)`); opening a Device from the inspector picks it and lands on Devices, and Back returns to the chat that was open. While Settings is up the toolbar has back and forward ahead of the title (a navigational `NSToolbarItemGroup`), walking the panes visited since Settings opened (`RootSplitViewController.paneHistory`). The panes' cards follow System Settings: a bold group title on the rows' text column, a fill with 12 pt corners and no border, and dividers between the rows' text margins (`SectionView.style = .heading`; the inspector keeps the captioned, bordered card). A pane's pop-ups are `SettingsPopUpButton`s (`Design/Controls.swift`), System Settings' look: the choice as plain text, as wide as it needs, and the chevrons on a small rounded platter, which grows to hold the text too under the pointer. The panes show while the CLI is not answering, since the CLI port and the relay URL live there. While onboarding is up there is no main window, and ⌘, opens General and Advanced in a small window of their own.

Updates come through [Sparkle](https://sparkle-project.org), embedded in Contents/Frameworks (`App/Updater.swift`). A release build polls the appcast at `https://mac-releases.lorca.app/appcast.xml` (`SUFeedURL`), checks each archive against the EdDSA public key in Info.plist (`SUPublicEDKey`), and swaps the bundle, CLI included. **Check for Updates…** is in the app menu, and General has the version, the last check, and switches for automatic checks and automatic installs. A debug build, the dev loop's bundle, leaves all of it out. The version is `"version"` in the root `package.json`, which `scripts/app.ts` writes into Info.plist. `bun run release-mac` builds, signs with the Developer ID under the hardened runtime, notarizes, and publishes the disk image, the Sparkle archive, and the appcast to the R2 bucket behind that domain: [docs/releasing-mac.md](../releasing-mac.md).

The command palette (⌘K, View › Command Palette…, `Palette/`) is a borderless child panel of the main window on Liquid Glass (`NSGlassEffectView`; the menu material before macOS 26): a search field over an inset `NSTableView` of actions, chats, historical message matches, and settings. The actions are the menu bar's own items, looked up by selector (`PaletteIndex.commands`): the palette validates the menus while the main window is still key, lists the enabled items with their titles and key equivalents, and runs one by sending the item's action down the responder chain after the panel closes, so a command reads and behaves as it does in the menu. A query is debounced into `chats.search`, which scans local chat metadata and visible message rows on demand; message rows show the newest matching snippets, and matching tokens in titles and snippets are highlighted. A chat opens with the composer focused; a settings pane opens in place, and a query also finds the settings on the panes (`SettingsSearch.entries`), which open scrolled to their row. The field keeps the keyboard while the arrows move the selection, the pointer selects as in a menu, and Return, a click, Escape, or the panel losing the keyboard closes it. The chats sidebar's search field is the palette's other door: a click on it, or ⌘F outside Settings, opens the palette, and the field never takes the keyboard. The phone's chat-list search bar calls the same API and shows highlighted chat and message results.

Chrome: split view, vibrancy, bubbles, `@` mentions. The titlebar is AppKit's own: the transcript and the settings panes run their scroll views under it, so the header has no background at rest and gets the scroll-edge effect and its separator once content is beneath it. The app renders CLI events and applies its own edits optimistically; `LORCA_MOCK=1` runs the seeded demo instead. Keys stay in the CLI.

Transcript: a view-based `NSTableView` (`Chat/ChatViewController.swift`), which builds cells for the rows on screen and, past a few hundred rows, estimates the heights of the rest until they come into view. `ChatLayout` parses a message's Markdown and measures it once per message version and bubble width, and the cell lays out from the segment heights it measured, so a reload or a resize asks for heights it already has. A bubble stops growing at 580 pt, so resizing a wide window measures nothing; during a live resize only the rows on screen are measured, the rest once it ends. A new message, the working row, and an older page go in as one run of inserted and removed rows (`ChatRow.changedRun`), which leaves the other cells, and a text selection in them, alone. Scrolled back, the first message on screen holds its place through replies, older pages, and width changes. Accessibility clients see the table the same way (`Chat/TranscriptTableView.swift`): one row element per row, whose words ("Chef: …", the message as shown) and frame come from the chat, and whose cell is the real one while the row is on screen and a stand-in with the same words while it is not. So VoiceOver or the Accessibility Inspector reads the whole transcript without the table building a cell. A row keeps its element through replies and older pages, and a row a screen reader moves to scrolls into view between the titlebar and the composer, which near the first message asks for the page before it.

Sidebar: an `NSOutlineView` (`Sidebar/SidebarViewController.swift`) with one item per chat, kept for as long as the chat is listed. Only the first rows come in with a reload. After that, a store event moves, inserts, or removes the rows whose place in the order changed (new activity moves a chat up in one move, without animation), and a cell is reconfigured only when what its row shows (`SidebarChatCell.Content`: avatars, working dot, title, preview, stamp, pin, unread count) changed. Cells come from `makeView(withIdentifier:)`, and a moved row keeps its row view, cell, and selection.

Inspector: `Inspector/InspectorViewController.swift` compares what each section would show with what it last showed on every store event and touches only a section that changed. A changed section reconfigures the rows it keeps for each bot, Runner, routine, and plugin; Runs with builds its pop-ups again only when the provider, model, thinking level, or credential changed, and the usage rows take each turn's values in place. Collapsed, or in a closed window, the inspector skips reloads and memory fetches and catches up in `viewWillAppear`.

Composer: the `+` button opens a file panel; files dropped on the composer or pasted (file URLs, or an image with no text beside it, written to a temporary PNG) attach the same way. Chips above the text show a thumbnail or the file's name and size, each with a remove button; a message can be attachments alone. The draft belongs to the chat on screen: opening another chat clears it (its text, files, and `@` picks), and a visit to Settings keeps it. The app mints the attachment ids and hands the CLI paths (`chats.send { attachments: [{ id, path, name, mime, width, height }] }`), so the bubble it shows at once matches the message the CLI echoes back. In a bubble, images are thumbnails sized from the width and height in the message and files are cards; a click opens the file. An attachment from another Device is fetched through `files.path`, which pulls the `file` blob from the relay into `~/.lorca/files/` and answers with the path; the bubble reloads when it lands. The Dictate button (`mic.fill`, the primary disc while the field is empty) starts Apple's speech recognizer (`Speech` + `AVAudioEngine`, `Dictation.swift`). While recording, the text gives way to Grok Bot's pill: a stop square, the elapsed time, and bars that follow the input level, with Send still beside it. The transcript accumulates and lands at the caret when the square is clicked; Send commits it and sends in one go; Escape discards it. The recognizer listens in the language of the keyboard input source in use (a Pinyin input method means zh-CN, whatever the system language), else the first of the system's preferred languages it supports (matched on language and region, so "zh-Hans-CN" finds "zh-CN"), or the language chosen in Settings › General or the button's right-click menu (`Preferences.dictationLanguage`). The bundle declares `NSMicrophoneUsageDescription` and `NSSpeechRecognitionUsageDescription`.

Working state, after Grok Bot: the CLI's `job.started` / `job.finished` events (and `running_turns` in the snapshot) name the chat and bot of every turn in flight on any Device. From them the app shows a breathing green dot on the bot's avatar in the sidebar, an "is working" row after the last message (the bot's avatar beside a shimmering line: "Working…" in a DM and "Chef is working…" in a group, or what the one working bot is doing: "Thinking…" from the Runner's `job.thinking`, sent when the model starts thinking and read until that bot's next message or the end of its turn, else its latest tool as an activity such as "Running command: Install dependencies…" from the call's `description`, kept between calls so it does not flash), the Stop button, and "Chef stopped without replying" when a turn ends with nothing said. A turn reads the same on every Device, whichever one started it. Each Device lists the turns in flight on it (the turns it runs and the group exchanges it holds, each with what it is doing, thinking or a retry, until the bot's next message) in its `machine` blob (`turns`), uploaded again whenever the list changes, and a Runner uploads each call's row as the call starts. Every other Device keeps each Device's latest list (`device_turns` in SQLite) while the relay's last machine list shows that Device online (`turns_online`, kept while this Device's own socket reconnects) and drops it when the relay shows it offline; a Device uploads its list again whenever its socket connects. So a Runner that quits mid-turn never shows that turn again, and one that only lost the relay shows it again when it is back. The CLI merges those lists with its own jobs, including one it sent to a Runner that has not listed it yet, and tells the app what changed (`App::turns_changed`). The Device that asked for a turn keeps the job in SQLite (`sent_jobs`) until its `job_result` arrives or its five-minute wait runs out, so a CLI or phone core that starts again shows its own turn at once (`runtime::resume_sent_jobs`) and the other Devices' turns once the relay says they are online. Stop cancels a turn wherever it runs: the CLI seals `job_cancel` to the Device that lists it. Replies arrive in chunks: the bubble appears with the first completed paragraph (or sentence, after 1.5 s) and grows by paragraphs, the way Grok Bot's server re-sends a message as it grows. Tool calls never appear in the transcript, as in Grok Bot: the CLI keeps them as `tool` messages so a later turn can rebuild its context, and the app renders none of them, leaving the "is working" row (with the running tool's activity) and whatever the bot says before and after its work. The exceptions are a sent `message_bot`, shown as the "Messaged ◉ X" marker, and a `bash` call's command card while the command needs the user (`Chat/CommandCellView.swift`, `ToolInvocation.isShown`; see Terminal sessions): while Auto-review asks, who wants to run it, the command's first line in a code block that opens the whole command in a sheet on click, why, Allow once, Always allow, and Deny, and the rule Always allow adds; once the bot handed the running command over, Stop on its title's line and its last lines in a code block of their own that grows to six lines and then scrolls, the newest line in view and an edge with more lines past it fading out (a gradient mask on the scroll view's layer, since the block's color is see-through); at a question, a field that hides what is typed unless the question is a yes or no, with Send. When the card leaves with the cursor in that field, the composer takes it. Running tasks (see Terminal sessions in [Tools](tools.md)) sit behind a `HoverButton` with the terminal symbol in the toolbar at the content area's trailing edge (`MainWindowController.updateRunningTasks`), whose item carries the toolbar's own badge (`NSItemBadge`, macOS 26 and later) with their number when there are two or more. The item stays in the toolbar while a chat shows and only its button hides, so the toolbar keeps its layout, and the button stays while its transient popover (`Chat/RunningTasksViewController.swift`) is open; clicking a command in it closes the popover and opens the whole command in a sheet. Sidebar rows carry an unread count pill beside the preview (the CLI counts each finished bot reply, failed response, and pending confirmation, from its own turns or the relay, unless the app reports that chat as the one on screen; reading a chat on one Device uploads a `ClearUnread` chat blob that zeroes the count on the others, and so does a message the user sends, on every Device it reaches), a preview without a "You:" prefix (a bot's name only in groups; "Messaged X" and "Message from X: …" for bot-to-bot messages), and a stamp that is the time today, "Yesterday", the weekday within a week, then the date. A transcript inserts "Today 4:13 AM" separators after fifteen minutes of silence; in a group a bot's name sits above the first bubble of a run with its avatar beside that bubble's bottom edge, the run's later bubbles follow 4 pt below in the same column, and a DM shows neither.
