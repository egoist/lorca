# macOS app

SPM `Lorca.app`, AppKit.

The app starts the bundled `lorca` (Contents/Resources/bin/lorca; `LORCA_CLI` overrides, PATH is the fallback) as `lorca serve --port <port>`, logs it under `~/Library/Logs/Lorca/` or `~/Library/Logs/Lorca Dev/`, and restarts it if it exits. Lorca uses port `4862`; Lorca Dev uses `4863`. If something already listens on that build's port, that instance is used.

Which window a launch opens depends on the identity, which only the CLI knows, so the app keeps a hint: `Preferences.hadIdentity`, whether the CLI's last answer had one. With it, the main window opens during AppKit launch with a loading indicator and the saved inspector visibility. Without it (a fresh install, or a Mac whose identity went away) no window opens until the snapshot picks onboarding or the main window, so onboarding never replaces a main window that just appeared; a startup failure or the 2.5-second deadline opens the main window on the offline recovery controls. The main window's inspector keeps its width while the snapshot loads; the chat and inspector views are built when their data arrives, and automatic layout changes apply without a collapse animation. A dedicated serial queue probes localhost, locates and spawns the CLI, and reads its readiness pipe while AppKit builds the window on the main thread. Only lifecycle notifications and the ready callback return to the main thread; stopping the launcher fences queued starts and terminates its child. It launches its child with `--ready-stdout`; after loading local state and binding its server, the CLI flushes `{"event":"ready","port":<port>}` to stdout. The app reads this startup pipe and opens its websocket on that signal. CLI logs go to stderr, and the app saves both streams in its log. An existing CLI is used once the localhost probe succeeds. A dropped connection backs off from 400 ms and asks the launcher to prepare the endpoint again; a child restart connects on its new readiness signal.

The first request is `bootstrap`, which carries identity, chat metadata, and messages together. The app buffers incoming events until the snapshot arrives, applies the snapshot and buffered changes with view notifications held back, then publishes one complete state with the connection marked ready. The sidebar creates its scroll view and outline when rows first arrive, with their previews and activity order, and restores the selection after creating the rows. Settings navigation, the Device picker, and offline/empty-state views are created on first use. The window configures its saved frame and toolbar before attaching the split view, sized to that frame, since a window takes the size of its content view controller; it uses deferred creation and is ordered front once with opening animations disabled. Notifications and the updater start after this initial presentation (or after startup fails). A startup failure or 2.5 seconds without a snapshot replaces the loading indicator with the offline recovery controls. `LORCA_TRACE_STARTUP=1` writes launch milestones and elapsed times to `startup.log` in the app's log directory. CLI milestones are recorded on the launcher queue and window milestones on the main thread. `bun run test:mac-startup` checks that the launcher progresses with the main thread blocked, handles fragmented readiness and early exit, and cancels queued starts without leaving a child running.

First run: the CLI's `bootstrap` snapshot has `has_identity: false`, and the app shows onboarding: create (the CLI returns the phrase), restore (phrase → relay), or pair (paste the string from a computer that already has the identity). After create, the user names the first bot (the CLI's default Chef, edited through `bots.update`), then connects an API-key or subscription provider for the account (skippable; Skip for Now during a browser sign-in cancels it through `providers.auth.cancel`), or picks a custom provider preset or Other Server, whose Set Up button opens the custom provider sheet over onboarding and moves the first bot to the provider it saves. In Chinese, onboarding offers **幕僚长** and a Chinese description for the default profile; Continue saves those values through `bots.update`. While a restore or a pairing runs, its field and button are disabled beside a spinner; Back cancels a pairing still waiting on the other Device (`pair.abort`), and stays disabled through a restore and the sync after either. Restore and pair then show "Syncing the account from the relay…" and ask the CLI for the account's providers (`sync.account`), which it answers once its first pull has brought the account's credentials, or after 30 seconds; the provider step shows only when the account has none connected. The last step says how the Mac came by the identity (the first Device, a restored identity, or a paired Mac) and points to Pair a Device in the File menu, which every paired Mac offers. Onboarding is the app's window until it finishes: closing it leaves the app running, the Dock icon brings it back (`applicationShouldHandleReopen`), a notification click brings it forward, and the menu commands that open the main window (New Bot, New Group Chat, Marketplace, Pair a Device, Find, Command Palette) are disabled. Settings › Advanced › Show Onboarding Again, like Debug › Show Onboarding, hides the main window and opens onboarding. Over an identity nothing there can run (create, restore, and pair refuse), so closing it is Cancel: the main window comes back as it was, on the same pane with its history, and a notification click does the same before opening its chat.

Settings is a mode of the main window. The foot of the sidebar has two icons and a button: the gear opens General (as ⌘, does), this Mac's icon, red while the CLI is not answering and orange while the CLI cannot connect to the relay (its tooltip says why), opens the Devices pane on this Mac, and at the other end the marketplace icon (`circle.grid.2x2`) opens the marketplace. The sidebar gives way to the settings sidebar: a search field where the chats' one is, the panes, and Back (a chevron and the word; Escape does the same) in the footer, where the chats' sidebar has the two icons (General, Providers, Auto-review, Plugins, Bots, Devices, Advanced). Plugins, Bots, and Devices each show one Device, picked from a pop-up in the window's toolbar: a standard toolbar item at the content area's trailing edge, in the toolbar while Settings is up. On macOS 26 the item's view is a plain container holding the pop-up on a glass capsule of its own (`NSGlassEffectView`), and the other panes hide that capsule: a toolbar item entering, leaving, or hiding makes the toolbar lay its glass out again, which blinks the back and forward buttons, and a hidden pop-up in a standard item leaves its platter behind. It lists the paired Devices with Pair a Device at its foot (`MainWindowController.updateToolbar`). The titlebar's Create button and the inspector toggle belong to the chats and leave while Settings is up. It starts on this Mac, and the pick holds across the three panes: the root keeps it in `settingsDeviceID` and hands it to the `DevicePaneViewController`s (`Settings/DeviceSettingsViewControllers.swift`). Providers has the account's credentials, with Connect and Disconnect for each, then the custom providers (`server.rack`, Edit…) and an Add Provider… row whose menu lists presets (OpenAI, OpenRouter, Gemini, Groq, Together AI, Ollama, LM Studio, then OpenRouter Decisions, OpenAI Decisions, TypeSafe; one the account has is checked and opens it) and Other Server…; the custom provider sheet (`Sheets/CustomProviderViewController.swift`) takes a name (the matching preset's or the host when left empty), the protocol, the base URL with a note naming the URL the CLI will call, and an optional key, and loads the server's models through `providers.list_models` half a second after those stop changing: a checklist with each model's name, id, window, and an eye for images, a search field that filters it and offers Add "…" for an id the server does not list (Return adds it), the count, and a Default pop-up. A short list (eight or fewer, a local server's) starts checked. It opens an existing provider with its key fetched through `providers.api_key`, its saved models checked above the rest of the listing, and Delete; Bots lists the bots assigned to the Device, each opening its chat; Plugins has what the Runner installed and the marketplace, each of a service's [named accounts](integrations.md) on its own row, then its own MCP servers ([MCP servers](mcp-servers.md#in-the-apps)); Devices has the machine key, role, a self-updating CLI's version with Update, last seen, relay (with why the last try to connect failed, while it is not connected), and Unpair, this Mac's too: there it is `identity.forget`, which brings back onboarding, and when this Mac holds the identity the confirmation is critical and says that the backup phrase becomes the only way to restore the identity. An unknown Device, a machine the relay lists that never sent its name or system (`Device.OS.unknown`), has a question mark for its icon, no model or OS, and a note above its key to unpair it if nobody recognizes it; Bots and Plugins show the same note. The demo, which has no CLI, opens onboarding over its account instead, as Show Onboarding Again does. A Device that is not a Runner shows a note in Plugins and Bots. A query (⌘F focuses the field) narrows the list to the panes and settings that match, each setting under its pane (a Device pane's bots and plugins are those of the picked Device); picking a setting opens the pane, scrolls to its row, and flashes it. The index is `SettingsEntry` (`Settings/SettingsSearch.swift`): a title, keywords, and the row label the panes take their labels from, so the results and the pages share one spelling. Both sidebars use a standard `NSSearchField`, which brings AppKit's capsule and focus ring. From macOS 26 a sidebar's list fills the pane and scrolls under everything in it, as System Settings' does: the bars (the chats' search field and footer, Settings' search field and Back footer) are `NSSplitViewItemAccessoryViewController`s the root sets on the sidebar's split view item for whichever sidebar shows, so AppKit insets the list by them through the safe area and softens the rows passing behind them and the titlebar. On macOS 14 and 15 the bars and the list are stacked inside the pane (`SidebarChrome.floats`). The selection says which sidebar shows (`Selection` is `chat` or `settings(pane)`); opening a Device from the inspector picks it and lands on Devices, and Back returns to the chat that was open. While Settings is up the toolbar has back and forward ahead of the title (a navigational `NSToolbarItemGroup`), walking the panes visited since Settings opened (`RootSplitViewController.paneHistory`). The panes' cards follow System Settings: a bold group title on the rows' text column, a fill with 12 pt corners and no border, and dividers between the rows' text margins (`SectionView.style = .heading`; the inspector keeps the captioned, bordered card). A pane's pop-ups are `SettingsPopUpButton`s (`Design/Controls.swift`), System Settings' look: the choice as plain text, as wide as it needs, and the chevrons on a small rounded platter, which grows to hold the text too under the pointer. The panes show while the CLI is not answering, since the CLI port and the relay URL live there. While onboarding is up there is no main window, and ⌘, opens General and Advanced in a small window of their own.

Updates come through [Sparkle](https://sparkle-project.org), embedded in Contents/Frameworks (`App/Updater.swift`). A release build polls the appcast at `https://mac-releases.lorca.app/appcast.xml` (`SUFeedURL`), checks each archive against the EdDSA public key in Info.plist (`SUPublicEDKey`), and swaps the bundle, CLI included. **Check for Updates…** is in the app menu, and General has the version, the last check, and switches for automatic checks and automatic installs. A debug build, the dev loop's bundle, leaves all of it out. The version is `"version"` in the root `package.json`, which `scripts/app.ts` writes into Info.plist. `bun run release-mac`, from a Mac or from the Release Mac app workflow on a `mac-v` tag, builds, signs with the Developer ID under the hardened runtime, notarizes, and publishes the disk image, the Sparkle archive, and the appcast to the R2 bucket behind that domain: [docs/releasing-mac.md](../releasing-mac.md).

The command palette (⌘K, View › Command Palette…, `Palette/`) is a borderless child panel of the main window on Liquid Glass (`NSGlassEffectView`; the menu material before macOS 26): a search field over an inset `NSTableView` of actions, chats, historical message matches, and settings. The actions are the menu bar's own items, looked up by selector (`PaletteIndex.commands`): the palette validates the menus while the main window is still key, lists the enabled items with their titles and key equivalents, and runs one by sending the item's action down the responder chain after the panel closes, so a command reads and behaves as it does in the menu. A query is debounced into `chats.search`, which scans local chat metadata and visible message rows on demand; message rows show the newest matching snippets, and matching tokens in titles and snippets are highlighted. A chat opens with the composer focused; a settings pane opens in place, and a query also finds the settings on the panes (`SettingsSearch.entries`), which open scrolled to their row. The field keeps the keyboard while the arrows move the selection, the pointer selects as in a menu, and Return, a click, Escape, or the panel losing the keyboard closes it. The chats sidebar's search field is the palette's other door: a click on it, or ⌘F outside Settings, opens the palette, and the field never takes the keyboard. The phone's chat-list search bar calls the same API and shows highlighted chat and message results.

Attention is a popover under a toolbar button beside Running tasks, shown while something waits on the user, and View › Attention (⇧⌘A); [Coordinator attention](attention.md#in-the-apps) describes it.

Chrome: split view, vibrancy, bubbles, `@` mentions. The titlebar is AppKit's own: the transcript and the settings panes run their scroll views under it, so the header has no background at rest and gets the scroll-edge effect and its separator once content is beneath it. The app renders CLI events and applies its own edits optimistically; `LORCA_MOCK=1` runs the seeded demo instead. Keys stay in the CLI.

The chat transcript is a view-based `NSTableView` with cached Markdown layout, incremental rows and complete accessibility. See [macOS chat](macos-chat.md#transcript).

Sidebar: an `NSOutlineView` (`Sidebar/SidebarViewController.swift`) with one item per chat, kept for as long as the chat is listed. Only the first rows come in with a reload. After that, a store event moves, inserts, or removes the rows whose place in the order changed (new activity moves a chat up in one move, without animation), and a cell is reconfigured only when what its row shows (`SidebarChatCell.Content`: avatars, working dot, title, preview, stamp, pin, unread count) changed. Cells come from `makeView(withIdentifier:)`, and a moved row keeps its row view, cell, and selection.

The Routines section, the routine sheet, and the Devices pane's Background service row are described in [Routines](routines.md#the-apps).

File › Share as Template… (also a DM's context menu) and New Bot from Template… open the [template sheets](templates.md#in-the-apps) in `Sheets/Template*.swift`; Settings › Shared Links lists the account's links. Info.plist registers `lorca://` (`lorca-dev://` for Lorca Dev), and `application(_:open:)` keeps such a link until the account and CLI are up.

A group's inspector lists its [project context](project-context.md#the-apps) under Group: a row per entry that opens it, and + to add one.

A bot's message offers Give Feedback… beside Reply, and the DM inspector's Feedback section, shown once the bot has any, holds the changes it suggests and All feedback ([Workflow feedback](feedback.md#in-the-apps)). The inspector reads `feedback.list` with the bot's memory and again on `feedback.changed`.

The inspector's Skills section, the skill sheet, and Save as Skill: [Playbooks](playbooks.md#app-and-api).

The DM Profile card's Access row opens the [Access sheet](bot-permissions.md#requests-to-the-user).

Inspector: `Inspector/InspectorViewController.swift` compares what each section would show with what it last showed on every store event and touches only a section that changed. A changed section reconfigures the rows it keeps for each bot, Runner, routine, and plugin; Runs with builds its pop-ups again only when the provider, model, thinking level, or the account's providers changed (custom providers follow the built-in ones in the Provider pop-up, and a custom provider's models fill Model), and the usage rows take each turn's values in place. Collapsed, or in a closed window, the inspector skips reloads and memory fetches and catches up in `viewWillAppear`. A chat with [durable tasks](tasks.md#in-the-apps) has a Tasks section; File › New Task… and the section title's + add one. While the chat's bots have something waiting for review, a section under the bots lists it, each row opening the review sheet ([Review queue](review-queue.md#in-the-apps)).

The composer accepts files, pasted images, replies, mentions and dictation. Its attachment previews and draft lifecycle are in [macOS chat](macos-chat.md#composer).

The inspector's Outputs section lists what the chat's bots published and opens each output's preview, check, and versions. See [macOS chat](macos-chat.md#outputs).

The chat renders the CLI’s cross-Device turns, commands, pending confirmations and read state. See [macOS chat](macos-chat.md#working-state).

The DM inspector's Limits row and the routine sheet's open the Limits sheet (`BudgetViewController`), and the plugin sheet's Call limit row opens the Call Limit sheet (`ConnectorLimitsViewController`); each is a `DisclosureRow`, a key and value with a chevron that is its own click target ([Budgets](budgets.md#in-the-apps)).
