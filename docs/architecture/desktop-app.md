# Windows and Linux app

`desktop/` is the app for Windows and Linux, a Go program built with [MyGo](https://github.com/egoist/mygo) and drawn with MyGo's native UI toolkit (`github.com/egoist/mygo/ui`): the windows, menu bars, tray icon, notifications, the CLI, and every view are Go. It follows the macOS app screen for screen: the same windows, panes, sheets, menus, and words, with Lucide icons standing in for SF Symbols (`icons_lucide.go` maps each symbol name the models and views use). `go.mod` pins MyGo 0.3.6 and its command line as a Go tool (`go tool mygo`).

- **Model** (`desktop/model`): the macOS app's AppStore, models, formatters, and demo reply engine (`LORCA_MOCK=1`) in Go. `store.go` holds the account as the CLI reports it and makes every change through the CLI's methods; `wire.go` reads the CLI's JSON, `format.go` writes times, sizes, and schedules as the Mac app does, `mcp.go` reads and writes a Runner's `mcp.json` entries, and message Markdown is goldmark's tree folded into the blocks and spans `crates/markdown` produces (`markdown.go`), with bare links found by the crate's autolink rules (`autolink.go`). The store lives on the main thread: CLI events and the answers of its asynchronous calls come back through one ordered queue the app runs there (`post` in `window.go`), and every window redraws after each.
- **Words** (`desktop/l10n`): `L("…")` and `Lc("…", "context")` are the English text as the key, looked up in `zh.go`; `bun run l10n` checks the table against the Go sources, as it does the Mac's and the phone's. The language is the one picked in Settings, else the system's.
- **The Go host** (`desktop/*.go`): `launcher.go` finds the CLI (`LORCA_CLI`, the app's `resources/bin`, `~/.local/bin`, `~/.cargo/bin`, then `PATH`), probes the port, and starts `lorca serve --port … --parent-pid … --ready-stdout` when nothing answers, restarting it with the macOS launcher's backoff; `client.go` holds the one websocket to the CLI, with the token from the CLI's data directory ([Protocols](protocols.md#app--cli-local-ws)), and reconnects it. `app.go` picks the window as the macOS AppDelegate does: onboarding until the CLI reports an identity, then the main window, and while onboarding is up, Settings as a small window of General and Advanced. A computer without an identity waits for the CLI's answer past the 2.5-second loading deadline, which a CLI's first start (a new binary, a new database) can outlast; a startup failure or 10 seconds without an answer opens the main window on the offline recovery controls. With a tray icon, closing the windows leaves the app running, since the bots on this computer run with it. `files.go` opens the system's file dialogs and reads attachments and bot images from their paths, `avatar.go` makes a bot's image a square PNG of at most 512 px, and `prefs.go` keeps the preferences (selection, pane widths, appearance, language, send key, the CLI port) in `preferences.json` in the app's data folder. `openExternal` (`host.go`) opens only http(s) links with a host and mailto links, as the macOS app's `NSWorkspace.openLink` does, since links from bots, plugins, and the marketplace reach it.
- **Views**: MyGo's views are immediate: a window's view function builds its elements every frame from the store and the window's own state, and MyGo keeps what an element owns (a field's text, a list's scroll, a hover) by its place and key. Constructors return `ui.Element` values that belong to that build pass; helpers take the current `*ui.Context` as an argument and return elements separately from their action results. Keys reach stateful controls before construction through `c.Key(...)`. Editable text binds to persistent state. Public click, shortcut, change, and submit queries apply pending bound input first, so inline handlers see edited values in the same build pass. Simple settings switches and row-click decisions use inline polling after control configuration. Sidebar navigation chooses a chat or settings row on pointer press, and MyGo rebuilds that choice before painting its focus colors, so clicking a different row from the composer shows the new selection in the first frame; button actions activate on release. Changes to routines, the MCP server list, tool visibility, and model selection use `OnChange` callbacks beside their controls, which run after the view and its bound inputs are built. The MCP form's mode and server type also use `OnChange`, so switching carries the latest edits forward and selecting the current mode keeps the draft; each field retains its previous text until its change is observed, so pasted JSON restores the field and opens the JSON editor. `window.go` gives every window its frame: the theme (`theme.go`, light and dark, in the desktop's accent color as the Mac app is in the system's), the view, and its sheets. `mainwindow.go` is the main window's three panes and the selection; `sidebar.go` the chats and the settings panes with their search (`settings_search.go`); `chat.go` the transcript, a `ui.List` that follows the newest message, loads older pages as it nears the top, and draws each message, tool, handoff, and day row, a message's text one selection that a drag runs across (MyGo's `Selectable` on its Markdown); `cards.go` the permission and command cards; `composer.go` the composer, a text area on Liquid Glass (MyGo's `glass` plugin, as the Mac draws it with `NSGlassEffectView`, over the plugin's backdrop blur so the messages scrolling under it frost as on the Mac), growing from one line to eight. Draft edits and changes to the composer's measured height request the next display frame until the transcript's bottom inset matches it, so clearing a multiline draft keeps the latest reply just above the collapsed composer without waiting for more input. It has mentions (in their bot's color as typed), replies, attachments, and pasted images; `inspector.go` the inspector, and `sheet_review.go` its Waiting for review section and the review sheet ([Review queue](review-queue.md#in-the-apps)); `palette.go` the command palette; `runningtasks.go` the running tasks popover; `attention.go` the Attention popover beside it, after the Mac's ([Coordinator attention](attention.md#in-the-apps)); `settings*.go` the settings panes; `marketplace*.go` the marketplace, with a service's [named accounts](integrations.md#stable-account-instances) on its page; `onboarding.go` onboarding; and `sheet_*.go` the sheets. The shared controls (`controls.go`) and settings rows and cards (`sections.go`) follow the Mac app's sizes. A sheet (`overlay.go`) is the key window, as on the Mac: it dims the window behind it and takes its clicks and keys, Escape cancels it and Return presses its default button, and closing one hands the keyboard back to what had it. The composer has no Dictate button and General no Dictation section: Windows and Linux give the app no speech recognizer it uses.
- **Outputs** (`outputs.go`, `model/outputs.go`): as on the Mac, the inspector's Outputs section, hidden while the chat has none, shows the three latest outputs and View all; a row opens the output's sheet with a preview of an image or the first 64 KB of a text file (read off the main thread), the check, the versions, Save As… and Open, or Try Again when the file could not be fetched. `Store.Outputs` lists a shown chat's outputs once and follows message events. Open and Save As… ask the CLI for the file under its own name (`files.path` with `named: true`); Save As… writes through a temporary file beside the destination, so a failed copy leaves what was there. Transcript tiles retry a failed fetch on a click. See [Outputs and evidence](outputs.md).
- **Limits** (`desktop/model/budgets.go`, `sheet_budget.go`, `sheet_connector_limits.go`): the snapshot's `budgets` and `budgets.changed` fill the store. The DM inspector's Limits row, the routine sheet's, and the plugin sheet's Call limit row are `disclosureRow`s that open the Limits and Call Limit sheets, as on the Mac. The Limits sheet's fields are its own until it closes; its calls go out in order (the limits, then Resume) on the ordered main-thread queue, and a reply for a closed sheet is dropped: [Budgets and connector limits](budgets.md#in-the-apps).
Routines (`sheet_routine.go`, `model/routine_health.go`) and the Devices pane's Background service row follow the Mac's; see [Routines](routines.md#the-apps).

A bot’s DM Profile card has the Mac's Access row (`disclosureRow`), which opens the same [Access sheet](bot-permissions.md#requests-to-the-user) (`sheet_access.go`): the plugins with their levels and tool checkboxes, then Files and Shell commands under the Runner's name. The sheet keeps the choices across frames and keys each plugin's row by its id; the tools the Runner sends arrive on the main-thread queue and keep what the user already chose, and a dismissed sheet ignores them. An access request in the chat offers Edit Access… and Dismiss, and the Plugins section reads No access for a plugin the bot may not use.
- **Title bar**: each pane of the main window has a header over its own background: the sidebar's holds the sidebar and Create buttons where the Mac app's titlebar accessory has them, the content's the title and subtitle, back and forward, the Device picker, and running tasks, and the inspector's its toggle. A chat's transcript runs under the content's header, as the Mac's runs under its titlebar: the header draws macOS's hard scroll edge (MyGo's `glass.ScrollEdge`, the transcript frosted under it with a hairline below) once the transcript scrolls from its top or the pointer is over the header, and nothing before. The main window has the sidebar material (`Vibrancy: VibrancySidebar`): where it shows (`c.Vibrancy()`: macOS, and Mica on Windows 11 22H2 and later), the sidebar is transparent over it, as the Mac's, and its text is antialiased in grayscale while the content and the inspector keep ClearType; elsewhere, Linux and Windows 10 included, the sidebar draws its own color. Each pane divider has its own key and uses captured pointer drag state to resize across the adjacent panes until release, when its width is saved in preferences. The sidebar stays between 232 and 340 DIPs and collapses when dragged well past its minimum; the inspector stays between 268 and 320 DIPs. The headers are the title bar: the main window hides its own (`TitleBarHidden`, 52 pixels tall like the headers), keeps the window controls over the headers, and the headers drag the window (`DragWindow`). On macOS the traffic lights sit in the sidebar's header (`TrafficLightPosition` at 19, 19, where the Mac app's toolbar puts them). On Windows and Linux MyGo puts the controls in a top corner: on Windows minimize, maximize, and close at the right, drawn as Windows 11 draws them, on Windows 10 too, and on Linux GTK's own title buttons wherever the desktop's button layout puts them, or none. The rightmost header and the sidebar and Create buttons keep clear of them by the insets `c.TitleBar()` reports. Onboarding hides its title bar too: its page fills the window under the window controls, the close button alone on Windows since the window can neither minimize nor maximize, and its background drags the window. The small settings window keeps the system's title bar. A window's title, which the taskbar and Alt+Tab show, is its content's title (the chat's, the settings pane's, Settings in the small window) followed by ` - Lorca`, the app's name, which stands alone where there is no title of its own (`setTitle` in `window.go`). On Windows and Linux every window's menu bar stays out of sight until Alt or F10 takes the keyboard to it (MyGo's `AutoHideMenuBar`), and its shortcuts work all along; the main window has no room for a bar on Windows, so there Alt and F10 open its menus from the window's top-left corner.
- **Commands** (`commands.go`): one table gives the menu bar (File, Edit, View, Chat, Window, Debug, Help, with Settings, Quit, About, and Check for Updates in File and Help) and the command palette's titles and enabled states, and the menu bars follow the table's states as the windows redraw. Ctrl stands where the macOS app has ⌘; Ctrl+1 to Ctrl+9 are the main window's own shortcuts, since the Windows menu bar keeps no hidden items. While a sheet is up only the app's own commands (Quit, About, Help, Check for Updates) run, as a sheet takes a Mac window's commands.
- **Updates** (`updater.go`): MyGo's updater plugin stands where Sparkle does on the Mac. It checks once a day in the background, and a window of its own shows a new version's release notes with Install Update, Remind Me Later, and Skip This Version, the download's progress, and the offer to relaunch. It installs releases signed with the update key, as a delta from the running version when the release has one, and keeps the user's choices in `updater.json` in the app's data directory. **Check for Updates…** opens that window, and General has the version, the last check, and switches for automatic checks and automatic installs, which follow the plugin's changes (`updater.OnChange` redraws the windows). The window speaks the language picked in Settings, else the system's; a new pick reaches it at the next launch, as the Mac's reaches Sparkle. Its releases are this repo's, tagged `desktop-vX.Y.Z` (`updates` in `mygo.config.ts`, with the public key). The repo's latest release stays the CLI's, so release builds find the newest `desktop-v` release through the GitHub API (MyGo's `tagPrefix`), and read its update manifests. `bun run release-desktop` uploads to a draft of the version through `go tool mygo build -upload`, here or in the Release desktop workflow (`.github/workflows/release-desktop.yml`), which a `desktop-vX.Y.Z` tag or a run by hand starts: it drafts the release with the changelog's section and builds Windows x64, Linux x64, and Linux arm64 side by side on Ubuntu, and publishing the draft, without making it the latest release, releases the update. The app has its own version, `version` in `desktop/mygo.config.ts`, apart from the Mac app's, and its own release notes, the version's section of `desktop/CHANGELOG.md`: [docs/releasing-desktop.md](../releasing-desktop.md). A build that cannot write where it is installed, `mygo dev`'s or the Debian package's in `/opt`, leaves the menu item and the General rows out.
- **Development and builds**: `bun run desktop` builds the CLI and runs `go tool mygo dev` (Lorca Dev, `app.lorca.dev`, with `~/.lorca-dev` and port 4863), which rebuilds and relaunches the app on a Go change; `LORCA_MOCK=1` runs the demo instead of the CLI, and `LORCA_PORT` points the app at a CLI on another port. `go tool mygo vet .` in `desktop/` runs Go vet and checks for build values stored in state or captured by workers. `go test ./...` runs the model's tests and the views' tests, which build the windows over the demo's store in MyGo's offscreen tester (`ui.NewTester`), click and type into them, and check what they show; with `LORCA_RENDER=<folder>` they also write each frame they look at as a PNG. `LORCA_E2E_PORT=<port> LORCA_E2E_SERVER=<base URL>` adds `TestE2EAgainstCLI`, which drives the main window over a CLI with an identity on that port: it adds an OpenAI-compatible server at that URL as a custom provider through its sheet, runs the first bot on it, and checks the reply that streams back. `bun run desktop:build [platforms]` builds the CLI for each platform into `desktop/resources/<goos>-<goarch>/bin` (static musl builds for Linux, with cargo-zigbuild, as the CLI releases are) and runs `go tool mygo build -platform`; MyGo needs no cgo, so every platform builds from any computer, and a Mac builds Windows and Linux on x86-64 by default.
