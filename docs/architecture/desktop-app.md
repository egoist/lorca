# Windows and Linux app

`desktop/` is the app for Windows and Linux, built with [MyGo](https://github.com/egoist/mygo): a Go process that owns the windows, the menu bars, the tray icon, notifications, and the CLI, and pages in the system webview (WebView2 on Windows, WebKitGTK on Linux) written with Solid 2 and TypeScript. It follows the macOS app screen for screen: the same windows, panes, sheets, menus, and words, with Lucide icons standing in for SF Symbols (`src/ui/icons.tsx` maps each symbol name the models and views use).

- **The Go side** (`desktop/*.go`): `launcher.go` finds the CLI (`LORCA_CLI`, the app's `resources/bin`, `~/.local/bin`, `~/.cargo/bin`, then `PATH`), probes the port, and starts `lorca serve --port … --parent-pid … --ready-stdout` when nothing answers, restarting it with the macOS launcher's backoff; `client.go` holds the one websocket to the CLI and reconnects it. A page calls the CLI through the bound `CLI.request` and hears its events as `cli:event`. `app.go` picks the window as the macOS AppDelegate does: onboarding until the CLI reports an identity, then the main window, and while onboarding is up, Settings as a small window of General and Advanced. A computer without an identity waits for the CLI's answer past the 2.5-second loading deadline, which a CLI's first start (a new binary, a new database) can outlast; a startup failure or 10 seconds without an answer opens the main window on the offline recovery controls. With a tray icon, closing the windows leaves the app running, since the bots on this computer run with it. `files.go` serves attachments and bot images to the pages by token under the `lorca-file` scheme, and `avatar.go` makes a bot's image a square PNG of at most 512 px; `prefs.go` keeps the preferences (selection, pane widths, appearance, language, send key, the CLI port) in `preferences.json` in the app's data folder; `menus.go` builds each window's menu bar from what the page describes and brings clicks back as commands. `Host.OpenExternal` opens only http(s) links with a host and mailto links, as the macOS app's `NSWorkspace.openLink` does, since links from bots, plugins, and the marketplace reach it.
- **The page** (`desktop/src`): `model/` is the macOS app's AppStore, models, formatters, and demo reply engine (`LORCA_MOCK=1`, or `?mock=1` in a browser tab) in TypeScript, and message Markdown is markdown-it folded into the blocks `crates/markdown` produces, with bare links found by the crate's autolink rules (`model/autolink.ts`). The store is plain and synchronous; `model/reactive.ts` turns its events into signals the views read. Routes (`@solidjs/router`) name each window's page: the main window at `/`, a chat at `/chat/:id` and a settings pane at `/settings/:pane` inside it, onboarding at `/onboarding`, and the small settings window at `/settings-window`. A selection replaces the route, and back and forward walk the settings panes, as the macOS toolbar's do. A sheet (`src/ui/overlay.tsx`) is the key window, as on the Mac: the window behind it is `inert`, keys typed while nothing has focus go to the sheet in front, and closing one hands the keyboard back to what had it. The composer has no Dictate button and General no Dictation section: WebView2 and WebKitGTK give a page no speech recognizer.
- **Title bar**: each pane of the main window has a header in its own color: the sidebar's holds the sidebar and Create buttons where the Mac app's titlebar accessory has them, the content's the title and subtitle, back and forward, the Device picker, and running tasks, and the inspector's its toggle. The headers are the title bar: the main window hides its own (`TitleBarHidden`), keeps the window controls over the headers, and the headers are marked `--app-region: drag`. On macOS the traffic lights sit in the sidebar's header (`TrafficLightPosition` at 19, 19, where the Mac app's toolbar puts them). On Windows and Linux MyGo puts the controls in a top corner, 52 pixels tall like the headers (`TitleBarHeight`): Windows 11's minimize, maximize, and close at the right, and on Linux GTK's own title buttons wherever the desktop's button layout puts them, or none. The rightmost header and the sidebar and Create buttons keep clear of them with MyGo's `--mygo-titlebar-inset-right` and `--mygo-titlebar-inset-left`. Onboarding and the small settings window keep the system's title bar. On Windows and Linux every window's menu bar stays out of sight until Alt or F10 takes the keyboard to it (MyGo's `AutoHideMenuBar`), and its shortcuts work all along; the main window has no room for a bar on Windows, so there Alt and F10 open its menus from the window's top-left corner.
- **Commands** (`src/ui/commands.tsx`): one table gives the menu bar (File, Edit, View, Chat, Window, Debug, Help, with Settings, Quit, About, and Check for Updates in File and Help), the command palette's titles and enabled states, and the shortcuts in a browser tab, which has no menu bar. Ctrl stands where the macOS app has ⌘; Ctrl+1 to Ctrl+9 are the page's own, since the Windows menu bar keeps no hidden items. While a sheet is up only the app's own commands (Quit, About, Help, Check for Updates) run, as a sheet takes a Mac window's commands.
- **Updates** (`updater.go`): MyGo's updater plugin stands where Sparkle does on the Mac. It checks once a day in the background, and a window of its own shows a new version's release notes with Install Update, Remind Me Later, and Skip This Version, the download's progress, and the offer to relaunch. It installs releases signed with the update key, as a delta from the running version when the release has one, and keeps the user's choices in `updater.json` in the app's data directory. **Check for Updates…** opens that window, and General has the version, the last check, and switches for automatic checks and automatic installs, which follow the plugin's changes (`updater.OnChange`, sent to the page as `updater:changed`). The window speaks the language picked in Settings, else the system's; a new pick reaches it at the next launch, as the Mac's reaches Sparkle. Its releases are this repo's, tagged `desktop-vX.Y.Z` (`updates` in `mygo.config.ts`, with the public key). The repo's latest release stays the CLI's, so release builds find the newest `desktop-v` release through the GitHub API (MyGo's `tagPrefix`), and read its update manifests. `bun run release-desktop` uploads to a draft of the version through `mygo build -upload`, here or in the Release desktop workflow (`.github/workflows/release-desktop.yml`), which a `desktop-vX.Y.Z` tag or a run by hand starts: it drafts the release with the changelog's section and builds Windows x64, Linux x64, and Linux arm64 side by side on Ubuntu, and publishing the draft, without making it the latest release, releases the update. The app has its own version, `"version"` in `desktop/package.json`, apart from the Mac app's, and its own release notes, the version's section of `desktop/CHANGELOG.md`: [docs/releasing-desktop.md](../releasing-desktop.md). A build that cannot write where it is installed, `mygo dev`'s or the Debian package's in `/opt`, leaves the menu item and the General rows out.
- **Development and builds**: `bun run desktop` builds the CLI and runs `mygo dev` (Lorca Dev, `app.lorca.dev`, with `~/.lorca-dev` and port 4863), which reloads the page on a frontend change and rebuilds the app on a Go change; `cd desktop && bun run dev:web` serves the page alone for a browser, where `?mock=1` runs the demo, `?port=` points it at a CLI, and `?platform=windows` or `linux` previews that system's shortcuts and words (Ctrl, Enter). `bun run desktop:build [platforms]` builds the CLI for each platform into `desktop/resources/<goos>-<goarch>/bin` (static musl builds for Linux, with cargo-zigbuild, as the CLI releases are) and runs `mygo build -platform`; MyGo needs no cgo, so every platform builds from any computer, and a Mac builds Windows and Linux on x86-64 by default.
