# Relay

`crates/relay`: Rust, axum, rusqlite (bundled SQLite) or tokio-postgres. `lorca-relay --bind 127.0.0.1:8787 --db lorca-relay.db` (or `--db postgres://…`); `LORCA_RELAY_SECRET` signs bearer tokens (random per boot when unset); `--quota-bytes` (`LORCA_RELAY_QUOTA_BYTES`) caps stored ciphertext per identity, 0 for none.

Storage sits behind one trait (`Store` in `db.rs`) with two backends, picked by `--db` / `LORCA_RELAY_DB`: a path opens SQLite, a `postgres://` URL opens Postgres. All SQL lives in a backend; `routes.rs` only decides what to ask for. One suite (`db/tests.rs`) runs against both; Postgres joins when `LORCA_RELAY_TEST_POSTGRES` names a database.

SQLite (`db/sqlite.rs`) is one WAL database (`synchronous = NORMAL`) behind a single writer connection and a pool of reader connections, one per core; every query runs on tokio's blocking pool. One relay process owns the file, so a deploy stops the old process before the new one starts, and the Devices reconnect after a few seconds.

Postgres (`db/postgres.rs`) is shared by as many relay processes as run, so a deploy overlaps the old process with the new one. An identity's writes are serialized with a transaction-scoped advisory lock, which orders them the way SQLite's single writer does. What a lone process keeps in memory goes through the database: an event (`Event`: a new blob, a changed machine list, an unpaired machine) travels by `NOTIFY` to every process, each of which signals its own sockets, drops the unpaired key's tokens, and closes its sockets; presence is the `relay_sockets` table; each process beats in `relay_instances` once a minute, and the sockets of one silent for 150 s stop counting. A process's store opens once its listener is listening, or after ten seconds without it, since a `NOTIFY` reaches only the sessions listening when it is sent: an event published at once is heard, and a key revoked meanwhile is among the revoked keys read at startup. A listener that came up late or lost its connection tells all its sockets to look again and reads the revoked keys afresh once it listens. The processes share `--secret`, or a token from one does not verify on another, and keep files in an S3 bucket. TLS to the database follows `sslmode` and checks certificates against the web's roots; a database on a private network takes `sslmode=disable`.

The sync sockets live in `hub.rs`, grouped by identity: a blob write signals the sockets of its identity alone, and an envelope sealed to one machine signals that machine alone. A signal is a nudge with no data, so a socket's queue holds four and drops the rest. `last_seen` is written when a machine's first socket opens and when its last one closes. On SIGTERM the relay stops taking connections and closes its sockets, and the Devices connect again, after a backoff with up to a second of jitter, to whichever process is serving. Once it has answered its last request, it gives APNs and FCM up to 5 s to take the pushes it answered `queued` for (`stop` in `main.rs`), then closes the database.

`file` ciphertext never enters the database (`store.rs`): it goes to a directory (`--files-dir`, default `lorca-relay.files` beside the database) or, with `--s3-bucket` and `--s3-endpoint` (access keys from `LORCA_RELAY_S3_*` or `AWS_*`), to an S3-compatible bucket (AWS, R2, MinIO) over SigV4 with path-style URLs. Objects are keyed `<identity pubkey>/<blob id>`; the row keeps the metadata with an empty `ciphertext`. The object goes up before the row and is removed when the row is refused or deleted.

Housekeeping (`sweep.rs`) runs hourly beside the minute `tick`. Envelopes sealed to one machine (`job`, `job_cancel`, `job_result`, `request`, `response`, `event`) are deleted by the machine that consumed them; one still there after seven days had a Runner that never came back, so it goes and its bytes return to the quota. A `deleted_groups` mark goes after 180 days. Once a day the sweep lists the file store (the directory, or `ListObjectsV2` pages of the bucket prefix) and removes an `<identity>/<blob id>` object that is over a day old and has no row: a delete the store refused, or a relay that stopped between an upload and its row. It only touches objects of identities the database knows, so a bucket pointed at by the wrong database loses nothing. The same daily pass drops an identity with no sign of life for `--inactive-days` (365; `0` keeps every identity): registered before then, no machine seen since, no blob written since, no socket open. Its rows and objects go but its keys are not revoked, so a Device that comes back is an unknown machine, not an unpaired one: the identity device attests itself again (`sync::ensure_registered`), starts the relay's log from seq 0, and uploads the `key` blob, the roster, its `machine` blob, and the credentials, which is what pairing or restoring another Device needs, and then the history as it holds it (`App::push_history`): the bots' photos, then each chat's messages in their order, each after the attachments it names that are on this Device, with the chat's read mark where this Device stopped reading. What its outbox still held for a chat goes up with the rest, so a message that waited there does not land ahead of older ones. A Device that pairs afterwards gets the history through its first sync, and one already paired pulls it through the log. It also sets `usage` to what the blobs add up to wherever the two disagree, settling each identity under its write lock with Postgres. Every process runs the sweep; each step is safe to repeat.

A `file` row whose object the store does not have answers `GET /v1/files/{id}` with `404`, which a Device takes as final, and counts in `missing_objects_total`. The row stays, so a relay pointed at the wrong bucket forgets nothing.

`DELETE /v1/identity` with a machine's bearer deletes the identity: its machines, blobs, attachments' objects, push tokens, pairings, sequence, and usage. The machines' keys stay in `revoked_machines`, so each Device's token dies, its socket closes, and the `410` it gets next makes it forget the identity, as an unpairing does. The backup phrase can register the identity again on a new machine key. The CLI's `identity.delete` makes that call and then forgets the identity locally; when the relay cannot be told it fails and nothing is deleted. The macOS app offers it as Settings › Advanced › Delete Account, behind a confirmation sheet.

An identity may store 5 GiB of ciphertext unless `--quota-bytes` says otherwise (`0` for no limit). A `PUT /v1/blobs` or `PUT /v1/files/{id}` over 1 MiB takes one of `--concurrent-uploads` places (3 by default) before its body is read and keeps it until the response, since an attachment's binary ciphertext is held whole in memory while it is sent to storage; one that waits 30 s gets `503` with `Retry-After`, and the Device's outbox sends it again after its backoff.

`GET /metrics` (`metrics.rs`) exists when `--metrics-token` is set and answers that bearer with Prometheus text, the only view of a relay that cannot read what it stores. Totals come from the database, the same from every process and read at most once in 30 s: identities, machines (and those seen within 1, 7, and 30 days), revoked keys, group marks, blobs and bytes by kind, the quotas' sum and the largest identity's, push tokens by platform. The rest is what the answering process counted since it started, labelled with its `instance`: open sockets and connected identities, requests and seconds by method, route template, and status, rate-limit refusals, uploads refused, reads of a file whose object is missing, pushes by platform and result, and the sweeps (envelopes, orphans, and inactive identities removed, usage rows corrected, objects listed, failures, when each last finished).

Rate limits (`limit.rs`) are token buckets in memory: per client IP on the routes that need no token (registration, auth, the pairing mailbox; `--ip-per-minute`, default 60, `--trust-proxy` to read `X-Forwarded-For`), and per identity on everything behind a bearer (`--identity-per-second`, default 50, burst ten times that). Over the limit is 429 with `Retry-After`; a Device's outbox sends the same blob again a second later, so a history uploaded again goes up at the identity's rate and loses nothing.

The image (`crates/relay/Dockerfile`) builds from the repo root, since the relay is a workspace member; cargo-chef keeps the dependency layer cached until a manifest or `Cargo.lock` changes. It runs the binary on `debian:trixie-slim` in `/data`, where the SQLite database and the files directory land, and listens on `[::]:$PORT` (8787 without `PORT`; `LORCA_RELAY_BIND` overrides both). A Railway service builds it through `RAILWAY_DOCKERFILE_PATH`, healthchecks `/v1/health`, and sets `RAILWAY_DEPLOYMENT_DRAINING_SECONDS`, since Railway otherwise follows SIGTERM with SIGKILL at once. With SQLite, a Railway volume at `/data` keeps the database. With Railway's Postgres, `LORCA_RELAY_DB` is its private `DATABASE_URL` with `?sslmode=disable`, since that server's certificate is self-signed, and files go to an S3 bucket, since the container's disk does not outlive a deploy. [crates/relay/README.md](../../crates/relay/README.md) lists the variables a Railway service takes. The production relay deploys from the `relay` branch, which its Railway service watches, so a deploy is a push of main to that branch (`git push origin main:relay`).

Auth is per machine:

1. `POST /v1/auth/challenge { machine_pubkey }` → nonce.
2. Client signs the nonce with the machine signing key: `POST /v1/auth/verify`.
3. Relay issues a one-hour HMAC bearer bound to the identity and machine.

Identity-level writes are signed requests: `{ payload: base64url(json), signature }` where the payload carries `identity_pubkey` and `ts` and the identity key signed the bytes. `POST /v1/identities` registers the identity (idempotent) and attests one machine; it is used at create, restore, and for each Device an identity device pairs. A Device without the identity key pairs one with `POST /v1/machines { machine_pubkey, box_pubkey }` behind its own bearer (protocol 2): the relay adds the machine to the caller's identity and keeps `{ by, at }`, the machine that vouched and when, as its attestation. Under the identity's write lock it refuses a caller that is no longer one of the identity's machines (`404`, or `410` once unpaired), a revoked key (`410`), and a key already paired with other keys or to another identity (`409`); the same keys again change nothing.

Tables:

- `identities(pubkey, content_pubkey, created_at)`
- `machines(machine_pubkey, identity_pubkey, box_pubkey, attestation, last_seen, created_at)`
- `blobs(identity_pubkey, id, kind, recipient_machine_pubkey nullable, seq, ciphertext, size, created_at)`, keyed on `(identity_pubkey, id)`
- `sequences(identity_pubkey, seq)`, `usage(identity_pubkey, bytes)`, `challenges`, `pairings(nonce, identity_pubkey, request, reply, expires_at)`

- `push_tokens(machine_pubkey, identity_pubkey, platform, token, environment, updated_at)`
- `schema_version(version, applied_at)`

`SCHEMA` in each backend creates the tables and is version 1; `MIGRATIONS` is the ordered list of changes after it (version 2 and up), and `schema_version` records what was applied. With Postgres a step runs once, under the schema advisory lock, and never again at a later start: DDL locks whole tables while the process being replaced is writing to them, so a start that re-ran `CREATE INDEX IF NOT EXISTS` could deadlock with a request. A step that still loses a deadlock runs again. SQLite runs `SCHEMA` at every open, since it carries the connection's pragmas and nobody else has the file. A deploy runs the old process beside the new one, so a step only adds: a table, a nullable column, an index.

`kind` is `task` | `handoff` | `review` | `attention` | `project_context` | `event` | `roster` | `chat` | `job` | `job_cancel` | `job_result` | `machine` | `credentials` | `key` | `file` | `request` | `response`. Ciphertext is bytes; the nonce sits inside it. `seq` increases per identity. An `attention` blob is an opaque account record in a latest-only hashed slot; its source ids and words stay encrypted ([Coordinator attention](attention.md)). A Device’s `name` and `os` are inside its `machine` blob, not columns. A `file` blob is an attachment's bytes under the attachment's id. A Device accepts files up to 100 MiB; the relay accepts 100 MiB plus the 40-byte encryption envelope (other kinds 4 MiB). Attachments travel as binary ciphertext with `Content-Type: application/octet-stream`: `PUT /v1/files/{id}?group=<chat id>` uploads one (the group is optional for avatars), and `GET /v1/files/{id}` downloads it when a transcript needs it. The upload answers with JSON containing the id and sequence. Names, MIME types, and dimensions stay in the encrypted message or roster. JSON blob routes carry non-file blobs and exclude attachments from their pages.

Blob API: `PUT /v1/blobs` (client-chosen id of up to 64 characters in `[A-Za-z0-9._-]`, idempotent; 413 over quota), `GET /v1/blobs?since=<seq>&kinds=` (a page of the blobs for the identity that are unaddressed or addressed to the caller’s machine, filtered by kind in the query), `GET /v1/blobs/{id}` (one blob, same visibility), `DELETE /v1/blobs/{id}`, `GET /v1/machines` (each machine with `online` and `last_seen`), `POST /v1/machines` (attest one, above).

Sync socket: `GET /v1/sync` with the bearer token upgrades to a WebSocket. The relay sends `{"type":"blobs"}` when the identity has a blob this machine may read and `{"type":"machines"}` when a machine connects, disconnects, or is unpaired; the Device sends nothing but control frames. A machine is online while it has a socket open. The relay pings every 25 s and closes a socket silent for 50 s; the Device gives up on one silent for 70 s, or 10 s after a ping of its own, and connects again.

Push API (`push.rs`): a phone registers where its pushes go with `PUT /v1/push/token { platform: apns | fcm, token, environment? }` (`sandbox` for a development build's APNs token; `DELETE` removes it). Any Device asks for a push with `POST /v1/push { ciphertext }`, at most 2560 bytes; the relay answers `{ queued }` at once and then sends to every token of the identity but the caller's. To APNs that is an alert with fixed words ("Lorca", "New reply"), `mutable-content`, and the ciphertext as `c`, over HTTP/2 with an ES256 provider token from the team's `.p8` key (`--apns-key`, the `.p8` key's text or the path of its file, as `--fcm-service-account` is the JSON or its path, so a deploy with no volume carries both in variables; `--apns-key-id`, `--apns-team-id`, `--apns-topic`, default `app.lorca`; the token's environment picks Apple's sandbox or production host). To FCM it is a data-only message carrying `c`, with an access token minted from a service account (`--fcm-service-account`). A relay with neither key queues nothing. `LORCA_RELAY_APNS_URL` and `LORCA_RELAY_FCM_URL` point either at a test server.

Clients set `LORCA_RELAY_URL` or the relay URL in Settings › Advanced. With neither, a Device uses the URL pairing handed it, then `LORCA_DEFAULT_RELAY_URL`, which the release macOS app sets to `https://relay.lorca.app` when it launches the CLI. Without a relay the CLI works on one Device alone. In dev (`bun run dev` sets `LORCA_DEV=1` and runs a relay on `0.0.0.0:8787`), a Device with no relay configured defaults to `http://<this computer's LAN IP>:8787`, so Pair a Device shows a code a phone on the same network can use. That relay (and `bun run relay`) runs with `--apns-topic app.lorca.dev`, since the phone that pairs with it is the development build.

A CLI holds one sync socket (`sync::session`). It opens the socket, then drains its SQLite outbox and pulls pages of blobs for its identity and envelopes for its machine public key until one comes back empty, decrypts, and emits events to the app on localhost. After that it waits on the socket and on its outbox: `blobs` is answered with a pull, `machines` with a fresh machine list, a queued blob with an upload, and a wake (`App::wake_sync`: a phone back in the foreground or pulling to refresh) with a pull and a ping on the socket, which may have died while the app was suspended. A wake keeps the bearer and drops the pooled HTTP connections, which may have died with the socket (a VPN on the phone can keep its end of one open), so no request waits out its timeout on one. A socket that fails ends the session; the next one starts after a backoff of 2 s doubling to 32 s, with up to a second of jitter, that starts over after every round that goes through, and until then the other Devices show as offline. When a wake came during the session that ended, the next one starts at once, and so does the one after the relay refused the bearer (`401`, as a relay that restarted with a new `--secret` does), since that one signs in again; a second refusal in a row waits out the backoff. A try that fails before its socket opens leaves why (`App::relay_problem`): `relay_error { message, unknown_machine }` in `hello`, the snapshot, and `relay.status`, kept until a try goes through, the relay URL changes, or the identity goes. The message is the relay's answer or, for a request that never got one, the last cause in reqwest's chain ("relay unreachable: Connection refused (os error 61)"). A socket that worked and then ended leaves none, since the next try usually connects, and neither does a stale bearer. `unknown_machine` is a `404` on a Device that is not the identity device: the relay has no record of it (a reset relay, or another relay), and only pairing again brings it back. A Device at seq 0 does not replay the log, which holds every message of the account (`sync::first_sync`). It pages through the log without the `chat` kind, which slots keep to a roster, a `machine` blob per Device, the credentials, and the envelopes sealed to it; then it asks for the newest 400 messages of each chat in the roster, the count a bot's turn reads, and follows the log from the head it saw when it began, so whatever landed meanwhile comes again and changes nothing. Where the relay had more, `chat_history` records the place the local copy of the chat begins at. `chats.messages` answers from SQLite until the local copy runs out, then reads a page of 100 back from the relay (`sync::older_messages`), puts it ahead of everything the chat has here (`LocalStore::insert_older`, with positions counting down below the first), and answers from SQLite again; `has_more` stays true while the relay holds more, and a chat read to its start loses its `chat_history` row. A message that was edited after the first sync and lies before the local copy arrives through the log and lands at the end; the page that holds it moves it to its place. Search and the `recall` tool read what is here. A page of twenty or more blobs is a backlog: the CLI applies each message as one SQLite upsert with message and roster events held back, commits the account metadata once, and emits one `snapshot` at the end of the page, so the app fills in at once instead of one message at a time. The page's `job_result` envelopes, and what its `machine` blobs change about the turns in flight, reach the app after that snapshot, so a turn's end comes after the messages it ended with.

Protocol 3 adds the opaque task, handoff, review, attention, project-context, and event kinds with the existing blob/slot storage. Task records use an account-encrypted latest-only slot, as review records do in the hashed slot of `review/<id>`, and task writes need no relay table migration. The client owns task revisions, evidence, and execution claims ([Durable tasks](tasks.md)); the relay cannot read them. Event envelopes join the sealed-to-machine kinds and their expiry/consume lifecycle.
