# Providers

**DeepSeek** — API key, streamed through DeepSeek's Anthropic-compatible endpoint (`https://api.deepseek.com/anthropic`, `providers::anthropic`), the one that runs DeepSeek's web search on the server: every request declares Anthropic's `web_search_20250305` tool, and the model's searches stream back as `server_tool_use` and `web_search_tool_result` blocks. `LORCA_DEEPSEEK_MODEL` overrides the model. The API root is the credential's own base URL when the user set one, else `LORCA_DEEPSEEK_BASE_URL`, else DeepSeek's (the key check calls its `/models`, bots its `/anthropic`; a root given with `/anthropic` already is used as is).

**Anthropic** — API key, the Messages API (`providers::anthropic`): `claude-opus-5` by default with adaptive thinking, and Anthropic's `web_search_20260209` and `web_fetch_20260209` tools on every request (the basic variants and no thinking parameter for Haiku 4.5 and the 4.5 generation). `LORCA_ANTHROPIC_MODEL` overrides the model; the API root is the credential's base URL, else `LORCA_ANTHROPIC_BASE_URL`, else Anthropic's.

An API-key credential (`credentials.json`: `api_key`, `base_url?`, `connected_at`) can name a custom API root, for a proxy or a compatible server. Every API-key connect method takes `base_url` beside `api_key`, checks the key against that root, and stores both. Before presenting the macOS provider sheet, the app fetches the saved key and base URL on demand from the local CLI with `providers.api_key { kind }`, so it opens fully populated at its final size. The key is masked by default, with an eye button to reveal or hide it. Connected API-key providers open this sheet through Edit, with Save and Disconnect actions. Snapshots and events carry provider statuses: `providers[].base_url` and a masked `key · url` detail.

Both stream the same way, with the conversation marked for caching (`cache_control` on the system prompt, the last user block, and the turn's cache points, so a turn reads what the last one cached even after many tool calls, since Anthropic looks at most 20 blocks back from a mark; the last tool takes one while fewer than four are used; DeepSeek ignores the marks and caches prefixes on its own), tool arguments streamed eagerly, and a request that fails before it streams retried twice: text, thinking (with its `signature`), `tool_use` blocks, and the server tools' own blocks. A server tool call becomes a `ServerToolStart` / `ServerToolEnd` pair for the Runner's activity rows, and the raw `server_tool_use` and `*_tool_result` blocks stay in the assistant message as `ServerBlock` parts, so when the same turn continues after a function call the model gets its searches, their results, and its sealed thinking back verbatim. A later turn's context is rebuilt from the chat and carries none of it. Opus 5.5, Fable 5.1, and Sonnet 5.5 bind each thinking block to the system prompt, tools, and messages before it and refuse one replayed after they change, so the Runner drops a turn's earlier thinking for those models when the turn compacts and in the memory flush (`anthropic::drop_bound_thinking`).

**OpenCode Zen** — API key, the curated pay-as-you-go gateway rooted at `https://opencode.ai/zen`. `deepseek-v4.1-flash` is the default; the catalog adds each lab's frontier model Zen serves on one of these wires (Gemini's own API is not one, so Gemini is not offered). The Runner follows the endpoint OpenCode publishes for each model, which the catalog carries as the model's `wire`: GPT, Grok, and Muse Spark use `/v1/responses`, Claude uses `/v1/messages`, and DeepSeek, Kimi, GLM, Qwen3.8 Max, MiniMax, and the free Big Pickle use `/v1/chat/completions`. A model the catalog lacks goes by its family's endpoint. `LORCA_OPENCODE_MODEL` and `LORCA_OPENCODE_BASE_URL` override the default model and root.

**OpenCode Go** — API key plus an active Go subscription, rooted at `https://opencode.ai/zen/go`. `glm-5.3-flash` is the default, followed by each lab's frontier model on the plan; the Muse Spark Contributor models, whose discount pays for Meta training on the prompts, are not offered. GPT and Grok use Responses, Qwen and MiniMax use Messages, and GLM, DeepSeek, Kimi, and MiMo use Chat Completions. `LORCA_OPENCODE_GO_MODEL` and `LORCA_OPENCODE_GO_BASE_URL` override the default model and root. Every OpenCode request identifies Lorca in `User-Agent` and carries the chat id as `x-opencode-session`, as Go requires for routing and prompt caching; Chat Completions and Responses requests carry it as `prompt_cache_key` too.

**ChatGPT** — subscription OAuth (`providers::chatgpt`, isolated): authorization code with PKCE, the localhost:1455 callback the Codex CLI uses, tokens refreshed by the adapter, and the Codex responses backend for streaming. A refused token request shows the endpoint's own reason, OAuth's `error_description` or OpenAI's `error.message` ("403 Forbidden: Country, region, or territory not supported"; see [proxies](runtime.md)). `LORCA_CHATGPT_MODEL` overrides the model. The chat id goes with every request as `prompt_cache_key` and in the `session-id` header, by which the backend keeps a chat on the server that holds its prompt cache, as the Codex CLI does. Every request carries the backend's built-in `web_search` tool, which searches and reads pages server-side; its `web_search_call` items stream back as `ServerToolStart` / `ServerToolEnd` events (`web_search` with the query, `web_fetch` with the URL for an `open_page`).

**Grok** — subscription OAuth (`providers::grok`, isolated): xAI's authorization code with PKCE at `auth.x.ai` (`/oauth2/authorize`, `/oauth2/token`) with the public desktop client id the Grok CLI uses, a loopback callback on a port picked at sign-in (`http://127.0.0.1:<port>/callback`; the `accounts.x.ai` page calls it from JavaScript, so the callback answers the CORS preflight and marks its response for that origin, else the page falls back to a code to paste), and tokens refreshed by the adapter (access tokens last about six hours; the refresh token rotates and the new one is stored at once). It needs a SuperGrok or X Premium+ account. Streaming is xAI's Responses API (`https://api.x.ai/v1/responses`) with the bearer; the Responses wire shape (`providers::responses`) is shared with ChatGPT. Every request carries the chat id as `prompt_cache_key`, which routes a chat's requests to the xAI server that holds its prompt cache. `grok-4.7` by default; `LORCA_GROK_MODEL` overrides it, `LORCA_GROK_BASE_URL` the API root, `LORCA_GROK_ISSUER` the OAuth issuer, for a test server. Every request carries xAI's `web_search` and `x_search` tools, run server-side; their `web_search_call` and `x_search_call` items stream back as `ServerToolStart` / `ServerToolEnd` events ("Searched the web for …", "Searched X for …", "Read …"). Disconnecting revokes the refresh token at `auth.x.ai`, best effort.

**Custom providers** — any server that speaks one of the wire protocols Lorca has, added by the user with a name, a protocol, a base URL, an optional API key, and a list of models: a gateway (OpenRouter), another vendor's API, or a model server on their network (Ollama, LM Studio, vLLM). The protocol is `chat-completions` (`providers::openai_compat`, at `{base_url}/chat/completions`), `responses` (`providers::openai_responses`, at `{base_url}/responses`), or `messages` (`providers::anthropic` with no server tools and no eager tool streaming, at `{base_url}/v1/messages`, the key in `x-api-key`). A provider's kind is `custom:` and a slug of the name it was added with (`custom:openrouter`, `-2` and on when another provider has it); renaming keeps the kind, and a bot's `provider` names it like a built-in one. `providers.connect_custom { kind?, name, api, base_url, api_key, models }` adds one, or saves the one `kind` names, from any Device: the name must be new among the account's providers, a pasted endpoint is cut back to its root (`…/v1/chat/completions` → `…/v1`; a Messages root loses a trailing `/v1`), and the Device asks the server for its model list (`GET {base_url}/models`, or `/v1/models?limit=1000` with `anthropic-version` for Messages, 20 s). A 401 or 403 rejects the key (or says one is needed), an unreachable server or a 2xx that is not JSON fails, and a server with no list (any other status) still saves with the model ids the user gave. The apps ask first: `providers.list_models { name?, api, base_url, api_key }` answers the same list (`listed`, `models`) without saving, and their sheet shows it as a checklist to pick from while the user fills in the server; `models` then names the picked ids, the default first. Empty `models` (as `lorca provider add` without `--model` sends) takes every model the list has. A list is `data`, `models`, or a bare array, without the models chat cannot use (embeddings, rerankers, speech, realtime audio, image and video generation, moderation, base completion models: by id words, a `type`, `capabilities.completion_chat`, or `architecture.output_modalities`), in the server's order. Each model keeps what the list says of it: a display name, a window (`context_length`, `context_window`, `max_model_len`, `max_context_length`, `max_input_tokens`), an output cap, and whether it takes images (`architecture.input_modalities`, `modalities.input`, `capabilities.vision`). The first model is the default. Chat Completions requests to a custom provider leave out `prompt_cache_key`, OpenAI's field that stricter servers (Gemini's) refuse.

At turn time a custom model takes the list's facts, else the catalog's entry for its id under any provider (`lorca_models::find_any`: a gateway's `vendor/` prefix is ignored, a dated suffix finds its model), else nothing: no window to compact by, text only. Its thinking follows the catalog entry when there is one; otherwise it takes `low`, `medium`, and `high`, sent as an effort word on the OpenAI protocols and as a token budget on Messages, the form servers that are not Anthropic accept, and no `off`, since an unknown server has no one way to turn thinking off (the default sends nothing). Each model of a custom provider's status carries those `levels` (`credentials::custom_levels`), so the pickers offer them as they do the catalog's. Its cost is zero, since Lorca does not know what the server charges. Auto-review and `models.ask()` run a custom provider's first model, at the catalog's lowest level for a model the catalog knows and with no thinking parameter for any other. `lorca provider add <name> <base-url> [--api …] [--model …]… [--api-key-stdin]` adds one from a terminal, and `lorca provider remove custom:<slug>` deletes it.

Server tool events from any provider become tool rows on the Runner, so the status line reads "Searching the web…" or "Reading the web…" while one runs; `build_context` never replays those rows to the model.

The encrypted bot profile carries `provider`, `model`, and `thinking` as string identifiers; the Runner resolves them against the account's credentials and the model catalog at turn time. A bot whose custom provider was deleted gets the not-connected notice until it moves to another provider or one is added again under that name. `thinking` is one of `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` (or unset for the provider's default) and is mapped to what the model takes: an `output_config.effort` with adaptive thinking on DeepSeek and current Claude models (Fable 5.1 and Opus 5.5 cannot turn thinking off, so `off` becomes their lowest level; Sonnet 5.5 refuses `disabled`, so its `off` is `between_tools`), a `budget_tokens` on Haiku 4.5, `reasoning.effort` on ChatGPT and API-key Responses, and `reasoning_effort` on OpenAI-compatible gateways. A catalogued model gets the word for its level; `off`, on a model that can stop thinking, is the effort `none` on Responses and `thinking: { type: "disabled" }` on Chat Completions. Each model clamps the choice to its catalogued levels; models with no explicit control receive no parameter. The bot tools that create and edit a teammate take `model` and `thinking` too, held to what the Model and Thinking pickers offer (see [Tools](tools.md)).

**The model catalog** (`crates/models`, `lorca-models`, which `lorca-agent` re-exports as `lorca_agent::models`) knows each offered model's context window, output cap, image support, thinking mode and levels, and rates, and for OpenCode the `wire` it is served on. It is its own crate so the phone's core, built without the agent, has it too. It is data, `crates/models/catalog.json`: a `version`, the UTC time it was `updated`, the `models` in order, and each provider's `review` model, the one Auto-review runs. A provider's first model is its default, so the defaults, Auto-review's models, and OpenCode's endpoints change with the file. Every build carries it, and the site serves it, minified, at `https://lorca.app/models/v1.json`, so a new model reaches every Device without a release: edit the file, merge, and deploy the site. A change must move `updated` later (`bun run check:catalog`, and the Catalog workflow on a pull request).

**Updating the catalog** (`crates/cli/src/catalog.rs`): the catalog in use is the one with the latest `updated` of the bundled one, the one cached in `catalog.json` in Lorca's folder, and the served one, and a later one replaces it whole, so a catalog can also drop or reorder models. `lorca serve` checks the server when it starts, the phone's core at its app's first `bootstrap`, every app's `bootstrap` after that, and `models.reload` (`lorca models reload`) even within the hour; any other check within the hour of the last one is skipped, and nothing checks on a timer. A check sends the cached ETag as `If-None-Match`, so an unchanged catalog costs a 304, and gives up after five seconds; a failure keeps the catalog in use. A turn on a built-in provider's model the catalog lacks checks first, at most every five minutes, since another Device may have offered the model from a newer catalog. A catalog installed while an app is open reaches its pickers in `roster.changed`, which carries `models` as the snapshot does. `LORCA_MODELS_URL` points the checks elsewhere (a mirror, or `bun run web`'s `/models/v1.json`), and `LORCA_MODELS_FETCH=0` turns them off; only `lorca serve`, the phone's core, and `lorca models reload` turn checking on, so tests never reach lorca.app.

**Reading a catalog** (`lorca_models::parse`): a catalog written for a newer Lorca never breaks an older one. Fields it does not know are ignored. A model it cannot run as listed (a thinking mode or wire it does not know, a required field missing, an id listed twice) is left out, and levels it does not know are dropped. A catalog is refused whole when its `version` is not 1, its `updated` is not `YYYY-MM-DDTHH:MM:SSZ`, or a provider it or the bundled catalog lists has no `review` model among its models. A change older builds cannot read is served as `v2.json` beside v1. The format carries no URLs or headers, so a catalog from lorca.app over HTTPS can change what a model costs, how it thinks, and which of OpenCode's endpoints serves it, but never which server a request goes to or what it carries. Lookups hand out `&'static` entries: each catalog read is leaked, a few kilobytes at startup and for each later catalog.

The snapshot carries the catalog's `models`, and every app's Model and Thinking pickers come from them, so a new model is added in the catalog alone. The Thinking picker offers Default and only the levels the bot's model takes, the default model's when the bot has none, and every level the provider has for a model the catalog lacks; a model without levels shows no Thinking picker, and picking another model returns a level the new one does not take to Default. Every assistant message carries `usage.cost` in dollars from those rates (ChatGPT and Grok sign-ins are not billed per token; their cost is what the work would cost at API rates). `usage.input` is the input read fresh and `usage.cache_read` the input served from the provider's prompt cache: Messages reports the two apart, and the adapters for Chat Completions and Responses, which count cached tokens inside their input total, take them out of `input`. The Runner adds each turn to the chat's `usage` (`context_tokens` and `context_window` of the last turn, totals of tokens, cost, and turns), kept in the local database and never synced; the app gets it in the snapshot, in `roster.changed`, and as `chat.usage` events, and the DM inspector shows "Context 128k of 1M · 13%" and "Spent $0.42 · 18 turns".

**Compaction** keeps a long chat inside the window (`lorca_agent::compaction`, pi's prompts and cut rule; `LORCA_COMPACTION=0` turns it off): when the transcript a turn rebuilds is estimated above `window - 16k` tokens, or more than 400 messages of the chat are not covered by a summary yet, or a turn's own context grows past the window between model calls (the loop's `prepare_next_turn` hook), or the provider answers that the prompt is too long, the older part is summarized by the same model into a structured checkpoint (goal, progress, decisions, next steps, files touched), about 20k tokens of recent messages stay as they are, and a `Compaction { bot_id, summary, after_message_id }` on the chat (local, per bot) makes every later turn start from the summary and the messages after that one. The summary covers the whole chat since the last one, in pieces of at most the window less twice the reserve, each piece updating the summary of the ones before, so a backlog of any size compacts. A compaction of the context a turn sends (a transcript over the threshold that the turn rebuilds whole, or a context that grows between the turn's model calls) asks the summary inside the conversation instead (`compaction::compact_in_place`): the request is the turn's next one, with its system prompt, tools, thinking, cache points, and messages, and the checkpoint prompt as one more user message that names the message the kept part starts with. The provider's prompt cache serves everything the turn's last request sent, where a summary of the transcript as text pays for all of it again. It falls back to the summary of the transcript when the window leaves under 4,096 tokens for the reply, or the model answers with a tool call, a reply the limit cut off, an error, or anything but the checkpoint. A backlog past what a turn rebuilds, a prompt the provider called too long, and Compact summarize the transcript. The memory flush runs first, the same way (see [Memory](bots.md#memory)). Automatic compaction is silent, as in Grok Bot; the inspector's Context row shows the result, and its Compact button (`chats.compact`) does it by hand with a notice in the chat.

**Retries**: a model call that fails before it streams in a way that reads as transient (overloaded, rate limited, 5xx, a dropped connection) is asked again after a backoff, three times at most on top of the adapters' own HTTP retries; the app hears `job.retry` and the working row reads "Retrying (2 of 3) in 4 s…". A failure that outlasts the retries is the bot's failed bubble, as before.
