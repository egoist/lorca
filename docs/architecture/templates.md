# Private bot templates

`crates/cli/src/templates/` packages selected reusable bot content as a private UTF-8 JSON file with the `.lorca-template` extension. The AppKit and native Go/MyGo desktop apps speak to their local CLI for contents, preview, file access, and import. Export writes the chosen local file; it has no publication or link-sharing operation.

## Selection and review

`templates.contents { bot_id }` lists the profile, saved reusable skills, curated memory entries and Markdown topics, routines, and the services installed on the bot's Runner. Every category starts unselected in the desktop export sheets. Selection uses `profile` and arrays of `skill_ids`, `memory_ids`, `routine_ids`, and `requirement_ids`. `templates.export.preview { bot_id, selection }` constructs the exact portable contents, redacts recognizable credentials and exact saved provider/plugin secret values, and returns a digest and review warnings. Secret records are inspected locally only for redaction and never appear in a preview or file. Warnings identify email addresses, machine paths, URLs, possible phone numbers, selected memories, and scripts. The user reads the full text and acknowledges reviewing personal content before saving.

The profile contains only name, description, SF Symbol, and accent. Skills contain only their name, description, instructions, examples, and inline references and scripts. Memory comes from the bot's canonical `workspaces/<bot id>/MEMORY.md` entries and direct `memory/*.md` topics; logs, attachments, and other workspace files are outside the selection. Reads are bounded, refuse symbolic links, and do not adopt a working directory's memory. A selected topic imports as curated memory text. Routines contain only name, schedule, prompt, optional check script, and available scheduling configuration (`timezone`, `missed_run_policy`); schedule cursors, health, and run history stay on the Runner. Plugin requirements contain only `service_id`. Provider credentials, plugin variables and tokens, bot and machine ids, working directories, avatars, chat history, run outcomes, and account metadata have no portable fields.

Reusable skills use the content-only `playbooks.list` / `playbooks.export` / guarded `playbooks.save` API. The template module owns no skill store, revision history, project registry, or connection registry. A CLI without the playbook methods reports that capability in the contents sheet and blocks importing a file with skills before creating a bot. New imported skills use the new bot's scope, new record ids, revision zero and an empty expected hash, with `template_import` provenance. Source scope, ids, provenance, and revisions remain with the exporting account.

`templates.export { bot_id, selection, path, expected_digest, reviewed, overwrite? }` rebuilds the selection and refuses changed contents. `reviewed` must be true and the digest must match the preview. The file is written atomically with mode 0600 on Unix. An existing destination requires explicit replacement, and the CLI refuses destinations inside Lorca's runtime data directory. The file is portable plaintext: its privacy comes from the local file and the user's choice of recipient.

## Format and validation

The root has `format: "lorca.bot-template"`, `version: 1`, optional `profile`, and arrays `skills`, `memories`, `routines`, and `requirements`. Omitted arrays are empty. This format is separate from the [marketplace index](marketplace.md#the-index); exporting or importing changes no marketplace entry.

A file is at most 1 MiB. The parser rejects unknown fields at every level, unsupported versions, invalid schedules, duplicate names or requirements, oversized text, NUL characters, and resource paths outside safe relative `references/` or `scripts/` paths. Skills fit the playbook content limits, memories fit the 256 KiB curated-memory limit, and routines fit the bot's routine count and check limits. Import refuses recognizable credential text instead of silently changing the file the user reviewed. Complete redaction markers remain stable when a scrubbed file is imported.

## Recipient setup

Scheduling fields validate through the canonical `routines.describe` API and import through `routines.create` with `enabled: false`. A CLI that does not expose a supplied `timezone` or `missed_run_policy` reports it as unsupported before setup, so the configuration is not silently lost. Omitted fields use the canonical routine API's defaults. The template module keeps no separate schedule or health store.

`templates.import.preview { path, runner_id, name?, mappings? }` reads the file locally and returns its contents and digest, warnings, setup issues, and the recipient Runner's connection candidates for each service. `mappings` maps each portable service id to an existing recipient-local installed plugin id. Each requirement needs an explicit ready connection on that Runner. Missing plugins, unready sign-ins, unknown fields, unsupported versions, and absent skill support appear before setup completes. Import installs no plugin and performs no sign-in.

Explicit plugin tool namespaces in selected text normalize to service namespaces during export, and to the selected recipient namespaces during import, within the runtime's 64-character tool-name limit. Literal source instance ids become `{{connection:<service-id>}}` references that import resolves to the selected recipient id. Each referenced namespace or connection needs a selected requirement. Content that uses multiple source accounts for one service is refused rather than collapsed into one account; the user splits that content into separate templates. Account labels and configuration stay with the Runner's connection records.

`templates.import { path, runner_id, name?, provider?, mappings, expected_digest, reviewed }` verifies the reviewed bytes and current recipient connections again. It creates a fresh bot and DM, uses the recipient's provider choice and default workspace, writes only the selected curated memory, saves new scoped skills through the guarded playbook API, and adds every routine paused with no run history. It starts no greeting, model turn, or routine check. Editing either bot afterwards changes only that bot. A failed setup removes the newly created bot, routines, workspace, and successfully saved skills.

For another Runner, the local CLI sends the reviewed text and recipient choices in a `templates.import` request sealed to that Runner. The Runner revalidates and creates its bot and memory locally. `templates.memories` and `templates.export.preview` sealed requests read candidates and build the selected preview on the bot's assigned Runner, so its integration secrets can be redacted there. The existing [request protocol](protocols.md#cli--relay) carries these operations; roster changes use the existing encrypted roster, and playbook persistence and sync remain owned by its account store.

## In the macOS app

A DM inspector's Profile card offers Template → Export…. The sheet has a checklist, full read-only contents preview, review warnings, and Save Private File… through `NSSavePanel`. File → Import Bot Template… opens `NSOpenPanel`, then a sheet with the contents, new name, Runner, provider, and an explicit connection menu per requirement. Refresh Preview rereads the file and Runner state. Create Independent Bot stays disabled while validation or setup issues remain, and until the user acknowledges review. The new bot's DM opens after import; its routine switches stay off.

## In the Windows and Linux app

The native Go/MyGo app offers the same Profile → Template → Export… row and File → Import Bot Template… command, also listed in the command palette. `desktop/model/templates.go` decodes the CLI's content, warnings, issues, digest, and recipient candidates; its requests and import reconciliation use the store's ordered main-thread reply queue. The UI reads no template bytes and owns no schedule, connection, permission, or accounting records.

`sheet_template_export.go` keeps explicitly selected profile/skill/memory/routine/requirement IDs and review state in the sheet, with stable control keys across build passes. Changing selection discards the preview and acknowledgment. The complete selected text is scrollable and selectable. Native Save chooses the private destination; an extension-induced change to an existing destination asks before replacement. Only the reviewed selection and digest go to `templates.export`.

`sheet_template_import.go` keeps the edited name, Runner/provider, and explicit service mappings across frames. Name or Runner/connection edits request a fresh preview and discard acknowledgment; a Runner change clears its mappings. Missing plugins, unsupported file/version/fields, absent capabilities, and request failures remain visible and keep creation disabled. Refresh Preview rereads the file. Generation checks ignore superseded replies and replies to dismissed sheets. Import sends the current recipient choices and reviewed digest to `templates.import`, then opens the returned independent DM. Routines stay paused under the CLI's admission rules; the client starts no check or turn.
