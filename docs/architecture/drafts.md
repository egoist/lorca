# Message drafts

An email or Slack message a bot writes in a chat waits there as a draft for the user to edit, then send or discard, after Grok Bot's draft cards. The draft is a [review item](review-queue.md): the exact call the bot made, version-bound, decided by the user and run on the bot's Runner. `crates/cli/src/drafts.rs` holds the mapping between a call and its card.

## Which calls are drafts

A plugin manifest names the tools that write to people in `tools.messages` ([Codemode and Plugins](plugins.md#plugins)): each entry has the `tool` (a name, or a pattern ending in `*`), its `kind` (`email` or `slack`), and the argument that holds each part of the message: `to`, `cc`, `bcc`, `subject`, `body`, `attachments`, and `reply` (what it answers). The marketplace's Gmail declares `create_draft`; Slack declares `slack_send_message` (`channel_id`, `message`, `thread_ts`). Gmail's server only makes drafts, so its entry has `send: gmail`: Send then sends the draft the call made.

In a chat's turn, when the bot's Access drafts messages, `mcp::review_call` checks Access for the call as for any plugin call, then stages it instead of letting Auto-review judge it: the user is the reviewer. A routine's, a watch's, a calendar routine's, and an event's turn (a routine's webhook included, [Routine triggers](routine-triggers.md)) has nobody to send a draft, so its message goes to Auto-review, which may hold it as the same card. A message that carries a [secret](secrets.md) saved on the Runner, in its fields or in a text file it attaches, or a secret's `{{secret:NAME}}` placeholder, is refused before staging: secrets never go into an email or a Slack message, or into the chat a draft shows in. `drafts::stage` moves each attachment's content out of the call into an encrypted file on the Runner (`drafts/<sha-256>`, under the account DEK with `draft_attachment` as associated data) and names it in the call by size and hash, so a megabyte attachment keeps the review item within its budget and the hash binds the file to what the user reviewed. It then creates the review item through `review_execution::stage_call` and returns a blocked result that tells the bot the draft is ready in the chat and has not been sent; the script stops there, and the bot writes any other message with another call. Staging takes the turn's cancellation, so a [Stop](stopping.md) while it waits on the server leaves no draft and removes its files; a card already in the chat stays for the user. A routine's message call goes through Auto-review as other effectful calls do, and one it holds is staged the same way, so it shows as the same card. Review items whose call writes a message carry `is_message`. A [channel's](channels.md#conversations) reply, which the bot sends as itself from its own Telegram bot or Slack app rather than in the user's name, is not a message tool and is never a draft.

## The card

`review_queue::publish_origin` writes a message item into its chat as a `draft` message by the bot (`review-status-<review id>`), in place of the review's notice, rewritten as the item changes: `{ review_id, version, state, plugin_id, account, draft, note?, direct }`. `draft` is the message as the card shows it: `{ kind, to, cc, bcc, subject, body, attachments: [{ name, size }], reply? }`. `note` says why it was not sent, or why it needs another look; `direct` is false for a server that only drafts. The bot's later turns read the card as what became of its draft and the message as it stands, with the user's changes (`drafts::history_line`).

Send is `reviews.edit { id, expected_version, message }` when the user changed the message, then `reviews.approve` of that version. The Runner puts the card's fields back onto the call's arguments (`drafts::write`): the recipients, subject, and text it shows, and the attachments it still names; what it does not show, such as the message a reply answers, stays as the bot wrote it. An email address must be a plain address. Discard is `reviews.reject`. As for any item, a stale version is refused, preconditions are captured again, and only the Runner sends. Running an approved message call restores the attachments from the Runner's files, then for `send: gmail` reads the draft id from `create_draft`'s result and posts it to Gmail's `drafts.send` with the account's own sign-in, refreshed first as a connection refreshes it (`mcp::service_token`). A confirmed send records `succeeded` ("Sent"); a refusal `failed` with the service's reason; a send cut off before an answer `uncertain`, since it may have gone out. Files of a sent or discarded message are deleted unless another open draft names them.

## Sending directly

A bot's [Access](bot-permissions.md) has `drafts` (on unless false). Off, the bot's message calls are the tools' own again, through Auto-review: Slack messages go out, and Gmail keeps its drafts in the account's Drafts. A Slack card offers Always Send: it sends the message, then `bots.update { id, drafts: false }` turns drafts off for that bot alone. The authorization fingerprint of a pending item leaves the flag out, so turning drafts off does not send an open draft back for another look.

## Feedback

Edits are [feedback](feedback.md) for the bot: when the user edits before sending, `feedback::review_decided` records the change as `edited`, with the message before and after in its own words (header lines, then the text) rather than the call's JSON; a send is `accepted` and a discard `rejected`.

## In the apps

The Mac (`Chat/DraftCellView.swift`) and the Windows and Linux app (`draftCard` in `cards.go`) show the card in the transcript with the other cards: who drafted it ("Chef drafted an email", "a reply", "a Slack message") with how it ended at the end of that line (Sending…, Sent, Not sent, Discarded, Not confirmed), the account, the header rows as Mail's compose window has them (To, then Cc and Bcc when the message has them, then an email's Subject) edited in place, the text, the attachments with a button to leave one out, why it was not sent, and Discard apart on the left from Send. A Slack card adds Always Send beside Send, with a line under the buttons saying it sends the bot's next Slack messages directly. Typing never resizes the card; a long message scrolls. The phone (`DraftRow` in `src/ui/transcript.tsx`, `app/draft/[id].tsx`) shows the same card with Send, Always Send, and Discard, and a tap opens the message as Mail's compose sheet: the fields, attachments, Send in the bar, Always Send and Discard as rows. A send that fails puts the card back and says why. Waiting for review in the inspector and in Details leaves message drafts to their cards. Access has a Messages section with Draft first and what it means.
