# Cloud sandboxes

A bot's [coding agent](coding-agents.md) can run in a cloud sandbox the user set up instead of on its Runner, on a clone of the repository; everything else about it, its driver, review, transcript, and message, is as on the Runner. `crates/cli/src/coding/sandbox/` holds it: `mod.rs` the settings, the clone, and the process, `vercel.rs` and `cloudflare.rs` each provider, and `sandboxes/cloudflare` the Worker users deploy.

## Setting one up

An agent can run in a cloud sandbox instead of on the Runner: Vercel Sandbox or Cloudflare Sandbox, each set up by the user on a Runner with an account of their own. Lorca has no account with either. Vercel Sandbox takes the user's Vercel access token, the project the sandboxes belong to, and optionally its team, image (Vercel's own has Node.js, Python, and coding agents), vCPUs, and time limit (45 minutes unless set; a session ends there). Cloudflare Sandbox takes the address of the Worker the user deployed from `sandboxes/cloudflare` (its README has the steps) and its `LORCA_TOKEN` secret. Each also takes the environment variables the agents need there: `GITHUB_TOKEN` or `GH_TOKEN` to clone, push, and open pull requests, and what each agent signs in with, such as `ANTHROPIC_API_KEY`. They stay in `sandboxes.json` in the Runner's data directory (0600), with a `default`: where a start that names no place runs, the Runner itself until the user picks a sandbox. `coding.sandboxes { runner_id }` answers both sandboxes, each set up or not, its settings, its token's last four characters, and its variables by name, never a token or a value; `coding.sandboxes.set { runner_id, default?, vercel?, cloudflare? }` sets one up or changes it (a token or a value left out keeps the saved one; variables it does not list go), `null` removes it, and answers the same; `coding.sandboxes.check { runner_id, kind }` asks the provider whether what was saved works. All three go to the Runner sealed when it is another Device. Every saved token and value is replaced by its placeholder (`{{sandbox:GITHUB_TOKEN}}`) wherever the Runner's saved secrets are ([Coding agents](coding-agents.md#its-transcript)).

## Starting one there

`coding_agent start` takes `sandbox: local | vercel | cloudflare`, which the tool tells the bot to name only when the user asked; without it the start runs where the user chose. The sandbox works on a clone, so `folder` must be a git repository with a remote: the one its branch tracks, or `origin`, cloned over https without the credentials its address may hold (`git@github.com:acme/shop.git` is `https://github.com/acme/shop.git`). The agent gets a sandbox of its own, `lorca-agent-3f9a2c1d`: a persistent named Vercel sandbox, or a Durable Object and its Container behind the Worker. Lorca clones the repository into it (`/vercel/sandbox/shop`, `/workspace/shop`) on the Runner's branch and checks out the commit the Runner is on when the remote has it, else the remote's; the status line says so ("Working in /vercel/sandbox/shop on main, a clone of github.com/acme/shop in Vercel Sandbox. It starts from what the remote has: commits not pushed from this Runner are not in it"). Git there signs in to GitHub with the sandbox's `GH_TOKEN` or `GITHUB_TOKEN`, and commits carry the name and email git has on the Runner. The first of the user's agents that is on and installed in the sandbox runs (`command -v`); none fails the start and says so. Its brief adds that the job is a clone in a cloud machine, so what it does reaches the user only through what it pushes, and names the variables it holds there.

## Its process

Its process runs there with the sandbox's variables and the secrets it was given, as `sh -c` and no login shell, whose profile could change `PATH` or print into the protocol, in a process group of its own (`setsid`, its stdin kept past the `/dev/null` a shell without a terminal gives a background job) that a stop's signal ends as one. The driver speaks to it as to a process on the Runner (`process::Host`): Vercel's API takes its stdin in chunks at the offset the sandbox counts, so a write sent again is not written twice, and streams its output as JSON lines, asked for again past what came when the stream breaks off; the Worker passes stdin and output over a WebSocket, binary messages with a first byte of 1 for stdout and 2 for stderr, `{ "signal": 15 }` to stop, and `{ "exit": code }` when it ended. A connection that is lost ends the process, and the agent fails saying so, for the bot to start it again on its session. What its work changed counts in the clone, with the same git commands run there.

Each of its commands passes the bot's Access and Auto-review as on the Runner ([What it may do](coding-agents.md#what-it-may-do)). The review hears that the command runs in the user's sandbox with a clone of the repository, not on the Runner, and which variables the sandbox holds; the fast paths are the reads and the file changes in its folder, and the git state, which is the Runner's to check, is left out.

## Pausing, resuming, and deleting

When its process ends, the sandbox pauses: Vercel stops the session and keeps the sandbox's files in a snapshot, and the Worker's Container sleeps two hours after the last thing it did, its files with it. A later message resumes the sandbox there, on its session, while the clone is there; once a Container slept, the message fails saying the clone is gone, and the bot starts a new agent on the job. Deleting the chat or the bot, or Lorca forgetting the agent a month after it ended, deletes its sandbox (`DELETE /v2/sandboxes/{name}`, `DELETE /sandboxes/{name}`).

## In the apps

The card's `folder` of an agent in a sandbox is where it works in words, "Vercel Sandbox · github.com/acme/shop", which every app shows as it does a folder. The Windows and Linux app sets the sandboxes up in a Cloud Sandboxes section under the agents in its Coding Agents pane (`desktop/settings_coding.go`): Run agents on, the Runner or a sandbox set up there, and a row for each sandbox whose Set Up… or Edit… opens its sheet (`desktop/sheet_sandbox.go`), with a field for each setting and the variables as names and hidden values. A saved token or value comes back empty, which keeps it. Saving asks the provider whether it works, and the sheet stays open saying why when it does not.
