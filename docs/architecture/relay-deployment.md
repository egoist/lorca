# Relay deployment

The [relay](relay.md) runs from `crates/relay/Dockerfile`, built with the repository root as its context.

The image (`crates/relay/Dockerfile`) builds from the repo root, since the relay is a workspace member; cargo-chef keeps the dependency layer cached until a manifest or `Cargo.lock` changes. It runs the binary on `debian:trixie-slim` in `/data`, where the SQLite database and the files directory land, and listens on `[::]:$PORT` (8787 without `PORT`; `LORCA_RELAY_BIND` overrides both). A Railway service builds it through `RAILWAY_DOCKERFILE_PATH`, healthchecks `/v1/health`, and sets `RAILWAY_DEPLOYMENT_DRAINING_SECONDS`, since Railway otherwise follows SIGTERM with SIGKILL at once. With SQLite, a Railway volume at `/data` keeps the database. With Railway's Postgres, `LORCA_RELAY_DB` is its private `DATABASE_URL` with `?sslmode=disable`, since that server's certificate is self-signed, and files go to an S3 bucket, since the container's disk does not outlive a deploy. [crates/relay/README.md](../../crates/relay/README.md) lists the variables a Railway service takes. The production relay deploys from the `relay` branch, which its Railway service watches, so a deploy is a push of main to that branch (`git push origin main:relay`).

The [Release relay workflow](../../.github/workflows/release-relay.yml) publishes `ghcr.io/egoist/lorca-relay` from a `relay-vX.Y.Z` tag for Linux amd64 and arm64, using the repo root and the same Dockerfile. Image tags are `X.Y.Z`, `sha-<full commit SHA>`, and `latest`, which follows the last successful publication. The workflow authenticates to GHCR with its `GITHUB_TOKEN` and `packages: write`. Hosts such as Dokploy pull a version or digest, route HTTPS and WebSocket traffic to port 8787, and check `/v1/health`; the database, file store, push, and receiver settings are the same as a source build. [Published image](../../crates/relay/README.md#published-image) covers publishing and registry access.

The build matrix uses native `ubuntu-24.04` (amd64) and `ubuntu-24.04-arm` (arm64) runners, with separate caches. Each pushes by digest; after both succeed, the publish job combines their digests into the tagged multi-platform image.

After publishing, the workflow's `deploy` job calls Dokploy's `/api/application.deploy` using the `DOKPLOY_URL`, `DOKPLOY_API_KEY`, and `DOKPLOY_APPLICATION_ID` repository secrets. The Dokploy application uses `ghcr.io/egoist/lorca-relay:latest`, so the requested deployment pulls the published image. A successful API response acknowledges the deployment request; Dokploy's deployment logs and the relay health endpoint establish rollout success. [Automatic Dokploy deployment](../../crates/relay/README.md#automatic-dokploy-deployment) covers configuration and retries.
