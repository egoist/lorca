# Lorca Architecture

Source of truth for how Lorca is built. Read this before writing code.

Lorca is a Grok Bot alternative: persistent named bots, 1:1 chats, group chats, handoff, and orchestration. Work runs on **Devices you own**. The Rust CLI runs on macOS, Linux, and Windows. The macOS app is a UI for the local CLI, which it bundles and launches.

Identity is a **key pair**. Devices pair. The relay stores public keys and ciphertext, after [Happy’s security model](https://happy.engineering/docs/security/).

## Constraints

1. **The app speaks only to the local CLI** over localhost websocket. The app ships the CLI binary inside its bundle and starts `lorca serve` itself, unless one already answers on the port. The CLI holds keys, talks to the relay, and talks to models.
2. **The UI is AppKit** (SPM): system materials, SF Symbols, Auto Layout, keyboard, accessibility.
3. **The CLI owns the agent loop:** inference, tools, streaming, cancellation, orchestration.
4. **The relay is zero-knowledge:** opaque blobs and public keys. Auth is a signature challenge.
5. **Every Device records its `os`.** A Device with a desktop `os` (`macos`, `linux`, `windows`) is a **Runner**. Phones and tablets (`ios`, `ipados`, `android`) are Devices, never Runners.
6. **Provider credentials belong to the account.** API keys and ChatGPT and Grok tokens are connected once, on any Device, and reach every paired Device as a `credentials` blob encrypted with the account DEK. A bot runs with them on whichever Runner it is assigned to.
7. **A bot runs on one Runner:** that Device’s CLI.

## Three processes

```
┌─────────────────────┐     local websocket      ┌──────────────────────────┐
│  Lorca.app        │ ◄──────────────────────► │  lorca CLI (Rust)      │
│  AppKit             │     127.0.0.1           │  keys + agent loop       │
└─────────────────────┘                          └────────────┬─────────────┘
                                                              │ HTTPS
                                                              │ ciphertext + signed requests
                                                              ▼
                                                 ┌──────────────────────────┐
                                                 │  Relay (Rust, axum +     │
                                                 │  SQLite or Postgres)     │
                                                 │  public keys + blobs     │
                                                 └──────────────────────────┘
```

- **App:** native chat UI. Create or restore identity, pair, through the CLI. Launches the bundled CLI as a child process and restarts it if it exits.
- **CLI:** identity and machine keys, local websocket, encrypt/decrypt, agent loop, the account’s provider credentials, sync with the relay.
- **Relay:** store-and-forward API. Rust, axum, SQLite or Postgres (`crates/relay`). Self-host it anywhere; clients point `LORCA_RELAY_URL` at it.

Production installs are named **Lorca** and use `app.lorca`; development installs are named **Lorca Dev** and use `app.lorca.dev`. They are separate applications on macOS, iOS, and Android. The production CLI stores its account under `~/.lorca` and listens on `4862`, while the desktop-app development build sets `LORCA_HOME=~/.lorca-dev` and listens on `4863`. On phones the distinct application ids give each build its own OS sandbox, and the core uses `lorca/core` or `lorca-dev/core` inside that sandbox. Their iOS keychain groups are `group.app.lorca` and `group.app.lorca.dev`.

If the CLI is down, the app shows a native empty state with the launcher’s status and the manual `lorca serve` command.

## Identity

An identity is keys you hold.

After Happy’s layering, the Device that creates or restores the identity is the identity device.

| Layer                    | What                                                                                | Where                                                                                                |
| ------------------------ | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Master secret (32 bytes) | Root. Backup as a base32 phrase (13 groups of 4).                                   | `~/.lorca/identity.json`, mode 0600. Stays on the identity device.                                 |
| Content keypair          | X25519, HKDF from master. Secret unseals the DEK. Public key seals it.              | Secret on Devices that have the master. Public key on the relay.                                     |
| Identity signing key     | Ed25519, HKDF from master.                                                          | Private local. Public key on the relay; the identity id is `hash(pubkey)`.                           |
| Account DEK              | Random XChaCha20-Poly1305 key. Encrypts roster, chats, messages, machine metadata, provider credentials. | Made locally. On the relay as a `key` blob **sealed** to the content public key; handed to each paired machine inside the sealed pairing reply. |
| Machine keypair          | One 32-byte secret per Device → HKDF → Ed25519 signing key + X25519 box key.        | `~/.lorca/machine.json`. Public keys on the relay, attested by the identity.                       |
| Chat/job envelopes       | Account DEK for roster/chat/machine/credentials blobs; sealed box to the Runner’s box key for jobs. | Relay stores ciphertext.                                                                          |
| Push key                 | HKDF from the account DEK. Seals what a push says.                                  | Every Device derives it. An iPhone keeps a copy in its app group's keychain for the notification extension. |
| Ephemeral pairing key    | X25519, one handshake.                                                              | Devices; discarded after pairing.                                                                    |

AEAD envelopes are `nonce(24) || ciphertext` with the blob kind as associated data. Sealed boxes are libsodium `crypto_box_seal` (`crypto_box` crate); signatures are `ed25519-dalek`.

Recovery: restore the master secret from the backup phrase → re-derive content keys → unwrap DEKs from the relay. The backup phrase is the identity.

### Pairing a Device

1. Device A (has the identity) asks the relay for a pairing nonce and shows a pairing string: `lorca://pair?relay=…&id=<identity pubkey>&ek=<ephemeral pubkey>&n=<nonce>`. The CLI waits on it for ten minutes whether or not the sheet stays open (Done keeps the code good). Cancel retires it: `pair.cancel` drops the waiter and deletes the mailbox (`DELETE /v1/pair/{nonce}`), so a Device that pastes the code afterwards is told at once instead of polling out the TTL.
2. Device B pastes it (onboarding, or `lorca pair <string>`). B generates its machine keys and posts a request sealed to `ek` into the relay’s pairing mailbox (`POST /v1/pair/{nonce}/request`, no auth): its machine public key, box public key, `name`, `os`. `pair.accept` emits `pair.posted` once the request is up and then polls for the reply; `pair.abort` ends that wait, a newer `pair.accept` replaces it, and a mailbox that is gone (cancelled or expired) fails the wait with a message that says to get a fresh code.
3. A polls the mailbox, unseals the request, attests B on the relay with an identity-signed `POST /v1/identities`, and posts a reply sealed to B’s box key: identity public key, content public key, the **account DEK**, and the relay URL.
4. B unseals the reply, saves `machine.json`, authenticates with the challenge, and uploads its `machine` blob (`name`, `os`, installed plugins and their state).
5. B syncs the roster, the account’s credentials, and the chats, and shows up in the Device list. A Runner is ready for bots as soon as the `credentials` blob lands.

App ↔ CLI on one machine uses `127.0.0.1`; those keys are already local.

### Unpairing a Device

Any paired Device can unpair any other from its Device list (`device.unpair`), and a Device unpairs itself with `identity.forget`. Either way the CLI calls `DELETE /v1/machines/{machine_pubkey}` with its bearer token: the relay drops the machine row, remembers the key in `revoked_machines`, deletes the envelopes sealed to it, closes its sync socket, and signals `machines` to the identity's other sockets. A revoked key never authenticates again: its bearer tokens are refused, its challenge answers `410 Gone`, and the identity cannot re-attest it. A Device that pairs again generates a new machine key.

The relay's machine list is the list of paired Devices. A Device reads it when its sync socket opens and whenever the relay signals `machines`, and drops a Device it no longer lists, so the other Devices see an unpaired one leave at once; a stale `machine` blob for a key the relay does not list is ignored. The unpaired Device learns when its socket closes and the relay refuses the next one: a `410` from the relay makes its CLI forget the identity (keys, credentials, chats), and the app shows onboarding. That holds for the identity device too: a phone can unpair a lost computer, and the backup phrase restores the identity on a new machine key.

### Devices and Runners

Every Device writes its `os` into its machine metadata blob. Values: `macos`, `linux`, `windows`, `ios`, `ipados`, `android`. The client sets it at pairing and re-sends it with presence. `name` starts as the name the machine already goes by: a Mac's Computer Name; on Linux the pretty hostname in `/etc/machine-info` (GNOME's Device Name), else the host name; `COMPUTERNAME` on Windows; a phone's device name. `--name` on `lorca pair` or `lorca identity new` gives another, and `device.rename` changes it later. `model` is the name a person knows the machine by ("MacBook Air (M5)": `system_profiler`'s machine name and chip on a Mac, where `hw.model` is an identifier such as `Mac17,3`). A CLI reads its model and OS version from the host on every run rather than from `machine.json`, and uploads its `machine` blob again when they change.

`os` decides the Device’s role:

| `os`                        | Role       | Can                                                                                      |
| --------------------------- | ---------- | ---------------------------------------------------------------------------------------- |
| `macos`, `linux`, `windows` | **Runner** | Everything a Device can, plus be assigned bots and run Jobs with the account’s credentials. |
| `ios`, `ipados`, `android`  | Device     | Hold keys, configure account providers, read and write chats, create bots for Runners, pair other Devices. |

Runner status is derived from `os` alone. There is no flag to opt a phone in or a desktop out. Peers read `os` from the decrypted metadata blob, so the relay never learns which Devices are Runners.

### Relay surface

The relay stores:

- Identity public key and content public key; machine signing and box public keys with the identity’s attestation
- Blob ids, kinds, sequence numbers, timestamps, size
- A blob's slot: the random id of the message it is a version of, `roster`, `credentials`, `machine-<machine public key>`, or `read-<chat id>`
- A blob's group: the random id of the chat a message, read mark, or attachment belongs to, and the ids of deleted chats
- Recipient machine public key on an envelope (so a Runner can fetch its jobs)
- Which machine public keys have a sync socket open (presence), and when each last connected or disconnected
- Keys of unpaired machines, refused for good
- A phone's APNs or FCM device token, one per machine, dropped with the machine or when Apple or Google calls it dead
- Pairing mailboxes keyed by nonce, expiring after ten minutes

Nicknames, Device names and `os`, bot profiles, provider credentials, and chat text live inside encrypted blobs.

## Domain model

Plaintext lives **on Devices**:

```
Identity 1──* Device
Device   1──* Bot          (only a Runner: os is macos, linux, or windows)
Identity 1──* Chat
Chat     *──* Bot          (kind dm: exactly 1 bot, fixed · kind group: 1–6 bots, members change)
Chat     1──* Message
Bot      1──* Routine      (a scheduled task, run in the bot's DM on its Runner)
Device   1──* Plugin       (an MCP server installed on a Runner, for every bot there)
Bot      1──* Job          (a turn on the bot's Runner)
```

| Entity             | Device                                                    | Relay                                                  |
| ------------------ | --------------------------------------------------------- | ------------------------------------------------------ |
| Identity           | Master + content + signing keys                           | Public key                                             |
| Device             | Machine keypair, `os`                                     | Machine public key + encrypted metadata blob           |
| Bot                | Decrypted profile                                         | Inside encrypted roster blobs                          |
| Routine            | Name, schedule, prompt, state                             | Inside encrypted roster blobs                          |
| Plugin             | Manifest, variables, secrets, tokens on the Runner        | Id and state inside the Runner's encrypted machine blob |
| ProviderCredential | `credentials.json` on every Device                        | Inside the encrypted `credentials` blob                |
| Chat / Message     | Account/chat DEK                                          | Encrypted blobs                                        |
| Job                | Any paired Device may create; the assigned Runner runs it | Sealed envelope to that Runner’s machine box key; deleted once run. A hard Stop sends `job_cancel` to the Device running it; the Runner seals how the turn ended (`job_result`) to the requesting Device, and lists the turn and what it is doing in its `machine` blob for every Device |

A bot's look is an SF Symbol (`symbol_name`) on an accent gradient (`accent`), or a profile image of the user's own: `avatar` is an attachment record whose bytes travel as an encrypted `file` blob, the same way a message attachment does, and every Device shows the image in place of the symbol once it has fetched it. Clicking a bot's avatar in the macOS inspector opens the Look sheet. The macOS Profile card keeps Name trailing-aligned and opens Description in its own editing sheet. On the phone, tapping the avatar in Details slides the Look screen in inside the same form sheet (`app/chat-info` has its own stack); Name is trailing-aligned there too, and the Description row pushes a full editor. Details also has native Provider, Model, and Thinking menus under Runs with; a provider change clears the other two to that provider's defaults. `bots.update` carries all of these changes, including `symbol_name`, `accent`, and `avatar` (a `{ path, … }` file to store and upload, or `null` to remove).

Creating a bot for Runner B from Device A: A writes an encrypted bot profile into the roster (paired Devices can read it) and pins B’s machine id. Bot create rejects a target whose `os` is not desktop. Turns are job envelopes addressed to B. B decrypts the job, runs the loop with the account’s provider credentials, and uploads encrypted replies.

If B is offline, the envelope waits on the relay until B fetches it. The UI infers that from decrypted roster state. A turn for a provider the account has not connected ends with a notice in the chat that says to connect it in Settings.

## Phone app

`mobile/` is an Expo app (React Native, expo-router, TypeScript) for iOS and Android. A phone is a Device and never a Runner, and it links the same Device core the CLI is built from rather than porting it: `crates/mobile` (`lorca-mobile`) wraps the `lorca` library, built without the `runner` and `server` features, in a UniFFI object with three calls, and `mobile/modules/lorca-core` is the Expo native module around it.

- **The core** (`crates/mobile/src/lib.rs`): `Core.start(home, name, os, osVersion, model, listener)` loads the App from the app's own folder, sets the host facts (a phone cannot probe them), and starts the relay sync loop on an embedded tokio runtime; `request(method, params)` is one call of the JSON API in `crates/cli/src/api.rs`, blocking on the module's background queue, answering `{ result }` or `{ error: { message } }`; `wake()` asks the relay again now (the app calls it on foreground, since the sync socket may have died while iOS suspended the app). Every event on the App's bus reaches the listener as the `{ event, data }` frame the websocket carries.
- **The native module** (`mobile/modules/lorca-core`, picked up by Expo autolinking): a Swift `Module` and a Kotlin one, each about forty lines, forwarding `start`, `request`, and `wake` and turning the listener's frames into a `sendEvent`. `bun run core` (`build.ts`) builds the Rust for `aarch64-apple-ios` and the simulator into an xcframework with the UniFFI Swift beside it, and for `arm64-v8a` and `x86_64` with `cargo ndk` into `jniLibs` with the Kotlin (over JNA). The built pieces are gitignored; a Rust change needs `bun run core` and a native rebuild, a JS change is a Metro reload.
- **The JS side** (`mobile/src/core`): `engine.ts` starts the core, mirrors its events into the zustand store (`store.ts`, the way the macOS app's AppStore mirrors the CLI: `snapshot`, `roster.changed`, `message.*`, `job.*`, `chat.usage`, `relay.status`, `identity.changed`; events that arrive while a `bootstrap` snapshot is on its way wait and apply after it, as in the macOS app, so a snapshot built before the relay connected cannot undo that `relay.status`), and offers the screens the same verbs the macOS app has, each one request (`chats.send`, `bots.create`, `bots.update`, `pair.accept`, `providers.connect_*`, `providers.disconnect`, `device.rename`, `device.unpair`, `identity.forget`, `sync.wake`, …). `prefs.ts` keeps the one thing that is the phone's own, the dictation language. Nothing about the account is stored outside the core's folder.
- **Pairing**: the phone scans the QR code the desktop app shows, pastes a string from the app or `lorca pair` on another computer, or opens it as a `lorca://pair?…` link; `pair.accept` does the handshake in the core and the first `bootstrap` snapshot fills the store.
- **Attachments**: the composer's `+` offers the photo library, the camera, and the file picker; a picked file's path goes with `chats.send`, and the core copies, encrypts, and uploads it as a `file` blob ahead of the message. A bubble that shows an attachment this phone does not have asks `files.path`, which fetches the blob and answers with the file. Images render as thumbnails sized from the width and height in the message (full screen on tap); other files as a name-and-size card.
- **Dictation**: the primary disc is Dictate while the field is empty (a small microphone sits inside the field once there is text). While recording, the field shows Grok Bot's pill: a stop square, the elapsed time, and bars that follow the microphone, with Send still beside it. The words land in the field after whatever was typed when the user taps the square, or go out at once when the user taps Send. The recognizer (`expo-speech-recognition`) listens in the first of the phone's preferred languages it supports (`src/ui/dictation.ts`; a Chinese speaker on an English-region phone gets zh-CN), or the language chosen in Settings or by a long press on the microphone.
- **Notifications** (`src/core/push.ts`, `expo-notifications`): after pairing, and on every launch and foreground, the app asks for permission once, reads the native device token, and registers it with the relay through the core (`push.register { platform, token, environment }`). The Swift module writes the core's push key into the build's keychain group (`group.app.lorca` or `group.app.lorca.dev`) at start and on `identity.changed` (removed when the phone holds no account); the notification service extension is its own target, generated at prebuild by `@bacons/apple-targets` from `targets/notify`. A tap opens the chat, a reply in the chat on screen makes no banner, and opening a chat dismisses its notifications.
- **Turns**: sending is `chats.send`; the core admits a `turn` Job on the bot's Runner or a group room, exactly as any Runner's CLI does. When a direct turn already owns the chat, the Runner promotes the new user message as steering after the current model step and its tools settle, and a question the turn waits on is dismissed rather than waited for; the admitted Job then exits when it reaches the lock because that message was already handled. In a group, the current member settles and the newly admitted room takes over. The `job.started` / `job.finished` events drive the "is working" row and "Chef stopped without replying"; `job.thinking`, `job.retry`, and the running tool rows fill in what the bot is doing, which the core reads in the Runner's `machine` blob and the chat log. The row shows every turn in flight, whichever Device started it, and is back when the app is closed and opened again (see Working state under macOS app). The phone has no hard Stop control.

The UI is native: a native stack with large titles, search, and toolbar items; a composer after Grok Bot's phone app, a liquid-glass `+` button and glass pill (`expo-glass-effect`, a filled pill where glass is unavailable) floating over the transcript with the Dictate or Send disc inside the pill's right edge, riding the keyboard as a `KeyboardStickyView` while the transcript's `KeyboardChatScrollView` lifts the last messages with the keys by growing its bottom inset, so the list is never resized; form sheets on iOS and full-screen Material modal screens on Android for chat info, new bot, new group, and settings; provider credential screens under Settings, with API-key fields and an in-app browser for subscription OAuth; Link previews and context menus on iOS chat rows and Material long-press menus on Android; SF Symbols on iOS and Material Symbols on Android; UIKit semantic colors and Material 3 dynamic colors; haptics. Android toolbar actions and popup menus are Jetpack Compose views from `@expo/ui`: the chat list has Settings on the leading side and Search plus the New menu on the trailing side, with no title, while the composer's attachment sources open in a Material bottom sheet. Conversation headers overlay the transcript on both platforms; UIKit supplies its navigation material, while Android lays a nearly opaque light or dark veil through the status-bar and controls and fades it into the transcript, leaving scrolled messages faintly visible like Gemini. The transcript follows the macOS app: bubbles with the bot's name above and its avatar beside the bubble's bottom edge in a group, neither in a DM; "Today 4:13 AM" separators after fifteen minutes; the "is working" row ("Working…" in a DM, "Chef is working…" in a group, or what the one working bot is doing, in the Mac's words and by its rules, such as "Thinking…" or "Running command: Install dependencies…" (`workingActivity` in `src/ui/format.ts`), its words shimmering inside `ShimmerView`, a native container in `lorca-core` that masks its children with the Mac's sweeping gradient) and the breathing green dot on avatars; "Message from ◉ X" and "Messaged ◉ X" markers; tool calls never shown, except a `bash` call's command card while the command needs the user, after the Mac's (`showsCard` in `src/core/model.ts`): the command's first line in a code block that opens the whole command in a sheet on tap; while Auto-review asks, its question with the answers; once the bot handed the running command over, Stop on the title's line and its last lines in a code block that scrolls past six lines, fading at an edge with more past it (Android's `fadingEdgeLength`, a gradient in the block's color on iOS); at a question, Answer, which opens `@expo/ui`'s bottom sheet sized to its content (SwiftUI's on iOS, Material's on Android; `src/ui/AnswerSheet.tsx`) holding only a field, with the command's question as its placeholder, that takes the text as typed, without capitalization or correction, and hides it unless the question is a yes or no, and Send; the sheet closes when the command ends; sidebar-style previews and stamps, and in the chat list, while a chat has a turn in flight, three dots lighting up in turn and "Working…" in place of its preview.

A window at least 700 pt wide (a tablet, or a tablet window with room to spare) shows two panes (`app/(main)/_layout.tsx`, `src/ui/layout.tsx`): the chat list as a sidebar (320 pt, 375 pt from 1100 pt) and the open chat beside it; a narrower one stacks the chat over the list. The route group `(main)` holds the list and the chat in a stack of their own inside the root stack, so sheets and the pairing screen cover both panes. The sidebar (`src/ui/Sidebar.tsx`) is the same `ChatsScreen` in a native stack of its own, one screen deep, in an independent navigation tree, so it keeps the native bar and toolbar buttons; the pane's stack starts at an empty "Select a chat" screen, a chat picked in the sidebar replaces the one open, its row stays lit, and the chat's bar has no back button. Sidebar rows open their menu on a long press on both platforms, with no Link preview. On iOS the sidebar sits in a `CompactWidthView` (`modules/lorca-core`), a container that overrides the horizontal size class to compact as a split view's sidebar column does. On both platforms the sidebar's search field is a capsule at the foot of the list (`src/ui/SidebarSearch.tsx`; glass on iOS, filled on Android), level with the composer and riding the keyboard: UIKit moves a search bar into the bottom toolbar only on an iPhone, and on Android the search action is an item of the activity's one action bar, which react-native-screens hands to whichever stack updated its header last, so a sidebar's item would vanish once the pane opens a chat. The transcript sits in a `SoftScrollEdgeView`, which gives its scroll view the soft top edge a phone has where an iPad would rule a line under the bar. Bubbles and Markdown measure against the pane's width (`usePaneWidth`) and stop growing at 620 pt.

## Account credentials

The account has one set of provider credentials (`crates/cli/src/credentials.rs`, with setup in `provider_auth.rs`): API keys with optional base URLs for DeepSeek, Anthropic, OpenCode Zen, and OpenCode Go, plus the OAuth tokens of a ChatGPT and of a Grok sign-in. Every Device keeps the set in its core folder as `credentials.json` (mode `0600`) and the relay holds it as one `credentials` blob, encrypted with the account DEK under the slot `credentials`, so the log carries the latest version alone.

- **A change** (a connect, a disconnect, a Runner refreshing OAuth tokens) stamps that provider's `changed_at`, saves the file, queues the blob, and tells the local app (`App::update_credentials`).
- **A blob that arrives** is merged provider by provider, the later `changed_at` winning (`Credentials::merge`); a disconnect is a `changed_at` with no credential beside it, so it travels like any change. A Device that holds a later change than the blob it received uploads its own set in return, so two Devices that changed different providers at once both end up with both.
- **A Device whose credentials the relay never had** (connected before the account carried them, or a relay that was reset) uploads them after its first pull has merged what the relay holds, so an older set never replaces a newer one.
- **OAuth tokens are shared.** A Runner that refreshes them publishes the new pair. One whose refresh fails because another Runner spent the refresh token first reads the set again and uses the tokens that arrived.
- **Connecting** an API key checks it against the provider from the Device where it was typed. A subscription sign-in opens the browser on that Device; the phone uses an in-app browser so its embedded core can receive the provider's loopback callback. **Disconnecting** removes the credential from every Device.
- **Unpairing** a Device makes its CLI delete `credentials.json` with the rest of the account.
- **Bot create** may target any paired Runner. The relay payload is ciphertext of the profile.

## Languages

The apps speak English and Simplified Chinese, and the key of every string is its English text, so a string with no translation reads as written.

- **macOS app** (`App/Localization.swift`): `L("New Bot…")`, `L("%@ is working…", name)` for a sentence with values (`%@`, `%d`; a translation reorders with `%1$@`), and `L("Pairing", context: "device state")` for one English word that means two things (the key `Pairing|device state`). The tables are `macos/Resources/<language>.lproj/Localizable.strings` with `InfoPlist.strings` for the permission prompts; `scripts/app.ts` copies them into `Contents/Resources` and lists the languages in `CFBundleLocalizations`, and the dev loop rebuilds on a saved `.strings` file. macOS picks the language, and Settings › General › App Language picks one for the app (System, English, 简体中文): it writes the app's `AppleLanguages` default, the one System Settings › Language & Region keeps per app, and takes effect at once: `L()` reads the table of `AppLanguage.bundle`, the date formatters are made again, and on `AppLanguage.didChange` the AppDelegate builds the menu bar again and the main window builds its panes, toolbar items, and titlebar buttons again in place (`MainWindowController.languageChanged`). The window, its toolbar, and its split view stay, so the window keeps its frame and its zoomed, tiled, or full-screen state, the sidebar and inspector keep their widths, and the selection and settings history stay. So `L()` is called when a view is built and never kept in a `static let`. What AppKit and Sparkle word themselves (Services, window tiling, the updater) follows at the next launch. Dates go through `setLocalizedDateFormatFromTemplate`.
- **Phone** (`mobile/src/i18n`): `t("{name} is working…", { name })` over `zh.ts`, in the language picked in Settings › App Language (`app_lang` in the phone's prefs), else the phone's from `expo-localization` (English where there is no native module, as under `bun test`). A pick changes the words in place: every component that says words calls `useLanguage()`, which renders it again, and a memo that holds words (the transcript's rows) lists the language among its dependencies, so the navigators and a presented sheet stay put. `t()` is called while rendering, never at module load. `app.config.ts` carries the permission prompts and locales that make the app offer its languages in iOS Settings. The mobile build uses the yellow launcher, adaptive, splash, favicon, and pairing-screen artwork in the local dev loop and EAS development profile, and the purple set otherwise; the same config feeds the native assets and splash plugin for that build variant. `src/ui/format.ts` words times and dates in Chinese from small tables. A row's value that offers choices is a `MenuAccessory` (`src/ui/forms.tsx`): a SwiftUI `Menu` on iOS and a Material 3 Jetpack Compose dropdown on Android, with a checkmark on the choice in force.
- **What the CLI words stays as it arrives**, with one exception: a routine's `schedule_text` ("Weekdays at 9:00 AM") is rebuilt in Chinese by `Format.schedule` in the macOS app and `scheduleText` on the phone. Notices, permission summaries, and the demo data are English.
- `bun run l10n` (`scripts/l10n.ts`) reads every `L("…")` and `t("…")` in the sources and reports a string with no translation, a translation nothing uses, and a translation that takes different values than its key; `--merge <file.json>…` adds `{ "English": "中文" }` files to the tables first.

## Relay

`crates/relay`: Rust, axum, rusqlite (bundled SQLite) or tokio-postgres. `lorca-relay --bind 127.0.0.1:8787 --db lorca-relay.db` (or `--db postgres://…`); `LORCA_RELAY_SECRET` signs bearer tokens (random per boot when unset); `--quota-bytes` (`LORCA_RELAY_QUOTA_BYTES`) caps stored ciphertext per identity, 0 for none.

Storage sits behind one trait (`Store` in `db.rs`) with two backends, picked by `--db` / `LORCA_RELAY_DB`: a path opens SQLite, a `postgres://` URL opens Postgres. All SQL lives in a backend; `routes.rs` only decides what to ask for. One suite (`db/tests.rs`) runs against both; Postgres joins when `LORCA_RELAY_TEST_POSTGRES` names a database.

SQLite (`db/sqlite.rs`) is one WAL database (`synchronous = NORMAL`) behind a single writer connection and a pool of reader connections, one per core; every query runs on tokio's blocking pool. One relay process owns the file, so a deploy stops the old process before the new one starts, and the Devices reconnect after a few seconds.

Postgres (`db/postgres.rs`) is shared by as many relay processes as run, so a deploy overlaps the old process with the new one. An identity's writes are serialized with a transaction-scoped advisory lock, which orders them the way SQLite's single writer does. What a lone process keeps in memory goes through the database: an event (`Event`: a new blob, a changed machine list, an unpaired machine) travels by `NOTIFY` to every process, each of which signals its own sockets, drops the unpaired key's tokens, and closes its sockets; presence is the `relay_sockets` table; each process beats in `relay_instances` once a minute, and the sockets of one silent for 150 s stop counting. A listener that lost its connection tells all its sockets to look again when it is back. The processes share `--secret`, or a token from one does not verify on another, and keep files in an S3 bucket. TLS to the database follows `sslmode` and checks certificates against the web's roots; a database on a private network takes `sslmode=disable`.

The sync sockets live in `hub.rs`, grouped by identity: a blob write signals the sockets of its identity alone, and an envelope sealed to one machine signals that machine alone. A signal is a nudge with no data, so a socket's queue holds four and drops the rest. `last_seen` is written when a machine's first socket opens and when its last one closes. On SIGTERM the relay stops taking connections and closes its sockets, and the Devices connect again, after a backoff with up to a second of jitter, to whichever process is serving.

`file` ciphertext never enters the database (`store.rs`): it goes to a directory (`--files-dir`, default `lorca-relay.files` beside the database) or, with `--s3-bucket` and `--s3-endpoint` (access keys from `LORCA_RELAY_S3_*` or `AWS_*`), to an S3-compatible bucket (AWS, R2, MinIO) over SigV4 with path-style URLs. Objects are keyed `<identity pubkey>/<blob id>`; the row keeps the metadata with an empty `ciphertext`. The object goes up before the row and is removed when the row is refused or deleted.

Housekeeping (`sweep.rs`) runs hourly beside the minute `tick`. Envelopes sealed to one machine (`job`, `job_cancel`, `job_result`, `request`, `response`) are deleted by the machine that consumed them; one still there after seven days had a Runner that never came back, so it goes and its bytes return to the quota. A `deleted_groups` mark goes after 180 days. Once a day the sweep lists the file store (the directory, or `ListObjectsV2` pages of the bucket prefix) and removes an `<identity>/<blob id>` object that is over a day old and has no row: a delete the store refused, or a relay that stopped between an upload and its row. It only touches objects of identities the database knows, so a bucket pointed at by the wrong database loses nothing. The same daily pass drops an identity with no sign of life for `--inactive-days` (365; `0` keeps every identity): registered before then, no machine seen since, no blob written since, no socket open. Its rows and objects go but its keys are not revoked, so a Device that comes back is an unknown machine, not an unpaired one: the identity device attests itself again (`sync::ensure_registered`), starts the relay's log from seq 0, and uploads the `key` blob, the roster, its `machine` blob, and the credentials, which is what pairing or restoring another Device needs. Messages stay on the Devices that hold them. It also sets `usage` to what the blobs add up to wherever the two disagree, settling each identity under its write lock with Postgres. Every process runs the sweep; each step is safe to repeat.

A `file` row whose object the store does not have answers `GET /v1/files/{id}` with `404`, which a Device takes as final, and counts in `missing_objects_total`. The row stays, so a relay pointed at the wrong bucket forgets nothing.

`DELETE /v1/identity` with a machine's bearer deletes the identity: its machines, blobs, attachments' objects, push tokens, pairings, sequence, and usage. The machines' keys stay in `revoked_machines`, so each Device's token dies, its socket closes, and the `410` it gets next makes it forget the identity, as an unpairing does. The backup phrase can register the identity again on a new machine key. The CLI's `identity.delete` makes that call and then forgets the identity locally; when the relay cannot be told it fails and nothing is deleted. The macOS app offers it as Settings › Advanced › Delete Account, behind a confirmation sheet.

An identity may store 5 GiB of ciphertext unless `--quota-bytes` says otherwise (`0` for no limit). A `PUT /v1/blobs` or `PUT /v1/files/{id}` over 1 MiB takes one of `--concurrent-uploads` places (3 by default) before its body is read and keeps it until the response, since an attachment's binary ciphertext is held whole in memory while it is sent to storage; one that waits 30 s gets `503` with `Retry-After`, and the Device's outbox sends it again after its backoff.

`GET /metrics` (`metrics.rs`) exists when `--metrics-token` is set and answers that bearer with Prometheus text, the only view of a relay that cannot read what it stores. Totals come from the database, the same from every process and read at most once in 30 s: identities, machines (and those seen within 1, 7, and 30 days), revoked keys, group marks, blobs and bytes by kind, the quotas' sum and the largest identity's, push tokens by platform. The rest is what the answering process counted since it started, labelled with its `instance`: open sockets and connected identities, requests and seconds by method, route template, and status, rate-limit refusals, uploads refused, reads of a file whose object is missing, pushes by platform and result, and the sweeps (envelopes, orphans, and inactive identities removed, usage rows corrected, objects listed, failures, when each last finished).

Rate limits (`limit.rs`) are token buckets in memory: per client IP on the routes that need no token (registration, auth, the pairing mailbox; `--ip-per-minute`, default 60, `--trust-proxy` to read `X-Forwarded-For`), and per identity on everything behind a bearer (`--identity-per-second`, default 50, burst ten times that). Over the limit is 429 with `Retry-After`.

The image (`crates/relay/Dockerfile`) builds from the repo root, since the relay is a workspace member; cargo-chef keeps the dependency layer cached until a manifest or `Cargo.lock` changes. It runs the binary on `debian:trixie-slim` in `/data`, where the SQLite database and the files directory land, and listens on `[::]:$PORT` (8787 without `PORT`; `LORCA_RELAY_BIND` overrides both). A Railway service builds it through `RAILWAY_DOCKERFILE_PATH` and healthchecks `/v1/health`. With SQLite, a Railway volume at `/data` keeps the database. With Railway's Postgres, `LORCA_RELAY_DB` is its private `DATABASE_URL` with `?sslmode=disable`, since that server's certificate is self-signed, and files go to an S3 bucket, since the container's disk does not outlive a deploy. [crates/relay/README.md](crates/relay/README.md) lists the variables a Railway service takes.

Auth is per machine:

1. `POST /v1/auth/challenge { machine_pubkey }` → nonce.
2. Client signs the nonce with the machine signing key: `POST /v1/auth/verify`.
3. Relay issues a one-hour HMAC bearer bound to the identity and machine.

Identity-level writes are signed requests: `{ payload: base64url(json), signature }` where the payload carries `identity_pubkey` and `ts` and the identity key signed the bytes. `POST /v1/identities` registers the identity (idempotent) and attests one machine; it is used at create, restore, and for every pairing.

Tables:

- `identities(pubkey, content_pubkey, created_at)`
- `machines(machine_pubkey, identity_pubkey, box_pubkey, attestation, last_seen, created_at)`
- `blobs(identity_pubkey, id, kind, recipient_machine_pubkey nullable, seq, ciphertext, size, created_at)`, keyed on `(identity_pubkey, id)`
- `sequences(identity_pubkey, seq)`, `usage(identity_pubkey, bytes)`, `challenges`, `pairings(nonce, identity_pubkey, request, reply, expires_at)`

- `push_tokens(machine_pubkey, identity_pubkey, platform, token, environment, updated_at)`
- `schema_version(version, applied_at)`

`SCHEMA` in each backend creates the tables and is version 1; `MIGRATIONS` is the ordered list of changes after it (version 2 and up), and `schema_version` records what was applied. With Postgres a step runs once, under the schema advisory lock, and never again at a later start: DDL locks whole tables while the process being replaced is writing to them, so a start that re-ran `CREATE INDEX IF NOT EXISTS` could deadlock with a request. A step that still loses a deadlock runs again. SQLite runs `SCHEMA` at every open, since it carries the connection's pragmas and nobody else has the file. A deploy runs the old process beside the new one, so a step only adds: a table, a nullable column, an index.

`kind` is `roster` | `chat` | `job` | `job_cancel` | `job_result` | `machine` | `credentials` | `key` | `file` | `request` | `response`. Ciphertext is bytes; the nonce sits inside it. `seq` increases per identity. A Device’s `name` and `os` are inside its `machine` blob, not columns. A `file` blob is an attachment's bytes under the attachment's id. A Device accepts files up to 100 MiB; the relay accepts 100 MiB plus the 40-byte encryption envelope (other kinds 4 MiB). Attachments travel as binary ciphertext with `Content-Type: application/octet-stream`: `PUT /v1/files/{id}?group=<chat id>` uploads one (the group is optional for avatars), and `GET /v1/files/{id}` downloads it when a transcript needs it. The upload answers with JSON containing the id and sequence. Names, MIME types, and dimensions stay in the encrypted message or roster. JSON blob routes carry non-file blobs and exclude attachments from their pages.

Blob API: `PUT /v1/blobs` (client-chosen id of up to 64 characters in `[A-Za-z0-9._-]`, idempotent; 413 over quota), `GET /v1/blobs?since=<seq>&kinds=` (a page of the blobs for the identity that are unaddressed or addressed to the caller’s machine, filtered by kind in the query), `GET /v1/blobs/{id}` (one blob, same visibility), `DELETE /v1/blobs/{id}`, `GET /v1/machines` (each machine with `online` and `last_seen`).

Sync socket: `GET /v1/sync` with the bearer token upgrades to a WebSocket. The relay sends `{"type":"blobs"}` when the identity has a blob this machine may read and `{"type":"machines"}` when a machine connects, disconnects, or is unpaired; the Device sends nothing but control frames. A machine is online while it has a socket open. The relay pings every 25 s and closes a socket silent for 50 s; the Device gives up on one silent for 70 s, or 10 s after a ping of its own, and connects again.

Push API (`push.rs`): a phone registers where its pushes go with `PUT /v1/push/token { platform: apns | fcm, token, environment? }` (`sandbox` for a development build's APNs token; `DELETE` removes it). Any Device asks for a push with `POST /v1/push { ciphertext }`, at most 2560 bytes; the relay answers `{ queued }` at once and then sends to every token of the identity but the caller's. To APNs that is an alert with fixed words ("Lorca", "New reply"), `mutable-content`, and the ciphertext as `c`, over HTTP/2 with an ES256 provider token from the team's `.p8` key (`--apns-key`, the `.p8` key's text or the path of its file, as `--fcm-service-account` is the JSON or its path, so a deploy with no volume carries both in variables; `--apns-key-id`, `--apns-team-id`, `--apns-topic`, default `app.lorca`; the token's environment picks Apple's sandbox or production host). To FCM it is a data-only message carrying `c`, with an access token minted from a service account (`--fcm-service-account`). A relay with neither key queues nothing. `LORCA_RELAY_APNS_URL` and `LORCA_RELAY_FCM_URL` point either at a test server.

Clients set `LORCA_RELAY_URL` or the relay URL in Settings › Advanced. With neither, a Device uses the URL pairing handed it, then `LORCA_DEFAULT_RELAY_URL`, which the release macOS app sets to `https://relay.lorca.app` when it launches the CLI. Without a relay the CLI works on one Device alone. In dev (`bun run dev` sets `LORCA_DEV=1` and runs a relay on `0.0.0.0:8787`), a Device with no relay configured defaults to `http://<this computer's LAN IP>:8787`, so Pair a Device shows a code a phone on the same network can use. That relay (and `bun run relay`) runs with `--apns-topic app.lorca.dev`, since the phone that pairs with it is the development build.

A CLI holds one sync socket (`sync::session`). It opens the socket, then drains its SQLite outbox and pulls pages of blobs for its identity and envelopes for its machine public key until one comes back empty, decrypts, and emits events to the app on localhost. After that it waits on the socket and on its outbox: `blobs` is answered with a pull, `machines` with a fresh machine list, a queued blob with an upload, and a wake (`App::wake_sync`: a phone back in the foreground or pulling to refresh) with a pull and a ping on the socket, which may have died while the app was suspended. A wake keeps the bearer and drops the pooled HTTP connections, which may have died with the socket (a VPN on the phone can keep its end of one open), so no request waits out its timeout on one. A socket that fails ends the session; the next one starts after a backoff of 2 s doubling to 32 s, with up to a second of jitter, that starts over after every round that goes through, and until then the other Devices show as offline. When a wake came during the session that ended, the next one starts at once. A Device at seq 0 does not replay the log, which holds every message of the account (`sync::first_sync`). It pages through the log without the `chat` kind, which slots keep to a roster, a `machine` blob per Device, the credentials, and the envelopes sealed to it; then it asks for the newest 400 messages of each chat in the roster, the count a bot's turn reads, and follows the log from the head it saw when it began, so whatever landed meanwhile comes again and changes nothing. Where the relay had more, `chat_history` records the place the local copy of the chat begins at. `chats.messages` answers from SQLite until the local copy runs out, then reads a page of 100 back from the relay (`sync::older_messages`), puts it ahead of everything the chat has here (`LocalStore::insert_older`, with positions counting down below the first), and answers from SQLite again; `has_more` stays true while the relay holds more, and a chat read to its start loses its `chat_history` row. A message that was edited after the first sync and lies before the local copy arrives through the log and lands at the end; the page that holds it moves it to its place. Search and the `recall` tool read what is here. A page of twenty or more blobs is a backlog: the CLI applies each message as one SQLite upsert with message and roster events held back, commits the account metadata once, and emits one `snapshot` at the end of the page, so the app fills in at once instead of one message at a time. The page's `job_result` envelopes, and what its `machine` blobs change about the turns in flight, reach the app after that snapshot, so a turn's end comes after the messages it ended with.

## CLI (runtime)

`crates/cli`, binary `lorca`. Local websocket for the app. Files live under the private data directory: `~/.lorca/` by default and for Lorca, `~/.lorca-dev/` when launched by Lorca Dev, or the explicit `LORCA_HOME`. It contains `identity.json` (master secret, identity devices only), `machine.json` (machine secret, identity and content public keys, account DEK, `name`, `os`), `credentials.json` (the account’s providers, as last merged), `settings.json` (relay URL), `lorca.sqlite3` (WAL-mode plaintext local state), and `files/<attachment id>` (attachment bytes, sent from here or fetched from the relay). SQLite holds devices, bots, chat metadata, routines, Auto-review, usage, compactions, sync bookkeeping, messages, the durable relay outbox, the jobs this Device sent to other Runners and still waits on, and the turns the other Devices list. The JSON and database files are mode 0600 and the directory is mode 0700; SQLite may create `-wal` and `-shm` companions inside that directory while it is open.

Commands:

- `lorca serve` — default; the app connects here
- `lorca identity new` / `identity restore <phrase>` / `identity show`
- `lorca pair` — show a pairing string and wait; `lorca pair <string>` joins
- `lorca provider set <kind> [api-key] [--base-url <url>]` — connect DeepSeek, Anthropic, OpenCode Zen (`opencode`), or OpenCode Go (`opencode-go`) with an API key, or open the browser sign-in for `chatgpt` and `grok`. The key is checked against the API first and read from stdin when omitted. `provider remove <kind>` / `provider list`. A running `lorca serve` carries out the change over the local websocket; with none, the command changes `credentials.json` itself and runs one sync pass
- `lorca status` / `doctor`

Bind: `127.0.0.1:4862` (`--port`, `LORCA_PORT`). Relay: `LORCA_RELAY_URL`. If the port is busy the CLI fails loudly.

### Installing the CLI

A computer without the app installs `lorca` with `curl -fsSL https://lorca.app/install-cli.sh | sh` (macOS, Linux) or `irm https://lorca.app/install-cli.ps1 | iex` (Windows). The script downloads the computer's build from the latest GitHub release of this repo, tagged `cli-vX.Y.Z` (`LORCA_VERSION` names another release): `lorca-cli-macos-aarch64`, `lorca-cli-linux-aarch64`, `lorca-cli-linux-x86_64`, or `lorca-cli-windows-x86_64`, the arm64 Mac build in a shell under Rosetta and the x86_64 one on Windows on Arm; an Intel Mac has none. It checks the archive against the `.sha256` beside it and renames `lorca` into `~/.local/bin` (`LORCA_INSTALL_DIR`), so a running `lorca serve` keeps its own file, then puts that folder on PATH: a line in the profile of the user's shell, or the user `Path` in the registry on Windows (`LORCA_NO_MODIFY_PATH=1` skips it). The Linux builds are static musl binaries; the Windows build is `x86_64-pc-windows-gnu` against the Universal CRT, and there the `bash` tool runs Git for Windows' bash. `.github/workflows/release-cli.yml`, run by hand or by a `cli-v*` tag, names the release after the `lorca` crate's version, builds with cargo on macOS and cargo-zigbuild on Linux, installs the builds with both scripts on Linux, macOS, and Windows runners, and drafts the release, or updates the draft an earlier run left; a published release is left alone, and publishing the draft makes it the one the scripts install: [docs/releasing-cli.md](./docs/releasing-cli.md).

### Agent loop

`crates/agent` (`lorca-agent`) is a port of pi-agent-core: `run_agent_loop` / `run_agent_loop_continue`, the same event sequence (`agent_start`, `turn_start`, `message_start/update/end`, `tool_execution_start/update/end`, `turn_end`, `agent_end`), steering and follow-up queues, `before_tool_call` / `after_tool_call` / `should_stop_after_turn` hooks, sequential or parallel tool execution, and `terminate` hints from tools, plus pi's harness behaviors: a model catalog with rates and windows, thinking levels, cost on every message, compaction, and turn-level retry. Tool arguments are salvaged from cut-off JSON, coerced and checked against the tool's schema before a call runs (a failure is an error result the model reads), and never run from a message the token limit cut off; a `prepare_next_turn` hook can swap the context or provider between turns. Every adapter puts the transcript through the same transform first (another model's thinking as text, failed turns left out, a result for every call, images downgraded for a text-only model) and retries a request that fails before it streams. A `Provider` turns a request into a stream of assistant events and never fails: errors become an assistant message with `stop_reason` `error` or `aborted`. The crate also ships `agent::harness::AgentHarness`, a general agent over the loop for hosts other than Lorca (model switching through a provider factory, skills and prompt templates, queues, hooks, events, an example chat), with persistence left to the host; the Lorca CLI uses the loop directly. `docs/agent/` is the crate's own documentation.

```
on decrypted Job:
  build context from the chat (this bot's turns are assistant, other bots' text is user "[Name]: …",
                               this bot's tool rows become tool_call + tool_result pairs)
    + this turn's notes, which later turns leave out: the recent-work brief, the group's turn cue or
      a finished command's, "Continue." after the bot's own reply, a template bot's setup
    cache points: the rebuilt transcript's end, and where the last turn's ended
  run_agent_loop_continue(context, provider = the account's creds, tools, sink)
    events → job.started / job.finished / job.retry / job.thinking (chat, bot) → local app WS, which shows the bot at work
           → the turn and what it is doing (thinking, a retry) → this Runner's `machine` blob, which every
             other Device's CLI turns into the same events
           → each finished turn's usage → chat.usage (context size, cost so far)
           → a reply grows in chunks, not tokens: the text so far is re-sent at paragraph ends,
             or at a sentence end after 1.5 s of silence, never mid-word; the end sends it complete
           → every chunk and every completed message is encrypted with the account DEK → relay,
             so a paired phone watches the reply grow the way the local app does
    tool calls execute: each call's row goes up as the app sees it when the call starts, for the
                        status line on other Devices, and whole when it ends
  a pending confirmation or a turn ending with a reply or failure → an encrypted phone push (see Notifications)
```

Turns in one chat run one at a time on a Runner. A direct turn registers an `AgentMessageQueue` from `crates/agent` while it owns the chat lock. A new user message goes into that queue, and the agent loop drains it at its next safe boundary: the current provider step and any tool calls finish, then the message is added before the next provider call. A question never holds a message back: the user's message dismisses whatever the chat's turn is asking them (a command's card or a permission card; `mcp::dismiss_questions`), the action does not run, and the call returns telling the bot the user wrote instead of answering, with a hint that ends the run unless the message is there to read next. A question that would go up while the queue holds a message is dismissed without asking. In a group, where a member's turn has no queue, the dismissed call ends the member's turn, and the room the message admitted answers it. Every message still admits a Job, so delivery survives Device races; the active turn marks messages it actually promotes, and those Jobs exit when they later reach the chat lock. In a group, a newer room waits while the current member settles, then takes the lock before another member starts. `chats.stop` is separate: it cancels active and waiting jobs immediately and sends a sealed `job_cancel` to another Runner.

### Notifications

Replies, failed responses, and pending confirmations reach the user wherever they are not looking.

- **Phones** (`crates/cli/src/push.rs`): when a turn ends with a reply or a failed response, or a question appears (a pending permission card, or a command's card that asks), the Runner seals a notice `{ title: the bot's name, subtitle: the group's title, body: the first 280 characters, chat_id }` and posts it to the relay's `/v1/push`. The envelope is `nonce(12) || ciphertext` of ChaCha20-Poly1305 under the push key with `push` as associated data: the IETF cipher, so iOS opens it with CryptoKit alone. Apple, Google, and the relay see "New reply" and ciphertext. On an iPhone the notification service extension (`mobile/targets/notify`) reads the push key from the app group's keychain, opens `c`, and sets the title, subtitle, body, thread, and `chat_id` before the alert shows; on Android `PushService` in the native module opens it through the core (`push_open(home, c)`, which needs only `machine.json`) and posts the notification. A push that cannot be opened shows the fixed words. Android's FCM tokens come from the Firebase project `lorca-a03db` (`mobile/google-services.json` through `android.googleServicesFile`, one client for `app.lorca` and one for `app.lorca.dev`), and the relay's `--fcm-service-account` is a key of the same project.
- **The macOS app** (`Notifier.swift`) posts a system notification itself from the CLI's events: a new question (a pending permission card, or a command's card that asks) alerts while the turn waits for an answer; on `job.finished` it takes the bot's last completed or failed response in that turn, for a turn on this Runner or another. A failure shows the error text, including when the bot sent partial output first. Confirmation alerts say what action needs approval; repeated card updates do not repeat the alert, and resolving or removing a card clears its Mac notification. A click brings the app forward on the chat; opening a chat clears what was posted for it. The Dock badge (`AppDelegate.swift`) shows the sum of the chats' unread message counts and clears when that total is zero or the Device has no identity.
- **Read on another Device**: the Runner waits three seconds before asking for a phone push, and the macOS app waits the same interval before posting its notification. Replies, failed responses, and questions (pending permission cards, command cards that ask) each count as unread when they arrive. Both notification paths check the chat's current unread count after the wait; an encrypted `ClearUnread` from a paired Device cancels the alert. A confirmation is checked again for a pending decision, so answering, denying, or expiring it during the wait cancels its alert. They check again after push authentication or notification permission, and drop a pending alert if its account or chat is gone. This is a grace period for sync: a read mark that arrives after delivery cannot prevent the alert that already showed.
- **Watching**: neither fires for a reply, failure, or confirmation the user watches arrive. The macOS app tells its CLI which chat is on screen while it is frontmost (`ui.watching { chat_id | null }`, cleared when the app disconnects); the Runner skips the push for that chat and the app skips its own notification. The phone app shows no banner for the chat it has open while it is in front. On iOS the notification handler declines it. On Android, where `PushService` posts the notification itself, the JS side hands the native module the chat on screen (`setOpenChat`) and the module follows the activity's resume and pause itself, so a push that lands as the user leaves is not lost behind a busy JS thread; while the app is in front `PushService` posts nothing for that chat, and what it posted for the chat comes down when the chat comes on screen.
- **Phone reads**: the focused chat route sets `openChatId`, and the engine follows the app's foreground state. While both are active, unread counts arriving in roster events or snapshots trigger `chats.mark_read`; returning to the app reads the visible chat too. An inactive or backgrounded phone leaves new replies unread, even while the chat remains mounted. A read mark acknowledges replies already received, so an open chat on a disconnected phone does not suppress later replies.

### Tools

Team tools (the CLI):

- `message_bot { bot_id, message }` — a message to a bot outside the current chat. The caller's chat shows a "Messaged ◉ X" marker: the tool row carries the recipient's id as `target_bot_id`, and the apps take its name and avatar from the roster for the marker and for "Messaging X…" while the call runs. The target's own DM gets a "Message from ◉ X" marker and a `message` Job (with `from_bot_id` and `hops`) whose envelope goes to the **target bot’s Runner**. The tool refuses a member of the same group: they read that chat and take their own turn.
- `list_teammates` — decrypted local roster with each bot’s id, Runner, and online state. `message_bot` and `edit_bot` name a bot by that id, since two bots can share a name; a user’s `@Name` arrives with the id (see Mentions), the system prompt gives the caller its own id and that of a bot whose message started the turn, and `create_bot` answers with the new bot’s.
- `memory_update { action: append | replace | remove | supersede, text?, old_text? }` — changes the bot’s curated `MEMORY.md` one fact at a time (see Memory below).
- `memory_log { text }` — one line in the bot’s daily log.
- `recall { query?, since?, until?, limit? }` — searches the bot’s memory files and every chat it is in, by words and by time (`24h`, `3d`, `today`, `yesterday`, a date).
- `create_bot { name, description, provider?, workdir? }` — a new teammate on the caller’s Runner with its own DM; in a group chat it joins that chat. The description says both what it does and how it should work. This is how a lead bot builds its team.
- `edit_bot { bot_id, name?, description?, provider?, thinking?, workdir? }` — changes a teammate’s profile, or the caller’s own. Only the passed fields change; a description is the complete account of the bot’s job and working style, and the new profile applies from that bot’s next turn.
- `routines { action: list | create | edit | pause | resume | run | delete, routine?, name?, schedule?, prompt?, enabled? }` — the caller’s own routines (see Routines below).
- `search_plugins { query? }` / `install_plugin { plugin }` / `connect_plugin { plugin }` — the marketplace, an install on the caller’s Runner that the user allows on a permission card first, and a sign-in card for an installed plugin (see Plugins below).
- `capability_search { query, plugin? }` / `mcp_select_tool { name }` — searches the installed plugins’ MCP catalogs on demand and loads matching tool schemas for the next model step; exact selection is the fallback when a returned tool did not fit the search’s schema budget.

Plugin tools (`<plugin>__<tool>`, such as `github__create_issue`) come from the MCP servers of the plugins installed on the bot's Runner. They enter a turn’s model context only after capability discovery selects them.

Coding tools (`lorca_agent::tools`, ports of pi’s built-ins, same schemas and truncation rules: 2000 lines / 50KB, whichever first):

- `read { path, offset?, limit? }`, `write { path, content }`, `edit { path, edits: [{ oldText, newText }] }`
- `bash { command, description, timeout? }` — `description` says what the command does in a few words, for the status line. It runs `/bin/bash` (else `/bin/sh`), or on Windows Git for Windows' bash (else `bash` on PATH), with the login shell's environment (below); `LORCA_SHELL` names another shell. The result is stdout and stderr together, tail-truncated, with the full output in a temp file; Stop kills the process group (the process tree on Windows). On macOS and Linux the command runs in a terminal of its own that can outlive the call (Terminal sessions, below). On Windows it runs on pipes with stdin closed, and the tool's description tells the model that interactive input is not available there
- `bash_input { session_id, text, enter? }` — types into a command `bash` left running, Enter after the text unless `enter` is false (`\u0003` is Ctrl-C; a text that spells one key out as its escape, `\u0003` as six characters or `\u001b[B`, types that key), and waits for what it does next; `bash_output { session_id, wait_seconds? }` — what it printed since the bot last read it, waiting up to five minutes for more. Neither is offered on Windows
- `grep { pattern, path?, glob?, ignoreCase?, literal?, context?, limit? }`, `find { pattern, path?, limit? }`, `ls { path?, limit? }` — respect `.gitignore` through the `ignore` walker, no `rg`/`fd` needed

Every bot has a working directory on its Runner (`workdir`, default `~/.lorca/workspaces/<bot id>`, so a rename never moves files); relative paths resolve there. The tools run as the Runner's user and retain that user's normal filesystem, process, credential, and network access. The working directory is context, not a security boundary: absolute paths and shell commands can control the rest of the computer.

Commands and stdio plugin servers run with the user's login-shell environment (`lorca_agent::login_shell`), since a CLI the app starts inherits launchd's bare `PATH`. When `lorca serve` starts, it runs the account's shell once as an interactive login shell and reads the variables it exports (`env -0`, written to a private temp file). The account's shell is its passwd entry, ahead of `$SHELL`, which launchd leaves stale after `chsh`. That shell gets a session of its own: under a terminal, an interactive shell in the CLI's session stops as it tries to take the terminal over. Every `bash` command and stdio server starts with those variables: the shell's `PATH` first, then the CLI's own, then the usual install folders (`~/.local/bin`, `~/.bun/bin`, `~/.cargo/bin`, mise shims, Volta, `/opt/homebrew/bin`, `/usr/local/bin`). So `npx`, `uvx`, `bun`, or `cargo` resolve as in the user's terminal, and a fish user's config sets up `PATH` while the command itself runs in bash. Exported keys come along as they would from a terminal, and a command that names one (`echo $OPENAI_API_KEY`) goes to Auto-review. The shell has five seconds, at most three of them interactive before a plain login shell tries; when none answers, commands keep the CLI's own environment. On Windows the CLI keeps the environment it started with.

**Terminal sessions** (`lorca_agent::tools::bash_session`, kept by `crates/cli/src/shell.rs`). pi's bash runs a command on pipes with nothing on stdin and fails fast, because the person is at the terminal and answers there. A Lorca bot's Runner is often a computer nobody is sitting at, so a command gets a pseudo-terminal of its own: `openpty`, then `setsid` and `TIOCSCTTY` in the child, so `/dev/tty` is that terminal and `sudo`, `ssh`, `gpg`, `getpass`, and `[Y/n]` questions ask there, never on a terminal `lorca serve` was started from. The shell leads its own session and process group, which is what stopping it kills. The terminal is 80×24 with `TERM=xterm-256color` and `PAGER` and `GIT_PAGER` set to `cat`, and echo is off, so what is typed (a `y`, a password) never comes back as output; a program that echoes for itself (readline, curses) still does, and prompts print as usual. The child ignores SIGHUP, so a job the command leaves in the background (`server > log 2>&1 &`) outlives the shell as under `nohup`. A reader drains the terminal into the session's last 200 KB whether or not anyone reads it, so a command never blocks on a full terminal; the raw bytes also go to a temp file once they pass 50 KB, up to 64 MB. What the model reads and what a card stores is text (`tools::sanitize`, after pi's `stripAnsi` and `sanitizeBinaryOutput`): escape sequences go, a carriage return redraws its line, a backspace takes back a character, and other control characters go. The temp file keeps the raw bytes.

A call returns when the command exits, as on pipes, or while it still runs: 2 s after it stops on an open line that reads like a question (`password`, `passphrase`, `[Y/n]`, `(yes/no`, `Enter `, `Press `, `PIN`, `token`, `code`, `OTP`, or a line ending in `?`, `:`, `>`, `)`, `]`, `$`, or `#`), or after 20 s with no output at all (`WAITING_AFTER`), which is also how a command blocked on something outside its terminal, such as a macOS permission dialog, surfaces instead of holding the turn. That result is the output so far, a note on where the command stands, and the session id; `bash_input` and `bash_output` wait the same way, and `timeout` still kills the command when it runs that long. At a question the note quotes it. Silence is not a question: a quiet command may be working, or asking where the terminal never shows it, since a question printed into a pipe or a file (`| tail`, `> log`) stays there, so the note says both. When the command has also put its terminal in raw mode, as a menu or a yes/no choice does (`BashSession::reads_keys`: the master reads the terminal's modes on macOS and Linux, pipe or not), the note says it is probably waiting for a key at a question it printed out of sight, to stop it and run it with its non-interactive options, and how to press Enter and the arrow keys. A question counts until something is typed after it: with echo off, an answered question stays the last line until the command prints again. The session stays on the Runner after the turn ends.

Every `bash` call has one card, the call's own row, from start to finish: `Body::Tool.run { session_id?, command, state, prompt?, output?, outcome?, device?, reason?, rule?, decision? }`. The row goes up with the card as the call starts (`running`), so it takes its place in the chat before anything the call leads to; `shell::Sessions` notes the call (`begin`), and the card follows it: `checking` while Auto-review judges the command, `asking` while it waits for the user's answer (below), then `running` or `waiting` once a session runs it (`insert`, as the command spawns), with its last 20 lines of output: `waiting` only at a question the user can read, whose line has held still for 2 s (`PROMPT_QUIET`) or has been followed by 20 s of silence, and `running` while it prints or is merely quiet, and at the end `exited`, `failed` (a nonzero code), `stopped`, `denied`, `expired`, or `dismissed` (the user wrote in the chat instead of answering), with how it ended, which a later turn reads in the rebuilt call when the call had left the command running. A call that returns (`call_ended`) leaves a running command's card to its session; a call no session ran, because it was not allowed or ran on pipes, ends its card from its result. The call's result and its card go up in one write, under the same lock as the session's own updates, so no Device sees the call returned beside a card from before. The apps show the card only while the command needs the user: while Auto-review asks, and once the bot has handed the running command over (`handed_over`), until it ends. It hands it over when its turn ends with the command still running (`Sessions::hand_over`, from the turn's `finish`), or when it waits on the command (`bash_output` with a wait) while the command sits at a question (`Sessions::bot_waits`), and a card stays handed over. Until then the bot deals with it: a question it answers itself with `bash_input`, or a command it waits out, reads only as the working row's activity, and one that ended leaves the chat, so the transcript does not shift for the commands a turn runs. The card keeps its first place in the relay's log however often it changes (`Slot::first_and_latest`), so it sits in the same place on every Device. The bot reaches only the sessions it started in the chat it runs in; the system prompt tells it that `/dev/tty` is the command's own terminal, to run scaffolders and installers with their non-interactive options since a question printed into a pipe or a file never shows, to answer what it knows with `bash_input`, and to send the user to the command's card for a password, a passphrase, or a one-time code rather than asking for it in a message. A command its call left running that ends by itself (exits, or dies on a signal) wakes its bot: once any turn in the chat is done, and unless that turn read the end itself with `bash_input` or `bash_output`, the Runner starts a `command` job (`shell::wake_job`, `runtime::command_job`), whose turn opens with how the command ended and its last lines (`turns::command_cue`), so the bot hears the result of an answer the user typed and carries on. A Stop, the idle limit, or Lorca quitting wakes nobody.

The user answers from any Device: `bash.stdin { chat_id, message_id, text }` writes the text and a Return to the terminal, on this Runner or sealed to it as a `request`, and nothing keeps it: not the row, the message store, a log, or a push, and with echo off, not the output the bot reads. `bash.stop` ends the command. Stop in the chat, deleting the chat or its bot, quitting Lorca (SIGTERM, SIGINT, SIGHUP, or the app that started the CLI going away), 30 minutes without output or input (`IDLE_LIMIT`), and a ninth command starting while eight run (`MAX_SESSIONS`; the oldest stops) each kill the session's process group, close its terminal, and say so on its card. A card that a Lorca which quit left open (checking, asking, running, or waiting) reads "Stopped when Lorca quit" once it starts again.

Shell review lives at the loop's `before_tool_call` boundary (`crates/cli/src/local_review.rs`). With Auto-review on, a parser is the fast path: it splits the command into its `&&`, `||`, pipe, semicolon, newline, plain subshell-group, and visible command-substitution stages without executing it, and a command whose every stage is a known read-only one (`git status`, `ls`, `rg`, `find … | xargs wc -l`), that writes nothing through redirection, evaluates nothing dynamically, and names no key, token, or password runs at once. So does one that stays in Lorca's own folders (`~/.lorca`, `~/.lorca-dev`, and the CLI's home), which belong to the bots, the account's own files included: it runs from inside one, every path it names lies inside one, it moves with no bare, backward, or variable `cd`, expands no variables, and neither elevates privileges nor sends data to another machine. Every other command goes whole to Auto-review before it starts. The command's card is `checking` while the review runs, which the apps do not show. When the review asks, the card itself asks (`local_review::ask_on_card`): why, Allow once, Always allow, and Deny, and a proposed plain-language allow rule for commands like this one, naming the folder the command acts on ("run the Rust tests in ~/dev/lorca", "delete and re-clone GitHub repositories in /tmp"), which Always allow adds to Auto-review. A card with no proposed rule (Auto-review off, or a review that could not run) offers Allow once and Deny. The answer is `chats.permission` naming the card's row, from any Device, as for a permission card (`mcp::await_answer`); an allowed command runs on the same card, and a denial runs none of the stages and ends the card as `denied`. What a bot types into a running command with `bash_input` goes through the same review, the command beside the input, since a shell, a REPL, or `ssh` runs whatever it is given; Ctrl-C alone runs at once.

**Auto-review** (`crates/cli/src/plugins/review.rs`) is shared by shell and plugin actions. Its setting lives in the roster (`AutoReview { is_enabled, rules[{ id, text, behavior: allow | ask, tool? }] }`), so every Device shows and edits the same one. A rule is plain language, written by the user or added by Always allow from the review's proposal. Only a plugin card's Always allow saves a rule for an exact tool (`tool` is `plugin/tool`), which decides that tool's calls without a review. Everything else goes to a small model on the bot's provider, whatever the bot itself runs (`providers::review_model`: DeepSeek V4.1 Flash on DeepSeek and both OpenCode plans, Claude Haiku 4.5, GPT-6 Luna, Grok 4.7), with thinking off where the model allows it and at its lowest effort where it does not, which judges the action against the plain-language rules, the built-in checks, and the request behind the turn: the message that started it (the user's, a teammate's `message_bot` handoff, or a routine's marker with the task as it stood when the run began, which an edit or a delete during the run does not change) and what the user wrote since (`plugins::review::request`). It answers `allow` or `ask` with a reason, plus the proposed `rule` when a shell command asks, both in the language of that request (English without one); an ask rule wins over an allow rule. Adding a rule replaces one with the same words. With Auto-review off, every shell command and effectful plugin action asks, regardless of saved rules. A held shell command asks on its own card; any other held action posts a `permission` message. Either waits up to ten minutes for `chats.permission { decision: allow | always | deny }` from any Device, and a new message from the user in the chat dismisses it (see Agent loop). A routine has nobody waiting, so an action that would ask is refused, and the bot hears the rule that would allow it; with Auto-review on, actions the review allows still run.

### The lead bot

A new identity starts with one bot, **Chef**, a chief of staff on the first Runner: an ordinary bot whose description has it plan the work, delegate each task to the right teammate with `message_bot`, propose a new one for `create_bot` when none fits, and do hands-on work when necessary. Nothing about it is privileged; rename or delete it like any bot.

A chat has a `kind`. A DM is one bot and never gains or loses members; there is one DM per bot. A group holds one to six bots, can add or remove them after creation, and has an `owner_bot_id` (the bot holding the work; defaults to the first member, `chats.set_owner` changes it).

Deleting a bot removes its DM and routines and removes it from every group. A group with other bots keeps its transcript and moves ownership when needed; a group whose last bot was deleted is removed. The macOS sidebar treats Delete on a DM as this bot deletion and says so in its confirmation sheet. Deleting a group removes only that chat.

Who answers, after Grok Bot's rooms:

- **DM:** its bot, always. An `@Name` is a reference the bot acts on: it calls `message_bot`, which delivers the message into that bot's own DM with the user, where that bot answers (and can message back).
- **Mentions:** picking a bot from the composer's `@` menu records its id, and `chats.send` carries the picks as `mentions`. The CLI keeps the picks whose `@Name` is still in the text, adds any other `@Name` that only one bot answers to, and stores the ids on the message (`Body::Text.mentions`). A bot reads the first `@Name` of each as `@Name (id bot-1a2b3c4d)`, so a name two bots share still says which one the user meant.
- **Attachments:** a user message can carry files. Their bytes travel as `file` blobs; before a turn the Runner fetches any it lacks (`files::prefetch`), copies each into the bot's workspace at `attachments/<attachment id>/<name>` (a stable path, so every turn names the same file), and the transcript's user message gets a line per file naming that path, plus the pixels as an image content part for an image up to 5 MB, so a vision-capable model sees it and any model can open it with its tools.
- **Group:** a room exchange (`run_room`). The Device that received the user's message offers every member a turn, one at a time, in chat order with the members the message mentions first. A member's turn is a `room_turn` Job with the whole transcript plus an ephemeral cue (round number, how many messages are new to it); the member replies to the group or answers `PASS`, which never becomes a bubble. A round with at least one reply is followed by another, offered only to members that have heard something new; the exchange ends after a silent round or after the fourth round, which is marked winding down so members add only what is essential. A new user message waits for the current member's turn, including its command, to settle; the old room then yields and a replacement room starts with the new mentions first. **Stop** cancels immediately. A member on another Runner gets its job through the relay and reports back with a `job_result` blob (`sent`, `pass`, `error`) sealed to the requesting Device; the room waits up to five minutes for it and skips an offline Runner.
- **Bot to bot:** `message_bot` from any chat to a bot outside it; the message lands in the target's DM. Each hop carries `hops`; after eight bot-to-bot hops without a user message the tool refuses, so two bots cannot loop. Members of one group talk to each other in the group.

### Routines

A routine is a task a bot runs on a schedule in its direct chat with the user, after Grok Bot's routines: a morning brief, an hourly check, a weekly report. The bot owns its routines: the user asks for one in chat and the bot sets it up with the `routines` tool (a name, a schedule, and the prompt, written as an instruction to itself), and edits, pauses, resumes, runs, or deletes it the same way. The system prompt of every turn explains routines and lists the bot's own with each one's next run.

The roster also carries Auto-review (see Plugins). Routines live in the roster (`Routine { id, bot_id, name, prompt, schedule, is_enabled, enabled_at, last_run_at?, last_outcome?, paused_reason?, created_at }`), so every paired Device lists them and can pause, resume, run, or delete one (`routines.create` / `routines.update` / `routines.delete` / `routines.run`, and `routines.describe` to read a schedule back). The bot's Runner runs them (`crates/cli/src/routines.rs`): every half minute it starts the routines of its bots whose next run is due, at most one run per routine at a time.

A schedule (`crates/cli/src/schedule.rs`) is `every 30m`, `every 2h`, `every 1d`, or five cron fields read in the Runner's local time (`0 9 * * 1-5`), never more often than every five minutes. An interval counts from the last run, or from when the routine was created or resumed; a cron fires at the next matching minute after that. The CLI says a schedule in words on the wire (`schedule_text`: "Weekdays at 9:00 AM", "Every 2 hours", "On the 1st of every month at 8:30 AM", else "Cron 5 4 * * 1-3") and gives `next_run_at` and `is_running` beside every routine.

A run is a `routine` Job in the bot's DM. It opens with a "Routine · Name" marker (a system notice carrying the routine id), then the turn runs with the routine's prompt as the task and a system prompt that says nobody is typing: the bot does the work, replies with what the user should know, or answers `PASS`, which leaves only the marker. Later turns rebuild the marker as `[Routine "Name" ran on its schedule. Task: …]`, so the bot can talk about a run afterwards; the daily log names the routine as the turn's source. `job.started` / `job.finished` carry `routine_id`, so the apps show the routine as running and the bot at work. A run's outcome (`sent`, `pass`, `error`) is kept on the routine. Run Now from a Device that is not the Runner seals the job to the Runner like any turn.

When the user has not written in any chat for seven days, due routines are paused instead of run (`paused_reason: away`) with a notice in the bot's DM, as Grok Bot does, so nothing keeps spending on results nobody reads; the switch turns them back on.

The macOS app's DM inspector has a Routines section: a row per routine (clock, pause, or running icon; the schedule in words and the next run; a switch that pauses or resumes) that opens a sheet with the state, schedule, next and last run, the prompt, and Run Now, Pause/Resume, Edit in Chat (which puts `Edit my routine "Name": ` in the composer), and Delete. With none, the section says routines are set up by asking the bot. The phone's chat details show the same list with a switch; a tap offers Run Now and Delete.

### Plugins

A plugin is an MCP server (or several) a bot can use, after Grok Bot's marketplace: GitHub, Jira, Notion, Stripe, Zapier, a headless browser, and the other services the bundled index lists. A plugin is described by a manifest (`crates/cli/src/plugins/mod.rs`): `id`, `name`, `description`, `icon`, `author`, `category`, and `featured` for the marketplace, `servers` (`stdio` with `command`, `args`, `env`, or `http` with `url`, `headers`, and `auth`: `oauth` or `bearer`), `variables` (setup fields, `secret` ones never read back), `skills` (notes written to the plugin's folder that the prompt points the bot at), and `tools` hints (`readonly` patterns, `hide`). `${VAR}` in args, env, and headers is filled from the variables; a header or an environment variable that names a variable with no value is left out, so an optional key left unset is never sent as its placeholder (Context7 refuses every call made with one). A stdio server starts in its plugin's folder with the login shell's environment (see Tools), so a `command` such as `npx` or `uvx` resolves from the user's `PATH`; the manifest's `env` goes on top.

**Installed per Runner, for every bot there.** The Runner holds the install under `~/.lorca/plugins/` (`installed.json`, the plain variables; `secrets.json`, mode 0600, the secret variables and OAuth tokens; a folder per plugin with its skills) and advertises each plugin's id, name, and state (`ready`, `needs_setup`, `needs_auth`, `connecting`, `error`) in its `machine` blob, so every Device lists what each Runner has without a secret leaving it. Every bot on the Runner may use every plugin installed there, as every Grok Bot agent draws on the account's installs. Installing, removing, setting variables, signing in, and reading a plugin's detail run on the Runner: locally when the app's CLI is that Runner, else as a `request` sealed to it (`plugins.install`, `plugins.uninstall`, `plugins.variables`, `plugins.connect`, `plugins.detail`), so a phone installs a plugin on another computer and hands it a key through ciphertext.

An installed marketplace plugin follows the index: at startup the Runner replaces the manifest it installed with the bundled one when that changed, and again when the marketplace loads, keeping variables, secrets, and sign-ins, so a new sign-in method or server reaches existing installs without a reinstall. A plugin installed from its own manifest (`plugins.install { runner_id, manifest }`) is left as it is.

**The marketplace** (`crates/cli/src/marketplace.rs`), after Grok Bot's, offers plugins and bots: a JSON index of plugin manifests (`plugins`) and bot templates (`bots`), the one bundled in the CLI (`crates/cli/marketplace/index.json`) plus the one at `marketplace_url` in settings (or `LORCA_MARKETPLACE_URL`), fetched at most hourly, whose entries add to the bundled ones or replace them by id. An entry with `featured` is listed under Featured Plugins or Featured Bots, in index order, and `category` names its section, one of Grok Bot's filter categories (`credentials`, `productivity`, `communication`, `design`, `code`, `data`, `sales`, `finance`, `research`, `support`). Each remote plugin in the bundled index is the service's own server, and it either needs no account or signs in through dynamic client registration with the Runner's loopback redirect (GitHub's device flow aside), so a plugin never asks the user to register an app first. `marketplace { query? }` answers with the plugins, each with the Runners that have it, and the bots, each routine with its schedule in words (`schedule_text`); a query keeps the entries that have every word.

**Bots from the marketplace.** A bot template is a bot's starting point: `id`, `name`, `summary` (its line in the marketplace), `description` (the new bot's description, so its instructions), `symbol_name` and `accent`, `category`, `featured`, `author`, `plugins` (the marketplace plugins it works with), `routines` (`name`, `schedule`, `prompt`), and `memory` (facts it starts with). `bots.create { template_id, greeting }` makes a bot from one, as Grok Bot's template import does: the template's profile, its routines added paused, and the app's `greeting` ("Hi Researcher, introduce yourself.", in the user's language) as the user's first message in its DM. The turn that answers carries the setup (`Job.setup`: a `TemplateSetup` of the plugins, the routines' names, and the facts), and the Runner puts a cue after the greeting (`turns::setup_cue`): save the facts with `memory_update`, ask once whether to turn the routines on and resume them only on a yes, call `install_plugin` for each plugin the Runner lacks (the user allows or denies each on its card), and greet the user. The cue exists only in that turn's context; the chat keeps the greeting and the reply.

**At turn time** (`crates/cli/src/plugins/mcp.rs`, `rmcp`), the base prompt carries a bounded catalog of installed plugin ids, names, states, and skill locations, but no MCP tool names, descriptions, schemas, or server instructions. `capability_search` starts the relevant servers only when a task needs an installed service (all ready plugins for an unscoped search, or one exact `plugin`), searches tool identity, description, a bounded schema prefix, and bounded server instructions, and returns at most five matches. Their executable schemas join the next model step under a 64 KiB loading budget; `mcp_select_tool` loads one exact returned name when explicit selection is needed. Search metadata and descriptions are bounded separately, and selected schemas last only for that agent turn. The Runner keeps connected servers in a pool (stdio children, or streamable HTTP with the plugin's headers, a pasted token, or the saved OAuth tokens), so later discovery reuses them without putting their whole catalogs back into context. Browser-flow OAuth tokens are refreshed by the transport and written back as soon as the handshake rotates them. A device-flow token is a plain bearer; the Runner refreshes and saves its rotating pair itself, and drops the pooled connection before that bearer expires so the next use reconnects with a fresh one.

A tool the server marks read-only (`readOnlyHint`) or the manifest lists as such runs at once. Any other tool goes through the same Auto-review boundary as local actions immediately before the MCP call. When it asks, the card reads "Chef wants to use GitHub · create_issue · repo: …"; Always allow saves the exact `plugin/tool`, and the working row reads "Using GitHub…" while the call runs. Server instructions travel only with a selected schema and do not replace the server’s own tool description at the permission-review boundary.

**Sign-in** for a remote server is the MCP authorization flow run on the Runner by `rmcp`: discovery from the server's challenge, dynamic client registration as a native app, PKCE, and a loopback redirect on a free port; the browser opens on the Runner, so a Device that is not the Runner is told to finish there. It starts from a card in the chat, as in Grok Bot: after an install that needs a sign-in, or when the bot calls `connect_plugin`, the bot posts a `permission` message with `tool` `connect` ("Chef needs a sign-in to GitHub · Sign in · Not now"); Sign in answers it with `chats.permission { decision: allow }`, which the Runner turns into the flow, and the card then reads "Finish signing in in the browser on Workbench", "Signed in", or "Sign-in failed: …" (`decision` `allowed`, `connected`, `failed`). The inspector's plugin sheet offers the same sign-in. Discovery is seeded from the server's own 401 challenge, since GitHub keeps its resource metadata under the server's path. A manifest can name a `token_variable` so a pasted token stands in for the sign-in, and `client_id_variable` / `client_secret_variable` (or fixed `client_id` / `client_secret`) for a server that registers no clients on the fly; the card says what to fill in when nothing is set. With a `client_id` and a `device_authorization_endpoint` plus `token_endpoint`, the sign-in is the device flow (RFC 8628) instead: the Runner asks for a code, the card shows it with the link ("Copy code and open github.com" on the Mac, the same on the phone), and the Runner polls until the code is entered. Nothing opens on the Runner's screen, so the card works from any Device, and no client secret ships. GitHub's entry uses the device flow with Lorca's own OAuth app. GitHub may issue an eight-hour access token and a rotating refresh token; Lorca refreshes it directly at GitHub's token endpoint, persists the new pair before connecting, and uses the access token as the MCP bearer. A saved browser-flow sign-in whose server metadata cannot be found again also falls back to a bearer. `LORCA_OAUTH_NO_BROWSER=1` fetches the authorize page instead of opening a browser, for tests against a fake server.

**The bot** can search the marketplace (`search_plugins`) and, when the user agrees on a permission card with `tool` `install`, install a plugin on its own Runner (`install_plugin`), as Grok Bot's InstallPlugin does after a question. It is told in the result what setup the user still owes (a sign-in, a variable).

**The apps.** The macOS marketplace (`macos/Sources/Lorca/Marketplace/`) is a sheet, as Grok Bot's is an overlay, of up to 800 by 700: the marketplace icon at the foot of the chats' sidebar opens it, as do File › Marketplace… (⌘⇧M, so the command palette has it too), Add from Plugins… in a DM inspector's Plugins section (on that bot's Runner), and the same row in Settings › Plugins (on the picked Device). Its top bar has Back, the Runner that plugins install on and bots are added to (a pop-up when there are two or more), and Close, which Escape presses from any page. The home page has the title with "N installed" (the Runner's plugins, on a page of their own), the search over plugins and bots, and then Featured Plugins, Featured Bots, and a section per category (its plugins, then its bots, leading with what the featured sections do not show and keeping half the rows for bots when it has both), each a two-column grid of up to four rows with View all (a featured section's lists every plugin or every bot, the featured ones first); a query puts the results in their place, and a category's View all or the results offer All, Plugins, and Bots when both kinds are there. A plugin shows its real mark on a white tile, in light and dark mode alike (`Design/PluginLogo.swift`: mostly Simple Icons' CC0 paths in the brand's color, Playwright's logo for Browser, and the brand's own mark for the rest), here and in the inspector and Settings; a plugin without one shows the SF Symbol its manifest names. A plugin's row offers Add, then shows Added, Connect, or Set Up (the last two open the plugin's own sheet); its page has the description, its state on the Runner with Manage…, its servers, skills, and setup variables, and its developer, category, and website. A bot's row and page offer Add; its page shows Instructions, Memories, Routines, and Plugins beside a list of the four, as Grok Bot's does, and adding the bot closes the sheet on its chat. A DM inspector's Plugins section has a row per plugin the bot's Runner has, with its state. A plugin's sheet shows its state, the sign-in per OAuth server, the variables (secret fields write only), the Always allowed rules for its tools with Reset, its skills, and Remove. Settings → Plugins lists what the picked Runner has installed. Settings → Auto-review has the switch ("Lorca checks each action before it runs and asks you first when needed") and a card per rule: its text, with its behavior, Edit, and Delete in a footer beneath it. The section's plus button and each rule's Edit button open sheets; the text of a rule for an exact plugin tool is read-only there, while its Allow automatically or Ask first behavior can change. The transcript shows the permission card: the question ("Chef wants to use GitHub"), the call, Auto-review's reason, Allow once, Always allow, and Deny, and under them the rule Always allow adds ("Always allow adds the rule “…”."); an install offers Allow and Deny. A shell command asks on its own command card instead (Terminal sessions), and what a bot types into a running command asks on a permission card with the command in a code block (its first two lines; a click opens the whole command in a sheet with Copy), Allow once, and Deny. Answered, the card is the answer and the call, and an Always allow says which rule it added. The row's height and the card's layout come from one measurement (`PermissionCellView.Layout`). The phone shows the same card, the Runner's plugins in chat details, and Auto-review in its settings.

### Memory

Every bot keeps its own long-term memory on its Runner, in Grok Bot's shape of a curated profile over append-only logs, as plain markdown under `~/.lorca/workspaces/<bot id>/` (keyed by id, so a rename or a changed working directory never moves it; `crates/cli/src/memory.rs`):

- `MEMORY.md` is the curated memory. Its first 200 lines or 24 KB, whichever cuts first, open in every turn's system prompt; past that nothing loads, and the prompt tells the bot how much is cut off and asks it to consolidate. The bot writes it only through `memory_update`, one dated entry per call (`- 2026-09-17 · from your chat with the user · the user prefers short replies`), never a whole-file write, so two of its turns cannot clobber each other: `append` adds a fact (an exact duplicate is refused), `replace` rewrites one unique passage, `supersede` strikes the old entry through with a date and adds the new fact so the file shows what changed, `remove` deletes a passage.
- `memory/<topic>.md` files hold longer notes the bot reads with `read` when it needs them; the prompt lists their names.
- `memory/log/YYYY-MM-DD.md` is the bot's diary: what happened, not what is true. The Runner appends one line per finished turn (`- 09:05 · in group "Standup" · said "Sent the three flagged invoices…" · used bash, edit`), and the bot adds events with `memory_log`. Logs are never loaded into a prompt; `recall` finds them.

Every write is atomic and goes through a credential scrubber first (API keys, AWS and GitHub tokens, bearer tokens, JWTs, private key blocks, `password: …` values become `«redacted N chars»`), since memory is bot-authored as often as person-authored.

Two things keep a bot's chats from being islands, after OpenMausBot. Every turn carries a **recent-work brief**, a bracketed note after the transcript: the newest thing the bot said in each of its *other* chats over the last two days, at most ten lines and about 350 tokens, newest first (`- today 09:05 · group "Standup" · you said: "…"`), so a bot in a group knows what it did in its DM an hour ago without the transcript. It stays out of the system prompt, which it would change each time the bot speaks elsewhere, costing the chat its prompt cache. And `recall` searches the memory files and every chat the bot is in by words and by time, naming the chat and the speaker of each hit.

Before a compaction summarizes part of a chat, a silent **memory flush** turn runs over the messages about to be cut, with only `memory_update` and `memory_log` as tools and a prompt to save what is durable and not yet in memory; nothing it says reaches the chat, a failure or a two-minute timeout is logged and the compaction goes ahead (`LORCA_MEMORY_FLUSH=0` turns it off). This is what keeps a fact from being lost because it was only ever said in conversation.

The macOS app's DM inspector shows the bot's memory (`bots.memory`): the index against its load budget, an editor (`bots.memory.write`, refused with the bot's current text when the file changed under the editor, then Reload or Overwrite), and a Show button for the folder. For a bot on another Runner the CLI asks that Runner through the relay (a `request` / `response` pair, see Protocols), so the same rows read and edit it; only the folder cannot be opened, and an offline Runner shows as such with a Retry. The phone shows no memory yet.

### Providers

**DeepSeek** — API key, streamed through DeepSeek's Anthropic-compatible endpoint (`https://api.deepseek.com/anthropic`, `providers::anthropic`), the one that runs DeepSeek's web search on the server: every request declares Anthropic's `web_search_20250305` tool, and the model's searches stream back as `server_tool_use` and `web_search_tool_result` blocks. `LORCA_DEEPSEEK_MODEL` overrides the model. The API root is the credential's own base URL when the user set one, else `LORCA_DEEPSEEK_BASE_URL`, else DeepSeek's (the key check calls its `/models`, bots its `/anthropic`; a root given with `/anthropic` already is used as is).

**Anthropic** — API key, the Messages API (`providers::anthropic`): `claude-opus-5` by default with adaptive thinking, and Anthropic's `web_search_20260209` and `web_fetch_20260209` tools on every request (the basic variants and no thinking parameter for Haiku 4.5 and the 4.5 generation). `LORCA_ANTHROPIC_MODEL` overrides the model; the API root is the credential's base URL, else `LORCA_ANTHROPIC_BASE_URL`, else Anthropic's.

An API-key credential (`credentials.json`: `api_key`, `base_url?`, `connected_at`) can name a custom API root, for a proxy or a compatible server. Every API-key connect method takes `base_url` beside `api_key`, checks the key against that root, and stores both. Before presenting the macOS provider sheet, the app fetches the saved key and base URL on demand from the local CLI with `providers.api_key { kind }`, so it opens fully populated at its final size. The key is masked by default, with an eye button to reveal or hide it. Connected API-key providers open this sheet through Edit, with Save and Disconnect actions. Snapshots and events carry provider statuses: `providers[].base_url` and a masked `key · url` detail.

Both stream the same way, with the conversation marked for caching (`cache_control` on the system prompt, the last user block, and the turn's cache points, so a turn reads what the last one cached even after many tool calls, since Anthropic looks at most 20 blocks back from a mark; the last tool takes one while fewer than four are used; DeepSeek ignores the marks and caches prefixes on its own), tool arguments streamed eagerly, and a request that fails before it streams retried twice: text, thinking (with its `signature`), `tool_use` blocks, and the server tools' own blocks. A server tool call becomes a `ServerToolStart` / `ServerToolEnd` pair for the Runner's activity rows, and the raw `server_tool_use` and `*_tool_result` blocks stay in the assistant message as `ServerBlock` parts, so when the same turn continues after a function call the model gets its searches, their results, and its sealed thinking back verbatim. A later turn's context is rebuilt from the chat and carries none of it. Opus 5.5 and Fable 5.1 bind each thinking block to the system prompt, tools, and messages before it and refuse one replayed after they change, so the Runner drops a turn's earlier thinking for those models when a plugin tool joins mid-turn, when the turn compacts, and in the memory flush (`anthropic::drop_bound_thinking`).

**OpenCode Zen** — API key, the curated pay-as-you-go gateway rooted at `https://opencode.ai/zen`. `deepseek-v4.1-flash` is the default. The Runner follows the endpoint OpenCode publishes for each model: GPT and Grok use `/v1/responses`, Claude uses `/v1/messages`, and DeepSeek, Kimi, GLM, MiniMax, and the free Big Pickle use `/v1/chat/completions`. `LORCA_OPENCODE_MODEL` and `LORCA_OPENCODE_BASE_URL` override the default model and root.

**OpenCode Go** — API key plus an active Go subscription, rooted at `https://opencode.ai/zen/go`. `glm-5.3-flash` is the default. GPT and Grok use Responses, Qwen and MiniMax use Messages, and GLM, DeepSeek, and Kimi use Chat Completions. `LORCA_OPENCODE_GO_MODEL` and `LORCA_OPENCODE_GO_BASE_URL` override the default model and root. Every OpenCode request identifies Lorca in `User-Agent` and carries the chat id as `x-opencode-session`, as Go requires for routing and prompt caching; Chat Completions and Responses requests carry it as `prompt_cache_key` too.

**ChatGPT** — subscription OAuth (`providers::chatgpt`, isolated): authorization code with PKCE, the localhost:1455 callback the Codex CLI uses, tokens refreshed by the adapter, and the Codex responses backend for streaming. `LORCA_CHATGPT_MODEL` overrides the model. The chat id goes with every request as `prompt_cache_key` and in the `session-id` header, by which the backend keeps a chat on the server that holds its prompt cache, as the Codex CLI does. Every request carries the backend's built-in `web_search` tool, which searches and reads pages server-side; its `web_search_call` items stream back as `ServerToolStart` / `ServerToolEnd` events (`web_search` with the query, `web_fetch` with the URL for an `open_page`).

**Grok** — subscription OAuth (`providers::grok`, isolated): xAI's authorization code with PKCE at `auth.x.ai` (`/oauth2/authorize`, `/oauth2/token`) with the public desktop client id the Grok CLI uses, a loopback callback on a port picked at sign-in (`http://127.0.0.1:<port>/callback`; the `accounts.x.ai` page calls it from JavaScript, so the callback answers the CORS preflight and marks its response for that origin, else the page falls back to a code to paste), and tokens refreshed by the adapter (access tokens last about six hours; the refresh token rotates and the new one is stored at once). It needs a SuperGrok or X Premium+ account. Streaming is xAI's Responses API (`https://api.x.ai/v1/responses`) with the bearer; the Responses wire shape (`providers::responses`) is shared with ChatGPT. Every request carries the chat id as `prompt_cache_key`, which routes a chat's requests to the xAI server that holds its prompt cache. `grok-4.7` by default; `LORCA_GROK_MODEL` overrides it, `LORCA_GROK_BASE_URL` the API root, `LORCA_GROK_ISSUER` the OAuth issuer, for a test server. Every request carries xAI's `web_search` and `x_search` tools, run server-side; their `web_search_call` and `x_search_call` items stream back as `ServerToolStart` / `ServerToolEnd` events ("Searched the web for …", "Searched X for …", "Read …"). Disconnecting revokes the refresh token at `auth.x.ai`, best effort.

Server tool events from any provider become tool rows on the Runner, so the status line reads "Searching the web…" or "Reading the web…" while one runs; `build_context` never replays those rows to the model.

The encrypted bot profile carries `provider`, `model`, and `thinking` as string identifiers; the Runner resolves them against the account's credentials and the model catalog at turn time. `thinking` is one of `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max` (or unset for the provider's default) and is mapped to what the model takes: an `output_config.effort` with adaptive thinking on DeepSeek and current Claude models (Fable 5.1 and Opus 5.5 cannot turn thinking off, so `off` becomes their lowest level), a `budget_tokens` on Haiku 4.5, `reasoning.effort` on ChatGPT and API-key Responses, and `reasoning_effort` on OpenAI-compatible gateways. Each model clamps the choice to its catalogued levels; models with no explicit control receive no parameter. Every bot tool that creates or edits a teammate takes `thinking` too.

**The model catalog** (`lorca_agent::models`, a snapshot of models.dev) knows each offered model's context window, output cap, image support, thinking levels, and rates. Every assistant message carries `usage.cost` in dollars from those rates (ChatGPT and Grok sign-ins are not billed per token; their cost is what the work would cost at API rates). `usage.input` is the input read fresh and `usage.cache_read` the input served from the provider's prompt cache: Messages reports the two apart, and the adapters for Chat Completions and Responses, which count cached tokens inside their input total, take them out of `input`. The Runner adds each turn to the chat's `usage` (`context_tokens` and `context_window` of the last turn, totals of tokens, cost, and turns), kept in the local database and never synced; the app gets it in the snapshot, in `roster.changed`, and as `chat.usage` events, and the DM inspector shows "Context 128k of 1M · 13%" and "Spent $0.42 · 18 turns".

**Compaction** keeps a long chat inside the window (`lorca_agent::compaction`, pi's prompts and cut rule; `LORCA_COMPACTION=0` turns it off): when the transcript a turn rebuilds is estimated above `window - 16k` tokens, or more than 400 messages of the chat are not covered by a summary yet, or a turn's own context grows past the window between model calls (the loop's `prepare_next_turn` hook), or the provider answers that the prompt is too long, the older part is summarized by the same model into a structured checkpoint (goal, progress, decisions, next steps, files touched), about 20k tokens of recent messages stay as they are, and a `Compaction { bot_id, summary, after_message_id }` on the chat (local, per bot) makes every later turn start from the summary and the messages after that one. The summary covers the whole chat since the last one, in pieces of at most the window less twice the reserve, each piece updating the summary of the ones before, so a backlog of any size compacts. The memory flush runs first (see Memory). Automatic compaction is silent, as in Grok Bot; the inspector's Context row shows the result, and its Compact button (`chats.compact`) does it by hand with a notice in the chat.

**Retries**: a model call that fails before it streams in a way that reads as transient (overloaded, rate limited, 5xx, a dropped connection) is asked again after a backoff, three times at most on top of the adapters' own HTTP retries; the app hears `job.retry` and the working row reads "Retrying (2 of 3) in 4 s…". A failure that outlasts the retries is the bot's failed bubble, as before.

## macOS app

SPM `Lorca.app`, AppKit.

The app starts the bundled `lorca` (Contents/Resources/bin/lorca; `LORCA_CLI` overrides, PATH is the fallback) as `lorca serve --port <port>`, logs it under `~/Library/Logs/Lorca/` or `~/Library/Logs/Lorca Dev/`, and restarts it if it exits. Lorca uses port `4862`; Lorca Dev uses `4863`. If something already listens on that build's port, that instance is used.

Which window a launch opens depends on the identity, which only the CLI knows, so the app keeps a hint: `Preferences.hadIdentity`, whether the CLI's last answer had one. With it, the main window opens during AppKit launch with a loading indicator and the saved inspector visibility. Without it (a fresh install, or a Mac whose identity went away) no window opens until the snapshot picks onboarding or the main window, so onboarding never replaces a main window that just appeared; a startup failure or the 2.5-second deadline opens the main window on the offline recovery controls. The main window's inspector keeps its width while the snapshot loads; the chat and inspector views are built when their data arrives, and automatic layout changes apply without a collapse animation. A dedicated serial queue probes localhost, locates and spawns the CLI, and reads its readiness pipe while AppKit builds the window on the main thread. Only lifecycle notifications and the ready callback return to the main thread; stopping the launcher fences queued starts and terminates its child. It launches its child with `--ready-stdout`; after loading local state and binding its server, the CLI flushes `{"event":"ready","port":<port>}` to stdout. The app reads this startup pipe and opens its websocket on that signal. CLI logs go to stderr, and the app saves both streams in its log. An existing CLI is used once the localhost probe succeeds. A dropped connection backs off from 400 ms and asks the launcher to prepare the endpoint again; a child restart connects on its new readiness signal.

The first request is `bootstrap`, which carries identity, chat metadata, and messages together. The app buffers incoming events until the snapshot arrives, applies the snapshot and buffered changes with view notifications held back, then publishes one complete state with the connection marked ready. The sidebar creates its scroll view and outline when rows first arrive, with their previews and activity order, and restores the selection after creating the rows. Settings navigation, the Device picker, and offline/empty-state views are created on first use. The window configures its saved frame and toolbar before attaching the split view, sized to that frame, since a window takes the size of its content view controller; it uses deferred creation and is ordered front once with opening animations disabled. Notifications and the updater start after this initial presentation (or after startup fails). A startup failure or 2.5 seconds without a snapshot replaces the loading indicator with the offline recovery controls. `LORCA_TRACE_STARTUP=1` writes launch milestones and elapsed times to `startup.log` in the app's log directory. CLI milestones are recorded on the launcher queue and window milestones on the main thread. `bun run test:mac-startup` checks that the launcher progresses with the main thread blocked, handles fragmented readiness and early exit, and cancels queued starts without leaving a child running.

First run: the CLI's `bootstrap` snapshot has `has_identity: false`, and the app shows onboarding: create (the CLI returns the phrase), restore (phrase → relay), or pair (paste the string from a computer that already has the identity). After create, the user names the first bot (the CLI's default Chef, edited through `bots.update`), then connects an API-key or subscription provider for the account (skippable). In Chinese, onboarding offers **幕僚长** and a Chinese description for the default profile; Continue saves those values through `bots.update`. Restore and pair wait a moment for the first sync and show the provider step only when the account has none connected. Onboarding is the app's window until it finishes: closing it leaves the app running, the Dock icon brings it back (`applicationShouldHandleReopen`), a notification click brings it forward, and the menu commands that open the main window (New Bot, New Group Chat, Marketplace, Pair a Device, Find, Command Palette) are disabled. Settings › Advanced › Show Onboarding Again, like Debug › Show Onboarding, hides the main window and opens onboarding. Over an identity nothing there can run (create, restore, and pair refuse), so closing it is Cancel: the main window comes back as it was, on the same pane with its history, and a notification click does the same before opening its chat.

Settings is a mode of the main window. The foot of the sidebar has two icons and a button: the gear opens General (as ⌘, does), this Mac's icon, red while the CLI is not answering, opens the Devices pane on this Mac, and at the other end the marketplace icon (`circle.grid.2x2`) opens the marketplace. The sidebar gives way to the settings sidebar: a search field where the chats' one is, the panes, and Back (a chevron and the word; Escape does the same) in the footer, where the chats' sidebar has the two icons (General, Providers, Auto-review, Plugins, Bots, Devices, Advanced). Plugins, Bots, and Devices each show one Device, picked from a pop-up in the window's toolbar: a standard toolbar item at the content area's trailing edge, in the toolbar while Settings is up. On macOS 26 the item's view is a plain container holding the pop-up on a glass capsule of its own (`NSGlassEffectView`), and the other panes hide that capsule: a toolbar item entering, leaving, or hiding makes the toolbar lay its glass out again, which blinks the back and forward buttons, and a hidden pop-up in a standard item leaves its platter behind. It lists the paired Devices with Pair a Device at its foot (`MainWindowController.updateToolbar`). The titlebar's Create button and the inspector toggle belong to the chats and leave while Settings is up. It starts on this Mac, and the pick holds across the three panes: the root keeps it in `settingsDeviceID` and hands it to the `DevicePaneViewController`s (`Settings/DeviceSettingsViewControllers.swift`). Providers has the account's credentials, with Connect and Disconnect for each; Bots lists the bots assigned to the Device, each opening its chat; Plugins has what the Runner installed and the marketplace; Devices has the machine key, role, last seen, relay, and Unpair. A Device that is not a Runner shows a note in Plugins and Bots. A query (⌘F focuses the field) narrows the list to the panes and settings that match, each setting under its pane (a Device pane's bots and plugins are those of the picked Device); picking a setting opens the pane, scrolls to its row, and flashes it. The index is `SettingsEntry` (`Settings/SettingsSearch.swift`): a title, keywords, and the row label the panes take their labels from, so the results and the pages share one spelling. Both sidebars use a standard `NSSearchField`, which brings AppKit's capsule and focus ring. From macOS 26 a sidebar's list fills the pane and scrolls under everything in it, as System Settings' does: the bars (the chats' search field and footer, Settings' search field and Back footer) are `NSSplitViewItemAccessoryViewController`s the root sets on the sidebar's split view item for whichever sidebar shows, so AppKit insets the list by them through the safe area and softens the rows passing behind them and the titlebar. On macOS 14 and 15 the bars and the list are stacked inside the pane (`SidebarChrome.floats`). The selection says which sidebar shows (`Selection` is `chat` or `settings(pane)`); opening a Device from the inspector picks it and lands on Devices, and Back returns to the chat that was open. While Settings is up the toolbar has back and forward ahead of the title (a navigational `NSToolbarItemGroup`), walking the panes visited since Settings opened (`RootSplitViewController.paneHistory`). The panes' cards follow System Settings: a bold group title on the rows' text column, a fill with 12 pt corners and no border, and dividers between the rows' text margins (`SectionView.style = .heading`; the inspector keeps the captioned, bordered card). A pane's pop-ups are `SettingsPopUpButton`s (`Design/Controls.swift`), System Settings' look: the choice as plain text, as wide as it needs, and the chevrons on a small rounded platter, which grows to hold the text too under the pointer. The panes show while the CLI is not answering, since the CLI port and the relay URL live there. While onboarding is up there is no main window, and ⌘, opens General and Advanced in a small window of their own.

Updates come through [Sparkle](https://sparkle-project.org), embedded in Contents/Frameworks (`App/Updater.swift`). A release build polls the appcast at `https://mac-releases.lorca.app/appcast.xml` (`SUFeedURL`), checks each archive against the EdDSA public key in Info.plist (`SUPublicEDKey`), and swaps the bundle, CLI included. **Check for Updates…** is in the app menu, and General has the version, the last check, and switches for automatic checks and automatic installs. A debug build, the dev loop's bundle, leaves all of it out. The version is `"version"` in the root `package.json`, which `scripts/app.ts` writes into Info.plist. `bun run release-mac` builds, signs with the Developer ID under the hardened runtime, notarizes, and publishes the disk image, the Sparkle archive, and the appcast to the R2 bucket behind that domain: [docs/releasing-mac.md](./docs/releasing-mac.md).

The command palette (⌘K, View › Command Palette…, `Palette/`) is a borderless child panel of the main window on Liquid Glass (`NSGlassEffectView`; the menu material before macOS 26): a search field over an inset `NSTableView` of actions, chats, historical message matches, and settings. The actions are the menu bar's own items, looked up by selector (`PaletteIndex.commands`): the palette validates the menus while the main window is still key, lists the enabled items with their titles and key equivalents, and runs one by sending the item's action down the responder chain after the panel closes, so a command reads and behaves as it does in the menu. A query is debounced into `chats.search`, which scans local chat metadata and visible message rows on demand; message rows show the newest matching snippets, and matching tokens in titles and snippets are highlighted. A chat opens with the composer focused; a settings pane opens in place, and a query also finds the settings on the panes (`SettingsSearch.entries`), which open scrolled to their row. The field keeps the keyboard while the arrows move the selection, the pointer selects as in a menu, and Return, a click, Escape, or the panel losing the keyboard closes it. The chats sidebar's search field is the palette's other door: a click on it, or ⌘F outside Settings, opens the palette, and the field never takes the keyboard. The phone's chat-list search bar calls the same API and shows highlighted chat and message results.

Chrome: split view, vibrancy, bubbles, `@` mentions. The titlebar is AppKit's own: the transcript and the settings panes run their scroll views under it, so the header has no background at rest and gets the scroll-edge effect and its separator once content is beneath it. The app renders CLI events and applies its own edits optimistically; `LORCA_MOCK=1` runs the seeded demo instead. Keys stay in the CLI.

Transcript: a view-based `NSTableView` (`Chat/ChatViewController.swift`), which builds cells for the rows on screen and, past a few hundred rows, estimates the heights of the rest until they come into view. `ChatLayout` parses a message's Markdown and measures it once per message version and bubble width, and the cell lays out from the segment heights it measured, so a reload or a resize asks for heights it already has. A bubble stops growing at 580 pt, so resizing a wide window measures nothing; during a live resize only the rows on screen are measured, the rest once it ends. A new message, the working row, and an older page go in as one run of inserted and removed rows (`ChatRow.changedRun`), which leaves the other cells, and a text selection in them, alone. Scrolled back, the first message on screen holds its place through replies, older pages, and width changes. Accessibility clients see the table the same way (`Chat/TranscriptTableView.swift`): one row element per row, whose words ("Chef: …", the message as shown) and frame come from the chat, and whose cell is the real one while the row is on screen and a stand-in with the same words while it is not. So VoiceOver or the Accessibility Inspector reads the whole transcript without the table building a cell. A row keeps its element through replies and older pages, and a row a screen reader moves to scrolls into view between the titlebar and the composer, which near the first message asks for the page before it.

Sidebar: an `NSOutlineView` (`Sidebar/SidebarViewController.swift`) with one item per chat, kept for as long as the chat is listed. Only the first rows come in with a reload. After that, a store event moves, inserts, or removes the rows whose place in the order changed (new activity moves a chat up in one move, without animation), and a cell is reconfigured only when what its row shows (`SidebarChatCell.Content`: avatars, working dot, title, preview, stamp, pin, unread count) changed. Cells come from `makeView(withIdentifier:)`, and a moved row keeps its row view, cell, and selection.

Inspector: `Inspector/InspectorViewController.swift` compares what each section would show with what it last showed on every store event and touches only a section that changed. A changed section reconfigures the rows it keeps for each bot, Runner, routine, and plugin; Runs with builds its pop-ups again only when the provider, model, thinking level, or credential changed, and the usage rows take each turn's values in place. Collapsed, or in a closed window, the inspector skips reloads and memory fetches and catches up in `viewWillAppear`.

Composer: the `+` button opens a file panel; files dropped on the composer or pasted (file URLs, or an image with no text beside it, written to a temporary PNG) attach the same way. Chips above the text show a thumbnail or the file's name and size, each with a remove button; a message can be attachments alone. The app mints the attachment ids and hands the CLI paths (`chats.send { attachments: [{ id, path, name, mime, width, height }] }`), so the bubble it shows at once matches the message the CLI echoes back. In a bubble, images are thumbnails sized from the width and height in the message and files are cards; a click opens the file. An attachment from another Device is fetched through `files.path`, which pulls the `file` blob from the relay into `~/.lorca/files/` and answers with the path; the bubble reloads when it lands. The Dictate button (`mic.fill`, the primary disc while the field is empty) starts Apple's speech recognizer (`Speech` + `AVAudioEngine`, `Dictation.swift`). While recording, the text gives way to Grok Bot's pill: a stop square, the elapsed time, and bars that follow the input level, with Send still beside it. The transcript accumulates and lands at the caret when the square is clicked; Send commits it and sends in one go; Escape discards it. The recognizer listens in the language of the keyboard input source in use (a Pinyin input method means zh-CN, whatever the system language), else the first of the system's preferred languages it supports (matched on language and region, so "zh-Hans-CN" finds "zh-CN"), or the language chosen in Settings › General or the button's right-click menu (`Preferences.dictationLanguage`). The bundle declares `NSMicrophoneUsageDescription` and `NSSpeechRecognitionUsageDescription`.

Working state, after Grok Bot: the CLI's `job.started` / `job.finished` events (and `running_turns` in the snapshot) name the chat and bot of every turn in flight on any Device. From them the app shows a breathing green dot on the bot's avatar in the sidebar, an "is working" row after the last message (the bot's avatar beside a shimmering line: "Working…" in a DM and "Chef is working…" in a group, or what the one working bot is doing: "Thinking…" from the Runner's `job.thinking`, sent when the model starts thinking and read until that bot's next message or the end of its turn, else its latest tool as an activity such as "Running command: Install dependencies…" from the call's `description`, kept between calls so it does not flash), the Stop button, and "Chef stopped without replying" when a turn ends with nothing said. A turn reads the same on every Device, whichever one started it. Each Device lists the turns in flight on it (the turns it runs and the group exchanges it holds, each with what it is doing, thinking or a retry, until the bot's next message) in its `machine` blob (`turns`), uploaded again whenever the list changes, and a Runner uploads each call's row as the call starts. Every other Device keeps each Device's latest list (`device_turns` in SQLite) while the relay's last machine list shows that Device online (`turns_online`, kept while this Device's own socket reconnects) and drops it when the relay shows it offline; a Device uploads its list again whenever its socket connects. So a Runner that quits mid-turn never shows that turn again, and one that only lost the relay shows it again when it is back. The CLI merges those lists with its own jobs, including one it sent to a Runner that has not listed it yet, and tells the app what changed (`App::turns_changed`). The Device that asked for a turn keeps the job in SQLite (`sent_jobs`) until its `job_result` arrives or its five-minute wait runs out, so a CLI or phone core that starts again shows its own turn at once (`runtime::resume_sent_jobs`) and the other Devices' turns once the relay says they are online. Stop cancels a turn wherever it runs: the CLI seals `job_cancel` to the Device that lists it. Replies arrive in chunks: the bubble appears with the first completed paragraph (or sentence, after 1.5 s) and grows by paragraphs, the way Grok Bot's server re-sends a message as it grows. Tool calls never appear in the transcript, as in Grok Bot: the CLI keeps them as `tool` messages so a later turn can rebuild its context, and the app renders none of them, leaving the "is working" row (with the running tool's activity) and whatever the bot says before and after its work. The exceptions are a sent `message_bot`, shown as the "Messaged ◉ X" marker, and a `bash` call's command card while the command needs the user (`Chat/CommandCellView.swift`, `ToolInvocation.isShown`; see Terminal sessions): while Auto-review asks, who wants to run it, the command's first line in a code block that opens the whole command in a sheet on click, why, Allow once, Always allow, and Deny, and the rule Always allow adds; once the bot handed the running command over, Stop on its title's line and its last lines in a code block of their own that grows to six lines and then scrolls, the newest line in view and an edge with more lines past it fading out (a gradient mask on the scroll view's layer, since the block's color is see-through); at a question, a field that hides what is typed unless the question is a yes or no, with Send. When the card leaves with the cursor in that field, the composer takes it. Sidebar rows carry an unread count pill beside the preview (the CLI counts each finished bot reply, failed response, and pending confirmation, from its own turns or the relay, unless the app reports that chat as the one on screen; reading a chat on one Device uploads a `ClearUnread` chat blob that zeroes the count on the others, and so does a message the user sends, on every Device it reaches), a preview without a "You:" prefix (a bot's name only in groups; "Messaged X" and "Message from X: …" for bot-to-bot messages), and a stamp that is the time today, "Yesterday", the weekday within a week, then the date. A transcript inserts "Today 4:13 AM" separators after fifteen minutes of silence; in a group a bot's name sits above its bubble with its avatar beside the bubble's bottom edge, and a DM shows neither.

## Protocols

### App ↔ CLI (local WS)

JSON on `ws://127.0.0.1:4862/ws`. Requests are `{ id, method, params }` and get `{ id, result }` or `{ id, error: { message } }`; events are `{ event, data }`.

App → CLI: `hello`, `bootstrap`, `identity.create`, `identity.restore`, `pair.start` / `pair.status` / `pair.cancel` / `pair.accept`, `config.set`, `bots.create` (`runner_id` may be another Device; it must be a Runner; `template_id` and `greeting` add a marketplace bot) / `bots.update` / `bots.delete`, `chats.create` / `chats.dm` / `chats.send` / `chats.stop` / `chats.delete` / `chats.rename` / `chats.pin` / `chats.add_bot` / `chats.remove_bot` / `chats.mark_read` / `chats.messages` / `chats.search` / `chats.compact`, `routines.create` / `routines.update` / `routines.delete` / `routines.run` / `routines.describe`, `marketplace`, `plugins.install` / `plugins.uninstall` / `plugins.set_variables` / `plugins.connect` / `plugins.detail` (`runner_id` names the Runner) / `auto_review.set` / `chats.permission`, `bash.stdin` / `bash.stop` (a command's row, on its Runner from any Device), `bots.memory` / `bots.memory.write` (this Runner's bots), `providers.connect_deepseek` / `providers.connect_anthropic` / `providers.connect_opencode` / `providers.connect_opencode_go` / `providers.connect_chatgpt` / `providers.connect_grok` / `providers.auth.cancel` / `providers.disconnect` (the account's credentials), `ui.watching` (the chat on screen in the desktop app), `push.register` / `push.unregister` (a phone's device token).

CLI → App: `snapshot`, `roster.changed` (devices, bots, chats, routines, and `providers`, the account's credentials as statuses: `kind`, `is_connected`, a masked `detail`, `base_url?`), `message.added` / `message.updated` / `message.removed`, `chat.removed`, `job.started` / `job.finished` (with `routine_id` for a routine's run) / `job.retry` / `job.thinking`, `chat.usage`, `relay.status`, `provider.auth` (the OAuth URL a phone opens in its in-app browser), `pair.completed`, `identity.changed`.

The app may choose ids (`bots.create.id`, `chats.create.id`, `chats.send.message_id`) so its optimistic rows match the CLI’s events.

What the apps get of a chat is a view of the message rows in `lorca.sqlite3` (`LocalStore::page`, then `Message::for_app`). A snapshot queries each chat's newest 60 messages and sets `has_more` when older rows remain; `chats.messages { chat_id, before?, limit? }` queries the page before a message id, oldest first, with `has_more`. The macOS transcript asks for it as it scrolls within reach of the first row and holds what is on screen in place; the phone asks from FlashList's `onStartReached`. Both keep pages they loaded when a later snapshot arrives. A `tool` message reaches the apps, in snapshots, pages, and `message.*` events, with its name, summary, running state, the first 400 characters of its detail, and a command's `terminal`, and without its arguments and result: the apps show none of that, and a file read or a command's output runs to hundreds of kilobytes. Permission cards likewise omit their reviewed argument payload. A Runner's database keeps the complete rows for later model context and permission handling. The no-Runner mobile core persists only `Message::for_app()` for these rows, so a phone never stores the full arguments or tool result it cannot use.

### CLI ↔ relay

- Every request, the sync socket's upgrade included, carries `Lorca-Protocol: <n>`, the relay protocol the build speaks (`relay::PROTOCOL` in the CLI; the relay's own is in `/v1/health`), and a `User-Agent` of `lorca/<version> (<os>)`. The relay's client is its own `reqwest` client, so neither reaches a provider. The number goes up when Devices come to rely on something new from the relay or the relay stops serving something old; 1 is group paging and `DELETE /v1/identity`. A relay started with `--min-protocol` answers a lower number (none is 0) with `426` on every `/v1` route but the healthcheck. The CLI then sets `relay_update_required` (in `hello`, the snapshot, and `relay.status`), waits fifteen minutes between tries instead of backing off from two seconds, and clears it when a session connects or the relay URL changes. The macOS app says so once per launch in a sheet with Check for Updates, and its Device pane reads "update Lorca to sync"; the phone shows "Update Lorca to sync" in the chat list's title slot and in Settings.
- Machine bearer for blobs, the sync socket, and the machine list; identity signature for registering and attesting machines.
- PUT/GET non-file blobs as base64url ciphertext in JSON, and PUT/GET files as binary ciphertext. `roster` is a whole-roster snapshot of bots, chats, and routines (latest wins); `chat` is one upsert or removal of a message; `machine` is a Device’s metadata and the turns in flight on it; `credentials` is the account's provider credentials; `key` is the DEK sealed to the content key.
- Jobs: `kind=job` with `recipient_machine_pubkey`, sealed to that machine’s box key, deleted by the Runner after the turn.
- Questions: `kind=request` sealed to one Runner (`crates/cli/src/requests.rs`: `{ id, verb, requested_by, body }`), answered with a `kind=response` sealed to the Device that asked (`{ request_id, body, error? }`); each side deletes the blob it consumed, and the asker gives up after 20 s. The verbs are `memory.read` and `memory.write`, so a bot's memory can be shown and edited from a Device that is not its Runner; `plugins.install` / `plugins.uninstall` / `plugins.variables` / `plugins.connect` / `plugins.detail`, so plugins on a Runner are managed from any Device; `permission.answer`, so a permission card is answered from any Device; and `bash.stdin` and `bash.stop`, so a command a bot left waiting is answered or stopped from any Device. A request is refused up front when the Runner is unknown or offline.
- Slots: a `roster`, `chat`, `machine`, or `credentials` blob goes up with a `slot` (`Slot` in `app.rs`, `ChatBlob::slot`), and the relay deletes the blobs of that slot it supersedes, so the log holds a message once and not once per streamed chunk. A message's versions and its removal share the slot named by the message id. An upsert sets `keep_first`, which spares the slot's oldest blob: its seq holds the message's place in the log, so a Device that replays from the start gets the transcript in order, first the early version and later the final one. A tool row is the exception: its running version goes up without arguments or results, for the status line on other Devices, and the finished row supersedes it outright, so the relay keeps one version of each call, at the finished row's place. A row that shows a terminal keeps its first place as a message does, since the transcript shows it. A removal supersedes every version. The SQLite outbox does the same before upload: a queued version updates its row without moving its queue position. `App::upsert_message` holds one lock from the SQLite write that gives a message its `position` to the enqueue, so the sending Device's transcript order is the log's order.
- Groups: a `chat` blob and a message's `file` blob go up with `group`, the chat's id (`ChatBlob::group`). Deleting a chat queues its id in `State::group_deletes`, drops what the outbox still held for it, and the sync cycle calls `DELETE /v1/groups/{group}` until it lands: the relay deletes the group's rows and the attachments' objects in one transaction, gives the bytes back to the quota, and remembers the group in `deleted_groups`, so a blob that names it later (a Runner finishing a turn in a chat another Device deleted) gets `409` and the outbox drops it. The other Devices learn of the deletion from the roster. A bot's avatar is a `file` with no group: the Device that replaces or removes it, or deletes its bot, removes its local copy and queues the attachment id in `State::blob_deletes`, and the sync cycle calls `DELETE /v1/blobs/{id}` until it lands, which removes the row and the object.
- `GET /v1/groups/{group}/blobs?before=<place>&limit=` reads a chat backwards a message at a time: `{ slots: [{ place, blobs }], has_more }`, oldest first, where a slot is a message (its first and latest blob, or its removal) or the chat's read mark, and `place` is the slot's lowest seq. A message other than a tool row keeps the place its first version took however late its last one landed, so pages read backwards give the transcript in the log's order. A page is up to 500 slots and 8 MiB, and leaves out the group's `file` blobs. A relay without the route answers `404`, and the Device replays the log.
- `GET /v1/blobs?since=` answers a page of up to 8 MiB of ciphertext (and at least one blob); a Device asks again from the last seq it got. A Device at seq 0 first takes `roster,machine` alone, so chats have their names and bots before their messages land.
- Every Device keeps `last_seq` and its outbox in `lorca.sqlite3`; queued ciphertext is a binary SQLite BLOB. Uploads retry until the relay accepts them. Attachment transfers have a ten-minute request timeout.

```
App_B → CLI_B
CLI_B encrypts user message + job-for-A → relay
CLI_A fetches envelopes for A, decrypts, runs loop, encrypts reply
CLI_B fetches chat blobs, decrypts → App_B
```

## Repo layout

```
lorca/
  ARCHITECTURE.md
  README.md
  Cargo.toml           # workspace
  crates/agent/        # lorca-agent: loop, tools, and Messages, Chat Completions, Responses, ChatGPT, and Grok providers
  crates/provider-auth/ # OAuth token types and PKCE flows shared by every Device
  crates/cli/          # lorca: the Device core as a library (keys, relay sync, jobs, the JSON API) + runner and server features + the binary
  crates/mobile/       # lorca-mobile: the core for the phone over UniFFI
  crates/relay/        # lorca-relay: axum + SQLite or Postgres, and its Dockerfile
  macos/               # AppKit SPM app; the build bundles the CLI
  mobile/              # Expo app for iOS and Android: a paired Device over the core (modules/lorca-core)
  web/                 # the site
  scripts/             # bun scripts: dev loop, bundle build, macOS release
  .github/workflows/   # release-cli.yml: the CLI's release builds
```

`bun run android` rebuilds the Rust core for Android, then builds and runs the Expo dev client on the Android emulator. `cd mobile && bun run core` rebuilds the Rust core for both phone platforms; `bun run mobile:dev` is the iOS development loop described below.

`bun run dev` rebuilds the CLI and Lorca Dev on Rust or Swift changes (the generated markdown bindings under `macos/Sources/LorcaMarkdown` are left out of the watch, and rewritten only when they differ) and relaunches the app through `open`, so the app is its own responsible process for TCC: a binary spawned from the terminal is charged to the terminal app, whose Info.plist decides whether a microphone or speech request aborts. `bun run build` produces the Lorca release bundle. The bundle step restamps the app binary's SDK version (`stampSDK` in `scripts/app.ts`, through `vtool`): the Swift Build engine writes the deployment target (14.0) there, and AppKit gives a binary stamped below the macOS 26 SDK its older look, with a flat sidebar and an opaque titlebar strip. `bun run relay` runs a local relay. `bun run mobile:dev` (`scripts/mobile.ts`) is the Lorca Dev phone loop on the iOS Simulator, or on `--device <name or udid>`: it fingerprints the crates the phone links, the prebuild inputs (Expo config, assets, `package.json`, plugins, targets), the pod inputs with the checkout's path, and the native module sources (stamps in `mobile/.expo/dev-stamps.json`), rebuilds what is stale (`bun run core ios`, a clean `expo prebuild`, `pod install`, `expo run:ios`), starts Metro, and opens the dev client on it. A Rust save while it runs rebuilds the core and installs the app again. The Mac and phone loops leave production Lorca processes alone, so all builds run side by side.
